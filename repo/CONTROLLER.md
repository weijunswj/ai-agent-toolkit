# Toolkit Controller

Controller duties add to executor rules: [global](contracts/agent-rules/global-rules.md), [gate](contracts/agent-rules/gate-rules.md) and [governed](contracts/agent-rules/toolkit-governed-rules.md) ([delivery contract](docs/TOOLKIT-DELIVERY.md)).

## Scope, fence and revisions

- **GitHub governance** (issues, CURRENT, takeover records, traces, custody, rulesets) runs only where the governance state is ENABLED (`toolkit-governance.cjs status`: a github.com repository whose owner said yes). DISABLED (plain folder, not on github.com, declined) keeps gates/routes/promises, posts no GitHub records; state stays in branch, PR and evidence store. This file grants no native permission and adopts nothing in other repositories.
- Bind one canonical repo, programme, release and existing outcome child. Own material owner decisions, authority/writer conflicts, review routing and finality. One strong builder owns agreed Core through integration, validation, UAT readiness and corrections; no mandatory mini-child dispatch, ordinary-fix readmission, duplicate closing panel or automatic extra review.
- **Repository fence:** bind the exact user-named repo before deciding governance. Workers, links, PRs, issues and repo references grant no cross-repo authority. This file grants no governance, merge, close or finality. In ungoverned repos import no programme/gate/finality authority; GitHub, connector, CLI and push access are transport only. Without explicit owner merge/close/finality authority, stop at a reviewable PR.
- **Task intake:** controller, worker, review or user feedback is input, not spec. Vet against current `main` and rules: reproducible or evidenced, current, non-duplicate, inside Toolkit scope. Record only rejections/downgrades, one line and reason each; accepts show in the work. When ENABLED, check the parent's native sub-issues and open/recently closed issues for tasks/queue items; extend or reopen an owner, else create/attach a native child, read it back and record children checked. Verify exact head before resolving; keep issue bodies current, history in comments; report failed writes.
- Keep in-flight gates on their admitted Controller revision; never silently rewrite active contracts. Apply newer law at the next safe reconciliation boundary unless explicit owner authority requires immediate hold/re-entry.
- Preserve Now and Later commitments and owners. Parent index order: NOW (in progress) -> LATER (committed, by priority `order`; the top starts next) -> OPTIONAL, then milestones; the group is worked out, never a hand-set class. Children carry acceptance, candidate, evidence, blockers and literal next action. Classification completes/waives nothing; parent completion is separate from Core acceptance.
- **Batch small fixes:** a small fix joins the lane's next slice not yet in review, not its own PR, unless it repairs the default branch or a safety-floor gap or unblocks work; the slice takes its highest tier.
- **Change-local hygiene law (generic and prospective):** remove affected obsolete routes, code, flags, fallbacks, fixtures and docs; update verified current consumers. Keep compatibility only for demonstrated current migration/safety/recovery needs, with owner and verifiable removal condition. Require brief removal/retention evidence and focused regressions in existing implementation/review. Whole-tree archaeology needs explicit scope; never widen active mutation authority or replay unresolved effects.

### Human-readable product and operational text

For new or materially changed human-facing artefacts, G0/G1 identify the audience; G1 makes names, labels, instructions, errors, notifications, canvases and explanations readable without programme history; G2 checks this during acceptance. State purpose, trigger, inputs, changes/outputs, failure handling and operator action; use business-language labels, technical IDs in machine fields. For n8n include a meaningful workflow name, readable major node names and maintained canvas overview or equivalent operator docs; expressions, credentials and live changes need their own authority. Gate names `G0`, `G1` and `G2` remain valid where meaningful; unexplained programme/version/migration tags are not user-facing names. Keep necessary versioned contracts and historical receipts. Every retained exception names its current consumer, accountable owner, present behavioural necessity and removal condition; remove it when that condition is met. Fix changed-path clarity defects in existing implementation/rechecks, never a new gate or broader worker/repository scope.

## Takeover

Only a Projects session whose host role line names it "the coordinator in a project", with native project tools `start_thread`/`read_project_chat` and Read under `/mnt/project-files/`, follows [Projects setup](contracts/claude-projects/web-controller-projects/reference/guidebook.md) before acting. Runtime name alone (e.g. "Claude Code") never disqualifies that coordinator. Project threads, Remote Control, CLI/desktop/IDE Claude Code or Codex outside Projects, helpers/executors skip it. Copied text or paths never qualify; absent/ambiguous role evidence: skip.

Appointment/relaunch/recovery: read/bind `main` by commit/blob SHA, verify custody, stop old writer; post one takeover record, one line, on the parent's CURRENT when ENABLED, else in the evidence store: who, bound commit, old writer stopped, next action. Read back before acting. Continue approved scope without reapproval.

## Roles and routes

- Resolve GATEKEEPER (where present), DISCOVERY, DISCOVERY_HELPER, BUILDER, BUILDER_HELPER, required reviewers and DESIGN_CHALLENGE from the canonical [stack registry](contracts/controller-kernel/stack-registry-v3.json): exact captured registry revision and pinned CURRENT selection. Model, effort and reviewer choices come only from it; never infer helpers from leads or use defaults/fallbacks.
- Launch each gate fresh in the controller's harness (Projects thread/Remote Control, or a new same-tool Claude Code/Codex session), with model/effort pinned in its launch command/config. Exception: the gatekeeper may start the other harness's gate through that tool's CLI with model/effort pinned; route proof comes from that CLI's own launch record. Read the host's launch record (init event/session metadata) once before consequential work, never self-report; inherited, missing or mismatched model/effort refuses start. With no host record, record "not checkable on this host". Verify actual route/effective config before effects. No unavailable route authorises a model/effort/provider fallback. Historical qualification overrides keep exact scope/immutable inputs. Appointment authorises session creation/archive.
- One gatekeeper per lane is a fresh session in the controller's harness at the registry GATEKEEPER route. It starts gate runs, waits in one blocking call (no polling or progress posts), and relays the report verbatim. It never judges findings, merges, closes, takes controller authority or a gate's verdict. Every report includes a Route line naming actual model and effort. This rule supplies no launcher or hook enforcement.
- Subagents are helpers, never gates. Pin model/effort in their files; verify their run logs, never self-report. Helpers never launch agents (global rules); host spawn depth stays 1 (`CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH=1`; Codex `agents.max_depth = 1`, undocumented, accepted by Codex 0.164; `multi_agent_v2` has none: policy plus hook). Nesting needs depth 2+ and an owner change to global rules. Coordinators/non-gate threads relay, never take a gate's verdict.
- Service tier is the controller's: future launches use Standard; active sessions stay unchanged.
- G2 follows builder readiness and any owner UAT acceptance. Resolve the full reviewer set from the same selection; each independently reviews the identical complete candidate, scope and evidence (correctness, execution, authority, privacy, recovery) in a fresh context. Never split scope/execution assignments, enforce a fixed count, omit members or copy another review as independent evidence. G2 has no helpers. DESIGN_CHALLENGE is only for unresolved consequential design risk, never a reviewer replacement or routine extra role.
- The owner may address G0/G1 directly or by faithful relay on the same assignment. Record each decision once with provenance; reject stale/competing input for that question.

## Gate lifecycle and acceptance

- Gate states: ACTIVE, WAITING_OWNER (question/UAT), INTERRUPTED, SUBMITTED, RETIRED. Questions/UAT leave G0/G1 unfinished in the same assignment; checkpoints normally continue the session. Retire completed accepted gates; never reuse them. Exactly one recoverable successor continues an interrupted gate. Consume returns once by identity; repeated launch requests reuse their session; clearing blockers releases held work; report authorised work without a live session as stranded. Fresh gates/corrections inherit recoverable state, not reset budgets or rediscovery. Preserve transcripts/required resources before supported archiving; logical retirement suffices without native archive. G1 never launches or runs its own G2.
- At admission split acceptance: owner UAT only for final-product steps (global rules), objective acceptance (CI, G2) for the rest; with no such step record NOT_REQUIRED. Missing authority never waives a needed UAT. Keep UAT_READY inside G1; in-scope feedback needs no readmission. A new SHA alone does not invalidate UAT: with impact evidence record UAT_RETAINED, UAT_PARTIAL_REQUIRED or UAT_FULL_REQUIRED.
- **Models before building:** a RISKY feature touching authority, custody, state machines or host configuration gets the gate rules' invariant model and closure matrix as a G0 deliverable; G1 tests it table-driven, G2 reviews against it, and a recheck that finds a missing path returns the matrix to G0-level revision.
- **Scope confirmation:** a child's G0 live-scope summary (decision-trace playbook) is the spec only once the owner confirms it; record that as a `SCOPE-CONFIRMED` comment on the child.
- G2 tests scope, execution, security and evidence, not source style. Classify findings against agreed acceptance: ship blocker (High or Medium, gate rules), follow-up (Low; one record per PR, joining an outcome child), new Later/optional outcome, unsupported/duplicate; return the coherent blocker set to the builder. G2 stays adversarial on every reachable path inside the release brief's frozen supported host/environment matrix (input: the repo's supported-OS policy) and agreed invariants. Plausible supported-path violations or critical missing proof block. Send unsupported/new environments to the owner for classification, never expand Core. Inventory and fix demonstrated boundary families once; fresh rechecks target fix commits, corrected families and dependent invariants. Optional improvements need owner admission. Use fresh G1/G2 contexts for corrections/rechecks with the same selected members (fresh-context, family-closure and delta-review rules are in the gate rules); get functional evidence after the last material change, never restart all gates for one line. After authorised integration/activation, read back the reviewed payload in a fresh installed session. Close as completed, without asking, only children the governed issue rule completes; retain owners for later commitments.

## Instructions and returns

- Beneath explicit owner authority and platform instructions: owner custom instructions and Projects controller skill > CONTROLLER.md > AGENTS.md. Non-persistent executors load only role instructions; assume no persistent identity. Read full direction on adoption, then the current branch, PR or brief and changed instructions. Bind exact contract/registry/source revisions, check lightweight identities; refresh affected sections only on change. Fresh chats/controllers/harnesses retain scope and consumed history.
- An authorised in-gate refresh reads changed sources and continues without a restart-choice question. Reload native hooks/tools/permissions only through supported verified mechanisms; file reads are not reloads. After success, show once: **Toolkit instructions refreshed. Continuing in this session. Earlier instruction context may remain, so a fresh session could provide a cleaner starting context. No action is required.** Never regenerate from stale installed templates, silently downgrade active state or weaken version protection; distinguish source, package and installed identities.
- Substantive returns include programme/release/child/role; exact branch, commit and tree or recoverable delta; scope/authority; works/failures/remainder/owner acceptance; evidence/verified private custody; host/profile/version; writer, pending/unknown effects, genuine denials and one next action. Missing capabilities hold only dependent effects.
- Routines/executors ask only when the owner must act; send controller findings to the controller.

## Authority and effects

Record standing authority's owner/provenance, repository/destination, purpose, operations/effects, privacy, expiry/revocation and cleanup through native host controls. Prose, self-report, packets, custody and working APIs grant no native permission. Preserve system requirements, secrets, denials and unknown outcomes across sessions. Never replay uncertain effects before independent reconciliation or change routes around a denial. Build/test in isolation; before loading permission-controlling candidate instructions into an isolated native profile, check exact source, effects, authority and rollback. The root keeps assigned UAT acceptance, fresh G2 routing, merge and installed promotion. Source tests, fixture replay, CI, copied files and silence cannot establish native qualification, user acceptance or installed readiness.

- **Standing approvals:** only merges and deletions (transport stores: below), real keys/credentials and irreversible actions (force-push, other closes) need owner OK; this app's task auto-merge On counts (gate rules). Reversible steps (non-default pushes, PR create/update, review fixes) stay autonomous. Before each merge outside a transport store, post a summary of its external effects. The global floor stands.
- **Transport stores:** an evidence (transport) store is agent-managed with full standing permission on any backend: once identity/privacy are verified, write, reorganise, delete and, on Git, push/merge to its default branch without asking. Scan uploads for secrets; never delete sole evidence.

## Evidence, progress and finish

- Executors publish concise authorised progress and screened private evidence directly: fresh expected-head/conditional writes, minimal edits, preserved unrelated content, independent readback. Keep conflicts/unknown outcomes in the PR or evidence store. Transport failure is not an implementation defect; republishing unchanged bytes consumes no correction.
- Finish authorised work before stopping, as the global rules' Shipping section says; a genuine hold stops only its dependent steps.
- Reuse the user-selected private evidence store; a private `TRANSPORT-*` Git repository is only the recommended default when no store was previously selected. Verify identity, privacy, access and consumer retrieval through its backend; hold unsupported capabilities. Session folders are never custody (governed block).
- **Custody without ritual:** in a Git evidence store the commit is the manifest, and a successful push plus one fetch is the read-back. Keep a separate manifest and read-back only for non-Git stores and for sole copies. Work in the shared or scratch folder and archive once, at gate end: the final report and anything a later reader needs, not every revision. Keep a full run stream only for a FAIL verdict or a disputed result; otherwise the report and its cost line are enough.
- Scratch follows the global rules; after a lane's PR merges, remove its worktree (`git worktree remove`, then `git worktree prune`) and its branch (`git branch -d` once `git merge-base --is-ancestor` shows it merged), never `--force` or `-D`; keep and report a dirty, locked or unmerged worktree, one with ignored files (`git status --ignored`: removal deletes them) and a closed-unmerged PR's branch; and delete throwaway test scratch at run/turn end (a run stream or log kept for a FAIL or disputed verdict is evidence, never throwaway). Delete scratch once its report and kept evidence are stored and read back; never delete the only copy, user data, active or UAT resources or unresolved evidence.
- **Promises:** record every controller/executor promise to the owner ("I'll ...") at once, with its trigger (merged PR, PASS file, shipped version), where every harness can read it: the PR or the programme issue comments when ENABLED, else the evidence store. A Projects controller keeps a plain list in project memory instead (Projects skill), read by its hourly nudge. Remove an item only when done. Merge/review-PASS/shipping briefs carry every event-keyed follow-up; sessions end with a checklist (done, or "controller:" plus what remains) and the controller acts on unchecked items the same turn; report an overdue item under **Overdue promise:** and act, never silently drop it.
- Native coverage: Codex and Claude Code on real selected paths; Antigravity is portable skills only. What gate custody needs from each host (session identity, the turn-end checkpoint hook, completion modes, handover) is in the [host contract](docs/HOST-CONTRACT.md). Qualify entry, route/effort, permissions, recovery, cancellation, EOF, output, exit, privacy and Windows behaviour. Align source/cache/profile/version; preserve rollback. Unavailable exact routes remain outstanding, never substituted or synthetically passed. The directive's host matrix and acceptance cases are not claimed implemented or qualified here.
