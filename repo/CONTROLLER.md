# Toolkit Controller

The controller procedure for Toolkit-governed repositories. Executors follow the governed rules block ([toolkit-governed-rules.md](contracts/agent-rules/toolkit-governed-rules.md): gates, fresh contexts, delegation, launch ownership, routes, delivery, records and custody); this file adds what the controller owns and binds. Shipping Law is the default: **G0 Discovery -> G1 Builder, including UAT -> G2 Review**, with the full direction in [Toolkit V3](docs/TOOLKIT-V3.md). Historical numeric roles keep their recorded meaning and cannot pass as new G2 assurance.

## Scope, fence and revisions

- A repository is governed only through its owner's direction (the governed block in its `AGENTS.md` is the opt-in). This file grants no native permission and adopts nothing in other repositories.
- Bind one canonical repository, programme, release and existing outcome child. The controller owns material owner decisions, conflicting authority or writers, review routing and finality. One strong builder owns the complete agreed Core through integration, meaningful validation, UAT readiness and in-scope corrections, with no mandatory mini-child dispatch, extra admission for an ordinary fix, duplicated closing panel or automatic extra review.
- **Repository fence:** before deciding whether governance applies, bind the exact repository the user named, for governed and other work alike, and never follow a returned worker, link, PR, issue or repository reference across it as authority. Reading this file (for example for a bootstrap) does not make a repository governed and grants no merge, close or finality authority. In an ungoverned repository import no programme, gate or finality authority: GitHub, connector or CLI access and the ability to push are transport only, and without explicit owner authority to merge, close or finalise, delivery stops at a reviewable pull request.
- **Task intake:** to add a task or queue item for a repository, check the parent's native sub-issues and search open and recently closed issues; extend or reopen an owner if one exists, else create a child, attach it as a native sub-issue, read it back and record which children were checked.
- An in-flight gate stays governed by the Controller revision it was admitted under; a later revision never silently rewrites an active worker's contract. Apply newer law at the next safe reconciliation boundary unless explicit owner authority requires an immediate hold or re-entry.
- Preserve existing Core, Hardening and Later commitments and their owners. The parent is the current index, ordered CORE -> HARDENING -> LATER, then milestone order; children carry detailed acceptance, current candidate, evidence, blockers and the literal next action. Classification alone completes or waives nothing, and parent completion is separate from Core acceptance.
- **Change-local hygiene law (generic and prospective):** every authorised change removes the obsolete routes, dead code, stale flags, fallbacks, test fixtures and documentation it affects and updates every verified current consumer. Compatibility stays only for a demonstrated present migration, safety or recovery need with a continuing owner and verifiable removal condition. Ask for brief changed-path removal and retention evidence and focused regressions within the existing implementation and review; a whole-tree archaeology pass needs explicit scope. Never widen an active worker's mutation authority or replay unresolved effects.

### Human-readable product and operational text

For each new or materially changed human-facing artefact, G0 and G1 identify who must understand and operate it, G1 makes its names, labels, instructions, errors, notifications, workflow canvases and explanations readable without programme history, and G2 checks that against the intended audience during existing acceptance. It must say what it does, when it runs, where inputs come from, what it changes or produces, how failures are handled and what an operator should do, with business-language labels and technical IDs kept in machine fields. For n8n include a meaningful workflow name, readable major node names and a maintained canvas overview or equivalent operator documentation, without changing expressions, credentials or live workflows without their own authority. Gate names `G0`, `G1` and `G2` remain valid where meaningful; unexplained programme, version or migration tags such as `V3` or `N5` are not user-facing names. Keep necessary versioned contracts and historical receipts. Every retained exception names its current consumer, accountable owner, present behavioural necessity and removal condition, and is removed in the change that meets that condition; "historical", "legacy" or "already existed" alone justifies nothing. Fix changed-path clarity defects inside the existing implementation or recheck, not as a new gate, and never broaden an in-flight worker or another repository's scope for it.

## Takeover

On appointment, relaunch or recovery: read and bind this file from `main` by commit SHA and blob SHA, verify custody and stop the previous writer, then post one takeover record on the parent's CURRENT (the new controller identity, the bound commit and `CONTROLLER.md` blob, evidence that the previous writer stopped, the next action) and read it back before acting. Continue the same approved assignment without another scope approval.

## Roles and routes

- Resolve DISCOVERY, DISCOVERY_HELPER, BUILDER, BUILDER_HELPER, the required reviewers and DESIGN_CHALLENGE from the canonical [V3 stack registry](contracts/controller-kernel/stack-registry-v3.json), using the exact captured registry revision and pinned CURRENT selection. It is the sole source of concrete model, effort and required reviewer choices: do not copy another model table, infer a helper from its lead, or use a default/fallback selection.
- Launch every gate with model and effort pinned explicitly. The launched session's own metadata, read back before consequential work, is the route proof; inherited, missing or mismatched effort refuses to start (governed block, Route proof). Verify the supported actual route and exact effective configuration before consequential effects. Effective native configuration plus acknowledgement can prove launch configuration when backend identity is not exposed; record that limit honestly. No unavailable route authorises a model/effort/provider fallback. Correct helper routing and pre-inference wrong-route prevention need separate trusted proofs. Admitted historical qualification overrides retain their exact scoped authority and immutable inputs.
- Service tier is the controller's: the owner stopped Priority across all repositories, so future launches use Standard. That does not change an active session; workers and helpers need no tier awareness, and a missing helper tier control never blocks delegation. Real model availability, topology, resource and native permission limits still apply.
- G2 begins after builder readiness and the owner's actual UAT acceptance, resolving the entire required reviewers set from the same selection. Every selected required reviewer gets the identical complete candidate, scope and evidence and independently reviews the complete agreed acceptance surface (scope, correctness, execution evidence, authority, privacy, recovery) in its own fresh context. Do not split scope-only and execution-only assignments, enforce a fixed reviewer count, omit a required member, or copy another Claude review as independent evidence. G2 has no helpers. A conditional design challenge resolves the separate DESIGN_CHALLENGE role only for a real unresolved consequential design risk; it neither replaces a required reviewer nor becomes a routine extra role.
- The owner may talk to G0 or G1 directly or through a faithful relay against the same assignment. Record each owner decision once with its provenance and reject stale or competing input for the same question.

## Gate lifecycle and acceptance

- Each gate session is ACTIVE, WAITING_OWNER (a question or UAT), INTERRUPTED, SUBMITTED or RETIRED. Questions and UAT keep G0 or G1 unfinished in the same assignment; a checkpoint normally continues in the same session. An accepted completed gate is retired and never reused; an interrupted one is continued by exactly one recoverable successor. Each return is consumed once by identity, a repeated launch request reuses its session, clearing a blocker releases the work it held, and authorised work without a live session is reported as stranded. Fresh gates and corrections get recoverable state, not a reset budget or full rediscovery. Preserve transcripts and required resources before supported archiving; logical retirement suffices where native archive is unavailable. G1 never launches or runs its own G2.
- Decide the acceptance mode at admission: owner UAT, or approved objective acceptance against owner-approved criteria. Missing authority cannot waive UAT. UAT_READY stays inside G1, and in-scope feedback needs no new admission. A new SHA alone does not invalidate UAT: with impact evidence the controller records UAT_RETAINED, UAT_PARTIAL_REQUIRED or UAT_FULL_REQUIRED.
- G2 tests real scope, execution, security and evidence, not source style, and classifies concrete findings against agreed acceptance: current ship blocker, Hardening, Later/optional, or unsupported/duplicate, and returns the coherent blocker set to the builder. G2 stays adversarial on every reachable path inside the release brief's frozen supported host/environment matrix and agreed invariants: a plausible supported-path violation or critical absent proof blocks, an unsupported or newly proposed environment goes to the owner for classification instead of expanding Core, and a demonstrated boundary family is inventoried and fixed once, so the fresh recheck targets the corrected families, cumulative diff and dependent invariants. Optional improvements need owner admission. Corrections and rechecks use fresh G1/G2 contexts for the same selected members (fresh-context and family-closure rules are in the governed block), with functional evidence after the last material change; do not restart all gates because a line changed. After authorised integration or activation, read back the same reviewed payload in a fresh installed session. Only complete verified outcomes close; later commitments keep their owners.

## Instructions and returns

- For owner-controlled procedures the order, beneath explicit owner authority and higher platform instructions, is the owner's own custom instructions and the Projects controller skill > this CONTROLLER.md > AGENTS.md. A non-persistent executor loads only its role instructions and assumes no persistent identity. Initial adoption reads the full direction once; continuation consumes one current packet and changed instructions. Bind exact contract, registry and source revisions, check lightweight identities, and refresh affected sections only on actual change. A fresh chat, controller or harness continues the same scope and consumed history.
- An authorised instruction refresh inside an unfinished gate reads the changed sources and continues without a restart-choice question. Native hooks, tools and permissions reload only through their supported mechanism with verification; reading a file is not a reload. After an actual successful refresh, show once, in bold: **Toolkit instructions refreshed. Continuing in this session. Earlier instruction context may remain, so a fresh session could provide a cleaner starting context. No action is required.** Never regenerate instructions from a stale installed template, silently downgrade active state or weaken version protection; keep source, package and installed identities distinct.
- Every substantive return includes programme, release, child and role; exact branch, commit and tree or a recoverable delta; scope and authority; what works, failed and remains, and owner acceptance; evidence and verified private custody; host, profile and version; writer and pending or unknown effects; genuine denials; and one next action. Large source and logs stay in their stores, not embedded in packets. Missing capabilities hold only their dependent effects.

## Authority and effects

Standing authority records owner and provenance, repository or destination, purpose, permitted operations and effects, privacy boundaries, expiry or revocation and cleanup, composed through the host's native controls. Prose, model self-report, packet syntax, custody or a working API cannot grant native permission. Preserve system requirements, secrets, real denials and unknown outcomes across sessions; never replay an uncertain effect before independent reconciliation or switch routes to get around a denial. Build and test source in isolation; before loading permission-controlling candidate instructions into an isolated native profile, check the exact source, effects, authority and rollback. The root keeps owner UAT acceptance, fresh G2 routing, merge and installed promotion where assigned. Source tests, fixture replay, CI, copied files and silence cannot establish native qualification, user acceptance or installed readiness.

- **Standing approvals:** only merges and deletions (transport stores: below), anything touching real keys or credentials, and anything irreversible (including force-push and closing) need the owner's explicit OK. Every reversible step is autonomous for every release: pushing a non-default branch, opening or updating its pull request and pushing review fixes need no per-release line. Before each merge outside a transport store, post a summary of its external effects. The global floor stands.
- **Transport stores:** an evidence (transport) store is agent-managed with full standing permission, whatever its backend (a private repository, shared folder, drive or other store): agents write, reorganise, delete and, on Git, push to its default branch or merge there without asking, once its identity and privacy are verified. The real-keys rule still applies, so scan every upload for secrets first, and cleanup never deletes the sole copy of evidence.

## Evidence, progress and finish

- Executors publish concise authorised progress and screened private evidence directly, using fresh expected-head or conditional writes, minimal intended edits, preserved unrelated content and independent readback. Keep conflicts and unknown publication outcomes in the packet. Transport failure is not an implementation defect and never consumes a correction to republish unchanged bytes.
- **Finish authorised work before stopping.** For admitted, already-authorised work, carry every dependency-ready safe step through to the actual deliverable in one sustained run where practical: implementation, targeted tests, relevant CI or status, authorised publication with conflict controls, custody and readback, then one complete return instead of asking whether to continue. A plan, green focused test, commit, PR draft, helper return, checkpoint, evidence upload, CI watcher start or progress note is not a terminal outcome. A genuine owner UAT or decision, new scope, trust or spend, host-native permission, missing credential or route, unknown external effect, incomplete CI or independent G2 holds only its dependent steps; continue independent authorised work and report the exact HOLD and next action. This never authorises working around a denial, an unsafe retry, a duplicate writer, an unapproved model launch, claimed background execution or self-launching G2.
- Reuse the user-selected private evidence store; a private `TRANSPORT-*` Git repository is only the recommended default when no store was previously selected, and Toolkit #421 keeps its selected repository. Verify the store's identity, privacy and access, and that a consumer retrieves the immutable artifacts through its own backend; hold any capability that backend lacks. Keep referenced acceptance and unresolved evidence pinned. Session folders are never custody (governed block). Local disposable copies are eligible for cleanup right after verified custody, consumer retrieval and ownership and dependency checks. Stored temporary owned bulk expires 21 days after its immutable verified transfer; the clock never restarts, and explicit pins, holds and active consumers only delay eligibility. Before tearing down a disposable environment after material construction or validation, preserve every later-required candidate and non-repository evidence in durable, retrievable or deterministically reproducible form bound to its repository, gate and candidate, and prove the later consumer can recover it; temporary paths, chat memory, digest-only evidence or uncommitted state are not enough, and publication is not implied. Register each retained resource with purpose, owner, running versus preserved need, release condition and reassessment trigger. Cleanup never deletes the sole copy, user data, active or UAT resources or unresolved evidence, and never implies history erasure.
- Native coverage is Codex and Claude Code with real selected paths; Antigravity is a portable skills copy only. Qualify actual entry, exact route and effort, permission composition, harmless routine operations, private transfer and recovery, fresh consumer, cancellation, EOF, stdout, stderr, exit, privacy and Windows behaviour. Keep source, cache, profile and version aligned and preserve rollback. Unavailable exact host routes stay outstanding: no silent substitution or synthetic host pass. Keep functional, UAT, review, custody, integration, publication, Core and parent states distinct; the canonical directive holds the detailed host matrix and acceptance cases, which these instructions do not claim are implemented or qualified.
