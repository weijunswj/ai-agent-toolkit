# Toolkit Controller

Controller procedure wherever the owner appoints a controller. Executors follow the [global rules](contracts/agent-rules/global-rules.md) for risk tiers and delegation, the [gate rules](contracts/agent-rules/gate-rules.md) for gate mechanics, fresh contexts, recoverable work, launch ownership and routes, and the [governed block](contracts/agent-rules/toolkit-governed-rules.md) for records and custody. This file adds controller duties. Default Shipping Law: **G0 Discovery -> G1 Builder, including UAT -> G2 Review** ([full direction](docs/TOOLKIT-V3.md)). Historical numeric roles retain their meaning, never new G2 assurance.

## Scope, fence and revisions

- **GitHub governance** (issues, CURRENT, takeover records, traces, custody, rulesets) runs only where the governance state is ENABLED (`toolkit-governance.cjs status`: a github.com repository whose owner said yes). DISABLED (plain folder, not on github.com, declined) keeps gates, routes and promises but posts no GitHub records; state lives in the branch, the PR and the evidence store. This file grants no native permission and adopts nothing in other repositories.
- Bind one canonical repository, programme, release and existing outcome child. Own material owner decisions, authority/writer conflicts, review routing and finality. One strong builder owns agreed Core through integration, meaningful validation, UAT readiness and corrections; no mandatory mini-child dispatch, ordinary-fix readmission, duplicate closing panel or automatic extra review.
- **Repository fence:** bind the exact user-named repository before deciding governance. Returned workers, links, PRs, issues and repo references never grant authority across it. Reading this file neither governs a repo nor grants merge, close or finality. In ungoverned repos import no programme/gate/finality authority: GitHub, connector, CLI and push access are transport only. Without explicit owner merge/close/finality authority, stop at a reviewable PR.
- **Task intake:** feedback from controllers, workers, reviews or users is input, not spec. Vet each item against current `main` and rules: reproducible or evidenced, current, non-duplicate and inside Toolkit scope. Record only rejections and downgrades, one line each with the reason; accepts show in the work itself. In an ENABLED repository, for tasks or queue items check the parent's native sub-issues and open/recently closed issues; extend or reopen an owner, else create and attach a native child, read it back and record children checked. Verify the exact head before resolving; keep issue bodies current and history in comments; report failed writes.
- Keep in-flight gates on their admitted Controller revision; never silently rewrite active contracts. Apply newer law at the next safe reconciliation boundary unless explicit owner authority requires immediate hold/re-entry.
- Preserve Now and Later commitments and owners. Parent index order: NOW (in progress) -> LATER (committed, by priority `order`; the top starts next) -> OPTIONAL, then milestones; never a hand-set class. Children carry acceptance, candidate, evidence, blockers and literal next action. Classification completes/waives nothing; parent completion is separate from Core acceptance.
- **Change-local hygiene law (generic and prospective):** remove affected obsolete routes, code, flags, fallbacks, fixtures and docs; update verified current consumers. Keep compatibility only for demonstrated current migration/safety/recovery needs, with owner and verifiable removal condition. Require brief removal/retention evidence and focused regressions in existing implementation/review. Whole-tree archaeology needs explicit scope; never widen active mutation authority or replay unresolved effects.

### Human-readable product and operational text

For new or materially changed human-facing artefacts, G0/G1 identify the audience; G1 makes names, labels, instructions, errors, notifications, canvases and explanations readable without programme history; G2 checks this during acceptance. State purpose, trigger, inputs, changes/outputs, failure handling and operator action; use business-language labels, technical IDs in machine fields. For n8n include a meaningful workflow name, readable major node names and maintained canvas overview or equivalent operator docs; expressions, credentials and live changes need their own authority. Gate names `G0`, `G1` and `G2` remain valid where meaningful; unexplained programme/version/migration tags are not user-facing names. Keep necessary versioned contracts and historical receipts. Every retained exception names its current consumer, accountable owner, present behavioural necessity and removal condition; remove it when that condition is met. Prior existence or history alone justifies nothing. Fix changed-path clarity defects in existing implementation/rechecks, never a new gate or broader worker/repository scope.

## Takeover

On appointment/relaunch/recovery, read and bind this file from `main` by commit and blob SHA, verify custody and stop the old writer. Then post one takeover record, one line, on the parent's CURRENT when ENABLED, else in the evidence store: who, bound commit, old writer stopped, next action; read it back before acting. Continue the approved assignment without scope reapproval.

## Roles and routes

- Resolve DISCOVERY, DISCOVERY_HELPER, BUILDER, BUILDER_HELPER, required reviewers and DESIGN_CHALLENGE from the canonical [V3 stack registry](contracts/controller-kernel/stack-registry-v3.json): exact captured registry revision and pinned CURRENT selection. This is the sole source of concrete model, effort and required reviewer choices: do not copy model tables, infer helpers from leads or use a default/fallback selection.
- Launch every gate with model and effort pinned explicitly in the launch command or config, as a fresh session inside the controller's own harness: a project thread or Remote Control session in Claude Projects, a new session of the same tool for Claude Code or Codex. The host's own launch record (init event or session metadata), read once before consequential work, is the route proof, never the model's self-report or a headless run; inherited, missing or mismatched model/effort refuses to start, and a host that keeps no record is recorded as not checkable (gate rules, Route proof). Verify the supported actual route and exact effective configuration before consequential effects. No unavailable route authorises a model/effort/provider fallback. Correct helper routing and pre-inference wrong-route prevention need separate trusted proofs. Admitted historical qualification overrides retain their exact scoped authority and immutable inputs.
- Subagents (agent files) are helpers, never gates. Pin helper model/effort in its agent file and confirm from its run log, never self-report. Helpers never launch agents (global rules), so Toolkit keeps host spawn depth at 1 (`CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH=1`; Codex V1 `agents.max_depth = 1`, undocumented, accepted by Codex 0.164; Codex V2 has none: policy plus hook); nesting needs depth 2+ and an owner change to the global rules. Coordinators and non-gate threads relay, never take over a gate's verdict.
- Service tier is the controller's: future launches use Standard; active sessions stay unchanged. Workers/helpers need no tier awareness. Availability, topology, resources and native permissions still limit work.
- G2 begins after builder readiness and any owner UAT acceptance; resolve the entire required reviewers set from the same selection. Every selected required reviewer gets the identical complete candidate, scope and evidence and independently reviews the complete agreed acceptance surface (scope, correctness, execution evidence, authority, privacy, recovery) in a fresh context. Do not split scope-only and execution-only assignments, enforce a fixed reviewer count, omit a required member, or copy another Claude review as independent evidence. G2 has no helpers. A conditional design challenge resolves the separate DESIGN_CHALLENGE role only for unresolved consequential design risk; it neither replaces a required reviewer nor becomes a routine extra role.
- The owner may address G0/G1 directly or by faithful relay on the same assignment. Record each decision once with provenance; reject stale/competing input for that question.

## Gate lifecycle and acceptance

- Gate states: ACTIVE, WAITING_OWNER (question/UAT), INTERRUPTED, SUBMITTED, RETIRED. Questions/UAT leave G0/G1 unfinished in the same assignment; checkpoints normally continue the session. Retire completed accepted gates; never reuse them. Exactly one recoverable successor continues an interrupted gate. Consume returns once by identity; repeated launch requests reuse their session; clearing blockers releases held work; report authorised work without a live session as stranded. Fresh gates/corrections inherit recoverable state, not reset budgets or rediscovery. Preserve transcripts/required resources before supported archiving; logical retirement suffices without native archive. G1 never launches or runs its own G2.
- At admission split acceptance: owner UAT only for owner-hands steps (global rules), objective acceptance (CI, tests, G2) for the rest; with no such step record NOT_REQUIRED. Missing authority never waives a needed UAT. Keep UAT_READY inside G1; in-scope feedback needs no readmission. A new SHA alone does not invalidate UAT: with impact evidence record UAT_RETAINED, UAT_PARTIAL_REQUIRED or UAT_FULL_REQUIRED.
- **Models before building:** a RISKY feature touching authority, custody, state machines or host configuration gets the gate rules' invariant model and closure matrix as a G0 deliverable; G1 tests it table-driven, G2 reviews against it, and a recheck that finds a missing path returns the matrix to G0-level revision.
- **Scope confirmation:** a child's G0 live-scope summary (decision-trace playbook) is the spec only once the owner confirms it; record that as a `SCOPE-CONFIRMED` comment on the child.
- G2 tests scope, execution, security and evidence, not source style. Classify findings against agreed acceptance: ship blocker, follow-up (joins an outcome child), new Later/optional outcome, unsupported/duplicate; return the coherent blocker set to the builder. G2 stays adversarial on every reachable path inside the release brief's frozen supported host/environment matrix (input: the repo's supported-OS policy) and agreed invariants. Plausible supported-path violations or critical missing proof block. Send unsupported/new environments to the owner for classification, never expand Core. Inventory and fix demonstrated boundary families once; fresh rechecks target corrected families, cumulative diff and dependent invariants. Optional improvements need owner admission. Use fresh G1/G2 contexts for corrections/rechecks with the same selected members (fresh-context, family-closure and delta-review rules are in the gate rules); get functional evidence after the last material change, never restart all gates for one line. After authorised integration/activation, read back the reviewed payload in a fresh installed session. Close only complete verified outcomes; retain owners for later commitments.

## Instructions and returns

- Beneath explicit owner authority and platform instructions: owner custom instructions and Projects controller skill > CONTROLLER.md > AGENTS.md. Non-persistent executors load only role instructions; assume no persistent identity. Read full direction on adoption, then the current branch, PR or brief and changed instructions. Bind exact contract/registry/source revisions, check lightweight identities; refresh affected sections only on change. Fresh chats/controllers/harnesses retain scope and consumed history.
- An authorised in-gate refresh reads changed sources and continues without a restart-choice question. Reload native hooks/tools/permissions only through supported verified mechanisms; file reads are not reloads. After success, show once: **Toolkit instructions refreshed. Continuing in this session. Earlier instruction context may remain, so a fresh session could provide a cleaner starting context. No action is required.** Never regenerate from stale installed templates, silently downgrade active state or weaken version protection; distinguish source, package and installed identities.
- Substantive returns include programme/release/child/role; exact branch, commit and tree or recoverable delta; scope/authority; works/failures/remainder/owner acceptance; evidence/verified private custody; host/profile/version; writer, pending/unknown effects, genuine denials and one next action. Missing capabilities hold only dependent effects.
- Routines and executors never end with a question to the owner unless the owner must act; findings for the controller go to the controller.

## Authority and effects

Record standing authority's owner/provenance, repository/destination, purpose, operations/effects, privacy, expiry/revocation and cleanup through native host controls. Prose, self-report, packets, custody and working APIs grant no native permission. Preserve system requirements, secrets, denials and unknown outcomes across sessions. Never replay uncertain effects before independent reconciliation or change routes around a denial. Build/test in isolation; before loading permission-controlling candidate instructions into an isolated native profile, check exact source, effects, authority and rollback. The root retains assigned UAT acceptance, fresh G2 routing, merge and installed promotion. Source tests, fixture replay, CI, copied files and silence cannot establish native qualification, user acceptance or installed readiness.

- **Standing approvals:** only merges and deletions (transport stores: below), real keys/credentials and irreversible actions (including force-push and closing) need owner OK. Reversible steps are autonomous for every release: non-default pushes, PR creation/updates and review fixes need no per-release line. Before each merge outside a transport store, post a summary of its external effects. The global floor stands.
- **Transport stores:** an evidence (transport) store is agent-managed with full standing permission on any backend: once identity/privacy are verified, write, reorganise, delete and, on Git, push/merge to its default branch without asking. Real-key rules still apply: scan every upload for secrets; never delete sole evidence.

## Evidence, progress and finish

- Executors publish concise authorised progress and screened private evidence directly: fresh expected-head/conditional writes, minimal edits, preserved unrelated content, independent readback. Keep conflicts/unknown outcomes in the PR or evidence store. Transport failure is not an implementation defect; republishing unchanged bytes consumes no correction.
- Finish authorised work before stopping, as the global rules' Shipping section says; a genuine hold stops only its dependent steps.
- Reuse the user-selected private evidence store; a private `TRANSPORT-*` Git repository is only the recommended default when no store was previously selected. Verify identity, privacy, access and consumer retrieval through its backend; hold unsupported capabilities. Session folders are never custody (governed block).
- **Custody without ritual:** in a Git evidence store the commit is the manifest, and a successful push plus one fetch is the read-back. Keep a separate manifest and read-back only for non-Git stores and for sole copies. Work in the shared or scratch folder and archive once, at gate end: the final report and anything a later reader needs, not every revision. Keep a full run stream only for a FAIL verdict or a disputed result; otherwise the report and its cost line are enough.
- Scratch follows the global rules; after a lane's PR merges, remove its worktree (`git worktree remove`, then `git worktree prune`) and its branch (`git branch -d` once `git merge-base --is-ancestor` shows it merged), never `--force` or `-D`; keep and report a dirty, locked or unmerged worktree, one with ignored files (`git status --ignored`: removal deletes them) and a closed-unmerged PR's branch; and delete throwaway test scratch at run/turn end (a run stream or log kept for a FAIL or disputed verdict is evidence, never throwaway). Delete scratch once its report and kept evidence are stored and read back; never delete the only copy, user data, active or UAT resources or unresolved evidence.
- **Promises:** record every controller/executor promise to the owner ("I'll ...") at once, with its trigger (merged PR, PASS file, shipped version), where every harness can read it: the PR or the programme issue comments when ENABLED, else the evidence store. A Projects controller keeps a plain list in project memory instead (Projects skill), read by its hourly nudge. Remove an item only when done. Merge/review-PASS/shipping briefs carry every event-keyed follow-up; sessions end with a checklist (done, or "controller:" plus what remains) and the controller acts on unchecked items the same turn; report an overdue item under **Overdue promise:** and act, never silently drop it.
- Native coverage: Codex and Claude Code on real selected paths; Antigravity is portable skills only. What gate custody needs from each host (session identity, the turn-end checkpoint hook, completion modes, handover) is in the [host contract](docs/HOST-CONTRACT.md). Qualify entry, route/effort, permissions, recovery, cancellation, EOF, output, exit, privacy and Windows behaviour. Align source/cache/profile/version; preserve rollback. Unavailable exact routes remain outstanding, never substituted or synthetically passed. The canonical directive's detailed host matrix and acceptance cases are not claimed implemented or qualified here.
