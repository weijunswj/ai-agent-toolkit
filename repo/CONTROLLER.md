# Toolkit Controller

Controller procedure for Toolkit-governed repos. Executors follow the [governed block](contracts/agent-rules/toolkit-governed-rules.md): gates, fresh contexts, delegation, launch ownership, routes, delivery, records and custody. This file adds controller duties. Default Shipping Law: **G0 Discovery -> G1 Builder, including UAT -> G2 Review** ([full direction](docs/TOOLKIT-V3.md)). Historical numeric roles retain their meaning, never new G2 assurance.

## Scope, fence and revisions

- A repository is governed only through its owner's direction (the governed block in its `AGENTS.md` is the opt-in). This file grants no native permission and adopts nothing in other repositories.
- Bind one canonical repository, programme, release and existing outcome child. Own material owner decisions, authority/writer conflicts, review routing and finality. One strong builder owns agreed Core through integration, meaningful validation, UAT readiness and corrections; no mandatory mini-child dispatch, ordinary-fix readmission, duplicate closing panel or automatic extra review.
- **Repository fence:** bind the exact user-named repository before deciding governance. Returned workers, links, PRs, issues and repo references never grant authority across it. Reading this file neither governs a repo nor grants merge, close or finality. In ungoverned repos import no programme/gate/finality authority: GitHub, connector, CLI and push access are transport only. Without explicit owner merge/close/finality authority, stop at a reviewable PR.
- **Task intake:** feedback from controllers, workers, reviews or users is input, not spec. Vet each item against current `main` and rules: reproducible or evidenced, current, non-duplicate and inside Toolkit scope. Record accept, downgrade or reject with a reason before slotting accepted items. For tasks or queue items, check the parent's native sub-issues and open/recently closed issues; extend or reopen an owner, else create and attach a native child, read it back and record children checked.
- Keep in-flight gates on their admitted Controller revision; never silently rewrite active contracts. Apply newer law at the next safe reconciliation boundary unless explicit owner authority requires immediate hold/re-entry.
- Preserve Core, Hardening and Later commitments and owners. Parent index order: CORE -> HARDENING -> LATER, then milestones. Children carry acceptance, candidate, evidence, blockers and literal next action. Classification completes/waives nothing; parent completion is separate from Core acceptance.
- **Change-local hygiene law (generic and prospective):** remove affected obsolete routes, code, flags, fallbacks, fixtures and docs; update verified current consumers. Keep compatibility only for demonstrated current migration/safety/recovery needs, with owner and verifiable removal condition. Require brief removal/retention evidence and focused regressions in existing implementation/review. Whole-tree archaeology needs explicit scope; never widen active mutation authority or replay unresolved effects.

### Human-readable product and operational text

For new or materially changed human-facing artefacts, G0/G1 identify the audience; G1 makes names, labels, instructions, errors, notifications, canvases and explanations readable without programme history; G2 checks this during acceptance. State purpose, trigger, inputs, changes/outputs, failure handling and operator action; use business-language labels, technical IDs in machine fields. For n8n include a meaningful workflow name, readable major node names and maintained canvas overview or equivalent operator docs; expressions, credentials and live changes need their own authority. Gate names `G0`, `G1` and `G2` remain valid where meaningful; unexplained programme/version/migration tags are not user-facing names. Keep necessary versioned contracts and historical receipts. Every retained exception names its current consumer, accountable owner, present behavioural necessity and removal condition; remove it when that condition is met. Prior existence or history alone justifies nothing. Fix changed-path clarity defects in existing implementation/rechecks, never a new gate or broader worker/repository scope.

## Takeover

On appointment/relaunch/recovery, read and bind this file from `main` by commit and blob SHA, verify custody and stop the old writer. Then post one takeover record on the parent's CURRENT (new controller identity, bound commit and `CONTROLLER.md` blob, stopped-writer proof, next action); read it back before acting. Continue the approved assignment without scope reapproval.

## Roles and routes

- Resolve DISCOVERY, DISCOVERY_HELPER, BUILDER, BUILDER_HELPER, required reviewers and DESIGN_CHALLENGE from the canonical [V3 stack registry](contracts/controller-kernel/stack-registry-v3.json): exact captured registry revision and pinned CURRENT selection. This is the sole source of concrete model, effort and required reviewer choices: do not copy model tables, infer helpers from leads or use a default/fallback selection.
- Launch every gate with model and effort pinned explicitly, as a fresh session inside the controller's own harness: a project thread or Remote Control session in Claude Projects, a new session of the same tool for Claude Code or Codex. The launched session's own start record (init event or session metadata), read back before consequential work, is the route proof, never a headless run; inherited, missing or mismatched model/effort refuses to start (governed block, Route proof). Verify the supported actual route and exact effective configuration before consequential effects. Effective native configuration plus acknowledgement can prove launch configuration when backend identity is not exposed; record that limit honestly. No unavailable route authorises a model/effort/provider fallback. Correct helper routing and pre-inference wrong-route prevention need separate trusted proofs. Admitted historical qualification overrides retain their exact scoped authority and immutable inputs.
- Subagents (agent files) are helpers inside a gate, never gates. Pin helper model/effort in its agent file and confirm from its run log, never self-report. Helpers never launch agents (governed block), so Toolkit keeps host spawn depth at 1 (`CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH=1`; Codex `agents.max_depth = 1`, not in OpenAI's docs, accepted by Codex CLI 0.164); nesting would need depth 2+ and an owner change to the governed block. Coordinators and non-gate threads coordinate and relay, never take over a gate's verdict.
- Service tier is the controller's: future launches use Standard; the owner stopped Priority everywhere. Active sessions stay unchanged. Workers/helpers need no tier awareness; missing helper tier controls never block delegation. Availability, topology, resources and native permissions still limit work.
- G2 begins after builder readiness and actual owner UAT acceptance; resolve the entire required reviewers set from the same selection. Every selected required reviewer gets the identical complete candidate, scope and evidence and independently reviews the complete agreed acceptance surface (scope, correctness, execution evidence, authority, privacy, recovery) in a fresh context. Do not split scope-only and execution-only assignments, enforce a fixed reviewer count, omit a required member, or copy another Claude review as independent evidence. G2 has no helpers. A conditional design challenge resolves the separate DESIGN_CHALLENGE role only for unresolved consequential design risk; it neither replaces a required reviewer nor becomes a routine extra role.
- The owner may address G0/G1 directly or by faithful relay on the same assignment. Record each decision once with provenance; reject stale/competing input for that question.

## Gate lifecycle and acceptance

- Gate states: ACTIVE, WAITING_OWNER (question/UAT), INTERRUPTED, SUBMITTED, RETIRED. Questions/UAT leave G0/G1 unfinished in the same assignment; checkpoints normally continue the session. Retire completed accepted gates; never reuse them. Exactly one recoverable successor continues an interrupted gate. Consume returns once by identity; repeated launch requests reuse their session; clearing blockers releases held work; report authorised work without a live session as stranded. Fresh gates/corrections inherit recoverable state, not reset budgets or rediscovery. Preserve transcripts/required resources before supported archiving; logical retirement suffices without native archive. G1 never launches or runs its own G2.
- At admission choose owner UAT or approved objective acceptance against owner-approved criteria. Missing authority never waives UAT. Keep UAT_READY inside G1; in-scope feedback needs no readmission. A new SHA alone does not invalidate UAT: with impact evidence record UAT_RETAINED, UAT_PARTIAL_REQUIRED or UAT_FULL_REQUIRED.
- **Models before building:** for any feature touching authority, custody, state machines or host configuration, the G0 deliverable includes (1) a written invariant/custody model (who may do what, in which state) and (2) a closure test matrix covering every command x state x role (or every config key x host limit, from cited host sources). G1 implements the matrix as table-driven tests; G2 reviews against the model and matrix. A recheck that finds a path missing from the matrix returns the matrix to G0-level revision, not a one-line patch.
- G2 tests scope, execution, security and evidence, not source style. Classify findings against agreed acceptance: ship blocker, Hardening, Later/optional, unsupported/duplicate; return the coherent blocker set to the builder. G2 stays adversarial on every reachable path inside the release brief's frozen supported host/environment matrix (input: the repo's supported-OS policy, e.g. Toolkit's README `Supported OS:` line) and agreed invariants. Plausible supported-path violations or critical missing proof block. Send unsupported/new environments to the owner for classification, never expand Core. Inventory and fix demonstrated boundary families once; fresh rechecks target corrected families, cumulative diff and dependent invariants. Optional improvements need owner admission. Use fresh G1/G2 contexts for corrections/rechecks with the same selected members (fresh-context and family-closure rules are in the governed block); get functional evidence after the last material change, never restart all gates for one line. After authorised integration/activation, read back the reviewed payload in a fresh installed session. Close only complete verified outcomes; retain owners for later commitments.

## Instructions and returns

- Beneath explicit owner authority and platform instructions: owner custom instructions and Projects controller skill > CONTROLLER.md > AGENTS.md. Non-persistent executors load only role instructions; assume no persistent identity. Read full direction on adoption, then one current packet and changed instructions. Bind exact contract/registry/source revisions, check lightweight identities; refresh affected sections only on change. Fresh chats/controllers/harnesses retain scope and consumed history.
- An authorised in-gate refresh reads changed sources and continues without a restart-choice question. Reload native hooks/tools/permissions only through supported verified mechanisms; file reads are not reloads. After success, show once: **Toolkit instructions refreshed. Continuing in this session. Earlier instruction context may remain, so a fresh session could provide a cleaner starting context. No action is required.** Never regenerate from stale installed templates, silently downgrade active state or weaken version protection; distinguish source, package and installed identities.
- Substantive returns include programme/release/child/role; exact branch, commit and tree or recoverable delta; scope/authority; works/failures/remainder/owner acceptance; evidence/verified private custody; host/profile/version; writer, pending/unknown effects, genuine denials and one next action. Keep large source/logs in stores, not packets. Missing capabilities hold only dependent effects.
- Routines and executors never end with a question to the owner unless the owner must act; findings for the controller go to the controller.

## Authority and effects

Record standing authority's owner/provenance, repository/destination, purpose, operations/effects, privacy, expiry/revocation and cleanup through native host controls. Prose, self-report, packets, custody and working APIs grant no native permission. Preserve system requirements, secrets, denials and unknown outcomes across sessions. Never replay uncertain effects before independent reconciliation or change routes around a denial. Build/test in isolation; before loading permission-controlling candidate instructions into an isolated native profile, check exact source, effects, authority and rollback. The root retains assigned UAT acceptance, fresh G2 routing, merge and installed promotion. Source tests, fixture replay, CI, copied files and silence cannot establish native qualification, user acceptance or installed readiness.

- **Standing approvals:** only merges and deletions (transport stores: below), real keys/credentials and irreversible actions (including force-push and closing) need owner OK. Reversible steps are autonomous for every release: non-default pushes, PR creation/updates and review fixes need no per-release line. Before each merge outside a transport store, post a summary of its external effects. The global floor stands.
- **Transport stores:** an evidence (transport) store is agent-managed with full standing permission on any backend: once identity/privacy are verified, write, reorganise, delete and, on Git, push/merge to its default branch without asking. Real-key rules still apply: scan every upload for secrets; never delete sole evidence.

## Evidence, progress and finish

- Executors publish concise authorised progress and screened private evidence directly: fresh expected-head/conditional writes, minimal edits, preserved unrelated content, independent readback. Keep conflicts/unknown outcomes in the packet. Transport failure is not an implementation defect; republishing unchanged bytes consumes no correction.
- **Finish authorised work before stopping.** For admitted, already-authorised work, carry every dependency-ready safe step through to the actual deliverable in one sustained run where practical: implementation, targeted tests, relevant CI or status, authorised publication with conflict controls, custody and readback, then one complete return instead of asking whether to continue. A plan, green focused test, commit, PR draft, helper return, checkpoint, evidence upload, CI watcher start or progress note is not a terminal outcome. A genuine owner UAT or decision, new scope, trust or spend, host-native permission, missing credential or route, unknown external effect, incomplete CI or independent G2 holds only its dependent steps; continue independent authorised work and report the exact HOLD and next action. This never authorises working around a denial, an unsafe retry, a duplicate writer, an unapproved model launch, claimed background execution or self-launching G2.
- Reuse the user-selected private evidence store; a private `TRANSPORT-*` Git repository is only the recommended default when no store was previously selected; #421 keeps its store. Verify identity, privacy, access and consumer retrieval of immutable artefacts through its backend; hold unsupported capabilities. Pin referenced acceptance and unresolved evidence. Session folders are never custody (governed block). Put scratch (temporary worktrees, briefs, outputs, test runs) first in a gitignored repo/worktree temp folder (e.g. `.tmp/`); ensure status-checking tests ignore it. Only when an outside path or more permission is needed, use a user-profile folder (e.g. `$env:USERPROFILE\t`), never a drive root. Transfer reports, logs and proof to the transport store with a manifest and read-back, verify consumer retrieval, ownership and dependencies, then delete local copies immediately. Delete throwaway test scratch at run/turn end without transport; remove worktrees with `git worktree remove`, then `git worktree prune`. Stored temporary owned bulk expires 21 days after its immutable verified transfer; never restart the clock; pins, holds and active consumers only delay eligibility. Before environment teardown after material construction/validation, durably preserve every later-required candidate and non-repository evidence, retrievable or deterministically reproducible and bound to repo/gate/candidate; prove consumer recovery. Temp paths, chat memory, digest-only evidence and uncommitted state do not suffice; publication is not implied. Register retained resources: purpose, owner, running/preserved need, release condition, reassessment trigger. Never delete sole evidence, user data, active/UAT resources or unresolved evidence; cleanup never implies history erasure.
- **Promises:** record every controller/executor promise to the owner ("I'll ...") at once: id, action, trigger (merged PR, PASS file, shipped version), status. Keep the controller's list in Claude Projects memory, or the Codex/terminal controller packet/transport store; remove only when done. Merge/review-PASS/shipping briefs carry every event-keyed follow-up. Sessions do each possible follow-up and end with a checklist: done, or "controller:" plus what remains. The controller acts on unchecked items the same turn it reads the checklist. Every periodic nudge/check-in/sweep runs `node repo/scripts/toolkit-promise-check.cjs --list <file>` ([format](docs/TOOLKIT-PROMISE-CHECK.md)); exit 1 means overdue: report under **Overdue promise:** and act, never silently drop it.
- Native coverage: Codex and Claude Code on real selected paths; Antigravity is portable skills only. Qualify entry, exact route/effort, permission composition, harmless routines, private transfer/recovery, fresh consumer, cancellation, EOF, stdout/stderr, exit, privacy and Windows behaviour. Align source/cache/profile/version; preserve rollback. Unavailable exact routes remain outstanding, never substituted or synthetically passed. Keep functional, UAT, review, custody, integration, publication, Core and parent states distinct; the canonical directive's detailed host matrix and acceptance cases are not claimed implemented or qualified here.
