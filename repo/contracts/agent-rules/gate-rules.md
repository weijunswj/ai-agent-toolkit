# Toolkit Gate Rules

Gates, reviewers and their controllers read this first. Global risk tiers and safety floor stand; repository conventions prevail.

## Gate order

- **G0 Discovery** runs for every new task, repository or environment; only LIGHT edits and fixes inside an already-discovered task skip it. Walk the real happy path, confirm the stack and test assumptions before planning; keep discovery short on known ground. It returns the G0 plan: findings, chosen approach, risks, what was tried and failed, and small slices (one reviewable PR each) with acceptance tests (action, expected result, test file). For a release plan in a governed repository, G0 also runs the `secure-ci-cd` CI check-up and gives each real gap a slice or child.
- **G1 Builder** starts in a fresh session, with the G0 plan passed in its brief as the handoff. G0 and G1 share the same strong lead route. One builder owns the whole approved outcome across corrections, checkpoints and fresh sessions; in-scope fixes need no new admission. G1 includes UAT and the PR's `UAT:` line. Before review, the builder self-checks its diff against the G2 review section in the same session, fixes what it finds and notes it in the PR; this replaces no review.
- **Review** follows the tier: full G2 for RISKY, one independent review for NORMAL, the builder's own diff read for LIGHT.
- Gate names `G0`, `G1` and `G2` are fine where the reader needs them.

## Fresh contexts

Fresh executor contexts are mandatory between G0 and G1, for initial G2, for a required model, effort or harness switch, runtime or environment replacement, activated instruction or profile revision or executor replacement, and after genuine session loss or forced compaction at a safe boundary. Planned G1 segment completion alone checkpoints and continues in the same session. An ordinary commit, test, helper return, tool call, milestone or evidence upload never requires renewal. A checkpoint (work pushed, the PR or brief current) is not a terminal outcome: the executor continues its next dependency-ready authorised step. A failed checkpoint save is a recovery boundary, never an automatic successor launch: keep the source and evidence, hold dependent effects and repair recovery. When renewal is actually required, reconcile any existing successor or uncertain launch, verify custody, stop the old writer and launch exactly one successor; it continues the same approved assignment without another scope approval.

## Recoverable work

There are no handover packets. Keep work recoverable: push progress to the branch, update the PR (or brief before a PR exists) at milestones, and post progress and decisions in the PR and, when GitHub governance is ENABLED, programme issue comments; otherwise use the evidence store. All harnesses must be able to read them. Never rely on chat or host memory: a Projects controller may mirror them in project memory, never only there. New controllers and executors load them and changed instructions, with no handover or full history.

A gate works in the primary checkout unless it needs its own worktree, then uses `.tmp/worktrees/<lane>-<gate>-<sha>` at the admitted commit and records HEAD; the controller removes it after merge. A writing gate's session opens in the folder it writes, never told to escalate into another (Codex: the host contract's gate workspace).

## Building

- **Design policy:** give stateful or effectful behaviour (application, runtime, resource, persistence, workflow) a cohesive owner object with explicit constructor dependencies and methods that enforce its invariants and effect order, composed through narrow interfaces. Pure transformations, data definitions, predicates and stateless adapters may stay functions. No mutable state in module globals and no classes that only forward. Refactors keep public behaviour, approvals, independent readback, concurrency controls and recovery semantics. Record the boundary and reason for a consequential exception, and have planning, validation and every review check the actual state and effect owners and their dependency contracts, not class counts. Never refactor generated or third-party code as canonical source; keep its licences and provenance.
- **Invariant models:** RISKY authority, custody, state-machine or host-config features start in G0 from a written model of who may do what in which state and a closure matrix (command x state x role, or config key x cited host limit). G1 implements it as table-driven tests and G2 reviews against it; a path missing from the matrix returns it to G0-level revision, not a one-line patch.
- **Input readers:** a safety decision read from YAML, shell or free text uses a default-deny reader over a subset its G0 states; G1 tests it with `repo/tests/support/hostile-inputs.cjs`.
- **Deployment branches:** unless the repository has its own convention, a deployment or release-preparation branch for a named environment is `deployment/<environment>` (lowercase, e.g. `deployment/staging`); never `deploy/`, `release-deploy/`, bare `prod/` or `staging/`. A branch name grants no deployment, merge or live authority.
- **Shipping floor:** before shipping, complete the applicable minimum: core functionality and critical workflows; consequential correctness; authentication, authorisation and tenant isolation; security boundaries; data integrity, persistence, migration and destructive-operation safety; privacy and secrets; required validation and truthful readiness evidence; deployment, health and rollback prerequisites when release is in scope; every explicit acceptance criterion. Classify remaining work as `SHIP_BLOCKER` or `POST_SHIP`. Known material defects in the floor block. Polish, speculative refactors, future-proofing, optional abstraction, non-critical cleanup and low-confidence risks are `POST_SHIP` unless concrete evidence makes them blockers.

## UAT

- G1 checks the actual user or operator surface for clarity during validation and UAT, and G2 treats unsafe or misleading text as a real finding.
- RISKY work gets agent UAT on the real installed hosts before any owner UAT; on a delta, rerun only the affected rows.
- **Owner test after merge:** owner UAT never holds a merge. An `OWNER_TEST_NEEDED` PR merges on G2 PASS and green CI; the controller records UAT PENDING on each `Refs` task at merge, open until the owner's OK on the installed build; a failure gets a fix-forward or revert PR.
- **One real-host round per release:** CI's Linux and Windows runs cover each PR; the qualification matrix and real-host smoke run once per release batch, after its merges, on the installed build, before the owner tests. On a delta, run the rows whose code changed plus one smoke row per mode.
- A new SHA alone does not invalidate UAT: supply impact evidence and record UAT_RETAINED, UAT_PARTIAL_REQUIRED or UAT_FULL_REQUIRED.

## G2 review

G2 starts after the working result (owner UAT follows the merge), in fresh independent contexts, and has no helpers. The pinned stack fixes the reviewer set (no added peer, duplicate or automatic closing panel), and every reviewer independently reviews the full accepted scope. Acceptance needs the whole roster, qualified routes, the exact candidate and coverage, verified evidence and no unresolved blocking finding, never a majority verdict or a scope/execution split. G2 stays adversarial on every reachable path inside the frozen supported host/environment matrix and agreed invariants. Reviewers rate findings: High breaks an agreed criterion or the safety floor; Medium is a plausible supported-path break, missing needed proof or an unexplained loosening (below); both block. Low is anything else, never blocks and joins one follow-up record per PR. G2 scans every commit, title and body of a PR for personal data, confirms the body's `UAT:` line (git-completion playbook), and checks where a computation ran before accepting that data stayed in place. No review has a dollar cap.

Windows Codex review briefs name the temp root, local tests and authorised network commands, owner and exact-SHA evidence. Use the [recipe](../../docs/HOST-CONTRACT.md#review-cli-permissions): confirm elevated; set temp variables inside review commands. Missing required results block acceptance; reviewers retain full responsibility.

- **No-weakening proof:** for changed detection or guard code, run base tests and fixtures on the head; each case blocked or flagged on base and now allowed needs a stated reason.
- **Early returns keep the guards:** every early return or fast path in changed code must still run the generic guards first (identity, path, secret, personal-data, approval), or show they are not needed, with a test.

## Fixes and delta reviews

- Before the first fix of a security finding, list every route to the same invariant and fix them together, with positive and negative controls.
- After a G2 PASS, a delta G2 runs when a new edit touches a RISKY path or changes behaviour the review relied on. Each delta G2 covers the whole diff since the last PASS, and rechecks target corrected boundary families rather than restarting discovery. Before merge to the default branch, any RISKY change no G2 has seen gets one.
- Correction rechecks use fresh contexts for the same selected reviewers unless a specific reviewer must be replaced, and review the fix commits, closed findings and dependent invariants, widening to the whole diff only where a fix reaches beyond them. A same-family recheck is readmitted only on a closed family-closure record evaluated against the exact corrected candidate; a passing latest reproducer is not enough, and after two NOT PASSED rechecks of one family a consolidated root-cause reassessment comes first.

## Hook changes

A hook change follows `repo/docs/agent-playbooks/hook-design.md`. It touches a `hooks.json`, a `*-hook.cjs`/`*-hook.ps1` script, a module they decide with, or setup that writes host hook config. It merges only when the hook test pack (`repo/tests/hook-pack/README.md`) passes on Linux and Windows on the exact head; each bug it fixes has a pack row that `run --against <parent>` shows failing there; each row it removes, lowers or changes (anything but a flip toward passing) has a reason under the body's "Pack changes" heading; G2 reads the pack from CI's Linux and Windows runs instead of feeding hook scripts by hand; and its release batch passes the real-host smoke (about 20 fixed rows, one update mid-chat, in fresh Claude Code and Codex chats on the installed build) after merge. A broken enforcing hook (push, attribution, governance, merge hold, agent launch) refuses only the calls it guards, with a plain reason and the recovery; advisory hooks stay fail-open.

## Routes

- Gate models and effort come only from an explicitly selected stack registry revision pinned in the controller decision and admission, never inferred from the host, provider, alias or newest bundled registry; a newer registry needs explicit adoption and never changes an active run. Keep qualification overrides separate from production selection, and each stack's lead and helper bindings independent.
- Model and effort follow launch ownership: a human's own choice for an agent they open directly (including a G2 chat) is advisory, not a blocker, and is recorded as the actual route, never labelled the recommended one; a model or effort difference alone is not a G2 failure. Every automation-launched G0/G1/G2 worker or successor, even as root of its own session, and every G0/G1 helper gets the exact pinned route for its role and member, with no fallback or weaker effort. A root label is not a human override, and no model lock goes into a human-run entrypoint. Native permissions, independence, reviewer obligations and delegation limits still apply.
- **Route proof:** pin model and effort in the launch command or config for every gate session. Where the host records the route it ran (the Claude init event or session metadata, a Codex run record), read that record once before consequential work and stop with a report when either is inherited, missing or different. Never ask the model which model it is: models misname themselves, so a self-report proves nothing. Where the host keeps no record, record "not checkable on this host" and carry on.
- Keep model, effort, tier and route out of portable task prompts unless a runtime requires them. Run parallel builders only on disjoint files with no dependency on work still in review.

## Task auto-merge

- The merged binding's `task_prs.auto_merge` is the only switch, one per repository, read alike by every app and the Projects controller: `after-gates` is On; `off` or no key is Off. It counts only in a fresh enabled version-2 binding; unknown apps grant nothing. `setup governance` sets it with yes; `refresh governance` shows it or prepares a change as a binding PR only the owner merges. Only after the new switch is merged and read back does Toolkit delete the old per-app answers and the controller remove any Projects `- Task auto-merge:` line. Update every app copy: older copies honour their own per-app answer until a newer copy removes it. Projects' one named merge thread stands in for a session the owner started.
- With On, the controller, in a session the owner started, merges when, on one head SHA: G2 PASS (or required delta G2) is recorded, every required check is green, no other merge is running, no FAIL, disputed verdict or overdue promise is open, and `node repo/scripts/toolkit-auto-merge-eligible.cjs --base <base SHA> --head <head SHA> --body-file <PR body>` exits 0 (scope and `UAT:` line). It posts the effects summary as a notice, then runs `gh pr merge N --merge --match-head-commit <full SHA>`; the merge hold checks scope first.
- That check exits 1 for bindings and their schemas/readers, hooks and their manifests, setup and its host bank helpers, governance runtime/state, merge rules and their helpers, the controller, global and gate rules, approval rules, the Projects skill's Approvals section, CI workflows, and a major bump (stamp-only changes aside). Those wait for the owner's typed `merge N`; no label grants anything. Rule-refresh pull requests always require a typed merge. To stop task auto-merge, merge an Off switch PR (`refresh governance`); `hold N` keeps one PR.
