# Web Controller for Claude Projects: recurring tasks

Reference for the `web-controller-projects` skill, opened when the coordinator sets up, renders, swaps or deletes a scheduled task. The skill's precedence, style and approvals apply; where this file and the skill differ, the skill wins.

## Recurring tasks
Whenever the user asks for anything recurring (the daily check-in, a sweep, a reminder), set it up this way, and tell the user which kind you used and where they will see it.

**How to set one up (project panel):**
1. A cloud thread creates, recreates and deletes tasks; you have no scheduling tool. Fresh-session routines cannot be created from a device-linked (local Remote Control) session, or from one that was ever linked, so brief that thread with no folder, device or Remote Control tools. If creation is refused, it reports; start a fresh cloud thread, then use the next fallback.
2. Every Toolkit scheduled task is bound to its own home thread (`<PROJECT>: <task name>`): start that thread on the task's model and effort, and it creates the task bound to itself (a task fires into the session that creates it). A fresh session per run is the fallback, only where a task can't be bound. Run every day by default (`CRON_TZ=<user zone> <m> <h> * * *`) unless the user picks another schedule; the hourly nudge runs in the user's waking hours only. Model and effort: the cheapest step of the `agent-cost-control` ladder that can do the task (small, mid or top tier; medium effort at least), set on purpose, never left on a default. A bound task runs on its home thread's model and effort, whatever the Scheduled tasks panel shows, so start the home thread on both; the prompt's RUN SETUP states the tier and effort too. Going above the step its job fits needs a reason in the params (`raise_reason`).
3. Write these requirements into every task prompt: its home thread (or fresh session per run); task model/effort; full report to `latest.md` and an immutable `runs/<run UTC>.md` in its report folder; a new run stamp at `/mnt/project-files/toolkit/task-runs/<slug>/<run UTC>.md`; one capped line in its home thread (first line and per-run report path), with a capped short message to the coordinator with retry when that post fails; never end with a question to the owner; never resolve a home thread (only a fresh-session run resolves its own run thread after delivery). Specify the message cap and retry bound in the prompt; report delivery failure, never claim success.
4. Test one run now; report trigger id and next run. Ask the user to confirm the task in the project's Scheduled tasks panel. Record it on the `SCHEDULED TASKS:` line.

**Task run relay.**
- A run with a matching `<run UTC>.failed` file follows the same relay and `.relayed` rules; its stamp is never amended. Mention delivery failure when listing unrelayed runs if the size limit allows.
- On every task report (a home-thread line or fallback message), skip the task if its `SCHEDULED TASKS:` entry says `stopped by owner`, before reading reports or acting on prefixes. Read its exact `/mnt/project-files/toolkit/task-runs/<slug>/<run UTC>.md` and the immutable per-run report path it names, never `latest.md`. Before posting, check `/mnt/project-files/toolkit/task-runs/<slug>/<run UTC>.relayed`; if it already exists, skip that run. Otherwise post one Update line in project chat on your running post (or a fresh post under the posting rules): the task name, run UTC, its first line and a link to its home thread. Only after the post succeeds, write that run's `.relayed` file with `relayed <run UTC> at <UTC> | <post link>` and read it back; only the coordinator writes `.relayed`. Act on the report's prefixes the same turn, as before.
- **Relay missed runs.** On the first wake of every coordinator session, and on every wake a task home thread starts, list `/mnt/project-files/toolkit/task-runs/<slug>/` for every task except those whose `SCHEDULED TASKS:` entry says `stopped by owner`. Relay every run whose matching `<run UTC>.relayed` is missing, oldest first, in one post: "Relaying <n> missed task runs: ...". Use the same per-run report read, check-before-post and write-after-success rules above for each run. The files hold this state, not your session; the hourly nudge flags any run still unrelayed after 15 minutes (`UNRELAYED TASK RUNS`) and the daily check-in any after an hour (`RELAY GAP`).

**Run records.** Records of tasks marked `stopped by owner` stay stored but are excluded from automatic processing. The task owns its reports and run stamps. The coordinator alone owns acknowledgement files. A run UTC is the actual run time in `YYYYMMDDTHHMMSSZ` form, shared by its report, stamp and acknowledgement filenames. Each run keeps its own report and stamp; `latest.md` is only a convenience copy. Toolkit task slugs come from their names. Custom task slugs are `custom-` plus the whole report folder after `/mnt/project-files/`, lower-cased with each run of other characters replaced by one hyphen and edge hyphens removed (for example, `security/sweep` becomes `custom-security-sweep`). A replacement uses the same slug, but a new run UTC. Never overwrite an existing per-run report or stamp; if that second is already taken, wait for a new UTC second and use it for this run. A missing acknowledgement means pending, whatever a newer run's state. A successful post followed by a failed acknowledgement write remains pending; report the write failure, never mark an unposted run acknowledged. This protocol suppresses a repeated notification once its acknowledgement exists; it does not make the post and file write atomic.

**Toolkit-made tasks** (the daily check-in and the hourly nudge) are rendered from Toolkit `main`, never hand-written: a cloud thread runs `node repo/scripts/toolkit-projects-tasks.cjs --render <daily-check-in|hourly-nudge> --params <file>`, and `--name` for the name (`<PROJECT>: Daily check-in`, `<PROJECT>: Hourly nudge`). Params: `project` (the project name in capitals), `repo` (`owner/name` or `none`), `parent_issue` (or `none`), `report_dir` (under `/mnt/project-files/`), `effort` (`medium`, `high`, `xhigh` or `max`), `model` (tier `small`, `mid` or `top`; when left out, the hourly nudge and custom tasks take `small` and the daily check-in `mid`), `raise_reason` (required when the tier is above that default or effort above `medium`), `session` `fresh` only for the fresh-session fallback (a bound task carries none; `--refresh <kind> <file> --session bound|fresh` moves a task between them), and `toolkit_repo` when not the default. Toolkit owns only the text inside the prompt's markers; the project-additions section is kept on every refresh and wins where it differs.

**Change = recreate.** A fresh-session task cannot be edited or renamed, and a bound task is swapped by starting a new home thread that creates the replacement bound to itself. A task whose `SCHEDULED TASKS:` entry says `stopped by owner` is never swapped, rebuilt or recreated; only the owner restarts it. When the daily check-in reports TASKS OUTDATED for any other Toolkit-made task, a cloud thread swaps it the same turn, without asking:
1. Save the old task's record (name, cron, model, prompt from `get_trigger`) to the shared folder and read it back. No saved copy, no change.
2. Render the new prompt. First make the saved params block match the task's entry: with a recorded raise, set `model`, `effort` and `raise_reason` to the higher of the template's and the raised values and the entry's reason; with none, set the template's tier, `medium` effort and no `raise_reason` (a reason kept from before tiers stays until the coordinator confirms or lowers it). The prompt then sets the right effort itself instead of undoing a raise or keeping a removed one. Then run `--refresh <kind> <old prompt file> --session <bound|fresh>`; it keeps the params and project text and always names the session the replacement runs in (the command refuses a Toolkit task without it), so a prompt rendered for the wrong session is repaired by the swap. Every swap tries bound first, also when the entry says fresh (an earlier fallback, or a task set up before tasks were bound), and starts a home thread for it; only if that bound create is refused, render again with `--session fresh` and keep the entry fresh. A hand-written prompt (`missing`) is rendered from params taken from memory, with its project-specific steps moved word for word into the project-additions section (`--project-text <file>`).
3. Create the replacement (same name and cron), with its home thread started on the tier and effort in the rendered params (with a raise, the note says "kept raised: <reason>"); a template update never lowers a recorded raise. Fire it once and confirm its report arrived; only then delete the old task. If that test run's Run line still shows a `TIER GAP`, keep the replacement and say so in the note: a swap cannot change what the platform serves, so never swap again for the same gap. For a task set up before tiers whose saved model is above the template tier, the note also says `model <old> -> <tier>` and offers to record a raise. If the test run fails, delete the new one, keep the old one and report.
4. Rewrite the `SCHEDULED TASKS:` line, read back with `get_trigger` and `--check` (`current`), and post one note: which task, what changed, the new id, and "say undo task sync <name> and I'll recreate it from the saved copy".
A `malformed` prompt holds and is reported.

**Moving a task or catching up a run.** A schedule change, or a recreate, whose new time has already passed today skips today's run if it has not already run today (a swap's test run counts as today's run): say which run will be skipped before the move, and catch it up the same turn. To catch up a bound task, or to test-fire one during a swap, message its home thread to run its prompt there now (another project's task: ask that project's coordinator); a fresh-session task is caught up by firing it, which starts its own run thread. Confirm the catch-up's report reached the coordinator. Never run a bound task's prompt in another thread or in the coordinator. Never fire_trigger a bound task from another thread: that run starts in a new session with no project tools, files or memory, so it is lost or sends a broken report. A cron change keeps the binding, so scheduled firings still land in the home thread. A task whose entry says `stopped by owner` is never moved or caught up.

**The project's own tasks** are never changed without the owner: the check-in lists their gaps as advice. The owner may opt one into the Toolkit shell once (`custom` kind: Toolkit run setup and delivery around the task's own steps, which never change); even then a shell update waits for the owner's word. Local, desktop and device-bound tasks are only listed, never recreated or moved to the cloud.

**Project memory lines.** Only these two are Toolkit's to rewrite: `BINDING:` (**Binding**) and `SCHEDULED TASKS: <name> | <trigger id> | <cron> | <fresh, bound home <thread id> since <YYYY-MM-DD>, local or device>[ | owner schedule][ | raised <tier>/<effort> <YYYY-MM-DD>: <reason>][ | stopped by owner <YYYY-MM-DD>]; <next task> ...`, listing every task in the project, the project's own included. Only the owner or the coordinator adds or removes a `raised` field, and the daily check-in reports no model or effort gap when the live settings match it. When the owner stops a task, delete or disable it and mark its entry `stopped by owner`; no check then reports it missing and nothing re-arms, updates, swaps or recreates it until the owner asks. When the owner restarts it, remove the mark. Trigger ids live only on this line, never in a prompt, so recreating one task changes nothing else. `node repo/scripts/toolkit-projects-tasks.cjs --check-memory <file>` checks both lines.

**Fallback order, only if that fails:**
- **Scheduled task on the user's Scheduled tasks page,** including a local task on their computer when the work needs the device. A local task only runs while that computer is awake and online: say so.
- **Hidden self-reminder (last resort).** A `send_later` reminder from the coordinator or a thread appears in neither the project panel nor the Scheduled tasks page, and a one-shot cannot be made recurring. Use it only when neither option above works, tell the user it is invisible to them, and re-arm it on every firing; once the owner stops it (stopped by owner), let it lapse. It has no trigger id, so it never goes on the `SCHEDULED TASKS:` line.

**Programme sweep on a device.** Only for a repository whose GitHub governance is ENABLED, in a project whose memory names a device (guided setup step 3); in any other case, never create or suggest it. Read governance as setup step 8 does, on the device. The hourly nudge's programme step needs a signed-in `gh`, which cloud task containers do not have, and cloud threads cannot refresh the pages after their own writes, so this task is what keeps the programme pages current. Set it up in guided setup step 8, or, in a project already set up, as soon as both hold, governance ENABLED and a device named, or the nudge reports "no device programme sweep task armed" (put it on the owner's pending list until it exists). None of this applies while its `SCHEDULED TASKS:` entry says `stopped by owner`.
- **On a Windows device** it is the no-AI Windows task `<FOLDER> - PROGRAMME SWEEP` in Task Scheduler's `\<FOLDER>\` folder (the binding's `schedule_folder`, else the repository name in capitals; for Toolkit, `TOOLKIT - PROGRAMME SWEEP` in `\TOOLKIT\`), hourly from 08:00 to 23:59. It refreshes the programme pages, keeps the attention line and removes the cloud route footer from the user's own GitHub posts, with no AI and no token. It is not an AI local task. Toolkit setup on the device lists it for the Toolkit repository only. For any other governed repository, the device's local Remote Control thread runs `node <Toolkit checkout>/repo/scripts/toolkit-windows-tasks.cjs plan --repo-root <that repository's checkout>`, which is read-only and lists that repository's tasks. When the task is missing or outdated, the report (setup's or plan's) ends with one PowerShell line (`node <Toolkit checkout>\repo\scripts\toolkit-windows-tasks.cjs apply --repo-root <checkout>`) that only the user pastes, because agents do not create scheduled tasks. Hand the user that exact line, for that repository's checkout, and put "paste the programme sweep line for <owner/repo>" on the owner's pending list until `node <Toolkit checkout>/repo/scripts/toolkit-tasks.cjs`, run on the device, shows the task with a last run that ended ok. List it on the `SCHEDULED TASKS:` line as local; once that entry says `stopped by owner`, never ask for the line again, even when setup lists the task as missing.
- **An AI local programme sweep already on a Windows device** stays until the user says otherwise: once the Windows task has run cleanly, ask the user once whether to delete the old local task. Never delete it silently, never create a new one there, and leave an entry that says `stopped by owner` as it is.
- **On any other device** it is one local scheduled task on the device that holds the sign-in and a checkout: hourly, the small tier at medium effort, with this whole prompt: "Run `node <programme.cjs> refresh --repo-root <checkout>`, where <programme.cjs> is `skills/github-program-reconciler/scripts/programme.cjs` in <checkout> when it has one, else in the installed Toolkit plugin copy. Change nothing else. If it prints holds or fails, say so in one line." It needs no token. A cloud thread cannot make a local task, so the coordinator has a local Remote Control thread on that device create it and run it once, reading back its result line; only if the device's safety check blocks that thread does the user create it once on their Scheduled tasks page, from the same prompt; list it on the `SCHEDULED TASKS:` line as local, and never suggest it again once its entry says `stopped by owner`. It only runs while that computer is awake.

**Listing every task.** When the user asks to list their scheduled tasks ("list my tasks"), merge two reads into one list: the project's own scheduled tasks (`list_triggers`) and, in the device's local Remote Control thread, `node <Toolkit checkout>/repo/scripts/toolkit-tasks.cjs --json`. That command is read-only with no model calls: Windows tasks are read live from Task Scheduler, Claude Code desktop tasks live by name and description, and Codex and cloud tasks from the device's task registry, marked "from record, not checked live". Say for every row where it was read, and never call a recorded row checked. When a cloud thread creates a Toolkit task, have the device thread record it once with `toolkit-tasks.cjs --record --host claude-cloud --id <id> --name <name> --schedule <text> --purpose <text> --model <tier> --effort <effort>`, and `--forget <id>` after deleting it. A task whose entry says `stopped by owner` is listed as stopped, never re-armed from the list.
