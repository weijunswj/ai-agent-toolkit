# Web Controller for Claude Projects: recurring tasks

Reference for the `web-controller-projects` skill, opened when the coordinator sets up, renders, swaps or deletes a scheduled task. The skill's precedence, style and approvals apply; where this file and the skill differ, the skill wins.

## Recurring tasks
Whenever the user asks for anything recurring (the daily check-in, a sweep, a reminder), set it up this way, and tell the user which kind you used and where they will see it.

**How to set one up (project panel):**
1. A cloud thread creates, recreates and deletes tasks; you have no scheduling tool. Fresh-session routines cannot be created from a device-linked (local Remote Control) session, or from one that was ever linked, so brief that thread with no folder, device or Remote Control tools. If creation is refused, it reports; start a fresh cloud thread, then use the next fallback.
2. Every Toolkit scheduled task is bound to its own home thread (`<PROJECT>: <task name>`): start that thread on the task's model and effort, and it creates the task bound to itself (a task fires into the session that creates it). A fresh session per run is the fallback, only where a task can't be bound. Run every day by default (`CRON_TZ=<user zone> <m> <h> * * *`) unless the user picks another schedule; the hourly nudge runs in the user's waking hours only. Model and effort: the cheapest step of the `agent-cost-control` ladder that can do the task (small, mid or top tier; medium effort at least), set on purpose, never left on a default. A bound task runs on its home thread's model and effort, whatever the Scheduled tasks panel shows, so start the home thread on both; the prompt's RUN SETUP states the tier and effort too. Going above the step its job fits needs a reason in the params (`raise_reason`).
3. Write these requirements into every task prompt: its home thread (or fresh session per run); task model/effort; full report to `latest.md` and an immutable `runs/<run UTC>.md` in its report folder; a new run stamp at `/mnt/project-files/toolkit/task-runs/<slug>/<run UTC>.md`; one capped line in its home thread (first line and per-run report path), with a capped short message to the coordinator with retry when that post fails; never end with a question to the owner; never resolve a home thread (only a fresh-session run resolves its own run thread after delivery). Specify the message cap and retry bound in the prompt; report delivery failure, never claim success.
4. Read it back with `get_trigger` (enabled, a future next run, bound to its home thread); never `fire_trigger` it: the first scheduled run is the proof. Report trigger id and next run. Ask the user to confirm the task in the project's Scheduled tasks panel. Record it on the `SCHEDULED TASKS:` line.

**Task run relay.**
- **Task runs come first.** A task run (its home-thread line, a fallback message, or a run found pending on a wake) outranks all other in-flight work except answering the owner. In the turn it arrives, before relaying thread updates, merge work or anything queued, handle it under the rules below: read its report, relay it and act on every prefix and every step its report or its task's own checklist names. A partial pass is never done: never write `.done` while any step is unfinished, however busy the turn. If a step truly cannot finish this turn, leave `.done` missing (the stamp stays unchanged), add the run UTC and the open step to the promise list, and finish that step first next turn.
- A run with a matching `<run UTC>.failed` file follows the same relay and completion rules unless its task is `stopped by owner`; its stamp is never amended. Mention delivery failure when listing unrelayed runs if the size limit allows.
- On every task report (a home-thread line or fallback message), identify its task as below and skip the task if its `SCHEDULED TASKS:` entry says `stopped by owner`, before reading reports or acting on prefixes. For a stamped run, skip it only if `<run UTC>.done` exists. Read its exact `/mnt/project-files/toolkit/task-runs/<slug>/<run UTC>.md` and the immutable per-run report path it names, never `latest.md`. Before posting, check `/mnt/project-files/toolkit/task-runs/<slug>/<run UTC>.relayed`; if it already exists, skip only the post. Otherwise post one Update line in project chat on your running post (or, when you must post fresh under the posting rules, a plain bullet in that fresh post, never an Update line): the task name, run UTC, its first line and the originating thread link recorded in that run's stamp, never memory's current home. Only after the post succeeds, write that run's `.relayed` file immediately with `relayed <run UTC> at <UTC> | <post link>` and read it back. With `.relayed` confirmed, act on every prefix of this run in the same turn, even on a replayed notification; check which effects already succeeded before repeating them. Only after every prefix has been acted on, write `<run UTC>.done` with `done <run UTC> at <UTC>` and read it back, including reports with no prefixes. A failed or unfinished action leaves `.done` missing for retry. Only the coordinator writes `.relayed` or `.done`; no task may write either file.
- **Relay missed runs.** On the first wake of every coordinator session, and on every wake a task home thread starts, list `/mnt/project-files/toolkit/task-runs/<slug>/` for every task except those whose `SCHEDULED TASKS:` entry says `stopped by owner`. Handle every run whose matching `<run UTC>.done` is missing, oldest first, including those already `.relayed`. Use the same per-run report read, check-before-post and write-after-success rules above for each run: post only when `.relayed` is missing, in one post "Relaying <n> missed task runs: ...", linking each run's originating thread from its stamp; then finish its prefix actions and write `.done`. Never use the memory line's current home as that link. The files hold this state, not your session; the hourly nudge flags any run still unrelayed after 15 minutes (`UNRELAYED TASK RUNS`) and the daily check-in any after an hour (`RELAY GAP`). The nudge also lists runs older than 15 minutes with `.relayed` but no `.done` under **Unrelayed:** as "relayed, actions not confirmed".

**Run records.** Records of tasks marked `stopped by owner` stay stored but are excluded from automatic processing. The task owns its reports, immutable run stamps and `.failed` files. The coordinator alone owns `.relayed` and `.done`. A run UTC is the actual run time in `YYYYMMDDTHHMMSSZ` form, shared by its report, stamp and receipt filenames. Each run keeps its own report and stamp; `latest.md` is only a convenience copy. Every kind's slug is `<kind>-<project prefix>-<digest>`: lower-case the project name, replace each run of other characters with one hyphen and trim edge hyphens; the digest is the first 10 hex characters of SHA-256 of `JSON.stringify([kind, project, report_dir])`, using the original values. A replacement with the same identity uses the same slug, but a new run UTC. Never overwrite an existing per-run report or stamp; if that second is already taken, wait for a new UTC second and use it for this run. A missing acknowledgement means pending, whatever a newer run's state. A successful post followed by a failed acknowledgement write remains pending; report the write failure, never mark an unposted run acknowledged. A missing `.done` means actions are not confirmed. This protocol suppresses a repeated post once its acknowledgement exists; it does not make the post and file write atomic.

**Match the task before processing.** Before relaying, catching up or acting, exclude `stopped by owner` using the exact task name on the `SCHEDULED TASKS:` line. Built-in stamps carry that name. For custom tasks, map the slug to its task from the saved trigger prompt's DELIVERY, not a guess from the readable prefix; `task this task` is not a name. Keep saved prompts for replaced tasks so their old slug still maps to the same task entry. If the mapping is missing or ambiguous, report the gap and hold that run. The originating thread link is recorded by `mcp__hearthbot__read_thread` with no `thread_id` in each run, so replacement homes and fresh-session failures keep their own links.

**Old custom shells.** Until the owner OKs that task's shell update, its stored prompt stays unchanged: it sends only a coordinator message naming `latest.md`, with no run stamp. On such a report, first exclude a task marked `stopped by owner`, then read its `latest.md` at once, relay the report to project chat and act on all its prefixes in that turn, linking the reporting thread. This bounded legacy route has no stamp, no `.relayed` or `.done`, no catch-up and no relay gap check; overwritten reports cannot be recovered. The daily check-in lists the task under **Tasks:** as "old shell: no run stamp or catch-up until the owner OKs the shell update". The removal condition is that task's owner-approved shell update; a template change alone never updates it.

**Recovery matrix.** The coordinator owns the effects; task prompts own only their reports, stamps and failure receipts. The following rows cover notification replay and wake catch-up, excluding tasks `stopped by owner`. Each run is independent, even when a newer run is complete.

| Run state | Coordinator rule | Task rule |
| --- | --- | --- |
| Task is `stopped by owner`, in any state | Skip report reads, posts and prefix actions. | Never write `.relayed` or `.done`. |
| No `.relayed`, no `.done`, not `stopped by owner` | Read the exact report, post, write and read back `.relayed`, act on every prefix, then write and read back `.done`. | Never write `.relayed` or `.done`. |
| Post failed, not `stopped by owner` | Leave both receipts missing; retry the run on replay or catch-up. | Never write `.relayed` or `.done`. |
| Post succeeded but `.relayed` write failed, not `stopped by owner` | Report the write failure; keep pending. A retry may duplicate the post. | Never write `.relayed` or `.done`. |
| `.relayed` exists, no `.done`, not `stopped by owner` | Skip posting; act on every unfinished prefix, confirm prior effects and then write and read back `.done`. | Never write `.relayed` or `.done`. |
| Prefix action or `.done` write failed, not `stopped by owner` | Keep `.relayed`; retry unfinished actions on replay or catch-up without reposting. | Never write `.relayed` or `.done`. |
| `.done` exists, not `stopped by owner` | Skip the run on replay and catch-up. | Never write `.relayed` or `.done`. |
| `.failed` exists, not `stopped by owner` | Use the same receipt states above; link the origin from the immutable stamp. | Never amend the stamp. |
| Old custom shell, not `stopped by owner` | Read `latest.md`, relay and act in the reporting turn only; no catch-up or gap checks. | Keep the stored prompt until its owner-approved shell update. |

**Toolkit-made tasks** (the daily check-in and the hourly nudge) are rendered from Toolkit `main`, never hand-written: a cloud thread runs `node repo/scripts/toolkit-projects-tasks.cjs --render <daily-check-in|hourly-nudge> --params <file>`, and `--name` for the name (`<PROJECT>: Daily check-in`, `<PROJECT>: Hourly nudge`). Params: `project` (the project name in capitals), `repo` (`owner/name` or `none`), `parent_issue` (or `none`), `report_dir` (under `/mnt/project-files/`), `effort` (`medium`, `high`, `xhigh` or `max`), `model` (tier `small`, `mid` or `top`; when left out, the hourly nudge and custom tasks take `small` and the daily check-in `mid`), `raise_reason` (required when the tier is above that default or effort above `medium`), `session` `fresh` only for the fresh-session fallback (a bound task carries none; `--refresh <kind> <file> --session bound|fresh` moves a task between them), and `toolkit_repo` when not the default. Toolkit owns only the text inside the prompt's markers; the project-additions section is kept on every refresh and wins where it differs.

**Stored prompts are pointers.** The stored prompt holds only a short Toolkit pointer, the params block and the project additions. Each run clones Toolkit `main` and prints its instructions with `--expand <kind> --params <file>`, so a Toolkit release reaches every task not stopped by owner on its next run with no swap. `--check` compares the pointer's text, not its version stamp: a pointer goes `outdated` only when its own text changes, or when the task still stores the full instructions from before pointers. A run that cannot load its instructions posts `TASK LOAD FAILED: <step>: <reason>` in its home thread instead of running from memory; treat it as `TASK FAILING`.

**Swap = update in place, recreate only to change the session.** `update_trigger` with a new prompt keeps the task's id, run history, schedule and home thread, so an outdated prompt is updated in place. Recreate only to move a task between bound and fresh (a bound task's home thread cannot be moved), or when the task is gone. A task whose `SCHEDULED TASKS:` entry says `stopped by owner` is never swapped, rebuilt or recreated; only the owner restarts it. A paused (disabled) task is swapped in place too and stays paused. When the daily check-in reports TASKS OUTDATED for any other Toolkit-made task, a cloud thread swaps it the same turn, without asking:
1. Save the old task's record (name, cron, model, prompt from `get_trigger`) to the shared folder and read it back. No saved copy, no change.
2. Render the new prompt. First make the saved params block match the task's entry: with a recorded raise, set `model`, `effort` and `raise_reason` to the higher of the template's and the raised values and the entry's reason; with none, set the template's tier, `medium` effort and no `raise_reason` (a reason kept from before tiers stays until the coordinator confirms or lowers it). The prompt then sets the right effort itself instead of undoing a raise or keeping a removed one. Then run `--refresh <kind> <old prompt file> --session <bound|fresh>`; it keeps the params and project text and always names the session the replacement runs in (the command refuses a Toolkit task without it), so a prompt rendered for the wrong session is repaired by the swap. Every swap tries bound first, also when the entry says fresh (an earlier fallback, or a task set up before tasks were bound), and starts a home thread for it; only if that bound create is refused, render again with `--session fresh` and keep the entry fresh. A hand-written prompt (`missing`) is rendered from params taken from memory, with its project-specific steps moved word for word into the project-additions section (`--project-text <file>`).
3. Same session as the entry (the usual case, the move from full prompt to pointer included): call `update_trigger` with only the new prompt, then read it back with `get_trigger` (the prompt matches, enabled state, schedule and home thread unchanged; never `fire_trigger` it). If that update is refused or the read-back differs, put the saved prompt back with `update_trigger` and report. Otherwise, to change the session, create the replacement (same name and cron), with its home thread started on the tier and effort in the rendered params (with a raise, the note says "kept raised: <reason>"); a template update never lowers a recorded raise. Read it back with `get_trigger` (enabled, the right next run time, bound to its new home thread; never `fire_trigger` it, the first scheduled run is the proof); only then delete the old task. If that first run's Run line still shows a `TIER GAP`, keep the replacement and say so in the note: a swap cannot change what the platform serves, so never swap again for the same gap. For a task set up before tiers whose saved model is above the template tier, the note also says `model <old> -> <tier>` and offers to record a raise. If the read-back fails, delete the new one, keep the old one and report.
4. Rewrite the `SCHEDULED TASKS:` line when the id changed, read back with `get_trigger` and `--check` (`current`), and post one note: which task, what changed, its id, and "say undo task sync <name> and I'll put back the saved copy".

**Other projects' Toolkit tasks.** In the project that runs the Toolkit repo, the daily check-in also reports `PROJECT TASKS OUTDATED: <PROJECT>=<task>` for another project's enabled Toolkit-made task that is not a current pointer. That coordinator swaps each one in place the same turn, owner-approved: steps 1, 2 and the in-place part of 3 above, with params and project additions read from that task's own stored prompt (never from this project's memory), the saved copy under this project's report folder, and the note naming the project. It changes only the prompt, and never for a task stopped by owner: never the name, schedule, enabled state, model or home thread, never another project's memory or files, and never a task whose stored prompt is hand-written (`missing`), `malformed` or `edited` (report those to the owner for that project's coordinator), or a disabled one: this project cannot read the other project's memory, so a paused task may be stopped by its owner there. A paused task is swapped once it is enabled again, by its own coordinator or by the next check-in here. A recreate in another project stays with that project's own coordinator.
A `malformed` prompt holds and is reported.

**Moving a task or catching up a run.** A schedule change, or a recreate, whose new time has already passed today skips today's run if it has not already run today: say which run will be skipped before the move, and catch it up the same turn. To catch up a bound task, message its home thread to run its prompt there now (another project's task: ask that project's coordinator); a fresh-session task is never fired (no `fire_trigger`), so its next scheduled run covers the gap. Confirm the catch-up's report reached the coordinator. Never run a bound task's prompt in another thread or in the coordinator. Never fire_trigger a bound task from another thread: that run starts in a new session with no project tools, files or memory, so it is lost or sends a broken report. A cron change keeps the binding, so scheduled firings still land in the home thread. A task whose entry says `stopped by owner` is never moved or caught up.

**The project's own tasks** are never changed without the owner: the check-in lists their gaps as advice. The owner may opt one into the Toolkit shell once (`custom` kind: Toolkit run setup and delivery around the task's own steps, which never change); even then a shell update waits for the owner's word. Local, desktop and device-bound tasks are only listed, never recreated or moved to the cloud.

**Project memory lines.** Only these two are Toolkit's to rewrite: `BINDING:` (**Binding**) and `SCHEDULED TASKS: <name> | <trigger id> | <cron> | <fresh, bound home <thread id> since <YYYY-MM-DD>, local or device>[ | owner schedule][ | raised <tier>/<effort> <YYYY-MM-DD>: <reason>][ | stopped by owner <YYYY-MM-DD>]; <next task> ...`, listing every task in the project, the project's own included. Only the owner or the coordinator adds or removes a `raised` field, and the daily check-in reports no model or effort gap when the live settings match it. When the owner stops a task, delete or disable it and mark its entry `stopped by owner`; no check then reports it missing and nothing re-arms, updates, swaps or recreates it until the owner asks. When the owner restarts it, remove the mark. Trigger ids live only on this line, never in a prompt, so recreating one task changes nothing else. `node repo/scripts/toolkit-projects-tasks.cjs --check-memory <file>` checks both lines.

**Fallback order, only if that fails:**
- **Scheduled task on the user's Scheduled tasks page,** including a local task on their computer when the work needs the device. A local task only runs while that computer is awake and online: say so.
- **Hidden self-reminder (last resort).** A `send_later` reminder from the coordinator or a thread appears in neither the project panel nor the Scheduled tasks page, and a one-shot cannot be made recurring. Use it only when neither option above works, tell the user it is invisible to them, and re-arm it on every firing; once the owner stops it (stopped by owner), let it lapse. It has no trigger id, so it never goes on the `SCHEDULED TASKS:` line.

**Programme sweep in the cloud.** Each governed repository carries the Toolkit Programme Sweep workflow, a GitHub Action that the pull request turning governance on adds and the one turning it off removes. It runs hourly with the governance GitHub App's tokens, cleans the cloud route's footer from the owner's posts, refreshes the programme pages and runs queued holder orders, so cloud writes and the owner's web edits need no computer. Toolkit creates no scheduled task on a computer for this, or for footer cleaning or shard timings. When the workflow cannot run for a repository (no App, missing or edited workflow copies, state on a public branch, an evidence store under another owner), `toolkit governance check` names the reason and the fix, and the run itself shows a warning. Old Toolkit tasks still recorded on a computer do nothing useful: setup names them and points to `remove toolkit`, whose plan the owner confirms. Never create, re-arm or suggest a local programme sweep.

**Listing every task.** When the user asks to list their scheduled tasks ("list my tasks"), list the project's own scheduled tasks (`list_triggers`) with the `SCHEDULED TASKS:` line, and say each row was read from the project. A task whose entry says `stopped by owner` is listed as stopped, never re-armed from the list. Toolkit runs no tasks on a computer, so there is no device list to merge.
