# Web Controller for Claude Projects: recurring tasks

Reference for the `web-controller-projects` skill, opened when the coordinator sets up, renders, swaps or deletes a scheduled task. The skill's precedence, style and approvals apply; where this file and the skill differ, the skill wins.

## Recurring tasks
Whenever the user asks for anything recurring (the daily check-in, a sweep, a reminder), set it up this way, and tell the user which kind you used and where they will see it.

**How to set one up (project panel):**
1. A cloud thread creates, recreates and deletes tasks; you have no scheduling tool. Fresh-session routines cannot be created from a device-linked (local Remote Control) session, or from one that was ever linked, so brief that thread with no folder, device or Remote Control tools. If creation is refused, it reports; start a fresh cloud thread, then use the next fallback.
2. Every Toolkit scheduled task is bound to its own home thread (`<PROJECT>: <task name>`): start that thread on the task's model and effort, and it creates the task bound to itself (a task fires into the session that creates it). A fresh session per run is the fallback, only where a task can't be bound. Run every day by default (`CRON_TZ=<user zone> <m> <h> * * *`) unless the user picks another schedule; the hourly nudge runs in the user's waking hours only. Model and effort: the cheapest step of the `agent-cost-control` ladder that can do the task (small, mid or top tier; medium effort at least), set on purpose, never left on a default. A bound task runs on its home thread's model and effort, whatever the Scheduled tasks panel shows, so start the home thread on both; the prompt's RUN SETUP states the tier and effort too. Going above the step its job fits needs a reason in the params (`raise_reason`).
3. Write these requirements into every task prompt: its home thread (or fresh session per run); task model/effort; full report to `latest.md` and an immutable `runs/<run UTC>.md` in its report folder; a new run stamp at `/mnt/project-files/toolkit/task-runs/<slug>/<run UTC>.md`; one capped line in its home thread (first line and per-run report path), with a capped short message to the coordinator with retry when that post fails; never end with a question to the owner; never resolve a home thread (only a fresh-session run resolves its own run thread after delivery). Specify the message cap and retry bound in the prompt; report delivery failure, never claim success.
4. Test one run now; report trigger id and next run. Ask the user to confirm the task in the project's Scheduled tasks panel. Record it on the `SCHEDULED TASKS:` line.

**Task run relay.**
- A run with a matching `<run UTC>.failed` file follows the same relay and completion rules unless its task is `stopped by owner`; its stamp is never amended. Mention delivery failure when listing unrelayed runs if the size limit allows.
- On every task report (a home-thread line or fallback message), identify its task as below and skip the task if its `SCHEDULED TASKS:` entry says `stopped by owner`, before reading reports or acting on prefixes. For a stamped run, skip it only if `<run UTC>.done` exists. Read its exact `/mnt/project-files/toolkit/task-runs/<slug>/<run UTC>.md` and the immutable per-run report path it names, never `latest.md`. Before posting, check `/mnt/project-files/toolkit/task-runs/<slug>/<run UTC>.relayed`; if it already exists, skip only the post. Otherwise post one Update line in project chat on your running post (or a fresh post under the posting rules): the task name, run UTC, its first line and the originating thread link recorded in that run's stamp, never memory's current home. Only after the post succeeds, write that run's `.relayed` file immediately with `relayed <run UTC> at <UTC> | <post link>` and read it back. With `.relayed` confirmed, act on every prefix of this run in the same turn, even on a replayed notification; check which effects already succeeded before repeating them. Only after every prefix has been acted on, write `<run UTC>.done` with `done <run UTC> at <UTC>` and read it back, including reports with no prefixes. A failed or unfinished action leaves `.done` missing for retry. Only the coordinator writes `.relayed` or `.done`; no task may write either file.
- **Relay missed runs.** On the first wake of every coordinator session, and on every wake a task home thread starts, list `/mnt/project-files/toolkit/task-runs/<slug>/` for every task except those whose `SCHEDULED TASKS:` entry says `stopped by owner`. Handle every run whose matching `<run UTC>.done` is missing, oldest first, including those already `.relayed`. Use the same per-run report read, check-before-post and write-after-success rules above for each run: post only when `.relayed` is missing, in one post "Relaying <n> missed task runs: ...", linking each run's originating thread from its stamp; then finish its prefix actions and write `.done`. Never use the memory line's current home as that link. The files hold this state, not your session; the hourly nudge flags any run still unrelayed after 15 minutes (`UNRELAYED TASK RUNS`) and the daily check-in any after an hour (`RELAY GAP`). The nudge also lists runs older than 15 minutes with `.relayed` but no `.done` under **Unrelayed:** as "relayed, actions not confirmed".

**Run records.** Records of tasks marked `stopped by owner` stay stored but are excluded from automatic processing. The task owns its reports, immutable run stamps and `.failed` files. The coordinator alone owns `.relayed` and `.done`. A run UTC is the actual run time in `YYYYMMDDTHHMMSSZ` form, shared by its report, stamp and receipt filenames. Each run keeps its own report and stamp; `latest.md` is only a convenience copy. Every kind's slug is `<kind>-<project prefix>-<digest>`: lower-case the project name, replace each run of other characters with one hyphen and trim edge hyphens; the digest is the first 10 hex characters of SHA-256 of `JSON.stringify([kind, project, report_dir])`, using the original values. A replacement with the same identity uses the same slug, but a new run UTC. Never overwrite an existing per-run report or stamp; if that second is already taken, wait for a new UTC second and use it for this run. A missing acknowledgement means pending, whatever a newer run's state. A successful post followed by a failed acknowledgement write remains pending; report the write failure, never mark an unposted run acknowledged. A missing `.done` means actions are not confirmed. This protocol suppresses a repeated post once its acknowledgement exists; it does not make the post and file write atomic.

**Match the task before processing.** Before relaying, catching up or acting, exclude `stopped by owner` using the exact task name on the `SCHEDULED TASKS:` line. Built-in stamps carry that name. For custom tasks, map the slug to its task from the saved trigger prompt's DELIVERY, not a guess from the readable prefix; `task this task` is not a name. Keep saved prompts for replaced tasks so their old slug still maps to the same task entry. If the mapping is missing or ambiguous, report the gap and hold that run. The originating thread link is recorded by `mcp__hearthbot__read_thread` with no `thread_id` in each run, so replacement homes and fresh-session failures keep their own links.

**Old custom shells.** Until the owner OKs that task's shell update, its stored prompt stays unchanged: it sends only a coordinator message naming `latest.md`, with no run stamp. On such a report, first exclude a task marked `stopped by owner`, then read its `latest.md` at once, relay the report to project chat and act on all its prefixes in that turn, linking the reporting thread. This bounded legacy route has no stamp, no `.relayed` or `.done`, no catch-up and no relay gap check; overwritten reports cannot be recovered. The daily check-in lists the task under **Tasks:** as "old shell: no run stamp or catch-up until the owner OKs the shell update". The removal condition is that task's owner-approved shell update; a template change alone never updates it.

**Recovery matrix.** The coordinator owns the effects; task prompts own only their reports, stamps and failure receipts. The following rows cover notification replay and wake catch-up, excluding tasks `stopped by owner`. Each run is independent, even when a newer run is complete.

| Run state | Coordinator rule | Task rule |
| --- | --- | --- |
| Task is `stopped by owner`, in any state | Skip report reads, posts and prefix actions. | Never write `.relayed` or `.done`. |
| No `.relayed`, no `.done`, not `stopped by owner` | Read the exact report, post, write and read back `.relayed`, act on every prefix, then write and read back `.done`. | Never write `.relayed` or `.done`. |
| Post failed, not `stopped by owner` | Leave both receipts missing; retry the run on replay or catch-up. | Never write `.relayed` or `.done`. |
| Post succeeded but `.relayed` write failed, not `stopped by owner` | Report the write failure; keep pending. A retry may duplicate the post. | Never write `.relayed` or `.done`. |
| `.relayed` exists, no `.done`, not `stopped by owner` | Skip posting; act on every unfinished prefix, confirm prior effects and then write and read back `.done`. | Never write `.relayed` or `.done`. |
| Prefix action or `.done` write failed, not `stopped by owner` | Keep `.relayed`; retry unfinished actions on replay or catch-up without reposting. | Never write `.relayed` or `.done`. |
| `.done` exists, not `stopped by owner` | Skip the run on replay and catch-up. | Never write `.relayed` or `.done`. |
| `.failed` exists, not `stopped by owner` | Use the same receipt states above; link the origin from the immutable stamp. | Never amend the stamp. |
| Old custom shell, not `stopped by owner` | Read `latest.md`, relay and act in the reporting turn only; no catch-up or gap checks. | Keep the stored prompt until its owner-approved shell update. |

**Toolkit-made tasks** (the daily check-in and the hourly nudge) are rendered from Toolkit `main`, never hand-written: a cloud thread runs `node repo/scripts/toolkit-projects-tasks.cjs --render <daily-check-in|hourly-nudge> --params <file>`, and `--name` for the name (`<PROJECT>: Daily check-in`, `<PROJECT>: Hourly nudge`). Params: `project` (the project name in capitals), `repo` (`owner/name` or `none`), `parent_issue` (or `none`), `report_dir` (under `/mnt/project-files/`), `effort` (`medium`, `high`, `xhigh` or `max`), `model` (tier `small`, `mid` or `top`; when left out, the hourly nudge and custom tasks take `small` and the daily check-in `mid`), `raise_reason` (required when the tier is above that default or effort above `medium`), `session` `fresh` only for the fresh-session fallback (a bound task carries none; `--refresh <kind> <file> --session bound|fresh` moves a task between them), and `toolkit_repo` when not the default. Toolkit owns only the text inside the prompt's markers; the project-additions section is kept on every refresh and wins where it differs.

**Change = recreate.** A fresh-session task cannot be edited or renamed, and a bound task is swapped by starting a new home thread that creates the replacement bound to itself. A task whose `SCHEDULED TASKS:` entry says `stopped by owner` is never swapped, rebuilt or recreated; only the owner restarts it. When the daily check-in reports TASKS OUTDATED for any other Toolkit-made task, a cloud thread swaps it the same turn, without asking:
1. Save the old task's record (name, cron, model, prompt from `get_trigger`) to the shared folder and read it back. No saved copy, no change.
2. Render the new prompt. First make the saved params block match the task's entry: with a recorded raise, set `model`, `effort` and `raise_reason` to the higher of the template's and the raised values and the entry's reason; with none, set the template's tier, `medium` effort and no `raise_reason` (a reason kept from before tiers stays until the coordinator confirms or lowers it). The prompt then sets the right effort itself instead of undoing a raise or keeping a removed one. Then run `--refresh <kind> <old prompt file> --session <bound|fresh>`; it keeps the params and project text and always names the session the replacement runs in (the command refuses a Toolkit task without it), so a prompt rendered for the wrong session is repaired by the swap. Every swap tries bound first, also when the entry says fresh (an earlier fallback, or a task set up before tasks were bound), and starts a home thread for it; only if that bound create is refused, render again with `--session fresh` and keep the entry fresh. A hand-written prompt (`missing`) is rendered from params taken from memory, with its project-specific steps moved word for word into the project-additions section (`--project-text <file>`).
3. Create the replacement (same name and cron), with its home thread started on the tier and effort in the rendered params (with a raise, the note says "kept raised: <reason>"); a template update never lowers a recorded raise. Fire it once and confirm its report arrived; only then delete the old task. If that test run's Run line still shows a `TIER GAP`, keep the replacement and say so in the note: a swap cannot change what the platform serves, so never swap again for the same gap. For a task set up before tiers whose saved model is above the template tier, the note also says `model <old> -> <tier>` and offers to record a raise. If the test run fails, delete the new one, keep the old one and report.
4. Rewrite the `SCHEDULED TASKS:` line, read back with `get_trigger` and `--check` (`current`), and post one note: which task, what changed, the new id, and "say undo task sync <name> and I'll recreate it from the saved copy".
A `malformed` prompt holds and is reported.

**Moving a task or catching up a run.** A schedule change, or a recreate, whose new time has already passed today skips today's run if it has not already run today (a swap's test run counts as today's run): say which run will be skipped before the move, and catch it up the same turn. To catch up a bound task, or to test-fire one during a swap, message its home thread to run its prompt there now (another project's task: ask that project's coordinator); a fresh-session task is caught up by firing it, which starts its own run thread. Confirm the catch-up's report reached the coordinator. Never run a bound task's prompt in another thread or in the coordinator. Never fire_trigger a bound task from another thread: that run starts in a new session with no project tools, files or memory, so it is lost or sends a broken report. A cron change keeps the binding, so scheduled firings still land in the home thread. A task whose entry says `stopped by owner` is never moved or caught up.

**The project's own tasks** are never changed without the owner: the check-in lists their gaps as advice. The owner may opt one into the Toolkit shell once (`custom` kind: Toolkit run setup and delivery around the task's own steps, which never change); even then a shell update waits for the owner's word. Local, desktop and device-bound tasks are only listed, never recreated or moved to the cloud.

**Project memory lines.** Only these two are Toolkit's to rewrite: `BINDING:` (**Binding**) and `SCHEDULED TASKS: <name> | <trigger id> | <cron> | <fresh, bound home <thread id> since <YYYY-MM-DD>, local or device>[ | owner schedule][ | raised <tier>/<effort> <YYYY-MM-DD>: <reason>][ | stopped by owner <YYYY-MM-DD>]; <next task> ...`, listing every task in the project, the project's own included. Only the owner or the coordinator adds or removes a `raised` field, and the daily check-in reports no model or effort gap when the live settings match it. When the owner stops a task, delete or disable it and mark its entry `stopped by owner`; no check then reports it missing and nothing re-arms, updates, swaps or recreates it until the owner asks. When the owner restarts it, remove the mark. Trigger ids live only on this line, never in a prompt, so recreating one task changes nothing else. `node repo/scripts/toolkit-projects-tasks.cjs --check-memory <file>` checks both lines.

**Fallback order, only if that fails:**
- **Scheduled task on the user's Scheduled tasks page,** including a local task on their computer when the work needs the device. A local task only runs while that computer is awake and online: say so.
- **Hidden self-reminder (last resort).** A `send_later` reminder from the coordinator or a thread appears in neither the project panel nor the Scheduled tasks page, and a one-shot cannot be made recurring. Use it only when neither option above works, tell the user it is invisible to them, and re-arm it on every firing; once the owner stops it (stopped by owner), let it lapse. It has no trigger id, so it never goes on the `SCHEDULED TASKS:` line.

**Programme sweep on a device.** Only for a repository whose GitHub governance is ENABLED, in a project whose memory names a device (guided setup step 3); in any other case, never create or suggest it. Read governance as setup step 8 does, on the device. The hourly nudge's programme step needs a signed-in `gh`, which cloud task containers do not have, and cloud threads cannot refresh the pages after their own writes, so this task is what keeps the programme pages current. Set it up in guided setup step 8. In a project already set up, when fresh status confirms ENABLED and a device is named, or when the nudge reports a missing device task, have a local device session follow the plan/apply route below. Hand the owner a device step only when the host blocks that session. An entry marked `stopped by owner` remains stopped.
- **On a Windows device** it is the no-AI Windows task `<FOLDER> - PROGRAMME SWEEP` in the Task Scheduler folder selected by the binding's `schedule_folder`, else the repository name in capitals (Toolkit uses `TOOLKIT`), hourly from 00:00 to 23:59. It first removes the cloud route footer from the user's own GitHub posts, then refreshes the programme pages and attention under fresh enabled governance. No AI or model tokens. Setup reports the managed repository and the original project, resolving worktrees to their verified primary checkout for reporting only. For another governed repository, resolve `<Toolkit>` as this computer's recorded managed Toolkit checkout and `<repo>` as that repository's main checkout, never a linked worktree. The local session can run the read-only plan command `node <Toolkit>/repo/scripts/toolkit-windows-tasks.cjs plan --repo-root <repo>`. Setup and `plan` only report what is needed. If task registration or a verified governance change is eligible, run exactly `node <Toolkit>/repo/scripts/toolkit-windows-tasks.cjs apply --repo-root <repo>` from the recorded managed Toolkit checkout against the target's main checkout under the global Toolkit task standing approval. Enabled verified governance selects PROGRAMME SWEEP and SHARD TIMINGS; fresh matching disabled governance or confirmed binding absence on a verified github.com origin selects FOOTER SWEEP for new enrolment. A fresh confirmed governance change can switch the proven owned cleaner shape in the same folder and checkout: apply registers and reads back the destination before retiring the source and carries its earlier valid scan boundary. If a proven owned PROGRAMME SWEEP or SHARD TIMINGS task is modified, the owner must answer keep or replace for that exact observed task each time; Keep holds the whole switch. Read back selected task registrations and the cleaner's first last-run result before updating `SCHEDULED TASKS:`. The first sweep can take up to ten minutes. Registration alone does not prove the first sweep completed. Check the command's exit and the job's own last-run result from `node <Toolkit>/repo/scripts/toolkit-tasks.cjs`; a failed, held, skipped or missing result stays visible for recovery. If standing approval does not apply, obtain approval for the exact action; hand the owner a device step only when the host blocks the session. List tasks on the `SCHEDULED TASKS:` line as local only after read-back. An entry marked `stopped by owner` is never registered, updated, moved or caught up, even if setup lists it as missing; never ask for it again.
- **An AI local programme sweep already on a Windows device** stays until the user says otherwise: once the Windows task has run cleanly, ask the user once whether to delete the old local task. Never delete it silently, never create a new one there, and leave an entry that says `stopped by owner` as it is.
- **On any other device** it is one local scheduled task on the device that holds the sign-in and a checkout: hourly, the small tier at medium effort, with this whole prompt: "Run `node <programme.cjs> refresh --repo-root <checkout>`, where <programme.cjs> is `skills/github-program-reconciler/scripts/programme.cjs` in <checkout> when it has one, else in the installed Toolkit plugin copy. Change nothing else. If it prints holds or fails, say so in one line." It needs no token. A cloud thread cannot make a local task, so the coordinator has a local Remote Control thread on that device create it and run it once, reading back its result line; only if the device's safety check blocks that thread does the user create it once on their Scheduled tasks page, from the same prompt; list it on the `SCHEDULED TASKS:` line as local, and never suggest it again once its entry says `stopped by owner`. It only runs while that computer is awake.

**After a governance merge.** After the owner merges a governance decision, the coordinator immediately relays the merged decision to the named device lane. That lane reads fresh status from origin's default branch, runs `node <Toolkit>/repo/scripts/toolkit-windows-tasks.cjs plan --repo-root <repo>`, applies a verified mismatch with `node <Toolkit>/repo/scripts/toolkit-windows-tasks.cjs apply --repo-root <repo>` under standing approval, then reads back installed tasks, enrolments and the cleaner's first result. Update `SCHEDULED TASKS:` only after that read-back. A pending proposal never triggers a switch. If this chat has ended, nothing runs on its behalf. Session start on the device informs an agent when recorded Windows tasks mismatch fresh confirmed governance; the agent must follow the same fresh-status and plan/apply route within existing approval, asking the owner if needed. Offline or stale reads stay silent. An entry marked `stopped by owner` stays stopped; host denials still hold.

**Footer-only cleaning.** A task marked `stopped by owner` stays stopped in every automatic path. A newly enrolled repository with fresh matching disabled governance or confirmed binding absence on a verified github.com origin selects `<FOLDER> - FOOTER SWEEP`, hourly from 00:00 to 23:59. It cleans only your own posts in the origin and, when freshly verified enabled governance identifies it, the evidence store. List the selected cleaner on `SCHEDULED TASKS:` as local only after device read-back; only PROGRAMME SWEEP counts as programme refresh coverage. A fresh confirmed governance change lets `apply` switch the proven owned cleaner shape in the same folder and checkout, carrying its scan boundary. Uncertain status keeps the installed shape and folder, withholds store/programme effects and permits no new FOOTER SWEEP or shape switch. A footer-only cleaner does not gain programme refresh. A programme cleaner continues origin cleaning when governance is off. Setup reports tasks without checkout paths; direct `plan` provides the exact command. Keep a device step pending only when a host denial requires the owner to act, and never repeat it after an owner stop.

Both cleaners save scan start after complete success and retry the saved boundary after failure or uncertain store scope. A task marked `stopped by owner` remains stopped on every retry or switch. Missing history starts at 48 hours without a warning; damaged history reports a 48-hour fallback, while future history names a clock anomaly. Older posts may need separately authorised full-history cleaning. A successful eligible installation has one cleaner; before apply, after removal or during interrupted owner recovery there may be none. Two cleaners are a conflict unless the registry records the proven replacement relationship from an interrupted apply; fresh apply can then finish retirement toward the current desired shape.

**Changing cleaner shape.** Fresh confirmed governance drives a bounded switch through ordinary `apply`. Before effects, it checks every cleaner and SHARD TIMINGS participant's repository, main checkout, Toolkit runner, folder, registry identity, marker, enrolled definition and stops; it takes the repository apply lock, then the footer lock, and rechecks governance and ownership. For a switch to enabled governance, apply registers and reads back PROGRAMME SWEEP, retires and verifies FOOTER SWEEP, then creates or verifies SHARD TIMINGS last. For a switch to disabled or absent governance, it registers and reads back FOOTER SWEEP, retires and verifies PROGRAMME SWEEP, then removes owned SHARD TIMINGS last. The switch carries the earlier valid scan boundary without copying a successful result or inventing a completed run, and records the replacement relationship so an interrupted switch can resume toward the latest fresh governance. It always stays in the same repository, checkout and folder; a changed folder holds for explanation and recovery. A running participant, held lock, owner stop, disabled or unexpectedly missing task, unprovable ownership or unpaired pair of cleaners holds the whole switch before effects. A modified proven-owned PROGRAMME SWEEP or SHARD TIMINGS task requires the owner's keep-or-replace answer for that exact observed definition each time. Keep leaves it unchanged and holds the switch; Replace is rechecked against the same observation under lock. The answer applies to that attempt only and never adopts the edit as Toolkit's baseline. The switch never clears an owner stop; an entry marked `stopped by owner` is never rearmed, retired or switched. Explicitly approved repair can reconcile missing owned participants and obsolete switch records towards fresh governance. A matching definition never proves who deleted a task. After acknowledged removal and independent absence read-back, apply clears the source enrolment and temporary cleaner relationship together; SHARD TIMINGS keeps its own complete enrolment until its removal. If edits or legacy proof prevent repair, obtain approval for scoped `remove --repo-root <repo>` then `apply --repo-root <repo> --repair-owned`, including reactivation of stops. Unrecorded native writes require separate inspection and approval for the exact cleanup command printed by plan, then ordinary apply. With a readable valid registry and verified current repository and managed Toolkit locations, supported recovery needs no manual registry edit. A moved live participant needs approved scoped removal first, temporarily leaving no cleaner, then explicitly approved repair including any stop reactivation. Oversized or invalid registries, missing managed-location records and changed or unprovable repository identity need separate resolution. There is no automatic cross-folder move or rollback across shapes.

**Windows task eligibility matrix.** The standing permission covers fixed PROGRAMME SWEEP and SHARD TIMINGS in ENABLED repositories with verified merged bindings, including stale enabled matching bindings for those two tasks. FOOTER SWEEP qualifies only for a verified github.com origin with fresh matching disabled governance or freshly confirmed binding absence. Freshness is required for FOOTER SWEEP eligibility and every shape switch; missing, invalid, foreign or unreadable governance grants no new FOOTER SWEEP or switch. `<Toolkit>` is the real managed checkout recorded in this computer's Toolkit state; it must be the expected Toolkit repository's main checkout. `<repo>` is the target repository's primary main checkout, verified through Git's common directory and worktree information, not a linked worktree just because its branch is named `main`. The `origin` identity and merged binding must agree. Use the binding's `schedule_folder`, else the repository's default folder, with no `--folder` override. Setup and `plan` are read-only. A working-tree binding alone is not verified. Read governance status and the merged binding on the device before acting; missing or unreadable evidence grants nothing. Never adopt or delete a conflicting task to get past a refusal. Only the job's own last-run record proves the sweep ended well. A `stopped by owner` entry is never reactivated by eligibility. Native permission remains separate.

**Modified governance tasks.** When plan reports `owner-choice-required`, ask the owner in their deciding/device chat, or in their interactive terminal: "Keep your changes or replace with Toolkit's original?" A cloud coordinator relays the actual question and answer to the device lane; no agent or script supplies the answer. Keep leaves the definition unchanged and holds the whole switch. After the actual answer, append `--task-choice keep|replace --task <id> --observed <fingerprint> --answer-ref <reference>` to apply; repeat the complete group with a distinct answer reference for each modified task. The device rechecks repository, governance revision and exact observation under lock, records the outcome and observation fingerprint in that task's registry metadata, and consumes the answer for this attempt. Stale or reused answers refuse. Flags attest a previously received answer; they cannot establish human authorship. Later edits or replacement attempts ask again. This grants no standing permission, does not adopt edits, and never clears `stopped by owner`, disabled tasks, lost ownership or moved identities.

For the supported managed-checkout and main-checkout pair, the task-state table applies:

| Existing task state | Agent, standing apply | Owner, explicit recovery | Setup or `plan` |
| --- | --- | --- | --- |
| Absent, never enrolled and no stop | Create | Create | Create, preview only |
| Healthy, same repository and checkout | Current | Current | Current |
| Healthy, other repository | Refuse | Refuse | Refuse |
| Healthy, other checkout | Refuse | Create with approved `--repair-owned` | Ask owner |
| Disabled | Refuse | Create with approved `--repair-owned` | Refuse; show stop |
| Hand-edited action | Refuse | Create with approved `--repair-owned` | Refuse; show stop |
| Hand-edited trigger | Refuse | Create with approved `--repair-owned` | Refuse; show stop |
| Removed by owner | Refuse | Create with approved `--repair-owned` | Refuse; show stop |
| Adopted or unowned | Refuse | Refuse | Refuse |
| Corrupt registry | Refuse | Refuse | Refuse |

For an intact enrolled task whose reviewed fixed definition changed, standing apply refreshes it in place and setup only previews. A live definition that differs from its enrolled baseline refuses under ordinary standing apply; owner recovery requires an approved `--repair-owned`, except a proven-owned PROGRAMME SWEEP or SHARD TIMINGS participant in a governance-driven switch follows the one-time keep-or-replace choice above. A legacy entry that cannot prove its checkout or enrolled definition holds ordinary apply. Approved scoped removal selects it by the verified primary checkout origin and matching non-adopted registry repository, even after a move; live marker and exact native definition still guard deletion. With governance off, approved remove followed by approved repair supplies the reset route. A task missing while its enrollment remains is unproven absence and refuses under standing apply without inventing an owner stop. A task using another Toolkit runner location also refuses unless its same-repository repair is explicitly approved. If any participant in a switch has an owner stop, ordinary apply refuses the whole switch before scheduler or registry writes, including every `stopped by owner` entry; approved repair can cover only the named tasks and paths. Missing or unavailable governance never becomes eligible through an owner approval. A folder override or recovery flag is outside standing approval. A host denial always refuses.

`--repair-owned` is outside the standing permission. It restores only demonstrably Toolkit-owned fixed definitions in the same repository, including an explicitly approved move back to that repository's main checkout. It cannot take over another repository's enrollment, adopt an unowned task or ignore a corrupt registry. The approval names the affected tasks, paths and changes. Ordinary apply never clears a `stopped by owner` entry.

The local owner stop is durable: `remove` records and reads back the stop before unregistering, and a failed stop write means no task is removed. A failed unregister leaves the stop in place; repeated removal preserves it. `plan` and `toolkit tasks` display `stopped by owner`, including when the live task is already missing. Ordinary apply refuses before creating an absent task. Only an explicitly approved successful repair clears the stop, after scheduler readback.

**Shard timings on Windows.** Apply registers SHARD TIMINGS in every eligible repository, even without shards; a task `stopped by owner` stays stopped. Each weekly run checks `repo/contracts/ci/test-shards.json`: `no shards yet` means no repository or external changes (only the local last-run record), and remains a quiet expected skip with no accumulating recovery count. When the manifest becomes available in the registered checkout, the next run starts timing automatically using Toolkit's fixed refresher; no repository-local script or hidden fetch is needed. The repository uses the Toolkit shard manifest and Validate summary contract (`Validate` on `main`, `test-summary-*` artifacts). Invalid or unreadable shard configuration fails visibly; other CI formats need that contract first. Timing opens a pull request only when measured times drift. No model calls.

**Listing every task.** When the user asks to list their scheduled tasks ("list my tasks"), merge two reads into one list: the project's own scheduled tasks (`list_triggers`) and, in the device's local Remote Control thread, `node <Toolkit checkout>/repo/scripts/toolkit-tasks.cjs --json`. That command is read-only with no model calls: Windows tasks are read live from Task Scheduler, Claude Code desktop tasks live by name and description, and Codex and cloud tasks from the device's task registry, marked "from record, not checked live". Say for every row where it was read, and never call a recorded row checked. When a cloud thread creates a Toolkit task, have the device thread record it once with `toolkit-tasks.cjs --record --host claude-cloud --id <id> --name <name> --schedule <text> --purpose <text> --model <tier> --effort <effort>`, and `--forget <id>` after deleting it. A task whose entry says `stopped by owner` is listed as stopped, never re-armed from the list.
