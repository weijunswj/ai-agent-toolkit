# Web Controller for Claude Projects: recurring tasks

Reference for the `web-controller-projects` skill, opened when the coordinator sets up, renders, swaps or deletes a scheduled task. The skill's precedence, style and approvals apply; where this file and the skill differ, the skill wins.

## Recurring tasks
Whenever the user asks for anything recurring (the daily check-in, a sweep, a reminder), set it up this way, and tell the user which kind you used and where they will see it.

**How to set one up (project panel):**
1. A cloud thread creates, recreates and deletes tasks; you have no scheduling tool. Fresh-session routines cannot be created from a device-linked (local Remote Control) session, or from one that was ever linked, so brief that thread with no folder, device or Remote Control tools. If creation is refused, it reports; start a fresh cloud thread, then use the next fallback.
2. Every Toolkit scheduled task is bound to its own home thread (`<PROJECT>: <task name>`): start that thread on the task's model and effort, and it creates the task bound to itself (a task fires into the session that creates it). A fresh session per run is the fallback, only where a task can't be bound. Run every day by default (`CRON_TZ=<user zone> <m> <h> * * *`) unless the user picks another schedule; the hourly nudge runs in the user's waking hours only. Model and effort: the cheapest that does the task well, starting one notch higher and stepping down after clean runs; the model is set on the task, the effort in the prompt.
3. Write these requirements into every task prompt: its home thread (or fresh session per run); task model/effort; full report to a file in the project's shared folder; capped short message to the coordinator with retry; never end with a question to the owner; never resolve a home thread (only a fresh-session run resolves its own run thread after delivery). Specify the message cap and retry bound in the prompt; report delivery failure, never claim success.
4. Test one run now; report trigger id and next run. Ask the user to confirm the task in the project's Scheduled tasks panel. Record it on the `SCHEDULED TASKS:` line.

**Toolkit-made tasks** (the daily check-in and the hourly nudge) are rendered from Toolkit `main`, never hand-written: a cloud thread runs `node repo/scripts/toolkit-projects-tasks.cjs --render <daily-check-in|hourly-nudge> --params <file>`, and `--name` for the name (`<PROJECT>: Daily check-in`, `<PROJECT>: Hourly nudge`). Params: `project` (the project name in capitals), `repo` (`owner/name` or `none`), `parent_issue` (or `none`), `report_dir` (under `/mnt/project-files/`), `effort`, `session` `fresh` only for the fresh-session fallback (a bound task carries none; `--refresh <kind> <file> --session bound|fresh` moves a task between them), and `toolkit_repo` when not the default. Toolkit owns only the text inside the prompt's markers; the project-additions section is kept on every refresh and wins where it differs.

**Change = recreate.** A fresh-session task cannot be edited or renamed, and a bound task is swapped by starting a new home thread that creates the replacement bound to itself. A task whose `SCHEDULED TASKS:` entry says `stopped by owner` is never swapped, rebuilt or recreated; only the owner restarts it. When the daily check-in reports TASKS OUTDATED for any other Toolkit-made task, a cloud thread swaps it the same turn, without asking:
1. Save the old task's record (name, cron, model, prompt from `get_trigger`) to the shared folder and read it back. No saved copy, no change.
2. Render the new prompt: `--refresh <kind> <old prompt file> --session <bound|fresh>` keeps the params and project text and always names the session the replacement runs in (the command refuses a Toolkit task without it), so a prompt rendered for the wrong session is repaired by the swap. Every swap tries bound first, also when the entry says fresh (an earlier fallback, or a task set up before tasks were bound), and starts a home thread for it; only if that bound create is refused, render again with `--session fresh` and keep the entry fresh. A hand-written prompt (`missing`) is rendered from params taken from memory, with its project-specific steps moved word for word into the project-additions section (`--project-text <file>`).
3. Create the replacement (same name, cron and model), fire it once and confirm its report arrived; only then delete the old task. If the test run fails, delete the new one, keep the old one and report.
4. Rewrite the `SCHEDULED TASKS:` line, read back with `get_trigger` and `--check` (`current`), and post one note: which task, what changed, the new id, and "say undo task sync <name> and I'll recreate it from the saved copy".
A `malformed` prompt holds and is reported.

**The project's own tasks** are never changed without the owner: the check-in lists their gaps as advice. The owner may opt one into the Toolkit shell once (`custom` kind: Toolkit run setup and delivery around the task's own steps, which never change); even then a shell update waits for the owner's word. Local, desktop and device-bound tasks are only listed, never recreated or moved to the cloud.

**Project memory lines.** Only these two are Toolkit's to rewrite: `BINDING:` (**Binding**) and `SCHEDULED TASKS: <name> | <trigger id> | <cron> | <fresh, bound home <thread id> since <YYYY-MM-DD>, local or device>[ | owner schedule][ | stopped by owner <YYYY-MM-DD>]; <next task> ...`, listing every task in the project, the project's own included. When the owner stops a task, delete or disable it and mark its entry `stopped by owner`; no check then reports it missing and nothing re-arms, updates, swaps or recreates it until the owner asks. When the owner restarts it, remove the mark. Trigger ids live only on this line, never in a prompt, so recreating one task changes nothing else. `node repo/scripts/toolkit-projects-tasks.cjs --check-memory <file>` checks both lines.

**Fallback order, only if that fails:**
- **Scheduled task on the user's Scheduled tasks page,** including a local task on their computer when the work needs the device. A local task only runs while that computer is awake and online: say so.
- **Hidden self-reminder (last resort).** A `send_later` reminder from the coordinator or a thread appears in neither the project panel nor the Scheduled tasks page, and a one-shot cannot be made recurring. Use it only when neither option above works, tell the user it is invisible to them, and re-arm it on every firing; once the owner stops it (stopped by owner), let it lapse. It has no trigger id, so it never goes on the `SCHEDULED TASKS:` line.

**Programme sweep on a device.** Only for a repository whose GitHub governance is ENABLED, in a project whose memory names a device (guided setup step 3); in any other case, never create or suggest it. Read governance as setup step 8 does, on the device. The hourly nudge's programme step needs a signed-in `gh`, which cloud task containers do not have, and cloud threads cannot refresh the pages after their own writes, so this task is what keeps the programme pages current. Set it up in guided setup step 8, or, in a project already set up, as soon as both hold, governance ENABLED and a device named, or the nudge reports "no device programme sweep task armed" (put it on the owner's pending list until it exists). It is one local scheduled task on the device that holds the sign-in and a checkout: hourly, the small tier at medium effort, with this whole prompt: "Run `node <programme.cjs> refresh --repo-root <checkout>`, where <programme.cjs> is `skills/github-program-reconciler/scripts/programme.cjs` in <checkout> when it has one, else in the installed Toolkit plugin copy. Change nothing else. If it prints holds or fails, say so in one line." It needs no token. A cloud thread cannot make a local task, so the coordinator has a local Remote Control thread on that device create it and run it once, reading back its result line; only if the device's safety check blocks that thread does the user create it once on their Scheduled tasks page, from the same prompt; list it on the `SCHEDULED TASKS:` line as local, and never suggest it again once its entry says `stopped by owner`. It only runs while that computer is awake.
