# Web Controller for Claude Projects: periodic runs

Reference for the `web-controller-projects` skill, opened when the coordinator works a daily check-in or hourly nudge run, or rebuilds either task's home thread. Both tasks are pings: their line is the run, and you work its checklist that turn (`tasks/ping-run.md`), so "the report" below is what that work finds. The skill's precedence, style and approvals apply; where this file and the skill differ, the skill wins. A bold section name, such as **Hourly nudge**, names a section of the skill.

## Acting on the check-in report
- **Task lines are work** (as in **Acting on the nudge report**). Its report's first line carries these prefixes, in this order. Act on each the same turn:
  - `CONTEXT RESET DUE`: rebuild the check-in and its home thread as **Hourly nudge** describes, unless its entry says `stopped by owner`.
  - `GUIDEBOOK MISSING` or `SKILL COPY STALE`: the check-in refreshed the library copy itself (**Guidebook copy**). On "block changed", apply the block as BLOCK CHANGED says; on `SKILL COPY FAILED`, follow **Guidebook copy**.
  - `SKILL UPDATE`: the guidebook's Version is newer than the one on the BINDING line. Read the new `SKILL.md` now, update the scheduled tasks' prompts where it says they changed (**Recurring tasks**), skipping a task whose entry says `stopped by owner`, record the Version on the BINDING line and say so in one line; never wait for a restart.
  - `SKILL CARD OUTDATED`: the owner's saved claude.ai copy of this skill, which threads and new chats load, is older than the guidebook, and no agent can save it. Offer the update card the same turn: when your session sees a saved copy, read it (current there: skip the card), then call `propose_skills` once with kind `improvement`, name and target `web-controller-projects`, the guidebook SKILL.md's frontmatter description, and `edits` that turn the saved text into the guidebook's SKILL.md exactly (with no saved copy in your session, `skillMd` with that file exactly). Record `skill card <guidebook Version> offered <date>` in memory and ping the owner in one line (**Call-to-action pings**). A dismissed card is recorded as `skill card <guidebook Version> declined <date>`, a refused one (too large, not the owner's skill) as `skill card <guidebook Version> refused <reason>` with one line to the owner, never a hand upload. Never offer a Version that has a `skill card` line again.
  - `BLOCK OUTDATED` (including `misplaced` and `overlaps`): **Managed project-instructions sync**.
  - `BINDING STALE` or `BINDING UNKNOWN`: rebind (**Binding**). When current, the report says `**Binding:** current` with the short blob, adding the newer short commit when only the commit moved.
  - `TOOLKIT CHANGED`: note the new version; the block and plugin checks follow from it.
  - `MEMORY FORMAT`: rewrite only the named Toolkit line.
  - `TASKS OUTDATED`: swap each named Toolkit-made task in place (**Recurring tasks**), never one whose entry says `stopped by owner`; add an `unlisted` task to the line.
  - `RELAY GAP`: a task run older than an hour has no matching `<run UTC>.relayed` file. Skip tasks marked `stopped by owner`; handle each remaining run without `.done` using **Task run relay** in `reference/recurring-tasks.md`: post only without `.relayed`, write it after success, finish every prefix action, then write `.done`.
  - `NUDGE NOT ARMED`: rebuild the hourly nudge and its home thread (**Hourly nudge**), without asking; a deleted nudge is rebuilt the same way, unless its `SCHEDULED TASKS:` entry says `stopped by owner`.
  - `GITHUB STEPS OWED`: the run could not read GitHub for the named steps, so they are not done. Hand them to a thread with the repos the same turn (**GitHub steps need repo access** in `reference/recurring-tasks.md`); write `.done` only after it reports back.
  - `PROJECT TASKS MISSING` (Toolkit project only): another project lost its check-in or nudge, not one its entry marks `stopped by owner`. Note which in your next status; that project's coordinator recreates them on its next wake (**Both gone**), never this one. Marked "3 days": the same set is still missing, so its coordinator never woke; ask the owner once under **Call-to-action pings** to open that project's chat.
  - `PROJECT TASKS OUTDATED` (Toolkit project only): another project's enabled check-in or nudge (a disabled one may be stopped by owner there, so it is never listed) still stores full instructions or an old pointer. Report only (**Other projects' Toolkit tasks** in **Recurring tasks**): note which in your next status; that project's own coordinator swaps it in place on its own check-in's `TASKS OUTDATED`, never this one.
  - `PLUGIN BEHIND`: this check-in's observed Toolkit plugin copy is strictly more than 24 hours behind main as it was when that copy was synced, or main today only when the report explicitly says "sync time unavailable; comparing with main today". No agent can update it: once per selected baseline version, post one plugin card in the project chat with the check-in's steps, the four numbered steps it puts under **Plugin:**, copied as written. Keep a genuine gap pending until a check-in verifies current, pinned or ahead. A verified `**Plugin:** pinned copy synced at <time>` means its copy was current or newer when it was synced; post no plugin card or owner update steps. Retire an obsolete pending card, including a legacy card caused by comparing a pinned copy with main today, without claiming the account was updated. Missing copy, missing history or other unverified evidence never clears a card. A hook-change advisory is one plain note only, with no prefix, card or automatic thread rotation. After each release merge, confirm the account copy using a fresh session's observation against main today; an old session's pinned report cannot confirm the release reached the account.
  - `TASK FAILING`: a project, local or device task failed its last run or missed its schedule. Find why the same turn: fix a cloud task yourself; for a device task, brief the device lane or put the exact step under **Call-to-action pings**. Never move a local task to the cloud for this.
  - `PR ATTENTION`: each named PR needs its next step this turn: a failing check goes back to its builder, a ready PR missing its UAT verdict gets the `UAT:` line from its lane, a quiet PR gets a lane, a recorded wait or a close with the reason, and an `unowned` PR is routed as for `PR UNOWNED`. A review-notification PR is triaged by the controller (keep, adapt in a separate PR, or close with the reason).
  - `STALE SWEEP`: judge each `JUDGE?` row against its child's DONE WHEN, PR GRAPH and notes first: a child you judge done becomes `CLOSE? #n done (<why>)`, and any other you acknowledge or plan. Then post the sweep's `CLOSE LIST` block to the owner, one line per child (its rows, your `CLOSE?` rows, the run's other rows, plus any child you judge obsolete or a duplicate, with why), asking which to close, or its "nothing to close today" line on an empty day; never one ask per child. For `FOLD?`, name the open child it folds into and copy its text there before closing it as not planned; with no fit, add its `Nearest child:` line instead. Close each approved child with a closing comment the same turn. For `MOVE?`, move its open sub-issues to the parent (a holder order) so the next sweep detaches it; for `POLISH FULL` or `POLISH OVER CAP`, plan the polish child's batched PR and open a fresh polish child for new rows.
  - `NEEDS SETUP`: as under **Acting on the nudge report**.

## Hourly nudge home thread
- Guards for the nudge's home thread:
  - Never resolve the home thread or list it as a resolve candidate; the nudge never resolves it either.
  - Each ping posts one line and reads only its run folder. The home thread also runs the tool steps you send it (`tasks/ping-run.md`): read-only, re-reading memory and files each time, one reply per request with its Run line; it writes no receipt, memory, task or setting.
  - The daily check-in reports NUDGE NOT ARMED when its last run is over 65 minutes older than the latest time its own cron should have fired (hours outside its waking window never count; a nudge that fires less often uses its interval plus 5 minutes) or its home thread is resolved, and TASKS OUTDATED `weekly-rebuild` once the home thread is 4 days old (a backstop to the nudge's own rebuild at 3 days). A run of either bound task (the nudge or the check-in) that reports `CONTEXT RESET DUE` asks for a rebuild of that task the same turn: new home thread and task, with the prompt rendered as in the swap (**Recurring tasks** step 2, so a recorded raise is carried). A task's home thread cannot be moved (the update tool edits only its name, schedule, enabled state, model and prompt), so never ask the owner to repoint it: the new home thread, briefed with the task's `handoff.md` when there is one, does every step itself. It creates a new task bound to itself with that prompt and the same name, schedule and model, reads it back with `get_trigger` (enabled, the right next run time, bound to this thread; never `fire_trigger` it, the first scheduled run is the proof), then deletes the outdated task (its record saved to the shared folder and read back first, as in the swap's step 1) and rewrites the `SCHEDULED TASKS:` line with the new id and today's "since" date. These steps change live scheduled tasks, so the first rotation needs the owner's go; record it in project memory, and later rotations proceed on it. Note each rebuild in memory. None of this applies once its entry says `stopped by owner`.
  - For a template update (never for a nudge marked `stopped by owner`), ask the home thread to update its own task's prompt, then read it back with `get_trigger` and `--check`; if that fails, rebuild.
  - If the bound nudge dies twice in 7 days, switch that project to a fresh-session nudge every 2 hours (rendered with `session` `fresh`, its entry saying fresh) and note it in your next status; never for a nudge marked `stopped by owner`.

## Reconcile Toolkit release branches

Open Toolkit PRs hold main's version and the merge thread bumps each one at merge (**Approvals**), so a merge leaves them nothing to reconcile. Only an older PR that already carries its own bump falls behind: the re-bump workflow re-bumps it after each merge. When the workflow holds one or has no push key, ask an available computer lane to run `node repo/scripts/toolkit-rebump-prs.cjs --apply`. Default mode only reports. Agree custody with the current builders before applying. While the computer is offline, keep reconciliation pending until its next wake. Follow **Approvals** for the existing GitHub permissions and branch writes.

The script compares the merge-base version with the head to prove exactly one patch, minor or major step and reapplies that level above main. It verifies the signed-in GitHub account and origin, using existing read and branch-write permissions without creating credentials. It skips drafts, forks, non-main targets and branches without a bump; queued auto-merge holds. In an isolated clone it resolves only version fields, generated stamps and the branch's new release entry through the fragment flow, keeping main's released entries byte for byte. Ambiguous versions, source conflicts, edited historical notes, failed validation or changed main/head hold the affected branch. Successful apply only fast-forwards the existing branch and never merges or accepts the pull request. Return holds to their builders, then run a fresh report after repair. Never blindly retry an uncertain push. Track the returned head, rerun CI there and request fresh G2 review of the complete delta. Keep old reviews on their old heads and record retained or affected UAT separately. Record the reconciled main commit only after accounting for every result.

## Acting on the nudge report
- **Task lines are work.** Every prefix in a home-thread line or report from any Toolkit task, the check-in's included, is a finding the controller owns (**Findings** in the Toolkit controller's evidence page), never progress on its own, and never ends your turn with `no_reply_needed`: give each an action and a deadline that turn, act, then write its `.relayed` and `.done`. A prefix you cannot clear (it needs the owner, or a real limit holds) goes to the owner once under **Call-to-action pings** with the exact step; that confirmed ping completes the prefix's action, so write `.done` and keep the step under **Waiting on you**. The same prefix on two runs in a row goes to the owner once, with the exact step and what blocks it.
- `COORDINATOR BEHIND`: the ping's own earlier runs have no `.done`. Clear the whole backlog this turn with one "Relaying <n> missed task runs" post (**Relay missed runs** in `reference/recurring-tasks.md`), act once on each distinct prefix the batch carries (one-off prefixes such as `BLOCK CHANGED` included), then write each run's own `.relayed` and `.done`.
- `CONTEXT RESET DUE` from the nudge (compacted, out of context or `(age)`): rebuild it this turn as **Hourly nudge home thread** describes, briefing the new home with the run's `handoff.md`, unless its entry says `stopped by owner`. If no thread can create the task, ping the owner with the exact step.
- `STUCK THREADS`: start a successor for each listed thread this turn under **Successors for stuck threads** below, and message each `STALLED` one once (**Message first** there). `STUCK FOR OWNER`: post each listed thread once under **Call-to-action pings** with its link and reason (a second stall within 2 hours, a long run, a Remote Control approval, denial or revoke); never start another successor or stop a long run. `STUCK CHECK FAILED`: fix the cause this turn; a repeat on the next run goes to the owner.
- `ROTATE DUE`: rotate each listed thread this turn (**One job per non-gate thread** in SKILL.md): it writes its handoff file, a fresh thread takes the work from it, and the old one is resolved once its output is saved and relayed.
- `NEEDS SETUP`: add the named memory line, id or file this turn; ping the owner only when only the owner can add it.
- `UNRELAYED ASK`: read the full source and project-chat relay, verify that the owner can act now, then follow **Call-to-action pings** in SKILL.md in this turn. Reconcile the actual ask, not just the source thread or post times. Do not repeat an already confirmed ping; keep its unfinished owner step on the pending list.
- **Nudge template changes** reach the nudge on its next run, because you read its checklist from the guidebook copy. Only a TASKS OUTDATED report refreshes its stored prompt, in place through **Recurring tasks**, preserving its schedule, bound home thread, recorded raises and any `stopped by owner` entry.
- **`DEVICE OFFLINE`:** follow **Offline alert** in `reference/device-work.md` in this turn. Ping when this outage has no entry in the promise list yet; otherwise keep it under **Waiting on you** in the reminder, with no second announcement.
- **Remote Control recovery findings:** follow **Remote Control wake** in SKILL.md in this turn. Combine the report with the other affected lanes and the existing recovery entry. The report is a check opportunity, not a separate reminder per lane or proof that every device and usage limit recovered.
- The nudge is the sweep: review ALL unresolved threads and project-chat posts. Include top-level posts with replies from coordinator or user: the thread list omits them, so also page through project chat with small page limits (large pages overflow). List:
  1. threads that are blocked, failed or stopped, or working but idle for over 45 minutes;
  2. stale thread labels and each overdue promise under **Overdue promise:**, from the promise list (**Promises wiring**);
  3. resolve candidates whose output is recorded and with nothing left open (**Threads**), with the evidence for each and "relay unverified" where relay is not proven;
  4. local Remote Control sessions whose work is finished but which are still running;
  5. open pull requests with their CI state;
  6. open project-memory items and ALL unanswered owner items with no reply or reaction, in project chat and threads, plus your answers in reply threads with no owner reply or reaction since, each with its link and ask date;
  7. `UNRELAYED`: threads resolved in the last day, or finished open ones, whose latest result never reached project chat; `HIDDEN REPLY`: an owner reply in a closed post thread with no answer, or your answer there with no top-level pointer;
  8. whether the daily check-in exists and is armed;
  9. the guidebook: one script call (`toolkit-controller-check.cjs`) runs it with the other checkers that need no model and prints one line when clear; it checks the copy against a fresh clone of main each run and refreshes a stale library copy itself (**Guidebook copy**), reporting `BLOCK CHANGED` or `SKILL COPY FAILED` on its first line.
- `UNRELAYED TASK RUNS`: skip tasks marked `stopped by owner`; handle each remaining run without `.done` the same turn using **Task run relay** in `reference/recurring-tasks.md`: post only without `.relayed`, write it after success, finish every prefix action, then write `.done`.
- `RESOLVE DUE`: in this turn, for each listed thread, read its final message in full (read_thread, full_bodies true; never this report's summary), act on or record every item in it, and resolve it once its result is relayed; for one marked "relay unverified", first add its one-line result to your post, then resolve it. If a thread still owes something, leave it open and say what it owes. Also resolve on relay between runs (**Resolve on relay** in SKILL.md), so the nudge only catches leftovers.
- `THREAD SCAN INCOMPLETE`: the resolve sweep did not run in full. Fix the cause the same turn (context exhaustion: rebuild the nudge on a fresh home thread as for `CONTEXT RESET DUE`, unless its entry says `stopped by owner`); a repeat on the next run goes to the owner.
- `LANES UNDER CAP`: start queued items the same turn until the lane cap is full or a real limit holds, and say which limit when one does.
- `CONTROLLER CHECK`: each listed check needs its next step this turn: a decision-trace gap gets the audit's `--repair` proposal applied in a records thread, a CI `GAP` goes to a lane, a leftover footer goes to the footer sweep, a retired or missing script reference goes to a lane that removes it (or registers the file in `repo/contracts/retired-scripts.json` when naming it is part of the retirement), and a check that could not run gets its cause fixed (the line names it). The same check listed on two runs in a row goes to the owner.
- `CI WAIT QUIET`: message each listed thread that turn to check its CI and carry on, and to confirm it armed its own check-in (**Threads waiting on CI arm a check-in** in SKILL.md); the same thread listed again on the next run goes to the owner.
- `SCHEDULE MISSED`: GitHub skipped a scheduled workflow's run. Re-read its newest run first; one started since the missed time needs nothing. A workflow whose run stays inside the repository's own GitHub state, as its schedule would (issues, pull requests, branches, checks; such as a source-watch notifier, programme sweep gate or shard-timings workflow), or one the owner approved by name for hand starts: the same turn, have a thread with the repos start it on the default branch (`gh workflow run <file> --ref <default branch>` or the GitHub MCP tools) and confirm the new run started. Anything else (a deploy, publish, sync, message or any other effect outside the repository) is never started without the owner's approval naming it: put it under **Waiting on you** with the file, ref and effect. A disabled workflow is not missed: tell the owner once that it is off and how to turn it back on. One without `workflow_dispatch` is a gap in that repository: route a fix that adds it with a default-branch-only job guard, and note in your next status what waits on its next schedule.
- `GITHUB STEPS OWED`: as in **Acting on the check-in report**; the nudge names steps 2b, 5 and 5b.
- `PR UNOWNED`: every open PR needs an owner and a live next step, bot and workflow PRs included. Route each listed PR that turn: green with a G2 PASS at its head to the merge train, otherwise to its builder, a reviewer or a fresh lane, or close it with the reason after the owner's OK (an evidence-store PR needs none: the store is agent-managed with standing permission, so merge or close it yourself); the same PR listed again on the next run goes to the owner.
- `WORK QUEUE`: each listed programme task needs its next step this turn: do the controller step yourself (judge done-when and close, set it back to planned, record the decision) or start its lane; a dispose needs a reason, and an ack is refused. For `BATCH_NEXT`, start the picked batch's next task; with none left, read all of LATER, pick the next batch (priority, then quickest; at most 6 PRs and one large task), set its order and record the pick on the parent (TOOLKIT-DELIVERY, Work in batches).
- `PROGRAMME FINDINGS`: work every listed finding this turn; no run only reports them. Post a missing closing story yourself (`programme.cjs closing-comment`). Skip a finding an unexpired order still in `<store path>orders/pending/` already covers. Fold every other holder write (`dispose` with its reason, `ack` with next step and due for work you start, `update`, `reopen`) into holder orders of at most 60 writes each, queue them as `<store path>orders/pending/<order_id>.json` (no more than the sweep takes in one pass, 10, counting orders already pending; the rest wait for the next run) and start the Programme Sweep workflow (**Queued orders** in the reconciler skill). The next run reads each result under `orders/done/` or `orders/refused/`. Never dispose of or ack a finding whose fix only the owner can make, such as closing an issue that needs their OK or an owner UAT: put that step under **Call-to-action pings** instead. If the store cannot be read or written, say so on the first line and hand the writes to a thread that can. Go to the owner once, with the order id, the finding and what blocks it, for a refused or expired order, or a finding still `new` after its order ran.
- **Gate assignments** (ENABLED repo, from **Programme attention before gates** in SKILL.md): every gate the coordinator starts on a programme task is one assignment, opened and ended by holder orders, so the board and the idle check follow it. The turn its thread starts, queue `assign --issue <n> --role <gate> --assignment <id>`; while the task's previous gate is still live (assigned, active, submitted or waiting on the owner), add `--supersede --reason "<gate> follows <previous gate>"`, since a plain `assign` is refused (`ASSIGNMENT_LIVE`). When the task's last gate is an accepted one of the same role (a second G0, a delta G2 after a PASS, a G2 recheck with no G1 round between), both `assign` forms are refused (`GATE_STATE`): queue `reopen --issue <n> --assignment <id> --reason "<gate> follows accepted <gate>"` instead, which keeps the role and opens the new assignment. The turn the thread reports its result, queue in one order `return --issue <n> --record <id>.r<round> --assignment <id>`, then for a G0 or G2 `return --issue <n> --consume <id>.r<round> --verdict ACCEPT` (`WAITING_OWNER` when the result is a question only the owner can answer); a G1's return stays submitted until its G2's `assign --supersede` ends it, since a G1 is accepted only after a G2 PASS. A gate thread that stops with no result gets `interrupt --issue <n> --reason <why>` instead. Write a task's lane wait as one blocker starting with the word `Queued` (never a real block); `assign` and `reopen` drop it and keep every other blocker, so a gate start needs no blocker write; check each result's `dropped_lane_waits`. Answer `QUEUED_BUT_MOVING` (a queued task's PR got a commit after the wait and outside every recorded gate) with the missed `assign`; a G0 or a push-less G2 moves no head, so only this step covers those. A G0 or G1 `assign` (or `reopen`) refused with `AGENT_UAT_UNSTARTED` means a landed task's agent UAT has not started: start it that turn in its own lane, in parallel with the gate lane, and queue in one order the `update` recording its start (`private.agent_uat` state `STARTED`) ahead of the `assign` again, or `dispose` its finding with a reason. It is not an owner question.
- `CLOUD SWEEP`: the repository's Programme Sweep workflow failed, skipped or has not run for 2 hours. Run `toolkit governance check` in a cloud thread with a clone; it names the reason and the fix (App variable or secret, workflow copies, state location). Fix what an agent can through a pull request; put an owner-only step under **Call-to-action pings**. Never set up a sweep on a computer instead.
- `RUN MISSED`: a scheduled task's run never fired or left no stamp. Check its home thread first; a run posted there since that time needs no catch-up. Otherwise catch it up the same turn as in **Moving a task or catching up** in SKILL.md, unless its entry says `stopped by owner`; the same task missed on two runs in a row goes to the owner. `RUN CHECK FAILED`: fix the input and run the check again that turn.
- `RUN PENDING`, `RECEIPT BROKEN`, `RECEIPT ORPHAN` (under `UNRELAYED TASK RUNS`): finish each pending run that turn (**Task run relay** in `reference/recurring-tasks.md`), and one deferred or paused gets its notified owner line. Rewrite a broken receipt beside its stamp with its one line, `.relayed` before `.done`, and read it back. Move an orphan receipt into `<slug>/orphans/`, never deleting it, and say which in your post.
- `CHECK-IN NOT ARMED` (including a deleted check-in): recreate it from the template the same turn, without asking, as in **Recurring tasks**, unless its entry says `stopped by owner`.
- **Both gone:** the two tasks watch each other, but if both are deleted nothing fires. So on the first owner message or wake of each day, call `list_triggers` once (a cheap read); if either Toolkit task is missing and its entry does not say `stopped by owner`, start a cloud thread that recreates it from the template on `main` (rendered as in the swap, **Recurring tasks** step 2), reads it back with `get_trigger` (never `fire_trigger`; its first scheduled run is the proof) and updates the `SCHEDULED TASKS:` line, and note it in your next status.

## Successors for stuck threads
Used for each thread the nudge lists `STUCK`, cloud thread or local Remote Control lane alike; task home threads follow **Hourly nudge home thread** instead. The nudge's stuck check (`repo/scripts/toolkit-projects-stuck.cjs`) lists a thread only when it is not busy, waits on nothing recorded (an open owner card, CI, a gate or review), and either its Remote Control session ended or is not connected or served with the session quiet 10 minutes or more, or it was failed, stopped or idle at the last run and did nothing of its own after your message. Failed or stopped is also what a usage-limit or API-error cut-off leaves, and such a thread continues on one message, so it gets that message first. The owner is not needed: a successor picks the lane up from its brief and pushed work.
- **Message first.** Each `STALLED` thread gets one `message_thread` that turn: a failed or stopped one "continue from where you stopped and report your next step", an idle one a ping for its next step or blocker. A thread listed `STUCK` for no answer gets a successor only when you sent that message; otherwise send it now and let the next run decide.
- **Check again first.** Read its state and latest messages now. If it is `working`, has posted since the report, or its branch has a newer push, it is alive: leave it. Never start one while its device is offline (**Offline alert** in `reference/device-work.md`) or a usage limit is known to still hold.
- **Start one successor.** A fresh thread with the old brief unchanged, its `Gate:` and `Route:` lines included, so a gate gets a fresh gate session on its pinned route, plus: "Successor of <old thread>, stuck at <time> (<reason>). Read its latest messages with read_thread. Pushed state: branch <branch>, head <short SHA>, PR <n>, evidence <paths>. First fetch the branch: if its head is no longer <short SHA>, stop and tell the coordinator, because the old thread may still be alive." No handover from the old thread is needed, because lanes keep their work pushed. A Remote Control lane's successor starts as any new local rc lane (**Device and cloud writes** in `reference/device-work.md`) and starts a fresh Remote Control session itself (`start_remote_control`) on the same listed folder, in its own worktree; the old session is never woken. An approval prompt on that start goes under **Call-to-action pings**, and nothing else waits on it.
- **Mark the old thread superseded.** `message_thread` it: "Superseded by <successor> at <time>: stop now, push nothing more and end your turn." End its Remote Control session under **End finished local Remote Control sessions** in SKILL.md, and resolve it as SUPERSEDED once the successor has taken over.
- **Record it.** Add `{"lane": <lane>, "old": <old thread id>, "new": <successor id>, "at": <UTC time>}` to the JSON array in `successors.json` in the nudge's report folder (start the array when the file is missing) and read it back. The lane is the old thread's own lane entry when it was itself a successor, else the old thread id. The stuck check reads it to hold each lane to one successor in 2 hours: a second stall comes back as `STUCK FOR OWNER`, never as a third thread. Add one **Update** line naming both threads; it is no owner ask.
