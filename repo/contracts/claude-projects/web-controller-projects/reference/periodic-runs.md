# Web Controller for Claude Projects: periodic runs

Reference for the `web-controller-projects` skill, opened when the coordinator acts on a daily check-in or hourly nudge report, or rebuilds either task's home thread. The skill's precedence, style and approvals apply; where this file and the skill differ, the skill wins. A bold section name, such as **Hourly nudge**, names a section of the skill.

## Acting on the check-in report
- **Task lines are work** (as in **Acting on the nudge report**). Its report's first line carries these prefixes, in this order. Act on each the same turn:
  - `CONTEXT RESET DUE`: rebuild the check-in and its home thread as **Hourly nudge** describes, unless its entry says `stopped by owner`.
  - `GUIDEBOOK MISSING` or `SKILL COPY STALE`: the check-in refreshed the library copy itself (**Guidebook copy**). On "block changed", apply the block as BLOCK CHANGED says; on `SKILL COPY FAILED`, follow **Guidebook copy**.
  - `SKILL UPDATE`: the guidebook's Version is newer than the one on the BINDING line. Read the new `SKILL.md` now, update the scheduled tasks' prompts where it says they changed (**Recurring tasks**), skipping a task whose entry says `stopped by owner`, record the Version on the BINDING line and say so in one line; never wait for a restart.
  - `BLOCK OUTDATED` (including `misplaced` and `overlaps`): **Managed project-instructions sync**.
  - `BINDING STALE` or `BINDING UNKNOWN`: rebind (**Binding**). When current, the report says `**Binding:** current` with the short blob, adding the newer short commit when only the commit moved.
  - `TOOLKIT CHANGED`: note the new version; the block and plugin checks follow from it.
  - `MEMORY FORMAT`: rewrite only the named Toolkit line.
  - `TASKS OUTDATED`: swap each named Toolkit-made task in place (**Recurring tasks**), never one whose entry says `stopped by owner`; add an `unlisted` task to the line.
  - `RELAY GAP`: a task run older than an hour has no matching `<run UTC>.relayed` file. Skip tasks marked `stopped by owner`; handle each remaining run without `.done` using **Task run relay** in `reference/recurring-tasks.md`: post only without `.relayed`, write it after success, finish every prefix action, then write `.done`.
  - `NUDGE NOT ARMED`: rebuild the hourly nudge and its home thread (**Hourly nudge**), without asking; a deleted nudge is rebuilt the same way, unless its `SCHEDULED TASKS:` entry says `stopped by owner`.
  - `PROJECT TASKS MISSING` (Toolkit project only): another project lost its check-in or nudge, not one its entry marks `stopped by owner`. Tell the owner once which; that project's coordinator recreates them on its next wake (**Both gone**), never this one. Marked "3 days": the same set is still missing, so its coordinator never woke; ask the owner once under **Call-to-action pings** to open that project's chat.
  - `PROJECT TASKS OUTDATED` (Toolkit project only): another project's enabled check-in or nudge (a disabled one may be stopped by owner there, so it is never listed) still stores full instructions or an old pointer. Swap each named task in place this turn under **Other projects' Toolkit tasks** (**Recurring tasks**); hold and report to the owner any it says to leave to that project.
  - `PLUGIN BEHIND`: this check-in's observed Toolkit plugin copy is strictly more than 24 hours behind main as it was when this check-in's own session started, or main today only when the report explicitly says "session start unavailable; comparing with main today". No agent can update it: once per selected baseline version, post one plugin card in the project chat with the check-in's steps, the four numbered steps it puts under **Plugin:**, copied as written. Keep a genuine gap pending until a check-in verifies current, pinned or ahead. A verified `**Plugin:** home thread copy pinned at <date>` means its copy was current or newer at session start; post no plugin card or owner update steps. Retire an obsolete pending card, including a legacy card caused by comparing a pinned copy with main today, without claiming the account was updated. Missing copy, missing history or other unverified evidence never clears a card. A hook-change advisory is one plain note only, with no prefix, card or automatic thread rotation. After each release merge, confirm the account copy using a fresh session's observation against main today; an old session's pinned report cannot confirm the release reached the account.
  - `TASK FAILING`: a project, local or device task failed its last run or missed its schedule. Find why the same turn: fix a cloud task yourself; for a device task, brief the device lane or put the exact step under **Call-to-action pings**. Never move a local task to the cloud for this.
  - `PR ATTENTION`: each named PR needs its next step this turn: a failing check goes back to its builder, a ready PR missing its UAT verdict gets the `UAT:` line from its lane, a quiet PR gets a lane, a recorded wait or a close with the reason, and an `unowned` PR is routed as for `PR UNOWNED`. A review-notification PR is triaged by the controller (keep, adapt in a separate PR, or close with the reason).
  - `NEEDS SETUP`: as under **Acting on the nudge report**.

## Hourly nudge home thread
- Guards for the nudge's home thread:
  - Never resolve the home thread or list it as a resolve candidate; the nudge never resolves it either.
  - Each run is self-contained (it re-reads memory and files) and replies in one line when nothing changed and it finds no unrelayed ask or parked lane.
  - The daily check-in reports NUDGE NOT ARMED when its last run is over 65 minutes older than the latest time its own cron should have fired (hours outside its waking window never count; a nudge that fires less often uses its interval plus 5 minutes) or its home thread is resolved, and TASKS OUTDATED `weekly-rebuild` once the home thread is 4 days old (a backstop to the nudge's own rebuild at 3 days). A run of either bound task (the nudge or the check-in) that reports `CONTEXT RESET DUE` asks for a rebuild of that task the same turn: new home thread and task, with the prompt rendered as in the swap (**Recurring tasks** step 2, so a recorded raise is carried). A task's home thread cannot be moved (the update tool edits only its name, schedule, enabled state, model and prompt), so never ask the owner to repoint it: the new home thread, briefed with the task's `handoff.md` when there is one, does every step itself. It creates a new task bound to itself with that prompt and the same name, schedule and model, reads it back with `get_trigger` (enabled, the right next run time, bound to this thread; never `fire_trigger` it, the first scheduled run is the proof), then deletes the outdated task (its record saved to the shared folder and read back first, as in the swap's step 1) and rewrites the `SCHEDULED TASKS:` line with the new id and today's "since" date. These steps change live scheduled tasks, so the first rotation needs the owner's go; record it in project memory, and later rotations proceed on it. Note each rebuild in memory. None of this applies once its entry says `stopped by owner`.
  - For a template update (never for a nudge marked `stopped by owner`), ask the home thread to update its own task's prompt, then read it back with `get_trigger` and `--check`; if that fails, rebuild.
  - If the bound nudge dies twice in 7 days, switch that project to a fresh-session nudge every 2 hours (rendered with `session` `fresh`, its entry saying fresh) and tell the owner; never for a nudge marked `stopped by owner`.

## Reconcile Toolkit release branches

Open Toolkit PRs hold main's version and the merge thread bumps each one at merge (**Approvals**), so a merge leaves them nothing to reconcile. Only an older PR that already carries its own bump falls behind: the re-bump workflow re-bumps it after each merge. When the workflow holds one or has no push key, ask an available computer lane to run `node repo/scripts/toolkit-rebump-prs.cjs --apply`. Default mode only reports. Agree custody with the current builders before applying. While the computer is offline, keep reconciliation pending until its next wake. Follow **Approvals** for the existing GitHub permissions and branch writes.

The script compares the merge-base version with the head to prove exactly one patch, minor or major step and reapplies that level above main. It verifies the signed-in GitHub account and origin, using existing read and branch-write permissions without creating credentials. It skips drafts, forks, non-main targets and branches without a bump; queued auto-merge holds. In an isolated clone it resolves only version fields, generated stamps and the branch's new release entry through the fragment flow, keeping main's released entries byte for byte. Ambiguous versions, source conflicts, edited historical notes, failed validation or changed main/head hold the affected branch. Successful apply only fast-forwards the existing branch and never merges or accepts the pull request. Return holds to their builders, then run a fresh report after repair. Never blindly retry an uncertain push. Track the returned head, rerun CI there and request fresh G2 review of the complete delta. Keep old reviews on their old heads and record retained or affected UAT separately. Record the reconciled main commit only after accounting for every result.

## Acting on the nudge report
- **Task lines are work.** Every prefix in a home-thread line or report from any Toolkit task, the check-in's included, is a finding the controller owns (**Findings** in the Toolkit controller's evidence page), never progress on its own, and never ends your turn with `no_reply_needed`: give each an action and a deadline that turn, act, then write its `.relayed` and `.done`. A prefix you cannot clear (it needs the owner, or a real limit holds) goes to the owner once under **Call-to-action pings** with the exact step; that confirmed ping completes the prefix's action, so write `.done` and keep the step under **Waiting on you**. The same prefix on two runs in a row goes to the owner once, with the exact step and what blocks it.
- `COORDINATOR BEHIND`: the nudge's own earlier runs have no `.done`. Clear the whole backlog this turn with one "Relaying <n> missed task runs" post (**Relay missed runs** in `reference/recurring-tasks.md`), act once on each distinct prefix the batch carries (one-off prefixes such as `BLOCK CHANGED` included), then write each run's own `.relayed` and `.done`.
- `CONTEXT RESET DUE` from the nudge (compacted, out of context or `(age)`): rebuild it this turn as **Hourly nudge home thread** describes, briefing the new home with the run's `handoff.md`, unless its entry says `stopped by owner`. If no thread can create the task, ping the owner with the exact step.
- `ROTATE DUE`: rotate each listed thread this turn (**One job per non-gate thread** in SKILL.md): it writes its handoff file, a fresh thread takes the work from it, and the old one is resolved once its output is saved and relayed.
- `NEEDS SETUP`: add the named memory line, id or file this turn; ping the owner only when only the owner can add it.
- `UNRELAYED ASK`: read the full source and project-chat relay, verify that the owner can act now, then follow **Call-to-action pings** in SKILL.md in this turn. Reconcile the actual ask, not just the source thread or post times. Do not repeat an already confirmed ping; keep its unfinished owner step on the pending list.
- **Nudge template changes** reach the nudge on its next run, because it loads its instructions from `main`. Only a TASKS OUTDATED report refreshes its stored prompt, in place through **Recurring tasks**, preserving its schedule, bound home thread, recorded raises and any `stopped by owner` entry.
- **`DEVICE OFFLINE`:** follow **Offline alert** in `reference/device-work.md` in this turn. Ping when this outage has no entry in the promise list yet; otherwise keep it under **Waiting on you** in the reminder, with no second announcement.
- **Remote Control recovery findings:** follow **Remote Control wake** in SKILL.md in this turn. Combine the report with the other affected lanes and the existing recovery entry. The report is a check opportunity, not a separate reminder per lane or proof that every device and usage limit recovered.
- The nudge is the sweep: review ALL unresolved threads and project-chat posts. Include top-level posts with replies from coordinator or user: the thread list omits them, so also page through project chat with small page limits (large pages overflow). List:
  1. threads that are blocked, failed or stopped, or working but idle for over 45 minutes;
  2. stale thread labels and each overdue promise under **Overdue promise:**, from the promise list (**Promises wiring**);
  3. resolve candidates whose output is recorded and with nothing left open (**Threads**), with the evidence for each and "relay unverified" where relay is not proven;
  4. local Remote Control sessions whose work is finished but which are still running;
  5. open pull requests with their CI state;
  6. open project-memory items and ALL unanswered owner items with no reply or reaction, in project chat and threads, plus your answers in reply threads with no owner reply or reaction since, each with its link and ask date;
  7. `UNRELAYED`: threads resolved in the last day, or finished open ones, whose latest result never reached project chat; `HIDDEN REPLY`: an owner reply in a closed post thread with no answer, or your answer there with no top-level pointer;
  8. whether the daily check-in exists and is armed;
  9. the guidebook: it checks the copy against a fresh clone of main each run and refreshes a stale library copy itself (**Guidebook copy**), reporting `BLOCK CHANGED` or `SKILL COPY FAILED` on its first line.
- `UNRELAYED TASK RUNS`: skip tasks marked `stopped by owner`; handle each remaining run without `.done` the same turn using **Task run relay** in `reference/recurring-tasks.md`: post only without `.relayed`, write it after success, finish every prefix action, then write `.done`.
- `RESOLVE DUE`: in this turn resolve each listed thread whose result you relayed; for one marked "relay unverified", first add its one-line result to your post, then resolve it. If a thread still owes something, leave it open and say what it owes. Also resolve on relay between runs (**Resolve on relay** in SKILL.md), so the nudge only catches leftovers.
- `THREAD SCAN INCOMPLETE`: the resolve sweep did not run in full. Fix the cause the same turn (context exhaustion: rebuild the nudge on a fresh home thread as for `CONTEXT RESET DUE`, unless its entry says `stopped by owner`); a repeat on the next run goes to the owner.
- `LANES UNDER CAP`: start queued items the same turn until the lane cap is full or a real limit holds, and say which limit when one does.
- `CI WAIT QUIET`: message each listed thread that turn to check its CI and carry on, and to confirm it armed its own check-in (**Threads waiting on CI arm a check-in** in SKILL.md); the same thread listed again on the next run goes to the owner.
- `PR UNOWNED`: every open PR needs an owner and a live next step, bot and workflow PRs included. Route each listed PR that turn: green with a G2 PASS at its head to the merge train, otherwise to its builder, a reviewer or a fresh lane, or close it with the reason after the owner's OK; the same PR listed again on the next run goes to the owner.
- `WORK QUEUE`: each listed programme task needs its next step this turn: do the controller step yourself (judge done-when and close, set it back to planned, record the decision) or start its lane; a dispose needs a reason, and an ack is refused.
- `CHECK-IN NOT ARMED` (including a deleted check-in): recreate it from the template the same turn, without asking, as in **Recurring tasks**, unless its entry says `stopped by owner`.
- **Both gone:** the two tasks watch each other, but if both are deleted nothing fires. So on the first owner message or wake of each day, call `list_triggers` once (a cheap read); if either Toolkit task is missing and its entry does not say `stopped by owner`, start a cloud thread that recreates it from the template on `main` (rendered as in the swap, **Recurring tasks** step 2), reads it back with `get_trigger` (never `fire_trigger`; its first scheduled run is the proof) and updates the `SCHEDULED TASKS:` line, and tell the owner once.
