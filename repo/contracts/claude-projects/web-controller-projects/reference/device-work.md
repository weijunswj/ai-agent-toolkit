# Web Controller for Claude Projects: device work

Reference for the `web-controller-projects` skill, opened before the coordinator starts a local Remote Control thread, moves device evidence, writes outward text from the cloud or runs a recovery sweep. The skill's precedence, style and approvals apply; where this file and the skill differ, the skill wins. A bold section name, such as **Hourly nudge**, names a section of the skill.

## Device and cloud writes
- **Read back outward text written from the cloud.** A cloud write path may alter what it sends, for example by appending a footer or changing link formatting. Diff PR bodies, comments and commit messages against what was sent; evidence files pushed to a Git store need no diff. If it was altered, repair it once through another path. If that is altered too, route that kind of write through local rc and record the limit in project memory.
- **Anchor local Remote Control threads on the user's message.** Start a local Remote Control thread on a related message the user wrote in the project chat (one that has no thread yet). A message inside an existing thread routes to that thread's own session instead of starting a new one. Anchoring on the coordinator's own post shows the user an extra Allow card every time, and some hosts refuse it.
- **Make the GitHub repository first, then clone it.** Before preparing a local Remote Control lane, make its GitHub repository and clone that remote. Never run `git init` in a local scratch folder before its remote exists. Until then, use a plain folder or an already-decided repository's ignored `.tmp/` folder.
- **Batch device writes behind one typed line.** Auto mode on the device blocks writes approved only by relay. Group a local Remote Control thread's writes into one step, and give the user the exact line to type in that thread before it starts, not after it trips.
- **Move device evidence through the shared folder.** A local Remote Control thread copies evidence it produced to the project's shared folder, and cloud archives it to the transport store once, at gate end (in a Git store the commit is the manifest and a push plus one fetch the read-back). If a cloud write path is refused (for example, pushes limited to a session branch), say so once and use the next path that works.

## Recovery sweep
Used by **Remote Control wake** in the skill once work can run again after an interruption.
- **Recovery reminder.** On the first successful wake after a recorded interruption, check every affected local rc lane with this sweep in the same turn. Owner messages, thread messages, timer wakes and periodic reports are check opportunities; never wait for the owner to request the reminder.
- **Check recovery from evidence.** Check on the owner's recovery report, the first successful coordinator wake after a recorded interruption, a relevant connection recovery, and each hourly nudge report. A gap or a parked status alone does not prove that a device or usage limit recovered. Report unavailable or unknown conditions plainly; never claim an exact reset time or a working lane without evidence.
- **Build one complete list.** Page through `list_threads`, reconcile the Remote Control inventory, and check each affected local rc lane with `remote_control_status` as supported by the host. Skip finished, superseded, resolved, cloud and already-working lanes. Separate sessions still waiting for a device or another prerequisite from resumable sessions needing owner input. A missing session, failed status read or incomplete inventory is not success. `remote_control_status` reads one thread per call by `thread_id` and reports its state (waiting for approval, active, denied, revoked or ended) with running, connected, served and last activity; an active session that is not running, connected or served is the usual parked case, so confirm it from these fields before asking for text.
- **Deduplicate recovery reminders.** Keep one entry for the interruption in the existing promise list: its cause and observation time, affected lanes, recovery evidence, reminder status, successful project-chat post link and outstanding lanes. Reuse it across timer wakes, owner messages and periodic reports. After context loss or uncertain posting, reconcile chat and thread status before posting again. Repeated observations do not create another recovery announcement. If another lane becomes resumable later, it is a new owner step under **Call-to-action pings**: carry forward the complete outstanding recovery list in that notifying post. A new observed interruption starts a new entry. Keep outstanding wake steps in ordinary hourly reminders. Mark a lane resumed only after current status or activity confirms it, it finishes, or an explicit owner decision disposes of it.
