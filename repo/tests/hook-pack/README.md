# Hook test pack

One list of tool calls that every hook change must keep deciding the same way: calls that must pass (no false blocks) and calls that must stop (no leaks), including what happens when a hook itself breaks. `repo/scripts/toolkit-hook-pack.cjs` runs them through the hooks exactly as Claude Code and Codex start them: it reads both `hooks.json` files from a temporary copy of the plugin, matches each call against the real matchers, writes the plugin folder into the command and starts every matching hook as its own process with the call on stdin. On Windows the Codex hooks run through the PowerShell launcher setup installs. It then reads the decision the host would act on and checks that no fixture file changed.

The pack starts hooks directly in fixtures. It cannot prove that the installed host trusts the plugin or delivers a real call. Codex bundle changes can revoke hook approval even when this pack is green. Real-host smoke requires a positive control refusal in the same chat, without editing the plugin root.

## Running it

- `node repo/scripts/toolkit-hook-pack.cjs run`: every row on this computer's system. Add `--suite <kind>`, `--family <file name>[,<file name>...]` (or joined by `+`), `--rows <id,id>`, `--host claude|codex` or `--verbose` (prints each refusal's text).
- `node repo/scripts/toolkit-hook-pack.cjs run --against <commit>`: the revert proof. It runs the rows that commit's pack does not have (or `--rows`) against the plugin as it was there, and passes only when each one fails there. Run it against the parent of a fix to show the fix is what makes its rows pass; no hook script needs feeding by hand.
- `node repo/scripts/toolkit-hook-pack.cjs check-expectations`: lists every row removed, lowered to `known-bad` or changed in any other way since the base (hosts, event, payload, fixture, fault, expect, kind, source or note); only flipping a known-bad row toward passing (`status`, `known_bad_on`, `lane`, `added`) needs no reason. In a pull request each needs a line under a `## Pack changes` heading in the body: `<row id>: <why>`.
- `node repo/scripts/toolkit-hook-pack.cjs validate`: checks the row format only.

CI runs the full pack on Linux in `hook-pack` and in four groups of families in the `hook-pack-windows` matrix of `validate.yml`: attribution with closure-matrix, closure-shell with push, governance with issue-closure, and fault with merge and task-governance. `--family` takes a list joined by commas or `+` (the workflow uses `+`), so each group runs in one job. The groups have about the same measured time and their union covers every row and host exactly once. Four jobs instead of nine keeps more of the account's concurrent runner slots free. The Linux job has a 360-second pack budget and each Windows group a 420-second one, all with a 15-minute timeout. The pack reports overdue work and fails the completed run if it exceeds its budget; the budget does not stop the process. The `gate` job waits for the Linux job and every Windows group and runs the expectation-change check.

The closure shell family covers hidden writes, strict Start-Process arguments and shell syntax, with retained read and data controls. It keeps new cases out of the issue-closure and merge families.

The closure matrix includes ordinary command data across folders and tool names, clean identity and body-file controls, and API, connector and approval-ordering cases. Keeping those rows together leaves headroom in the executable issue-closure family without changing any row, host or expectation. Step rows share one fixture to check merge, attribution and push decisions across Codex shell names and input shapes.

## Rows

Each file in `corpus/` is one family (the effect it guards: push, attribution, governance, merge, fault and so on), `{ "schema": "toolkit-hook-pack/v1", "family": "<file name>", "rows": [...] }`. A row:

- `id`: starts with a capital letter, unique in the pack.
- `source`: where the row came from (an incident, a review report, a seed).
- `kind`: the suite it belongs to: `benign` (must pass), `hostile` (must stop), `fault` (the hook breaks), `update` (the plugin folder changes mid-chat), `state` (a decision that depends on earlier sessions or transcripts) or `parity` (both hosts and shell readings must agree).
- `hosts`: `claude`, `codex` or both. A row on both hosts must decide the same on each, unless `expect_by_host` gives a host its own expectation and `note` says why.
- `event`: `PreToolUse` (the default), `PostToolUse`, `UserPromptSubmit` or `SessionStart` (whose payload gives `source`, such as `startup` or `resume`).
- `host_session` (optional, also on each step): puts only a fixture value into the hook's host-session variable for that event: `matching`, `mismatching` or `empty`. Omit it for an absent variable. Steps never inherit this value from the final event or another step.
- `steps` (optional): 1 to 24 preceding hook events in order, each with `event`, `payload` and `expect`, and optional `expect_by_host` and its `note`. These run before the row's final payload in the same isolated home on each host. Every step must meet its own expectation. This proves prompt recording, governance holds and single-use approvals through the real hook entry points without running a merge command. Nested sequences and arbitrary runner actions are refused.
- `payload`: the call as the host sends it (`tool_name`, `tool_input`, or `prompt`). The runner adds `session_id`, `transcript_path`, `cwd` and `hook_event_name` unless the payload sets them.
- `fixture` (optional): `repo` with `governance` (`enabled`, `disabled`, `undecided` or `none`), `name`, `branch`, `commits` (`{ files, message }`, the default is one commit), `worktrees` (branch names, each its own working tree beside the working folder), `nested_worktrees` (`{ branch, commits }`, each its own working tree under the working folder's ignored `.tmp/worktrees/`, with its own commits), `staged` files, `task_auto_merge` (a governed fixture's merged task auto-merge answer), and for an `undecided` fixture `owner` (its remote's owner) and `legacy_answer` (`yes`, `no` or `damaged`, frozen historical test data), `binding_status` (`unavailable`, otherwise a fresh confirmed absence), `can_write` (false: startup verified this account cannot push), and `cached_binding_store` (true: another governed repository on this computer has a cached programme binding naming `toolkit-test-fixture/<name>` as its evidence store); `gate_role` (`G0`, `G1` or `G2`: the session is a Toolkit gate run, as a launcher marks it); `owner_session` (true: the user started the session); `files` written into the working folder; `transcript` entries written to the session's transcript file.
- `fault` (optional): `deleted-plugin-root` (the plugin version folder is gone), `remove-file`, `throw-module` or `stall-module` with a `file` under `repo/scripts`, `bad-json` or `empty-input`.
- `expect`: `decision` (`allow` or `deny`) and optionally `reason`, the script name of the hook that refused (with `:failure` when the host refused because the hook itself failed). A refusal that comes only from a hook failing meets a row only when the row names that `:failure` reason, so a broken hook never stands in for a real decision. Never the refusal's text.
- `expect.context_contains` and `expect.context_excludes`: unique nonempty strings required exactly once or forbidden in delivered SessionStart or UserPromptSubmit context. Claude checks JSON `additionalContext`; Codex checks plain stdout for SessionStart and JSON `additionalContext` for UserPromptSubmit. Stderr is never context evidence; diagnostics never print the compared text.
- `fixture.windows_tasks`: isolated recorded Windows jobs (`programme-sweep`, `shard-timings`, `footer-sweep`, `task-health`). With enabled, disabled or undecided fixture governance, a test-only preload injects Windows into the advisory reader alone and enables its local observation while refresh stays offline. No production platform switch is added.
- `fixture.task_health`: `local-only`, `failed` or `stopped`, with `windows_tasks`, writes only the isolated cached health document. `health-stopped` also marks the isolated TASK HEALTH enrolment stopped and gives it an old, unshared document to check that sessions stay quiet. `fixture.windows_deferred_auth: true`, with a recorded shard, writes an isolated deferred authentication result for the session-line regression. Neither changes production host or scheduler state.
- `postcondition` (optional): `no-local-decision-write` checks that the retired laptop decision file is absent or unchanged after every step and the final hook event. This proves an answer stays pending instead of silently writing an off/on decision.
- `status`: `pass`, or `known-bad` for a bug its lane has not fixed yet, with `lane`, `added` (the date) and optionally `known_bad_on` (the hosts it fails on; all of them when absent) and `issue` (the number of the issue that tracks the fix). The runner fails when a known-bad row starts passing, so the fix flips it to `pass` in the same change. A run also fails when a known-bad row is over 30 days old and names no `issue`: the row is owed work, so its lane fixes it or the controller files the tracking issue and adds its number. The runner reads the real clock for this; tests pass a fixed clock to `main`.

Placeholders in a payload, fixture file or transcript: `{work}` (the working folder), `{trees}` (the extra working trees), `{home}` (the fixture's home), `{transcript}` (the session transcript), `{now}` (the current UTC time for a fresh Projects delivery) and `{credential}` (a fake credential built at run time, so none sits in the repository). Merge rows also use `{head}` and `{head7}` (the fixture's head commit, in full and as its first seven characters). A placeholder works in an object key too, such as an answer keyed by its question.

`{planner_apply}` and `{planner_remove}` expand through the tested plugin's real task planner, including in `--against` runs. These rows need `fixture.managed_tasks: true`; their managed checkout is the fixture working folder under its isolated home. They prove that the actual printed command passes the hold without running that command.

Task merge fixtures use `fixture.repo.task_auto_merge`: `after-gates`, `off`, `after-gates-stale` (stale governance binding), `codex-only`, `claude-code-only`, or `unreadable`. These create app-local preference files in the temporary home, separate from a fresh enabled binding. The host-only cases prove one app never inherits the other app's answer.

Each row gets its own fixture and home, so no row reads the real user's state or another row's; the home is put back as built before the second host runs. Fixture timestamps use the system clock, matching the hook processes after the caller's test clock injection is removed. Session-start binding refresh is disabled, so the pack does not contact remotes.

Evidence merge rows use `fixture.evidence_merge`: `from` is `store` (an undecided repository named `evidence`) or `parent` (an enabled repository). `binding` defaults to `fresh`, with `stale` as a negative control. `metadata` defaults to `verified`; negative controls are `public` and `wrong-head`. Four positive rows and four refusal controls cover the real hook entry points, including a compound merge into a source repository. The other refusal controls run in one table-driven test in `repo/tests/toolkit-merge-hold.test.cjs`. These fixtures create an exact merged parent binding and fixed repository and pull request responses. A process-local preload intercepts the fake GitHub executable before it runs, while the production transport parses its HTTP response. Every row receives this isolated transport, returning unavailable metadata for unspecified requests, so no pack row can call the real GitHub CLI. No production hook accepts fixture metadata or gains a new permission switch.
