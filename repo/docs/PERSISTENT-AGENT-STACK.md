### GitHub transport order

For all routine already-authorised mechanical GitHub mutations, start with a qualified executor on the mechanical-GitHub role above, including private admission records, CURRENT/status updates, issue/PR/comment bodies and branch/file writes. The persistent controller retains connector reads and consequential decisions. Give the executor the exact approved bounded operation and required evidence/readback; it may use its GitHub connector or qualified task-scoped escalated `gh` under current permissions and the operation-specific exception below. Verify its actual intended-account authentication, supported launch configuration and effects; neither route availability nor escalation grants additional authority. Do not change credentials or security settings to make a route work. Pending approvals, explicit denials, no-retry restrictions and unresolved effects carry into the executor unchanged; delegation is not permission to reroute a denied action, and a required approval must use the actual supported approval prompt. Other persistent hosts keep their existing routing.

Apply this transport order only to operations already within task authority. The selected model role covers routine non-gate mechanical work with an exact approved diff/payload, not complex, ambiguous or consequential decision-making. Keep those decisions with the controller and any separately qualified stronger route. Preserve all other helper preferences, the G1-G4 stack registry and assignments, and admitted workers; do not hot-swap live work.

A tool/service failure is not an access/authority denial. Explicit denials, mandatory confirmations, no-retry instructions and unresolved effects carry across all routes. Never launch an executor, change transport or narrow a payload to evade a denied effect.
