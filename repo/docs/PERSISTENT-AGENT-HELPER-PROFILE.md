## Coding-agent launch and supervision

For already-authorised controller-directed coding work, use one capability-qualified lightweight executor to launch and supervise the selected coding agent. The controller supplies the bounded task, exact selected route, permitted effects, evidence return and stop conditions; the controller/host resolves the launcher role and matching host mapping from the persistent-agent stack before dispatch. The selected coding route is the exact pinned-stack route for the dispatched role and member, enforced at the launch boundary rather than merely named in the prompt; the persistent controller's own manually selected model and effort stay advisory. Prefer the fewest reliable handoffs without inferring cost savings or changing required roles.

- Apply Controller's fresh-job context and operational-handoff rules. Use a fresh qualified chat for a new job; retain an existing chat only for a context-dependent continuation. Keep launch packets and status reads focused on the current job rather than accumulating completed-job history.
- Configure the coding agent's supported launch and permission settings explicitly within the exact task authority and current host permissions. A launcher, visible terminal, installed CLI, model label or owner task approval does not itself establish capability or clear a permission boundary. Preserve mandatory confirmations, denials and unresolved outcomes; do not select bypass settings or change routes to evade them.
- Verify the admitted task/process/session and distinguish prepared, accepted, running and terminal states. Use supported completion notifications and the smallest sufficient status checks or bounded log excerpts; avoid busy polling and repeated full-log reads. Monitor enough to detect completion, a genuine stall or an uncertain outcome, then reconcile before any permitted recovery or retry.
- Retrieve the complete decision-relevant return, exact candidate and validation evidence through approved custody. Independently read back the required result before claiming completion; an exit code, visible window or worker summary alone is insufficient. Return the verified outcome or exact blocker and next action promptly, preserving consumed limits and required evidence.

The supervisor performs mechanical launch, observation and authorised recovery only. It is not an additional semantic gate or independent controller, does not implement or review the candidate itself, and cannot widen task scope, change the selected coding route or relax required assurance. Preserve Controller's semantic parent/leaf topology and delegation limits, fresh gate contexts, active-worker protections and publication boundaries. Apply Controller's finish-before-stop rule: advance every independently runnable authorised step to its verified terminal state before reporting, and hold only steps that depend on a genuine owner, UAT, permission, capability, unknown-effect or G2 boundary. If the required route or observation/return capability is unavailable, hold only the dependent action and report the exact gap. This workflow adds no framework, scheduler or runtime-enforcement claim. ### Approval, denial and generic-cancellation handling

Diagnose the exact blocked operation and reconcile its actual effects before choosing a remedy. Use safe already-authorised recovery within current scope and bounds. If approval is genuinely missing, ask once for the exact action and target through a supported approval flow and keep that request pending. If approval already exists, provide its exact primary evidence through the supported review channel to resolve a missing-authority conflict; make only a permitted, reconciled retry. An unchanged explicit denial, no-retry restriction or mandatory confirmation remains binding.

A generic `user cancelled MCP tool call` result alone is an uncertain tool failure, not evidence that the owner withdrew approval. Unless the owner communicates cancellation, reconcile possible partial success and automatically make a bounded safe retry of the already-authorised operation without a redundant approval question, within the accepted task/retry limits. Preserve consumed attempts; do not retry blind, indefinitely, after an explicit denial/no-retry instruction, or while consequential effects remain ambiguous. An applicable host-specific service fault uses the qualified exception in the referenced stack rather than repeated no-progress connector attempts. An actual owner stop or cancellation always controls.

For a persistent permission barrier, owner manual action means approval in the actual blocked task/chat or supported approval prompt, not editing GitHub files, committing or executing commands. First verify an actionable control exists; provide its verified link, exact bounded approval text, intended effect and material risks. If no supported control exists, state that exact limitation and retain the dependent hold. Never promise that a chat reply or "full permissions" clears a connector denial. Verify whether supported approval actually cleared the specific blocker and independently read back the result before continuing; one resolved blocker clears no unrelated restriction.
