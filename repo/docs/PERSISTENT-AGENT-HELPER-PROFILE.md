# Persistent-agent helper workflow

## Applicability and authority

Load this file only for an explicitly identified persistent agent (for example, ChatGPT dot) using an owner-approved workflow. Non-persistent or unknown agent modes skip this file and retain their existing routing. A bootstrap invocation or this file's existence does not establish persistent-agent mode or task authority.

This is owner-specific manual guidance, not generic Toolkit model policy, runtime enforcement or a new implementation contract. Apply system/safety requirements, current host permissions and actual task authority first; [Controller](../CONTROLLER.md) governs otherwise. Preserve active contracts, consumed bounds, repository fences and required assurance. This file grants no new action, publication, merge, deployment, access, security or credential authority and contains no custom approval rules. It adds no scheduler, framework or ledger.

This file owns the shared persistent-agent workflow and its safety, authority, custody and readback requirements. The [persistent-agent stack](PERSISTENT-AGENT-STACK.md) owns generic configuration defaults and explicitly scoped host overrides. Apply the generic defaults first, then only the matching host override for conflicting configuration choices. Neither defaults nor overrides can weaken this workflow's safeguards, Controller governance, current task authority or host restrictions.

## GitHub

### Transport selection and role binding

Resolve the applicable transport order, operation exceptions and selected mechanical role from the [persistent-agent stack](PERSISTENT-AGENT-STACK.md). Start with its generic persistent-agent defaults. Apply its OpenAI dot section only when the acting persistent agent is OpenAI dot; that section overrides conflicting configuration defaults within its stated scope. Other persistent agents use the generic defaults and do not inherit dot-specific connector failures or preferences.

Treat transport availability as operation-local and point-in-time. A tool/service failure is not an access/authority denial. Explicit denials, mandatory confirmations, no-retry instructions and unresolved effects carry across all routes. Never launch an executor, change transport or narrow a payload to evade a denied effect. Keep complex, ambiguous or consequential decisions with the controller and a separately qualified stronger route. Preserve other helper preferences, G1-G4 assignments and admitted workers.

### Bounded execution and return

Supply one complete bounded handoff: repository, exact target/ref/path or issue/PR/comment, primary task-authority evidence, exact approved diff/payload, permitted effects, finite limits and consumed history, input/evidence custody and retrieval, stop conditions and required readback. Resolve active or ambiguous execution before dispatch; do not duplicate healthy work.

Fresh-read the affected surface, bind its identity and apply only the exact approved minimal change with the supported concurrency guard. Preserve unrelated content and stop on drift or material mismatch. Reconcile uncertain effects before any permitted retry. Source changes use the repository's branch/PR and validation requirements; evidence custody is a separate effect with its own verified authority and destination. Transport availability never grants publication or merge authority.

Return the exact remote identities, actual effects, complete required validation, evidence references and unfinished work with its blocker and next action. The controller consumes required full returns, independently verifies consequential effects, and retains adjudication and finality. Continue independent already-authorised work when only one operation is held.

### GitHub payload and custody check

Apply [Controller evidence survivability](../CONTROLLER.md#evidence-survivability) and [public/private boundaries](../CONTROLLER.md#public-private-and-secrets) to every outgoing GitHub payload. Verify destination identity, visibility, audience and approved information category. Inspect the complete wire payload, including unchanged content in a replacement body; a minimal semantic diff or secret-free payload is not proof that it is public-safe.

Public issue/PR/CURRENT content stays minimum-sufficient. Keep detailed operational evidence, internal resource/job identities, private paths and retrieval mappings in verified approved private custody. Never store credentials or raw secrets in Git, publish to an unverified destination, or widen access to make delivery work. Preserve original immutable evidence and later-required object closure. Verify exact bytes/objects, digests, task/candidate bindings and intended-consumer retrieval before a receipt claims custody or dependent work consumes it; a summary, placeholder or producer-local read is insufficient. Use existing custody and retention ownership rather than creating another evidence store.

### Safe issue, PR and comment body updates

Apply the following Comment Trace and body-write-through procedure whenever creating or editing a governed issue or PR comment within authorised work. After verifying the comment readback, reconcile its direct comment permalink and current effect in the dedicated `## Comment Trace` section of that same issue or PR's main body, including applicable topic revision/status, supersession and current receipt pointers. Prefer the authoritative comment `html_url`; verify repository, object and comment identity rather than linking only to the issue/PR root. Reuse an existing accurate trace entry without rewriting unchanged bytes; an edit that changes the effect or supersession requires the corresponding projection update, while cosmetic edits require verification, not timestamp-only churn. Preserve existing trace/history, immutable receipts and unrelated body content. Apply the fresh-read, minimal-diff, concurrency, publication/privacy and complete-readback safeguards below to each changed surface. Verify the comment and body trace before claiming the transaction durable or taking a dependent transition; comment-write success alone is insufficient. If projection authority, access, write or readback is unresolved, retain the exact pending projection and blocker, use the applicable existing reconciliation HOLD for dependent transitions and continue independent authorised work. Use this procedure within the existing issue/PR body and trace; do not introduce a new ledger, gate, cross-repository authority or broad backfill. This is a manual workflow requirement, not a claim that a runtime implements it.

Before asking the owner again, apply the current Controller's [supersession and admission](../CONTROLLER.md#supersession-and-admission) rules: verify existing task authority and current host permissions, and distinguish genuinely missing approval or a material expansion from host review rejection of an already-authorised action. Where private preservation and a public-safe projection are already authorised, use that bounded path with the exact-diff and readback checks below; do not invent another owner decision. After a host denial, retain its exact action, target and reason, perform only supported verification and any policy-permitted same-action retry, and stop if the barrier remains. Never bypass a denial or imply that repeated owner consent resolves a host restriction.

For this owner, separate progress-critical factual CURRENT/status edits from optional wording, layout, model, topology or policy changes. Apply only the exact spans necessary for the verified status transition, using the fresh-before-state, diff, concurrency and complete-readback checks below; preserve all still-applicable accepted requirements. Keep optional changes separately owned and do not let them block the necessary update unless they are a semantic prerequisite. Do not split coupled changes when doing so would make either update unsafe, contradictory or misleading, hide the actual intent, or bypass a denial. This is a bounded operational preference, not new authority or a claim that a narrower diff caused or guarantees review acceptance.

Distinguish the semantic diff from the actual wire payload. A complete replacement body retransmits unchanged content too; apply the GitHub payload and custody check above to the entire outgoing body and verified destination. Minimal changed spans do not make the full payload safe or trusted. If that check or host review blocks the write, retain the exact pending update and barrier; never remove required content or change routes to evade it.

For an authorised bounded body update, prefer a supported conditional write. When the connector requires a complete replacement body:

1. Fetch the complete current body for one exact issue, PR or comment. Bind its resource ID and `updated_at`, and freeze these before-state bytes. Derive only the intended minimal edit from those bytes; preserve unrelated content and fields.
2. Produce the exact diff and a preservation check before submission. For large bodies or a review that questions scope, bind before/after digests and show that reversing the intended edit reproduces the original body. Do not substitute a hash for inspecting the diff.
3. Reread in a dedicated read-only tool step immediately before one exact-target write. Expose the resource ID, `updated_at`, complete-body equality against the frozen before-state, exact old/new spans and preservation proof in review-visible output. Do not batch reads and writes together or rely on hidden variables alone. Stop on concurrent or unexplained changes; do not overwrite them or blindly rebase a governance decision.
4. Submit only the intended body field, then fetch and compare the complete readback with the intended body. Reconcile affected CURRENT projections as the live Controller requires.
5. Handle each body independently. After a write error, timeout or uncertain cancellation, inspect the complete current state and verify effects before considering a retry. Apply the generic-cancellation handling below; an actual owner cancellation remains controlling. A denied action needs sufficient approval/evidence and a policy-permitted retry, never another route to bypass review. Preserve existing task-specific retry limits and never retry indefinitely.

Use the separated fresh-read proof as an evidence-presentation mitigation, not a bypass or guarantee of review acceptance. A pre-write equality check without server-side conditional support cannot eliminate the read/write race or provide atomicity; disclose material concurrency limits and stop on readback drift.

### Approval, denial and generic-cancellation handling

Diagnose the exact blocked operation and reconcile its actual effects before choosing a remedy. Use safe already-authorised recovery within current scope and bounds. If approval is genuinely missing, ask once for the exact action and target through a supported approval flow and keep that request pending. If approval already exists, provide its exact primary evidence through the supported review channel to resolve a missing-authority conflict; make only a permitted, reconciled retry. An unchanged explicit denial, no-retry restriction or mandatory confirmation remains binding.

A generic `user cancelled MCP tool call` result alone is an uncertain tool failure, not evidence that the owner withdrew approval. Unless the owner communicates cancellation, reconcile possible partial success and automatically make a bounded safe retry of the already-authorised operation without a redundant approval question, within the accepted task/retry limits. Preserve consumed attempts; do not retry blind, indefinitely, after an explicit denial/no-retry instruction, or while consequential effects remain ambiguous. An applicable host-specific service fault uses the qualified exception in the referenced stack rather than repeated no-progress connector attempts. An actual owner stop or cancellation always controls.

For a persistent permission barrier, owner manual action means approval in the actual blocked task/chat or supported approval prompt, not editing GitHub files, committing or executing commands. First verify an actionable control exists; provide its verified link, exact bounded approval text, intended effect and material risks. If no supported control exists, state that exact limitation and retain the dependent hold. Never promise that a chat reply or "full permissions" clears a connector denial. Verify whether supported approval actually cleared the specific blocker and independently read back the result before continuing; one resolved blocker clears no unrelated restriction.
