# Hook Design Playbook

Use this before adding a Toolkit hook, adding a rule inside an existing hook, or widening what a hook matches. Hooks run on every tool call of every session that loads Toolkit, so a hook that guesses wrong stops ordinary work everywhere at once.

## When A Hook Is Allowed

A hook is allowed only for one of these:

- An effect that cannot be undone or that leaks something: a merge, a push to the default branch, a force push, a credential in what a push sends, AI attribution in a commit or pull request, an agent recording an owner-only answer.
- A behaviour the owner named that a written rule has already failed to hold, and that a hook can check where it runs. A hook only acts in the host sessions that load the plugin: the Projects post hook was removed because the coordinator it was written for runs where Toolkit's hooks do not.

Everything else is a written rule in a playbook, a skill or the global rules. CI stays the backstop for checks it already runs (plain-text findings, skipped commit checks, personal data).

## Harness-specific by default

Every new or changed Toolkit hook is harness-specific: each harness (Claude Code, Codex, any later one) runs its own hook entry scripts, and one dialect file per harness holds what is shaped like that harness (its events, tool names, input fields, environment names, transcript format and output shape). A hook script never runs from two harnesses' `hooks.json` files, and one harness's entry never loads another's. The reason: a fix for one harness must not quietly change another, and a new harness adds its own two files instead of branches in every shared module.

- **Hard rules are written once.** A rule every harness must follow (the closed list in `repo/contracts/hooks/hook-scope.json`: the merge hold, the push floor, closure and UAT, owner-only answers and user state, coding gate routes, helper admission) lives in one shared `policy` module. It takes the dialect's neutral call and returns a neutral decision; it never reads a harness's payload or builds its output. Adding a hard rule to the list is an owner decision.
- **Shared code is harness-neutral.** Readers and helpers that two harnesses load are `library` modules and hold no harness vocabulary: no tool name, no `CLAUDE_` or `CODEX_` name, no hook output field, no comparison with a harness name.
- **Every hook names its event and why.** Its scope row gives its harness, the hard rules it enforces (or `harness-only` with the reason) and, for each event it runs on, a `why_event` line naming the moment that matters.
- **Pick the latest event that still catches the slip in time, and the one that fires least:** before a tool only to refuse that call; after a tool only to react to that call's own result; turn end for anything that can wait until the agent stops (nudges, journals, refresh starts, snapshots); turn start only for the owner's own words (approvals, governance answers); session start only for what this chat needs before its first step and cannot get later (on/off status, the context compaction erases). A feature that needs one fact per day, chat or turn keeps a stamp so the rest of its firings return at once. The pull request that adds or moves a hook states its cost per firing (wait, child processes, network reads, added context) and how often its event fires.

`repo/scripts/check-hook-scope.cjs` enforces this in Toolkit's own CI only; it reads Toolkit's hook sources and nothing a governed repository installs. It fails when a `hooks.json` is not listed under a harness, a command is not one node script with plain arguments or has no scope row, an entry runs on an event its row does not list and justify, a row names a hard rule off the list, a script serves two harnesses, a module two harnesses load has no `policy` or `library` row, a shared module holds harness vocabulary, or a require cannot be followed (declare a dynamic one with what it loads). Its `known_open` list holds the mixing that existed when the rule landed, each item naming the issue that clears it; an item already clean fails, and the list only shrinks against the base. A new hook never goes on it. A whole subsystem that serves every harness by design (the updater) is a `boundary` with its reason, and the check does not walk inside it.

## What A Hook Checks

- **An exact effect, never intent.** Match a command and its arguments, a tool name, a path or a field. Never read free text (chat wording, report bodies, prompts, file contents being written) to guess whether a call means something. The readers that tried, a short-answer launch reader and a session resume reader, refused ordinary reads, metadata saves and reports and were removed.
- **One named failure.** The hook's header comment names the concrete failure it prevents, as the global rules ask of every safeguard.
- **Its own failure.** It says what happens when it cannot read the call or its own process fails: fail closed only where the effect is irreversible or leaks (the merge hold, the push guard), and fail open with a note everywhere else.

## Proportionate, Not Bank-Grade

A hook stops realistic agent slips, not a determined attacker, so it may accept a rare gap to avoid a common false block. Write each accepted gap down where the hook is described. For example, the push check reads a new or empty remote against what any remote already holds, so it does not re-read a long history on every first push; a credential already in history that another remote holds is not caught again when that history goes to the new remote.

## Tests

Every hook carries both kinds of rows:

- **Must-refuse rows** for each effect it exists to stop.
- **Must-pass rows** for ordinary daily commands near its pattern: reads of `.claude` and `.codex` folders, reports and metadata files that name Claude or Codex next to yes, no or ok, `grep -rn` and `head -c`, heredocs and here-strings, loops over file names, SSH reads. Run them in an enabled repository, a disabled one and a plain folder, on every shell tool name both hosts report.

CI runs the full pack on Linux and one Windows job per family. The nine Windows families, including closure-shell, each keep the 360-second pack budget; the required `validate` check waits for all of them. Sharding changes execution layout only: corpus rows, hosts and expectations stay intact.

## Owner Approval

A new hook, or a new rule inside a hook, needs the owner's yes on one line: what it stops, and what it might wrongly stop. Put that line in the pull request body.

## Attribution and force-push reader

The attribution, force-push, evidence-store push and credential checks read a command line as bash does and, where PowerShell may run it (Claude Code's PowerShell tool and every Codex shell call, which names no shell), as PowerShell does too; a check refuses when either reading does. The two readings differ only at a backslash, which escapes in bash and is plain text in PowerShell, so a push hidden from bash inside backslash-escaped quotes is still read. Claude Code's Bash tool keeps the bash reading alone, and a script handed to a POSIX shell (`bash -c`) is read as bash. PowerShell's stop-parsing word `--%`, unquoted, is dropped first, so `gh --% pr create` is judged as `gh pr create`; a quoted one stays an argument that gh refuses.

## Review

At each release, as a fixed row of the release-batch real-host smoke, and at least once a year, the controller lists the hooks with their false-block fixes and their real catches since the last review. A hook with repeated false-block fixes and no catch moves to a written rule.

## Closure command reader

The closure guard uses a default-deny reader over recognised executable command positions with separate flag-arity tables for PR create, PR edit, issue close and API calls. An unquoted guarded gh write found elsewhere in a command, including with a brace or equals sign attached to gh or as a PowerShell hash value (a value that starts gh, a shell runner or Start-Process is read as that command), is refused by name, including assignments with clean text and unknown wrappers, and so is a gh command whose noun, or whose verb under pr or issue, comes from a variable. Where PowerShell may run the command (its own tool, an unknown shell or Codex Bash), a guarded gh command with a parenthesised argument or an `@name` splat is refused too, as is `iex` text built by `+`, `-f`, `-join`, a method call, a cast or a `$(...)` substitution that mentions gh or its pieces (a guarded noun, a character cast or a lone quoted g), and a script block made from such text with `[scriptblock]::Create` or `$ExecutionContext.InvokeCommand`. The stop-parsing word and block comments are skipped first; cmd scripts have no comments and only double quotes. Shapes the reader cannot see are listed as accepted gaps in the programme reconciler skill. The reader works on words, so substituted program names and functions defined outside the command stay accepted gaps. Quoted examples and arguments of echo, printf, Write-Output, Write-Host, Write-Warning, Write-Error, Write-Verbose, grep, rg, Select-String, cat, Get-Content, git and command lookups remain data, except a block inside a parenthesised group or a hash literal, or, where PowerShell may run it, one followed by a member call such as `.Invoke()` or piped on to any further stage of the same statement, which may run it (so even `| Out-Null` after such a block is refused); quoted text, comments, nested groups and an escaped line break stay in the statement, and a next line that starts with `|` carries it on. Every statement in a group outputs to the group, so a block inside `(...)`, `$(...)` or a block run inline (`. { }`, `% { }`, `Invoke-Command { }`) counts as piped when the statement around the group pipes on. Literal heredoc bodies and here-strings are inspected as text; expansion is never executed. Supported condition positions, wrappers, substitutions and shell-fed heredocs are read as command positions. Recognised shell runners recurse only into their script argument, which may be a here-string or heredoc; `iex(...)` reads like `iex ...`, and a guarded gh command among the arguments after a POSIX `-c` script, as separate words, one word the script runs with `$1` or `eval`, or several words it joins with `$@` or `$1 $2`, is refused, and a gh command among those arguments, even a read such as `gh api user`, never stands in for reading the script. A script that expands its positional parameters is also read with them put in place (`"$@"` as one quoted word each), and, since `set --` and `shift` can reorder them first, refused when another order of the words that can be pieces of a gh write puts a guarded write in place. Words count only whole, so gh inside `high` or `ghost` is not gh. The placed and reordered reads, nested `-c` scripts and the reads of their words share one budget per command (2,048 placements and 2 MB, each placement charged, before it builds anything, the larger of the script and words it reads and the text it builds), so a script that repeats `$1` or is mostly empty slots stays a quick read; a call past the budget that could make gh is refused, and one with no gh in reach is not read further. A PowerShell cmd script is also read with its quotes ignored, since PowerShell passes cmd.exe embedded quotes unescaped. Where PowerShell may run a command with backslash-escaped quotes, it is also read as PowerShell and refused when that reading runs a guarded write that the judged reading does not see, compared by noun, verb, repository and target (a folder change or `GH_REPO` before a write without `-R` counts as a different repository), API method and fields, and the closing references and UAT line of PR text; the likeliest wrong holds are a gh command quoted inside `node -e "...\"...\"..."` and a close after a path ending in a backslash, such as `dir "C:\work\"`. Heredoc and here-string data stay separate; executable shell heredocs, bounded loop bodies and PowerShell script blocks are inspected without expansion or execution. Unknown flags on a guarded write, duplicate scalar options and unresolved closure-sensitive text hold local writes.

Only supplied edit text is checked before an edit. Merge and CI checks retain responsibility for existing title, body and commits. PR closing targets pass without child traversal. Same-repository missing targets pass only after the inspected PR was read; cross-repository failures remain unknown. Clean supplied shell text needs no repository lookup; unresolved closing targets hold only the affected write. Codex checks closure before consuming a merge approval. A merge seen by the merge detector but unmatched by the command reader refuses with an unresolved-message reason and keeps its approval. Cloud connector merge-message text is checked, with unknown state advisory. Each hook invocation shares a monotonic deadline across origin, evidence and closure reads; the non-consuming merge pre-pass skips closure reads.

The supported wrappers are time, nohup, builtin, call, winpty, sudo, doas, nice, timeout, env, xargs, command and exec. Script arguments of POSIX shells, cmd and PowerShell are read, as are Start-Process, saps and start calls with one literal argument string and known options. Other gh argument forms are refused. A command lookup with command -v or -V remains data. These are bounded readers, not shell execution.

Wrapper option forms follow the reader's tables. PowerShell command options concatenate the remaining argument strings; quotation marks needed by that script must be present in those strings. Nested scripts retain outer expansion information, and an unreported shell uses conservative escape handling. Generated files and literal stdin follow one shared reader for PR and merge-message text.

## Real-host smoke and hook approval

A smoke never renames, swaps or edits files inside the installed plugin root. Codex fingerprints the whole bundle, so such edits revoke approval and make an apparent allow result meaningless. Install a candidate through the supported setup path, then let the owner approve its hooks in `/hooks`. Require a positive control refusal in the same fresh chat before counting any ALLOWED result. Record config hashes before and after without recording private config values.

The fixture pack exercises hook processes, not Codex approval or delivery. Nested code-mode shell calls reach the hooks as Bash, including PowerShell commands. In a 29 October 2026 test the outer JavaScript cell reached no hook; the capture planned to re-measure that on Codex 0.166 did not run, so the controller keeps that re-measure as a fixed row of the release-batch real-host smoke until it runs. That cell, write_stdin into an already allowed shell and opaque Desktop REPL code remain accepted delivery gaps. Before a Codex gate launches, the installed hook-state `--check` must pass as the host contract defines; anything else holds the launch until the owner reviews `/hooks`.

The release-batch real-host smoke also keeps one Windows PowerShell row each for the owner's Enter prompts that CI cannot reach without a real terminal: `pressEnterSync` (the programme's owner Enter), setup's RAM-risk Enter and setup's Codex configuration Enter. The header of `repo/scripts/owner-terminal.cjs` says what each row checks.
