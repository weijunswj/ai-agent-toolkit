# PR Review And CI Playbook

Use this for PR review, CI status, merge readiness, diff analysis, test failure verification, PR feedback, check runs, workflow logs, or release readiness.

## Review Standard

Do not review from metadata alone. Inspect the relevant diff, files, tests, and CI/check status when available.

Lead review responses with findings ordered by severity. If no issues are found, say so and mention residual risk or test gaps.

## Managed PR Continuity

When a managed programme opens a prerequisite, replacement, superseding, or successor PR for an existing child, update the controlling child in the same transition window. The child must durably identify the new PR and its relationship to the previous PR or blocked work. A predecessor-PR comment may provide extra history, but it is never sufficient as the only cross-PR reference.

Keep PR presentation state separate from programme authority. `draft: false` does not by itself mean accepted, Ready-for-merge, complete, or Web-final. Preserve the programme's explicit role, `completes_child` value, gate/finality state, exact candidate identity, and merge authority independently of GitHub's Draft/Ready UI state.

If the available GitHub client or connector cannot reliably perform or verify Draft -> Ready, do not make that transition a required future control point. Unless a repository contract explicitly requires a Draft PR and a working transition capability is available, create the PR as non-draft from the outset and continue to enforce readiness/finality through the programme authority records and exact-head checks. Never weaken review, CI, Web finality, or merge authorization merely because the PR is non-draft.

## GitHub CLI

For already-authorised GitHub reads and writes, use only authenticated task-scoped escalated `gh` in a supported shell execution mode permitted by the actual host. Verify the intended authenticated account, repository and exact operation scope before execution. Before creating or updating PRs, verify the active account with:

```powershell
gh auth status
gh api user --jq .login
```

If the active account is not the intended user, stop and report it. If that route is unavailable or not permitted, hold the affected operation. Authentication and escalation do not grant task authority or automatic approval; preserve current permissions, explicit denials and mandatory confirmations.

## CI Check-Up

When a change touches CI or adds a package, language or test folder, run the `secure-ci-cd` CI check-up (`skills/secure-ci-cd/scripts/ci-checkup.cjs --base <ref>`) and fix the real gaps it lists in the same PR.

## Cloud Footer On GitHub Posts

In cloud sessions the GitHub route appends a "Generated by Claude Code" footer to posts after they leave the session. In a governed, guarded or evidence-store checkout, Claude Code's after-tool footer hook reads what GitHub sent back and says what to do; follow it.

| Post | Clean edit from the cloud |
|---|---|
| Issue or pull request comment | GitHub connector `update_issue_comment` |
| Pull request body | GitHub connector `update_pull_request` |
| Issue body | GitHub connector `issue_write` with method update |
| Review comment, review reply or review body | None: list it in the report; the device sweep cleans it |

Cloud `gh api` writes add the footer even on an edit, so they cannot clean anything. The device sweep runs on a computer whose `gh` sign-in adds no footer, with no AI step, so a scheduled task can call it. It reports posts ending with the footer and, with `--apply`, edits the signed-in account's posts to the same text minus the footer: it re-reads each post first and skips one changed since the scan, then reads the edit back and reports a mismatch as a failure:

```powershell
node repo/scripts/toolkit-github-footer-sweep.cjs --repo <owner/name> --since <ISO time>
node repo/scripts/toolkit-github-footer-sweep.cjs --repo <owner/name> --since <ISO time> --apply
```

On Windows the independent `FOOTER SWEEP` task runs hourly from 00:00 to 23:59 for each configured GitHub checkout, even where governance is off or cannot be refreshed. It runs with `--apply` over origin and adds the evidence store only from a validated, fresh, enabled binding matching origin. An unverified store is withheld and reported while origin cleaning proceeds. The shared retry window advances to scan start only after the complete eligible batch succeeds; a withheld store or failed or interrupted sweep retains it. A new job starts with a 48-hour window. `node repo/scripts/toolkit-tasks.cjs` shows the recorded result and skip streak. Setup prints plans for the managed and original working checkouts, and the owner reviews and runs each printed apply command. Existing checkouts use `toolkit-windows-tasks.cjs plan --repo-root <checkout>`; no directories are scanned and no tasks are created by setup. `PROGRAMME SWEEP` separately refreshes programme pages and attention under its fresh-governance guards. Without `--since` it scans the whole repository, which reads the reviews of every pull request. Exit codes: 0 no post with the footer, 3 posts with the footer found and none cleaned, 4 at least one cleaned and nothing failed, 1 a scan, edit or read-back failed, 2 bad arguments.

Owner-run `apply` adds the independent task and installs full-day schedules. Before that, the programme task cleans first using its installed hours, even when programme governance fails. It reports `Footer task not set up; paste the apply line.` until a matching recorded footer task passes live marker and action checks. A verified disabled companion stops substitute cleaning. Both cleaners share a repository lock; first handover saves the earliest valid pending cursor before scanning, and damaged history holds for recovery. The 48-hour initial window applies only to genuinely new repositories. GitHub API requests specify github.com and verify the returned repository identity. Setup and both task commands use a verified primary checkout for linked worktrees and visibly refuse an unusable layout.

## Before Asking To Merge

Post a short summary of the merge's external effects (what changes on the user's machines, hooks, rules, setup defaults and other repositories) naming the pull request, before asking the owner for their own "merge N". The merge hold waits for that typed "merge N"; no hook checks the summary.

## Plain-Text Findings

The push check refuses only a credential in what a push or new pull request sends. Plain-text findings leak nothing, so CI's plain-text check is the gate for them: read its result on the pull request and fix what it lists.

## CI Honesty

Do not claim CI passed unless checked. If checks are pending, failed, or inaccessible, say so and provide the exact command or user action needed.
