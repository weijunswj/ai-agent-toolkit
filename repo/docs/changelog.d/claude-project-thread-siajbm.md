### Fixed

- The merge hold now judges a shell command by every real folder it may run in, not only by its text, and refuses by default: the starting folder always counts (a comment, a pipeline part or a background job can drop a `cd`), every folder a `cd` in it could reach counts too, and a folder the command does not spell out (`cd -` with no move before it, `~-`, `$OLDPWD`, a wildcard or a substitution) counts as Toolkit's own folder. Inside Toolkit's user-state folder nothing runs; in Toolkit's own folder only listing, reading, changing folder, read-only git and running a script file with node pass, with no wildcards, variables, substitutions, quotes, escapes, redirections or `..`; deeper in Toolkit's folder, a word naming user-state, a wildcard, brace, variable or substitution, or a path back up to Toolkit's folder is refused. Line continuations are joined as the shell joins them, and in PowerShell a backslash stays a folder separator. Links, junctions and letter case on Windows cannot hide the folder, a command too long to read is refused there, and the reader takes time in step with the command's length.
- A push after more than 16 folder changes is judged in a folder Toolkit cannot see, so a push to any branch there is refused, and the push reader no longer slows down on long chains of folder changes.
- A push to the default branch through `--git-dir` or a `GIT_DIR=` prefix, or split by a line continuation, is now judged against the repository it names, so it is held like any other default-branch push. A `GIT_DIR` set earlier in the command (`export`, `$env:`, `set`, `declare`) is judged beside the folder's own repository, since it may never reach git.
