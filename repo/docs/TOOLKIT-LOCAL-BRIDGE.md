# Toolkit Local Bridge

This document defines the plugin/update architecture for `weijunswj/ai-agent-toolkit`.

## Current installation scope

Native Toolkit sources target Codex and Claude Code. OpenCode is not a Toolkit target in this release; it returns in its own later change. Antigravity receives portable workspace skills only. Candidate construction, metadata validation and copied files do not prove native invocation, selected model/effort, user UAT or installed acceptance. Qualify each selected host before advertising it as supported; retain route gaps visibly and preserve rollback.

The existing Codex/Claude managed-update paths remain host-local. Antigravity uses `--copy-antigravity-skills --antigravity-project-root <absolute-path>`, which previews by default and requires the explicit authorised `--write` effect. It chooses no provider, copies no credentials, changes no global settings and enables no auto-sync. Toolkit 3.3.0 removed the OpenCode and AG2 bridge targets; the next hub write drops their old records from `state.json`, and files they wrote earlier are left in place.

## Current Source-Of-Truth Chain

Current inspected chain:

1. Root `AGENTS.md` routes repo work and includes the managed source-of-truth contract.
2. `skills/**` stores complete copyable skill surfaces.
3. `repo/contracts/**` stores machine contracts, fixtures, templates, agent-rule inputs, and plugin source contracts.
4. `repo/source-watch/provenance/**` stores active third-party source locks and attribution records.
5. `repo/scripts/sync-repo-doc-contract.cjs` and `repo/scripts/sync-agent-instruction-shims.cjs` maintain only managed root blocks and shims.
6. `repo/scripts/validate-toolkit.cjs`, `repo/tests/*.test.cjs`, source-lock audit, and canonical-surface audit enforce drift and safety rules.
7. `.codex-plugin/**` and `.claude-plugin/**` are platform-specific native plugin metadata. They are not cross-platform source of truth.
8. The Toolkit Local Bridge Hub under the user profile stores bridge state, the manifest and update-report bookkeeping. It is not repo source of truth.

## Architecture

Codex and Claude Code update Toolkit through their own native plugin systems.

Codex agents verify and refresh only the Codex native Toolkit plugin cache; Claude Code remains responsible for its own native cache.

- Codex uses `.codex-plugin/plugin.json`.
- Claude Code uses `.claude-plugin/plugin.json`.
- Both native package manifests point at the same Toolkit `skills/` surface.
- Both native packages use hooks only for optional bridge autocheck, passive repo-local instruction managed-block preflight, and repo-backed auto-update.
- Codex never installs or updates Claude Code.
- Claude Code never installs or updates Codex.
- Toolkit does not publish to public marketplaces from this repo. Marketplace-ready metadata is present in the manifests, but publication remains a separate human action.

The shared bridge has one explicit portable route: Antigravity portable workspace skills under `.agents/skills/`. That copy is an explicit project write; it is never native/plugin auto-sync. The bridge writes into no other app.

## Local Bridge Hub

Default hub path: `%USERPROFILE%\.ai-agent-toolkit\current`.

The hub contains:

- `manifest.json`.
- `state.json`.
- Version data and a checksum over the current Toolkit skill files.
- Source commit or `unknown` when Git metadata is unavailable.
- Sync source: `repo`, `codex-plugin`, or `claude-plugin`.
- Per-source bridge versions in `bridge_versions_by_source`, allowlisted to `repo`, `codex-plugin`, and `claude-plugin`.
- A monotonic `hub_version` compatibility/reporting watermark. New bridges do not use it as downgrade authority.
- Sync timestamp.
- Repo auto-update state: `repo_auto_update_enabled`, `repo_path`, `repo_branch`, `repo_remote`, `last_repo_update`, `last_repo_update_status`, `last_repo_update_from_commit`, `last_repo_update_to_commit`, and `last_repo_update_error`.
- Update-report state: `last_update_report_path`, `update_report_enabled`, failure-only opening behavior, `update_report_retention_days`, max retained report count, and last cleanup status. Legacy `update_report_open_enabled=true` is retained only as migration evidence and is normalized to failure-only behavior.
- Codex instruction limit choice: `codex_doc_limit_enabled` (default false; set by the setup question "Raise Codex's instruction limit", or `--enable-codex-doc-limit` / `--disable-codex-doc-limit`). Only an explicit true lets the Codex session-start hook raise `project_doc_max_bytes` (see Instruction Layers).
- Rule-refresh pull requests always stop at the open PR for the owner to merge; Toolkit 3.7.0 removed the auto-merge choice, and the next state write drops its old `refresh_pr_auto_merge_enabled` key. The rate-limit ledger for SessionStart notes is `agent-rules-notices.json` beside the hub snapshot directory (next to `update.lock`), so snapshot writes by auto-sync or repo auto-update do not reset it.
- Codex plugin cache auto-refresh preference: `codex_plugin_auto_refresh_enabled`.
- Target paths.
- Target detected, enabled, disabled, stale, and synced state.

The lock file lives beside the hub at `%USERPROFILE%\.ai-agent-toolkit\update.lock`.

Writes are rename-first and atomic in the normal case. On Windows, when the final staging-to-`current` directory rename is blocked by a transient `EPERM`, `EBUSY`, or `ENOTEMPTY` after the previous target has already been moved to a backup path, the bridge may fall back to copying the validated staging directory into the empty target path and then cleaning up staging plus backup. If the fallback copy fails, it removes the partial target and restores the backup.

### Owned Staging Generations

Every bridge-created hub or target staging directory uses a generation-scoped ownership protocol. Before `mkdir`, the bridge exclusively creates an immutable sidecar that binds Toolkit owner/schema, generation ID, random ownership token, exact staging path and parent, exact final target, operation and source type, process lease identity, creation time, bridge version, and initial state. After `mkdir`, a second sidecar and an in-directory marker bind the token to the directory identity. Completion and handled failure use separate token-bound state markers.

The bridge cleans only its current proven generation in `finally` handling after success, payload-write failure, staged validation failure, replacement failure, and rollback. Initialization cleanup removes an unmarked partial directory only when the current invocation's own `mkdir` succeeded and the directory still has the identity captured immediately afterward; `EEXIST` and every other ambiguous creation result preserve both sidecar and directory for review. Immediately before deletion it revalidates the exact parent, target, generation ID, token, path containment, ordinary directory type, real path, directory identity, and unchanged ownership record. Ambiguous ownership is preserved and reported instead of deleted. A dead PID is only one liveness signal; it never establishes ownership or authorizes cleanup, and a reused live PID remains protected.

Ordinary `--audit` includes a bounded `staging_generations` inventory. It distinguishes live owned, dead safely attributable, completed awaiting cleanup, malformed, ownership-mismatched, unrelated matching, historical unmarked, special filesystem object, and indeterminate entries. Historical `.staging-*` directories without the new ownership format are reported but never modified.

Safe reconciliation stays inside the existing bridge command family and is dry-run first:

```powershell
node repo/scripts/toolkit-local-bridge.cjs --reconcile-staging <generation-id>
node repo/scripts/toolkit-local-bridge.cjs --reconcile-staging <generation-id> --write
```

The write form is the established explicit approval convention. It acquires the bridge lock, constructs the exact generation sidecar path under every approved managed parent, requires exactly one candidate across the complete parent set, and revalidates ownership immediately before mutation. This exact lookup is independent of the bounded general audit, which remains supplemental diagnostics only. It refuses live, indeterminate, malformed, mismatched, escaped, symlink, junction, reparse-point, or unrelated targets. Repeating an already successful exact reconciliation is a no-op only after absence was checked under every approved parent. Never use a generic recursive `.staging-*` cleaner or delete by name, timestamp, or dead PID.

Reconciliation uses an isolated command route before hook no-op handling, requested-state application, update-report retention cleanup, report writes/opening, repo auto-update, native plugin refresh, or ordinary state persistence. Its accepted controls are limited to `--reconcile-staging`, optional `--write`, `--hub`, `--sync-source`, and `--force-downgrade`; every other bridge flag is rejected before mutation. Dry-run creates no lock. Write mode may acquire and release the existing bridge lock, then remove only the exact generation and ownership sidecars.

Locks are owner-aware. Each lock records the PID of the process that created it, and acquisition classifies that owner with a signal-0 existence probe before deciding anything:

- A lock whose recorded owner is a live process is always respected and never deleted, regardless of age. Hook runs skip safely; manual runs fail with the owner PID in the message.
- A lock whose recorded owner is provably dead (no such process) is recovered immediately, even when the lock file is younger than the stale-age threshold, so a killed bridge run cannot wedge later setup or hook runs.
- A lock with a missing, malformed, or non-positive PID keeps the pre-existing age rule: fresh locks cause a safe skip, stale locks are removed before retry.
- An indeterminate liveness probe (for example permission denied) is not proof of death and also falls back to the age rule.
- A lock file with unreadable JSON or an unparsable `created_at` uses the file mtime for the age rule, so a mid-write lock from another process is not treated as instantly stale.
- The bridge never signals the recorded owner for real.

Recovery of a recoverable lock is race-safe through an atomic recovery claim and per-run ownership tokens:

1. Every acquisition, including the no-main-lock path, claims the existing recovery marker before its authoritative displaced-evidence inspection and keeps that marker through any evidence retirement, main-lock recheck or recovery, and exclusive main-lock creation (`wx`). An optional initial evidence inspection can only fail fast; it never authorizes creation. This serialization makes evidence validation and no-lock ownership commitment one race-safe protocol, so evidence created after an initial scan is seen before creation and no replacement writer can enter behind a recoverer.
2. A recoverable lock may only be displaced by the process that first exclusively creates the `update.lock.recovery` marker. The exclusive marker create is the atomic recovery claim: two contenders that inspected the same dead lock serialize on it, and the loser never deletes anything.
3. Reclaiming a marker left by a dead or stale recovery is itself atomic and identity-safe. The reclaimer must first exclusively create a tombstone named after a hash of the exact marker bytes it inspected; contenders that inspected the same marker generation compute the same tombstone path, so exactly one wins, and the tombstone is never deleted by the protocol (spent tombstones are only aged out after 24 hours, far beyond any contender's inspect-to-claim window). The winner re-reads the marker under its tombstone and proceeds only when the bytes are still the inspected generation; any change means another process cycled the marker and the reclaimer yields without touching it. A marker owned by a live process is never reclaimable.
4. While holding the marker, the recoverer re-inspects the lock. A replacement written in the interim has a live owner and is respected untouched.
5. The recoverable lock is displaced by rename (not deleted in place) and the displaced file's owner is verified not alive before it is discarded. A displaced generation that cannot be proved safe to discard is never renamed back over `update.lock`, because destination replacement semantics cannot guarantee no-clobber restoration across supported platforms. It remains preserved on disk as evidence, this contender does not write a replacement, and the skip/error message names the preserved path. This remains true even when the main path looked free before the preservation decision; a concurrently created main lock is never altered.
6. The replacement lock is exclusively created and carries a unique per-run ownership token in addition to the PID. The marker is then released by its own token.
7. Preserved displaced evidence is a persistent fail-closed acquisition barrier, not just a one-run refusal. Every acquisition -- including the no-main-lock path -- authoritatively inspects `update.lock.displaced.*` evidence while owning the recovery marker before creating anything, so a later or already-running contender does not acquire merely because the recovery marker was released, the intruding main lock went away, or the evidence is old. While the recorded owner is alive the evidence blocks and is never deleted, protecting a long-running displaced owner indefinitely; an owner whose liveness is indeterminate (for example a permission-denied probe) also fails closed; evidence with unusable owner data uses the age fallback. Evidence enumeration, read, or age-inspection failures also fail closed because unreadability is not proof of absence or death; only `ENOENT` proves that a particular enumerated or retirement-verified path vanished. Hook runs skip and manual runs fail with the preserved evidence path and precise reason; the messages never tell the user to delete evidence that may belong to a live owner.
8. Once the displaced owner is provably dead, the evidence is retired under recovery-marker ownership through the same atomic identity-safe tombstone protocol as marker reclaim (exclusive tombstone on the inspected bytes, verify-under-claim, yield untouched if the generation changed). `ENOENT` during verification means that generation genuinely vanished; every other read failure preserves the evidence and blocks. Exactly one contender retires each generation, and the barrier cannot become a permanent wedge after the owner dies. Artifact cleanup ages out only exact Toolkit-owned recovery-claim tombstones (`update.lock.recovery.claim-<16 hex>`) and displaced-evidence retirement tombstones (`update.lock.displaced.<UUID>.retired-<16 hex>`); it never deletes displaced evidence, unrelated similarly suffixed files, or directories.

Release removes the lock only when the current lock file still carries that run's ownership token: a lock replaced by another process is never deleted, even by the process that previously owned that path. Marker release is equally token-guarded. Locks are released in normal success and caught-failure paths; recovery from abrupt process termination relies on the dead-owner rule above, not on cleanup code running after a forced kill.

Every successful state write rereads the latest state while holding this authoritative lock. From that locked state generation, the bridge resolves the Toolkit source again and rebuilds adapter payloads, checksum, discoveries, target plans, skipped-target context, manifest inputs, and related report context before writing. Pre-lock derived values are audit-only and are never combined with a later locked state in a committed snapshot. The write preserves unrelated top-level and forward-compatible fields, updates only the running source in `bridge_versions_by_source`, and preserves every other recognized source entry. `hub_version` is then calculated as the maximum of its existing valid value and every valid per-source value, so an older source run or forced same-source downgrade cannot lower the compatibility watermark. Staged hub replacement remains atomic and crash-safe under the existing transaction.

An active `--write` run persists this prepared source state after it acquires the lock even when no target, repo, cache, or report action is needed. Report eligibility is evaluated only after that first snapshot; report metadata causes a second snapshot only when a report is actually created. A fully disabled hook remains a deliberate early no-write return when repo auto-update and auto-sync are disabled, or when no enabled target or maintenance action makes the hook active. Lock contention also remains a visible hook skip and does not claim that an unpersisted source version was recorded.

Downgrade enforcement is source-scoped. A running bridge compares itself only with `bridge_versions_by_source[sync_source]`; a newer repo, Codex, or Claude Code entry never blocks another source. `--force-downgrade` bypasses only that same-source comparison and updates only the running source entry. New bridges never use `hub_version` for downgrade enforcement.

Old state migrates lazily. When a valid legacy `hub_version` has one recognized `last_sync_source` and no usable per-source history, only that attributed source is seeded. Missing or unknown attribution seeds nothing, so an unattributed legacy watermark cannot cross-block a recognized source. Once any usable per-source history exists, `hub_version` is not used to infer a missing source entry. Arrays and other non-map values are treated as absent; unsupported and prototype-polluting keys are discarded; invalid values assigned to recognized source keys fail visibly instead of silently weakening same-source protection.

In hook mode a genuine same-source rollback skip is printed to stdout with source-specific remediation. For `claude-plugin`, Claude Code runs the installed copy in place from the managed checkout, so a newer record means another Toolkit copy, such as a test candidate, ran a session here before Toolkit 3.2.0; the message gives the one-time `--force-downgrade` command that clears it, or `setup toolkit` to install the newer version. For `codex-plugin`, run `setup toolkit` in Codex. For `repo`, update or restore the managed Toolkit source checkout.

### Mixed Cache Rollout

Codex hooks execute the bridge copy in Codex's installed plugin cache. Claude Code runs Toolkit in place from the managed checkout (measured on Claude Code 2.1.304 and 2.1.306; see Claude Code Install Check), so its hooks use whatever that checkout holds. A source patch or one refreshed Codex cache does not repair the other host's copy. During rollout, a new Codex cache may write per-source state while an older Claude Code bridge still uses the legacy global `hub_version` guard; that older bridge may continue to self-block until the managed checkout holds the fixed bridge. The issue is fully resolved on a machine only after the Codex cache and the managed checkout both have the fixed bridge.

Required post-merge refresh flows:

- Codex: run `setup toolkit` in Codex.
- Claude Code: run `setup toolkit --host claude-code` (or `setup toolkit` from Claude Code), then start a new Claude Code session. With automatic updates on, the next session start updates the managed checkout without this step.

## Repo-Backed Auto-Update

Repo auto-update uses the configured local Toolkit Git repo as source of truth. The default setup configures the managed clean `main` checkout under the user-local `.ai-agent-toolkit/source/ai-agent-toolkit` path. Native Codex and Claude Code plugin hooks remain launchers only; they do not become source of truth and do not update each other.


Advanced bridge-only configuration can still point at an explicit trusted checkout (PowerShell, for a person to type):

```powershell
node repo/scripts/toolkit-local-bridge.cjs --enable-repo-auto-update --repo-path "$env:USERPROFILE\.ai-agent-toolkit\source\ai-agent-toolkit" --repo-branch main --enable-auto-sync --write
```

Use `--repo-remote <url>` only when intentionally testing or maintaining a non-default remote. The expected production remote is `https://github.com/weijunswj/ai-agent-toolkit`.

Release-branch auto-update consideration: the current default setup uses `main`. If the repo later adopts a stable `release` branch for user-facing Toolkit updates, configure `--repo-branch release` only after that branch exists and has a clear CI/merge policy. The bridge remains pull-on-session-start: GitHub pushes to the configured branch are picked up by the next native hook run or explicit `--repo-update-now`; the Toolkit does not run a GitHub webhook listener or background push daemon.

When a native SessionStart hook runs and repo auto-update is enabled, the bridge:

1. Acquires the Toolkit bridge lock.
2. Validates `repo_path` exists and is a Git worktree.
3. Reads the current branch and validates `origin` matches `repo_remote`.
4. Refuses to continue when the working tree is dirty, leaving the current branch and local changes untouched.
5. If the clean configured checkout (setup configures only the managed clean checkout) is on a different branch, switches it to `repo_branch` with `git switch <repo_branch>` and records that auto-switch in the update report.
6. Fetches `origin <repo_branch>`.
7. Updates only with `git merge --ff-only FETCH_HEAD`.
8. Runs hook-light validation:

```powershell
node repo/scripts/validate-toolkit.cjs
node --test repo/tests/toolkit-local-bridge-hook-light.test.cjs
```

9. Checks the running host's native plugin cache state against the configured repo source. When Codex is the running host and `codex_plugin_auto_refresh_enabled` is true, the trusted `main` hook refreshes only the Codex Toolkit plugin cache through `repo/scripts/setup-codex-toolkit-plugin.cjs --write --json --repo-root <repo_path>` after repo validation and before the delegated hub sync completes, so a stale Codex cache can still be refreshed when that later step fails safely. Claude Code hooks run the Claude Code install check instead (see Claude Code Install Check) and do not mutate Codex or Claude plugin caches from the opposite host.
10. Delegates the hub sync to the freshly updated repo script with `--skip-repo-auto-update`, so the hub records the updated bridge version.

Before the repo-update work, the same startup hook also runs a passive repo-local instruction preflight against the current working directory. For Codex it checks `AGENTS.md`; for Claude Code it checks `AGENTS.md` and `CLAUDE.md`. The preflight reads only the expected files and bundled repo-local templates, verifies `AI-AGENT-TOOLKIT` managed marker structure, compares expected managed block content, and never writes repository files, creates backups, or performs repair. It is silent outside Toolkit-managed git roots: a root counts as managed only when one of the expected files carries an `AI-AGENT-TOOLKIT` managed block, or when hub state names it as the managed Toolkit checkout. Inside a managed root it prints at most one neutral line, chosen by direction: when the repository rules may come from a newer Toolkit than the running copy (a newer recorded Toolkit version, or a newer Toolkit source checkout), the line says the repository rules are authoritative and Toolkit can be refreshed when convenient; when no newer Toolkit is known on this machine, the line says the repository rules differ from the running Toolkit's templates and offers a refresh with `repository-agent-rules`. The line never asks the agent to halt or to question the user. Each line is shown once per (root, running version, finding digest); the record lives in `agent-rules-notices.json` beside the hub snapshot directory, so resume, compact and later sessions with the same finding stay quiet, including when auto-sync or repo auto-update rewrite the snapshot.

The delegated repo script builds the target payload from the updated local Toolkit repo `skills/` tree plus the small `ai-agent-toolkit` adapter skill. It must not use Codex or Claude private plugin caches as the skill payload source.

The delegated command shape is:

```powershell
node <repo_path>/repo/scripts/toolkit-local-bridge.cjs --sync-enabled --write --sync-source repo --hub <same-hub> --skip-repo-auto-update
```

The hook validation is intentionally lighter than `npm run validate:all` so SessionStart stays short. Run full validation manually before release, merge, or broad maintenance changes:

```powershell
npm run validate:all
node --test repo/tests/toolkit-local-bridge.test.cjs repo/tests/toolkit-local-bridge-codex.test.cjs repo/tests/toolkit-local-bridge-claude.test.cjs
```

Repo auto-update never runs `git pull`, merge commits, rebase, package installs, marketplace installs, credential writes, `n8n_live` actions, or arbitrary project-repo mutations. Codex native Toolkit cache refresh and exact supported n8n Skills hook reconciliation run only after the user enables Codex plugin cache auto-refresh. If validation, fetch, fast-forward, delegation, native cache refresh, or n8n hook reconciliation fails in hook mode, the hook prints or reports a concise warning, records the last status when possible, and exits successfully so agent startup is not blocked.

## Claude Code Install Check

Which copy Claude Code runs was measured on Claude Code 2.1.304 (Desktop) and 2.1.306 (CLI) on 21 October 2026, with an isolated, zero-spend probe: Toolkit's local directory marketplace makes Claude Code run Toolkit in place from the managed checkout, when no claude.ai account copy of the plugin is enabled. The Claude desktop app may load the account copy instead, and only claude.ai updates it (from main), so after a release that copy must be synced too. Both the `SessionStart` and the `Agent|Task` `PreToolUse` hooks receive `CLAUDE_PLUGIN_ROOT` set to that folder. The cache folder that `claude plugin install` writes is not executed. A second probe on Claude Code 2.1.310 (29 October 2026) confirmed it: a new version in the marketplace folder takes effect in the next session without `claude plugin update`, the session runs the same way after the cache folder is deleted, and the install record keeps the version and commit of its first install. So setup installs the plugin once (Claude Code loads only an installed plugin) and never updates one that `claude plugin list` shows running in place (`readFromFolder`); it judges that install by the folder's version (`folderVersion`), not the record's. `repo/scripts/toolkit-claude-plugin-registry.cjs` is the one reader of Claude Code's plugin registry (`known_marketplaces.json`, `installed_plugins.json` under `CLAUDE_CODE_PLUGIN_CACHE_DIR` or `<CLAUDE_CONFIG_DIR>/plugins`); setup and the bridge both use it.

- **Uninstalled copies do nothing at session start.** When the `claude-plugin` hook runs from a Toolkit copy that is not the installed one (a test candidate loaded with `--plugin-dir`, or an account-synced copy), it writes `Toolkit: this session runs an uninstalled Toolkit copy (<folder>); session-start maintenance is skipped and nothing is recorded.` to the hook output and exits. Claude Code adds session-start hook output to the session's context; it is not shown in the chat. To see it, ask the session to quote its session-start hook message, or open the transcript view (Ctrl+O in the terminal). It writes no update state, report or ledger and never updates the managed checkout. When the session's folder, one of its parents or one of its direct subfolders holds a Toolkit source checkout with a newer version than the running copy (a cloud session starts in the folder its repositories are cloned into), it adds a second line: `Toolkit: this copy is <old>, older than the <new> in the Toolkit repository at <folder>, so safety hooks added since then do not run in this session. Ask the owner to refresh the account's Toolkit plugin copy.`
- **The Claude app reminder.** When the running copy is the Claude desktop app's copy from the user's claude.ai account (a plugin folder inside the app's account-plugin folders, the same folders the install check reads) and its version is older than the managed checkout recorded in the hub state, the hook reads those two `plugin.json` files and nothing else, and prints one JSON object instead: `systemMessage` holds the reminder for the owner, and the context repeats it with a line asking the session to say it once in its first reply, so the owner sees it whichever of the two the app shows. The reminder names both versions and gives the steps shared with the install check and the daily check-in (`repo/scripts/toolkit-claude-account-copy.cjs`): Check for updates on claude.ai, then remove only the plugin on claude.ai in a web browser, then remove and add the marketplace again, then fully quit and reopen the Claude app. A current account copy, a `--plugin-dir` test copy and a cloud session get only the line above; when the managed checkout is missing or unreadable, a "could not compare" line goes to the context only. An account copy older than the release that added the reminder runs its old hooks and stays quiet; the install check row and the daily check-in still report it. Its older hooks lack guards the repository already ships.
- **Merges wait for the user's own "merge N" (a tripwire, not a lock).** The Claude Code governance hook and the Codex helper hook catch an agent that merges a pull request, or pushes to the default branch, on its own initiative or by mistake. They read command text, which can be reshaped, so they cannot stop an agent set on getting past them; and agents act as the user on GitHub, so GitHub cannot tell the two apart either. The hard limit is the repository's own GitHub rules where it has them (`toolkit governance check` reports them): a pull request for every change to the default branch, no force-push and no deletion. **What counts as an approval:** one line of the user's own typed message that says "merge" right next to a pull request number, or names one with `#N`, `owner/name#N` or a link: `merge 618`, `618 merge`, `ok to merge #N`, `can merge 618`, `merge owner/name#N`, `merge 601, 605 and 609`, `merge 618 at 62405eb` (a short SHA right after "at" may be all digits). A line that is only one inline code span, such as `` `merge 618` `` (the way Codex and Claude show a suggested reply), is read without its backticks, and every other rule still applies to what is inside. Other numbers on the line are not read as pull requests, nor is a number before "merge" that a word follows ("3 merge issues") or one after it that a count word follows ("merge 2 branches"); a count in another form may still be. A line does not count when it sits inside a fenced code block (between ``` or ~~~ lines, so pasted output never approves), or has a quote (a leading `>`, also after a list marker, double quotes, guillemets, backticks anywhere but around the whole line, angle or corner brackets, an ellipsis or single quotes), a question (a question mark, a line that opens like one, or "can we" or "may I" anywhere), or one of a fixed list of words for a no, a doubt, a condition, a delay, a report or another kind of merge: for example "don't", "not yet", "reject", "revert", "cancelled", "holding", "waiting", "pause", "defer", "maybe", "I think", "if", "provided", "given", "should", "pending", "on green", "later", "soon", "tmrw", a weekday, month or clock time ("at 5pm", "at 17:00", "at 1700"), "or", "then", "says", "ready", "plan", "into", "conflicts" and branch names such as "main", "master", "develop", "dev", "development", "staging", "release", "production", "stable", "upstream" or "default", so "merge main to #N" does not count. Words inside a link or a repository name are not read, but a word glued to the end of a link is. This is a fixed word check, not a judgement by a model; other wording may still count, so the list leans towards not counting. Curly quotes count as straight ones, and a full-width `>` as a `>`. An approval is kept only in a session the user started (not one another session or a Toolkit launcher started, and not a resumed or forked run), for the repository the session is in or the one the message names; a bare number typed outside a GitHub repository is not kept. A tap on a card in the Claude app is not seen by a session on the computer. **What one allows:** one merge of that pull request in that repository within a day, by any session on this computer; it is used when the hook lets the call through, even if a later prompt or the merge itself fails. A "merge N" typed while the repository's governance question holds the message is not kept, so the user types it again after answering. **What is held** (line continuations with `\`, a PowerShell backtick or a cmd caret are joined first, and Codex's `cmd` field and word lists are read): `gh pr merge` (any flags, `--auto` included), `gh api` to a pull request's merge endpoint (found anywhere in the command, placeholders such as `{owner}/{repo}` included) and any connector's merge tool need an approval and must name the head commit they expect (`--match-head-commit`, a `sha=` field value, or the tool's head SHA field); a typed SHA pins it. A connector merge tool is any `mcp__` tool named `merge_pull_request`, `merge-pull-request` or `mergePullRequest`, whatever its server is called, in every GitHub connector shape: the official GitHub server (`owner`, `repo`, `pullNumber`, `expectedHeadSha`) and Codex's GitHub app (`repository_full_name`, `pr_number`, `expected_head_sha`). A `sha` field is never read as the head commit, since a server that drops it would merge whatever head is there, so older servers (`pull_number`, `sha`) stay refused and are pointed at `gh pr merge N --match-head-commit <sha>`. A call whose fields are missing, cannot be read or disagree is refused, and the refusal names the fields it found and the one that is missing. Refused when written directly: any connector's auto-merge tool (it cannot name a head commit; use `gh pr merge N --auto --match-head-commit <sha>`), GraphQL merges, the merge queue, branch merges and writes to the default branch's ref (anywhere in the command, multi-line queries included), `gh repo sync`, gh aliases that mention merge, a `git push` to the remote's default branch (an evidence store excepted by its name, and a new remote with no default branch yet is not held), a merge whose target is moved by `cd`, `pushd`, `Set-Location` or `GH_REPO`, and a bare number in a folder with more than one remote or a gh default repository (`gh repo set-default`) other than its own, unless `--repo` or a URL names the repository. As a tripwire against an agent approving for itself, commands that start a Claude or Codex session and mention merging, or that set or clear `TOOLKIT_HOST_SESSION`, name Toolkit's user-state folder, or name its hook scripts together with what would feed them a prompt, are refused. The Claude hook runs this check before, and apart from, the governance check; when Node cannot start, the Codex Windows launcher refuses every shell command the check would look at. **Not covered:** wrapped or nested host launches (`bash -lc`, `timeout`, `Start-Process` and the like), a prompt file fed to a hook script, pasted text outside a code fence that has a plain approval line, scripts or programs that call git or the GitHub API themselves, `curl` and other HTTP clients, a `sha=` field put in a comment or an echo on purpose, git and shell aliases, commands inside files, pushes through a second remote or a wrapper, `GH_REPO` set outside the command (an env file, a profile or a long-lived shell), direct commits to the default branch through the Contents API, GraphQL `createCommitOnBranch` or the connector's file-write tools (`push_files`, `create_or_update_file`), which a repository rule that requires a pull request refuses, and cloud sessions, which keep no lasting user state.
- **Task auto-merge: a per-repository answer, off unless the owner says yes.** `toolkit governance check` asks once in each governed repository whose merged binding has no answer: "When a task's pull request has passed review, CI and your testing, should it merge without waiting for you to type merge?" Yes is recommended (the owner's choice), so an "all recommended" reply answers yes; that answer still takes effect only through the binding pull request and the required check below, which the owner merges and sets, and the machine setup questions never ask about merging. The answer lives in the programme binding as `task_prs.auto_merge` (`off` or `after-gates`) and counts only once merged on the default branch and read on this computer within a day; a missing answer, a stale or failed read or a working-tree edit counts as off. Older Toolkit copies refuse a binding that has the new key, so the question is asked, and an answer merged, only once every computer and the Claude account copy run a version that has it. Yes is enforceable only when the binding's `required_checks` and the default branch's rules both require `auto-merge-eligible` (the `auto-merge-eligible.yml` workflow, which runs the default branch's copy of `repo/scripts/toolkit-auto-merge-eligible.cjs`); the check reports "not enforceable" until then. With an enforceable yes, the merge hold lets through, without a typed approval, only a merge in a session the user started, from that repository's folder, for that repository, as a merge commit pinned to the full head SHA (`gh pr merge N --merge --match-head-commit <sha>`, or a connector merge tool call with `merge_method` "merge" and its head SHA field); `--auto`, `--admin`, `--squash`, `--rebase`, `--delete-branch`, any other flag, the API endpoint and connector auto-merge still need a typed approval. `auto-merge-eligible` fails a pull request that touches the programme binding or merge rules, a `hooks.json`, a script it runs or any module those load (worked out from `hooks.json` at both ends of the pull request), setup that writes host hook config, host hook settings, CI workflows or agent instruction files, or that makes a major version bump; a change that only moves version stamps does not count. While the binding on the default branch does not say `after-gates`, nothing merges without the owner anyway, so the check passes and only lists what would be always manual; a binding it cannot read keeps the full check, and the controller's own run before a merge (without `--binding-at`) is always the full check. A pull request whose check passed while auto-merge was off keeps that result until its next push, label or edit, so after turning auto-merge on, the controller's own run is what stops an always-manual pull request that has not run again: the gate rules make it run the check without `--binding-at` on the head it merges, and merge only on exit 0 or with the owner's label. Such a pull request merges only once the owner adds the `toolkit-owner-merge` label in GitHub. The label counts only when the event's sender is the repository owner's own user account; a bot, an app or anyone else adding it has it removed and the check fails. In a repository an organisation owns, no user is the owner, so the label never counts there and such a pull request stays red (it fails closed). Taking the label off sets the head's `toolkit-owner-merge` status to failure, and only the newest status counts, so a label added back later cannot reuse the earlier OK. The run for that labeled event records a `toolkit-owner-merge` commit status on the head it was added on, with the workflow's own token, and every other run passes only while the current head carries that status from `github-actions[bot]`; a push, or a label without the status on the current head, removes the label and fails, whichever runs were cancelled before. Pushes run in their own group that nothing cancels. The label removal and that status are the workflow's only writes. Agents never set the label: the merge hold refuses a shell command that names it with a GitHub client, and a connector tool for labels, issues or pull requests whose call names it. That is an accepted gap: agents act through the owner's own login, so GitHub cannot tell who added it, and a label name built at run time or read from a file gets past the tripwire. The rest of the conditions (review, CI, testing, one merge at a time) are the controller's, in the gate rules' task auto-merge section.
- **The install check.** `repo/scripts/toolkit-install-health.cjs` gives one result: `passed`, `restart-required` or `action-required`, with numbered steps for a person. It checks the Claude Code plugin (setup only: installed, current, and run from the managed checkout), the update record (no recorded `claude-plugin` or `repo` version newer than the install), the Toolkit helper definitions (refreshed when stale, held when a file was not written by Toolkit), the Toolkit global rules (refreshed when stale, held on broken markers; see Instruction Layers), and the Toolkit-owned depth setting against the selected topology.
- **Setup** names both Claude copies under `## Claude Code native plugin`: `Claude Code in a terminal: <version> (runs from this PC's Toolkit folder)` and `Claude app: claude.ai copy <version>, which only claude.ai updates` (or that none was found), pointing to the install check's `Claude app account copy` steps when that copy is behind. It runs the check last on Claude Code and prints an `## Install check` section. `action-required` makes setup exit with code `24` after its other steps; a same-run plugin install is `restart-required`, because Claude Code loads the new version only in a new session. A root-only profile without a verified hook this run (just installed, a setting turns hooks off, or the agent hook did not answer the test launch) prints `safe-root-only`, Toolkit's safe default: the hook keeps root-only, and the next `setup toolkit` in a new session verifies it. The `Helper routes` line reports the stored native result for this computer's platform (`repo/contracts/host-qualification/claude-code.json`) as qualified or not yet qualified, plus the known limits; it is informational and always passes. A failed prune of old helper-definition backups is a note on the `Toolkit helpers` line, not a failed check.
- **Session start** runs the check in a fresh process after its maintenance, so after an update it uses the updated code and stack registry. A stale helper definition is refreshed there (with a backup kept for the report retention days); an `action-required` result writes an action-required update report with an `Install check` section.

## Update Reports

When a hook run performs meaningful work or safely skips a risky update, the bridge writes a markdown report under the user temp directory:

```text
%TEMP%\ai-agent-toolkit\update-reports\toolkit-update-YYYYMMDD-HHMMSS.md
```

Meaningful work means at least one of:

- The configured Toolkit repo fast-forwarded.
- The configured Toolkit repo was already advanced before the hook run compared with the last recorded bridge update state. This is reported as an inference, likely from a manual pull or another local Git update, not as proof of a manual action.
- Delegated repo sync failed.
- Hook-light validation failed after a repo update.
- Repo auto-update auto-switched a clean non-configured branch back to the configured branch.
- Repo auto-update skipped safely because the tree was dirty, the remote did not match, branch switching failed, fetch failed, or the fetched commit was not a fast-forward. Dirty-checkout reports should name the configured Toolkit source path and suggest finishing or stashing those changes, or rerunning `setup toolkit` to use the dedicated clean managed `main` checkout for startup updates.
- The Codex native plugin cache is stale relative to the configured repo source, was auto-refreshed, or failed auto-refresh.

Normal no-op hook runs with the same observed repo commit and no stale plugin cache, skip, or validation issue do not write or open a report. Meaningful reports are also deduplicated by event signature: if a later hook sees the same repo status, target-sync result, native plugin cache status, and checksum, it does not create or open another timestamped report. In hook mode, the bridge prints only:

```text
Toolkit updated: <report path>
```

The report starts with a short `TL;DR` section for the triggering source (Codex plugin hook, Claude Code plugin hook, or manual/repo run), repo status, and any action needed. Details include the new and previous observed commits, sync source, Singapore time (`SGT`), a Repo Update section with configured branch and configured remote, changed files from the fast-forward or already-advanced observed range when available, the explicit live n8n skip note, repo update status, hook-light validation result, Codex native plugin cache status when checked, checksum, and any warning/error. If auto-update finds a clean local Toolkit repo on the wrong branch, the report says it auto-switched back to the configured branch. If the repo is dirty, the report explains that dirty local changes prevent auto-update and the hook leaves the current branch and changes untouched. For the default production configuration, this shows configured branch `main` and configured remote `https://github.com/weijunswj/ai-agent-toolkit` so users can see whether updates are coming from GitHub `main`. The latest report path is stored in hub state as `last_update_report_path` and appears in `--audit`.

For first-restart compatibility after a bridge update, an older installed native hook may fast-forward the configured local Toolkit repo and then delegate into the newly updated repo script without passing `--hook`. An unsuppressed delegated command with `--sync-enabled --write --sync-source repo --hub <same-hub> --skip-repo-auto-update` is report-eligible. When hub state contains `last_repo_update_from_commit`, `last_repo_update_to_commit`, and `last_repo_update_status`, the delegated repo script uses that stored metadata plus a local `git diff --name-only` over `repo_path` to populate the update report. New parent hooks pass `--suppress-update-report` to delegated sync so the parent hook remains the single report writer and duplicate reports are avoided.

Meaningful update reports are enabled by default and can be persisted with `--enable-update-reports` or disabled with `--disable-update-reports`. A central deterministic classifier marks each report as `action-required`, `successful-activity`, or `no-op`. Action-required reports open automatically; successful reports remain closed; true no-ops create no report. `--open-update-report` remains an explicit one-run request for the current report. Legacy `--enable-update-report-open` and `--disable-update-report-open` are compatibility aliases for failure-only behavior and cannot restore all-success opening. On Windows, opening uses only `notepad.exe <reportPath>` and only for files created under the Toolkit temp update-report folder.

During `setup toolkit`, report creation and retention remain in the upfront wizard. Existing `update_report_open_enabled=true` is explicitly migrated to action-required-only behavior, and the setup proposal states that failures open while successes stay closed.

Toolkit-managed update reports/logs older than the configured retention window are cleaned up best-effort on setup and hook/update runs. Default retention is 7 days and can be configured with `--update-report-retention-days <positive-integer>`. Cleanup also caps retained files to the newest 200 Toolkit reports inside the retention window. Cleanup only considers Toolkit report filenames under the Toolkit-managed update report/log directory, never arbitrary user files, and never treats cleanup failure as a setup or startup blocker. Setup and audit summaries include retention days, max retained reports, deleted count, skipped/error count, and the report/log directory path.

Codex plugin cache auto-refresh is included in the setup checklist. Codex may refresh only the Codex Toolkit native plugin cache from the managed `main` checkout. Claude Code runs its own install check (see Claude Code Install Check) and does not let Codex mutate Claude Code cache.

## Windows Scheduled Tasks

On Windows, setup ends with a `## Windows scheduled tasks` section for the managed checkout's repository: each no-AI task Toolkit keeps, with its folder, name, schedule, purpose and state (to create, to update in place, up to date, or refused), and why a task does not apply. For any other governed repository, `node repo/scripts/toolkit-windows-tasks.cjs plan --repo-root <its checkout>` gives the same read-only report and line. Setup never creates a task itself. When one needs creating or updating, the section ends with one PowerShell line for the user to paste:

```powershell
node "$env:USERPROFILE\.ai-agent-toolkit\source\ai-agent-toolkit\repo\scripts\toolkit-windows-tasks.cjs" apply --repo-root "$env:USERPROFILE\.ai-agent-toolkit\source\ai-agent-toolkit"
```

It registers the tasks, records them in `~/.ai-agent-toolkit/user-state/tasks.json`, then starts a new or changed programme sweep once (once more if a closing console stopped it, 0xC000013A) and calls it healthy only when the job's own last-run record says it ended well.

- **Tasks:** `<FOLDER> - PROGRAMME SWEEP` runs hourly from 08:00 to 23:59 for a repository whose GitHub governance is ENABLED: the programme refresh, the attention line and the footer sweep over the bound repository and its evidence store. `<FOLDER> - SHARD TIMINGS` runs on Mondays at 09:15 for the Toolkit repository only and opens a pull request when the CI shard times drift. Both run `repo/scripts/toolkit-scheduled-job.cjs`, which starts only node and gh and records each run in `~/.ai-agent-toolkit/user-state/tasks/<id>/last-run.json`.
- **Folder and names:** the folder is the binding's `schedule_folder` (`TOOLKIT` here), else the repository name in capitals. Names are `<FOLDER> - <TASK>`; Windows keeps each task as a file, so a name never holds `\ / : * ? " < > |`.
- **Ownership:** a task is Toolkit's only when it sits in that folder, its Description carries `[toolkit-task v1 id=<id> def=<digest>]`, and the registry lists that id. Toolkit lists every other task and never changes it, including the root folder's n8n backups and a same-named task of your own.
- **How they run:** as you, only while you are logged on, with no stored password, through `conhost.exe --headless` so no console window opens. A second start while one runs is ignored, and each run stops at 30 minutes. A headless console host does not pass the job's exit code to Task Scheduler, so the job's result is in its last-run file.
- **A task you made yourself** can be recorded so the list shows it as known: `toolkit-windows-tasks.cjs adopt --folder <F> --task <name> --id <id> --purpose <text>`. Toolkit never changes or removes an adopted task.
- **List every task:** `node repo/scripts/toolkit-tasks.cjs [--json]`, read-only: Windows tasks live from Task Scheduler, Claude Code desktop tasks live by name and description, and Codex and cloud tasks from the registry, marked "from record, not checked live".
- **Remove:** `node repo/scripts/setup-toolkit.cjs --remove-toolkit-tasks` removes only Toolkit's own tasks and their records, then the folder when nothing else is in it.

## Hook Policy

Hooks are optional automation. They must not contain unique critical policy.

The startup hooks call the shared updater. Toolkit helper hooks call the shared deterministic routing guard through native adapters:

- Codex hook source: `.codex-plugin/hooks/hooks.json`.
- Claude Code hook source: `.claude-plugin/hooks/hooks.json`.
- Shared policy source: this doc, `AGENTS.md`, Toolkit docs, and validators.
- Deterministic enforcement: `repo/scripts/toolkit-local-bridge.cjs` and tests.

The shared updater may run a passive repo-local instruction preflight from the hook path. That preflight is a notice-only freshness check for expected `AI-AGENT-TOOLKIT` managed blocks; it does not install, repair, back up, create, refresh, or rewrite repo-local instruction files, and it never blocks the current task.

Antigravity does not need Codex or Claude hooks to receive core policy because the policy remains in portable docs and validators.

The bridge uses `SessionStart` for update and sync. Codex registers `PreToolUse` for helper launches and shell calls with the matcher `^(?:Agent|[A-Za-z0-9_-]*spawn_agent|Bash|exec_command|shell|local_shell|PowerShell)$`, and its after-tool programme refresh for the same shell names; Claude registers the parent `Agent|Task` path. Codex documents its shell and exec calls as `Bash`; the other shell names are listed so a call reported under one of them still reaches the checks. In a 29 October 2026 test, Codex Desktop ran every command through its code-mode tool `exec`: that program reached no hook, and each shell call it made reached `PreToolUse` as `Bash` with a string `command`, no `workdir`, and the session folder as `cwd`. A 30 October 2026 test showed that `cwd` stays the chat's folder even when the program ran the command in another folder, such as a lane worktree, so the push check does not take it as the run folder (below).

Codex names a hook tool `spawn_agent` only in its default namespace and in V1 (`multi_agent`). A V2 (`multi_agent_v2`) spawn reaches hooks under the flattened name `<namespace>spawn_agent` (`collaborationspawn_agent` for the default namespace), with no `Agent` alias, and Codex treats a matcher made only of names and pipes as an exact list. The earlier `spawn_agent|Agent` matcher therefore never ran for the V2 spawn seen in the 19 October 2026 native UAT. Codex accepts a configured `features.multi_agent_v2.tool_namespace` only as `[A-Za-z0-9_-]+`, so the registered matcher and the hook's spawn recogniser are one constant (`CODEX_SPAWN_MATCHER`) over that alphabet, hyphen included; a hyphenated namespace such as `multi-agent` is matched and held unless bound. Changing the matcher changes the hook hash, so an installed Codex needs the owner to trust the changed hook again. Codex V2 (`multi_agent_v2`) forks the full parent history unless `fork_turns` is exactly `none`; the guard treats any other value, or its absence, as a session transition. An admitted Codex request exits 0 with no output, because Codex records a bare `permissionDecision: allow` as a failed hook run. A denial exits 2 with the reason on stderr.

Both helper hooks first ask one shared predicate (`repo/scripts/toolkit-governed-repo.cjs`) whether the work is Toolkit-governed. It answers yes when a launcher marker is set (`TOOLKIT_GATE_ROLE`, `TOOLKIT_NATIVE_HELPER_BINDING` or `TOOLKIT_CLAUDE_TASK_PROFILE_SHA256`), or when the repository's governance state (`toolkit-governance-state.cjs`) is ENABLED with the governed rules binding. UNDECIDED, DISABLED (plain folders included) and incomplete repositories are not governed. The Codex hook uses the same predicate, so a governed repository is governed on both hosts. Outside governed work the Codex hook makes no decision. The Claude hook allows every main-session launch with no decision. Unless the stored Claude profile is `broader-native`, it refuses an `Agent` or `Task` launch whose caller is a subagent or teammate (`agent_id` present) with a plain reason: "a subagent can't start another agent (one layer only). Do the work in this subagent, or hand it back to the main session." A missing, unconfigured or unreadable profile reads as root-only, so the refusal stays. `agent_type` alone no longer marks a subagent in these hook decisions, in governed work or elsewhere, because Claude Code also sends it from a main session started with `--agent`. The launcher-bound checks (the native helper adapter, the Claude task session and the dispatch observer) still refuse on `agent_type`, but a `--agent` main session cannot reach them, because the gate session launcher refuses `--agent`. After a decision failure the hook still refuses a subagent caller with that reason; otherwise it gates only governed work or a set launcher marker.

Governance gate. Toolkit splits what it does in two. Wherever the plugin is installed, the global rules apply in every folder: the coding gates (G0, G1, G2), subagent limits, routes, safety rules and the portable skills. GitHub governance is the part that needs a github.com repository: parent and child issues for programme tracking, records and decision traces, a private evidence store, the governed rules block and the no-force-push ruleset. Only GitHub governance is switched per folder, and each folder is in one of three states:

- **No git** (a plain folder, for example a project folder on the desktop): DISABLED automatically, never held and never asked. Nothing is written into the folder.
- **Git, but not on github.com** (no origin remote, more than one, or another host such as GitLab): held once with a short notice that GitHub governance will be off here, because it works only for github.com repositories. The user replies ok (yes, no and later work too, with the same effect) and Toolkit records DISABLED; `enable` is refused. If the repository later moves to github.com, Toolkit asks the github.com question there.
- **Git on github.com:** UNDECIDED until the user answers the governance question. The held-message notice is three short lines: the question ("Turn on GitHub governance (issues, records, evidence store) for this repository?"), the answers (yes; no, never ask again; later, ask next session) and a line telling agents that only the user answers. `yes` turns on parent and child GitHub issues for programme tracking, records of plans, reviews and decisions, a private evidence store of the user's choice and the no-force-push ruleset, and setup then helps add the governed block and programme file. `no` keeps GitHub records out of the repository while the coding rules still apply, and Toolkit does not ask again. `later` records nothing and asks again next session.

How the question is shown depends on the host:

- **Claude Code:** a tap-to-answer card (Yes, No, Later) with the same three lines as text above it, so the question is seen even where the card is not drawn and the user can type the answer. A hook's own hold message is not shown in the mobile app or Remote Control, so Claude Code does not block the held message: the turn runs, but only to show the card. The message itself stays held and comes back after the answer, as with a typed one, and the instruction Claude gets says not to act on it. On that turn every other tool, read-only ones included, is refused, except loading tool definitions. The card must be exactly Toolkit's, with no answer filled in by whoever called it: Claude Code itself drops an answer the model fills in before the card is shown, and Toolkit's tool gate refuses such a call too. The tool gate notes each card it lets through, and the tapped answer counts only for a noted card, once, in the same run of the session that was asked, with the same checks as a typed answer. A dismissed card, or a typed "Other" answer on it, records nothing, and the next message asks again. Typing `yes`, `no` or `later` still works. A session with no session mark, one another session or a launcher started, a host that sends no session id, and a repository not on github.com get the text hold instead. Claude Code's hook input does not say whether a run is headless, so a `claude -p` run, and a resumed or forked run, get the card turn too: the held message reaches Claude with the instruction not to act on it, every tool but the card is refused, and nothing is recorded there (`claude -p` offers no card, and a resumed or forked run is a new run, so its answer counts only once it is asked again).
- **Codex:** the three lines as text; Codex has no card a hook can ask for.
- **Claude Projects thread (a Remote Control session):** the user answers by replying in the thread. The thread hands the session each message wrapped in one envelope, and Toolkit reads the answer from the one message in it that the user sent. The app's own notes at the end of the envelope are set aside and never read as the answer, and a message that carries a file or image is not an answer, though it no longer stops the user's reply beside it from being read. The same checks apply as to a typed answer. A coordinator's relay of the user's words, a scheduled task, a message from anyone else and any other wrapped text never answer.

The user can answer in their own words. In the held repository itself, `yes`, `no` and `later` (and the full `toolkit governance` forms) answer at once; a reply in another folder answers nothing for it. Any other message of the user's own in the run that was shown the question, typed or from a thread, goes to the agent with a one-use reply ticket: the agent reads what the user means and, when it clearly answers, records it with `toolkit-governance-answer.cjs` and that ticket, then tells the user what Toolkit recorded; when it is mixed or a question, it records nothing and asks again. When the agent thinks the user means one answer but is not sure, it records `confirm-yes`, `confirm-no` or `confirm-later` with the ticket instead: Toolkit records nothing and gives it a question naming exactly what would be recorded, and the user's next own message, a bare `yes` included, is read only as the reply to that question, with a ticket that can record that one answer and nothing else. Toolkit only checks that the message is the user's own reply after its question: a ticket is never given for a relay, a reminder, a tagged scheduled task, another person or agent, a session another session or a launcher started, a resumed run, or a thread message that already had one. It works once, in that session's run only, for the repositories that question named, lapses after half an hour, and only the newest one counts.

Software that runs as the user can fill in the card's answer the same way a tap arrives, and Toolkit cannot tell the two apart: another plugin's hook, an SDK host, or a process an agent starts that answers its own permission prompts (Claude Code's `--input-format stream-json` with `--permission-prompt-tool`). Each of these could equally send `yes` as a message today (the known limit below), so the card does not lower that bar.

The programme binding `.github/toolkit-programme.json` as merged on the repository's default branch is the repository's own governance setting, and it decides on every computer: a repository with a merged binding is never asked. Only that copy counts, read from the URL git really uses for `origin` and only when that is the same repository as the identity: a working tree, another branch, a fork's copy, a redirected remote or a copy of the state an earlier version left in the repository grants nothing, since an agent can write them. The read is also held when the repository's own config, or command-scope config (`git -c`, `GIT_CONFIG_COUNT`, `GIT_CONFIG_PARAMETERS`), carries a transport, proxy or TLS override, or when `GIT_SSH` or `GIT_SSH_COMMAND` is set for an ssh origin (they do nothing for https); the fetch runs with the repository's hooks off and replace refs ignored, and the fetched ref must be the commit the remote reported. Trust boundary: the user's own global and system git config are trusted (a global `core.sshCommand` for Windows OpenSSH or a company proxy is ordinary setup), so they are not held; anything that can change them can already act as the user. The user's own environment is trusted the same way (`GIT_CONFIG_GLOBAL`, `GIT_CONFIG_SYSTEM`, proxy and TLS variables such as `HTTPS_PROXY`), apart from the command-scope config and ssh variables above. When a refresh keeps the last read, `toolkit-governance.cjs status` says why in plain words. While governance is on but the merged binding is not freshly read, or GitHub cannot be reached, the turn-end checkpoint keeps each turn in an offline queue next to the session binding in Toolkit's user-state (at most 200 turns, 7 days), never in the repository; the next turn end that can write replays them in order, once, and deletes the queue after the write is confirmed, and governance confirmed off deletes it unreplayed. Limits: there is one queue per session, replayed only by that session's next turn end (or `programme.cjs checkpoint --session <id>`), so a session that never resumes leaves its queued turns unwritten; turns older than 7 days, or beyond the newest 200, are dropped with a note in the session's error log; a turn queued before a rebind is skipped with a note, never written into the new assignment's journal; each dropped, skipped or unreadable turn is noted once however often the write fails; session start deletes the queues of a repository whose governance is confirmed off, and `status` shows `Queue: <n> turns waiting (oldest <date>)`. A signed-out `gh` is an error, never queued. A `GIT_SSH` or `GIT_SSH_COMMAND` set for good (Plink, TortoiseGit) keeps every refresh of an ssh origin held, so its queued turns are dropped unwritten after 7 days; `status` says so. `status` also shows which hosts here run Toolkit's hooks (`Hooks: <host> <state>`: Claude Code `present (trust not checkable)`, or `present (claude.ai account copy; trust not checkable)` when the Claude desktop app runs Toolkit from the user's claude.ai account, `disabled`, or `plugin present, no hooks declared`, Codex `present, trust unknown`, Claude Projects `no local hooks`, or `plugin absent`), naming the portable path (`programme.cjs refresh` and `attention` by hand) for any host without running hooks. In an ENABLED repository the session-start line also carries the programme's `Attention:` line from this computer's cache, and a `Checkpoint:` line when a session's last turn-end record failed; a missing or hour-old cache starts `programme.cjs refresh` in the background (at most once per 15 minutes per repository, and the line says so only when one started), and the hook itself makes no network call. `toolkit-governance.cjs status` and the session-start hook read it into a cache next to the registry; hooks read only the cache, programme records, gate admission and finality need a read from the last 24 hours, and an unusable merged binding is ERROR (ordinary work continues, governed effects hold). Where nothing is merged, the user's answer decides: once the user answers yes or no, the answer is kept on that computer for the repository (every clone, worktree and new session shares it), so no later session there asks again; only `later` asks again in the next session. Right after a yes, the agent runs the read-only `toolkit-governance.cjs discover` and puts its one adoption proposal to the user before other work: the parent issue and private evidence store it found, with their evidence (or the alternatives, or the create defaults), and what Toolkit would reuse, add, repair, keep and defer. After one yes it adds the governed block and binding in one pull request for the user to merge. Until the binding merges, the repository is ENABLED with setup not finished: nothing is held, GitHub governance does not run, and every new session start reminds the agent to ask again; the user can say not now. A state that cannot be read is UNDECIDED and held. `decline` is the older word for `disable` and still works. On github.com the user's own next message is the answer: `yes` records ENABLED, `no` records DISABLED, and `later` (or `not now`) records nothing and lets that session carry on under the global rules (Toolkit asks again in the next session, and when the session is resumed; it needs the host's session id, which Claude Code and Codex send). Each session's "later" is its own, so one session never re-holds another, and after "later" the user can still decide by sending `toolkit governance enable` or `disable` as a message; a short `yes` there is an ordinary message. Every answer in chat, short (`yes`, `ok`) or full (`toolkit governance enable` or `disable`), counts only in the same run of the session that was shown the question or notice (or said "later" in it), as the whole message (a reply in other words goes through a reply ticket, in the same run only): a fresh session (for example one an agent starts with `claude -p` or `codex exec`) has nothing held, so its answer is just held and the notice shown. Each host's session-start hook gives every session start a random session mark, and the repository it starts in a new repository mark, kept next to the registry (one small file each, the newest 256 of each kind): starting, resuming or forking a session begins a new run, while `/clear` and compaction keep the run's marks. A held message carries both marks, and an answer counts only while both still match, so a resumed session, or one whose repository has had another session start since, is shown the question again and only its next reply answers. An agent that resumes or continues the session from another process (`claude -p yes --resume <id>`, `claude -pc yes`, `codex exec resume <id> yes`) is always a new run, whatever session id it reports, so its reply is held. The same goes for the full answer after "later": once another session has started in the repository, Toolkit asks again. A session that started before Toolkit could mark it cannot answer in chat; the notice says to start a new session (on Codex, after trusting Toolkit's SessionStart hook in `/hooks`) or use the terminal. A mark that cannot be replaced fails safe: the session's own mark is written first and, if it cannot be, the old one is removed so the run cannot answer; the repository's mark is handled either way, and one that cannot be replaced is removed, so every answer held before it is asked again. A mark that can be neither replaced nor removed (a file another process holds open, a read-only folder) stays, so the held messages and "later" answers that carry it lose their marks instead: they live in another file, no run can match them, and the question is asked again. Only if that file cannot be changed either can the old run still answer; that is part of the speed-bump limit below. A host that sends no session id cannot answer in chat; the same subcommand of `toolkit-governance.cjs` in a terminal always works. Agents are told to raise the question or notice in plain words and never to ask the user to run a command. A repository's own instruction files (`AGENTS.md`, `CLAUDE.md`, `GEMINI.md`) are changed only when it is ENABLED; only the user-level global files are the plugin's to write. Portable skills are offered in every state, undecided included, and the GitHub governance skills only when ENABLED with its materials; the programme reconciler refuses every command otherwise. Until the user answers:

- Every other prompt is held. In Codex it reaches the agent only as a possible reply in other words, with a reply ticket; in Claude Code it reaches Claude on the turn that shows the card, with the instruction not to act on it, or with a reply ticket. Held prompts are kept in a private local file next to the registry (at most 20, 4,000 characters each, dropped after seven days), each with the session that sent it. A session gets back only its own, as context on the turn that answers, or on its next message once the repository is decided elsewhere; other sessions' messages wait for those sessions. A session that another session started, or a Toolkit launcher, is refused in a held repository and nothing it sends is kept: Claude Code's session-start hook exports the session's id (`TOOLKIT_HOST_SESSION`, through `CLAUDE_ENV_FILE`) to the shell commands that session runs, so a `claude -p` or `codex exec` started from one of them sees an id that is not its own.
- Every tool is refused in the held repository, read-only ones included, except the card, loading tool definitions, and the exact answer command with the session's live reply ticket (Toolkit's own script path as written, nothing a shell would expand, nothing chained). Codex's hooks see only state-changing tools (shell, edits, agent launches, MCP tools).
- From any other folder, an edit whose target is in the held repository is refused, and so is a shell command that moves into it (`cd`, `pushd`, `Set-Location`, `-C` or `--cd`) or names a path in it. Writing the governed block and binding in from elsewhere would not change the state anyway: only a binding merged on the default branch, or the user's own yes, enables a repository.
- From a plain folder or a decided repository (for example a session working in a parent folder of several repositories), that refusal says to answer in the held repository's own chat. A reply in the parent folder answers nothing for it. No new prompt can be scheduled for the session (`CronCreate`, `ScheduleWakeup`, `RemoteTrigger`) while a reply ticket, a confirmation or a "later" answer is open in the run. A prompt scheduled before that, or a recurring one, is not stopped.
- Reading free text for a session launch with a short reply, or for a session resume or fork, is not a hook: those readers refused ordinary commands (reads of `.claude` folders, metadata saves, reports and loops that name Claude or Codex). What stops a nested or resumed session answering is the run rule above: a session another session started, and a resumed run, has nothing held, so nothing it sends answers; in a held repository the hold refuses the launch itself. The written rule in the safety-gates playbook covers the rest: never start, resume or fork a session to answer the question.
- In every folder, two exact checks stop an agent giving the answer itself: a tool call that runs `toolkit-governance.cjs enable`, `disable`, `decline`, `reopen`, `migrate` or `repair`, or names Claude or Codex next to the full `toolkit governance enable`, `disable` or `decline`, is refused, and so is any edit under `.ai-agent-toolkit/user-state`. A command that only names Claude or Codex next to a bare yes, no or ok is data and runs.

A github.com decision is stored in the user's registry, keyed by repository identity, so every clone shares it; an ok for a repository not on github.com is kept in a separate file next to it (by remote, or by the repository's path when it has no remote). These user-state files are the only governance state: Toolkit writes nothing into the repository or plain folder for it and never edits its `.gitignore` or any other file there. Earlier versions also kept a copy in `.ai-agent-toolkit/governance.json` inside the repository or folder. Nothing reads that copy now and Toolkit never changes it, so it can be deleted: ask your agent to delete `.ai-agent-toolkit/governance.json` in that folder, and the `.ai-agent-toolkit` folder too if only its `.gitignore` is left; it asks you before deleting. Never delete the `.ai-agent-toolkit` folder in your home folder: it holds the user-state files. Each session start states the effective state in one line.

Claude Code runs the gate as the governance hook (`toolkit-governance-hook.cjs`) on `UserPromptSubmit`, `PreToolUse`, `PostToolUse` (the card's answer only) and `SessionStart`. Prompts and state-changing tools (shell, edits, agent launches, MCP tools) have `onFailure: "block"`: if the check itself fails inside a repository, or the hook cannot start, the prompt or tool is held. Every other tool (read-only ones and the card) is let through when the check fails, as it was before the hook saw it; a card let through that way records nothing, because its answer counts only with the tool gate's note. A failed `PostToolUse` records nothing either. Codex runs it through the helper hook on `UserPromptSubmit` and a second `PreToolUse` group, and through the session-start hook. Codex documents no failure setting for hooks, so a Codex hook that crashes or times out lets the prompt through; that is a known limit. Codex also runs plugin hooks only after the owner trusts them in `/hooks`, one by one; setup names every hook event to trust (`SessionStart`, `UserPromptSubmit`, `PreToolUse` and `Stop`), read from the installed hooks file. A command that works in a held repository from another folder is refused as well (after `cd`, `pushd` or `Set-Location`, with Codex's `-C` or `--cd`, or by a full path), whatever it runs there. A damaged or missing "later" or ok file counts as none, so the question, the notice and their answers still work, and a damaged held-message file is moved aside next to the original and a fresh one started. A decisions file (the registry) that cannot be read holds every github.com repository, decided ones included; every hold, the session line, `status` and `check` then name the file and the way out: `toolkit-governance.cjs repair`, run by the user in a terminal, moves it aside next to the original after a typed yes, and Toolkit asks about each repository again. Every governance refusal and hold (a failed check included) and every session line also tells the agent never to act as the user: not to answer the question itself, start a session or script to answer it, or click a confirmation through a UI or computer use; the global rules say the same for every owner-only question. The answer guard is a speed bump, not a security boundary: it reads command text, so an agent that runs Node code or a script against the user-state files or a held repository is not screened (edit tools under `user-state` are refused, but shell commands are checked only for paths inside held repositories), and a determined agent in another folder could still write them. The session marks and held messages are files the agent's own shell can read and change too. The guard stops ordinary attempts, not a hostile agent. Neither host's hook input says whether a run is headless or who is typing, so a single process that an agent feeds several messages (for example Claude Code's `--input-format stream-json`, Codex's MCP server or `codex app-server`, or an interactive session driven through a terminal multiplexer) can still answer the question it was shown in that run; that is a known limit. Runs of one session share its id, so when messages replayed after an answer came from more than one run of the session, or any came from a resumed or forked run (the session mark records which), the agent is told another process may have sent some and to confirm with the user first. Claude Code cloud sessions (`CLAUDE_CODE_REMOTE=true`) are not enforced, because they have no lasting registry; the session line says so and the rules text still applies.

Default-branch protection. "CI green" means every check named in the programme binding's `required_checks` passed at the head, so `toolkit governance check` also checks, for an ENABLED github.com repository with a binding, that a passing check can never hide a failing or pending one: the default branch requires exactly the binding's checks (active rulesets and classic branch protection together), each pinned to an app so a job of the same name elsewhere cannot satisfy it; exactly one workflow job produces each (a job named by an expression that could produce it leaves this unverified); that job's workflow runs on every pull request to the default branch (no path filter, no branch filter that leaves it out); its job condition is absent or exactly `always()` or `!cancelled()`, because a skipped job reports success; a job that waits for others has a step whose result is the declared aggregate command's (no step condition, `continue-on-error`, custom shell or working directory; `TEST_LEGS: ${{ toJSON(needs) }}`; a script of plain node commands ending with this repository's `node repo/scripts/run-tests.cjs --verify-ci`, which fails unless every needed job succeeded), and without one it is unverified; and the default branch allows merge commits only. GitHub settings are read through the signed-in `gh` (classic branch protection needs admin); the workflows are read from the checkout, also with `--offline`, which takes the default branch from `origin/HEAD`. The workflow reader is default-deny: it follows only printable ASCII on every line, comments included, in plain `key: value` lines and `- ` items, each at its mapping's or list's indent, with block scalars only for `run`, `if`, `shell` and `continue-on-error` (no anchors, aliases, tags, explicit keys, flow mappings, values continued on the next line, duplicate keys, tabs, control characters, Unicode line breaks, non-ASCII spaces, lone carriage returns, second documents or a block scalar line shallower than its first), and a workflow with anything else is unverified. A leading byte order mark is removed first. `continue-on-error` counts as off only when written as the plain `false`, a job name written as any YAML null (`~`, `null`, `Null`, `NULL`) is no name, and only an `on` key (plain or quoted) is the trigger, never a `true` key. Anything that cannot be confirmed leaves default-branch protection unverified, never conformant, and the check's first line counts unverified items. `toolkit governance migrate` then lists repositories whose default branch misses a binding check or allows squash or rebase merges, with any workflow problem the ruleset does not fix, and, after its own typed yes, creates or updates one ruleset named "Toolkit: protected default branch" (the default branch, a pull request for every change, the binding's checks pinned to GitHub Actions, merge commits only, no bypass; an update replaces that ruleset's rules). A repository where no workflow job produces a binding check, or where that job's workflow does not run on every pull request to the default branch, is not offered it, because the required check would wait forever and block those merges. It never edits a ruleset or branch protection it did not create: an extra or unpinned check there, or a workflow that can mask its check, is listed to change by hand, and a refused write is reported once, not retried.

Dependency and security settings. For the same repositories `toolkit governance check` also reports Dependabot alerts, Dependabot security updates, a `.github/dependabot.yml` (or `.yaml`) entry for every package ecosystem it finds (npm, pip, GitHub Actions, Docker, Go, Cargo, Bundler, Composer, at the root and one folder down), secret scanning with push protection, CodeQL (default setup, or an advanced setup: a workflow on the default branch, run by a push, pull request, merge queue, schedule or as a reusable workflow, with CodeQL init and analyze steps in one job that is not switched off, or CodeQL results GitHub received on the default branch in the last 90 days from anything but default setup, such as a composite action; any other workflow whose text names CodeQL, other than its upload-sarif step, keeps default setup off and is reported for a hand check, and CodeQL run from outside the workflow files counts only once it has uploaded) and private vulnerability reporting. GitHub's free settings are on by default under governance: the owner's yes to governance covers them, so `toolkit governance security` (agents may run it) and `toolkit governance migrate` turn them on without another question, write a `dependabot.yml` only where none exists (weekly, a three-day cooldown, seven for GitHub Actions, patch and minor updates grouped), and read everything back. They write nothing when GitHub cannot be read, report a read-back that fails for any written setting as unverified with exit 2, leave alone a setting GitHub does not allow on the plan or under an organisation policy, and record each change with what GitHub showed before, next to the decisions file. On a public repository the free set includes secret scanning, push protection, CodeQL and private vulnerability reporting. Toolkit never asks about, turns on or reports as drift a GitHub feature that needs billing. On a private or internal repository GitHub bills for secret scanning, push protection and CodeQL, so the check reports them as not applicable (private repository) and nothing is asked or written; Dependabot alerts and security updates stay on there, because they are free everywhere. A binding's `paid_security` key is deprecated and ignored: off or on is accepted, and any other value makes the binding invalid. On a private repository the update pull requests also use the owner's Actions minutes. The auto-merge policy counts only from the binding merged on the default branch, read through GitHub: an edit in a working tree turns nothing on, and an unreadable binding counts as auto-merge off. Dependabot pull requests merge on their own only when the binding says so: `dependency_updates.auto_merge` is `off` by default, and `patch-minor` is the owner's standing permission for that repository. Then the check also wants the auto-merge workflow (copied from `skills/secure-ci-cd/templates/github-actions/dependency-auto-merge.yml`), the repository setting that allows auto-merge, and conformant default-branch protection with at least one required check. The workflow uses only the built-in token, never checks out the pull request's code, acts only on pull requests to the default branch whose every commit is Dependabot's, reads the policy from the default branch, refuses when no ruleset requires a check, and turns on GitHub auto-merge with a merge commit for patch and minor updates, pinned to the head commit it checked, so GitHub merges only after every required check passes. A re-run started by anyone else never turns it on. A major update, a minor update from a 0.x version, an update whose maintainers changed, or a GitHub Actions update (unless `dependency_updates.github_actions` is `auto-merge`; the default is `owner`) gets one comment for the owner and stays open. A push or re-run by anyone but Dependabot, or a base branch change, turns auto-merge off again and tells the owner; if that cannot be confirmed, the job fails instead. A merge made with the built-in token starts no push workflows on the base branch; they run on its next push. ## Codex SessionStart Output Contract

The current official [Codex hooks documentation](https://developers.openai.com/codex/hooks) is the behavior source of truth:

- Plain text written to `stdout` by a `SessionStart` hook is added as extra developer context.
- JSON `stdout` may instead use `hookSpecificOutput.hookEventName: "SessionStart"` plus `hookSpecificOutput.additionalContext`. Do not mix JSON and plain text.
- `systemMessage` is surfaced as a UI or event-stream warning; it is not a substitute for model-visible `additionalContext` or plain-text `stdout`.
- Command hooks receive one JSON object on `stdin`, including `cwd`, and run with the session `cwd` as their working directory.
- Plugin hooks use the normal hook trust flow. Installing or enabling a plugin does not trust its hooks; new or changed hook definitions are skipped until reviewed and trusted through `/hooks`.
- Only command handlers run today. Async command hooks and prompt/agent handlers are parsed but skipped, and `suppressOutput` is parsed but not implemented.

The Toolkit bridge already emits concise bridge status text on hook `stdout`, so its passive agent-rules preflight uses documented plain-text `stdout` rather than trying to combine status text with a JSON response. The preflight runs before bridge no-op handling, resolves the nearest Git root from the documented session working directory, and never creates, repairs, backs up, or writes repo-local instruction files. In a repository whose Toolkit GitHub governance is ENABLED it also compares the vendored Toolkit checks under `.github/scripts/` (plain-text check, personal-data guard) with the running Toolkit's sources, and notes a missing plain-text check; it only reports, once per finding.

## Instruction Layers

Toolkit instructions come in two layers, both inside versioned, hashed Toolkit markers (`repo/scripts/toolkit-managed-block.cjs`: `BEGIN <NAME> v2 toolkit=<version> sha256=<12 hex>`). Toolkit only writes between its markers; every byte outside them, line endings included, is kept.

- **Global rules** (`repo/contracts/agent-rules/global-rules.md` plus the n8n adapter) go into each harness's user-level file: `$CLAUDE_CONFIG_DIR/CLAUDE.md` or `~/.claude/CLAUDE.md`, `$CODEX_HOME/AGENTS.md` or `~/.codex/AGENTS.md`, and `~/.gemini/GEMINI.md` only with `--antigravity-global-rules` or when it already carries the block. `repo/scripts/toolkit-global-rules.cjs` owns them. Setup installs or refreshes them (Claude Code in its install check, Codex in a `## Global rules` section); the Claude Code install check and the Codex session-start hook (only once setup configured the bridge with auto-sync on) refresh their own file when stale. A file that is not UTF-8 (for example UTF-16 from Windows PowerShell) is held and never rewritten. Every change is backed up with its exact bytes under `~/.ai-agent-toolkit/backups/global-rules/` (pruned after the report retention days); a block edited by hand is restored and reported (in the setup output, the session-start update report, and one Codex session-start line); broken markers hold with `action-required` instead of guessing. Hand-written sections the block now covers (for example `Toolkit Controller Bootstrap`) are reported, never edited. Codex reads the repository's `AGENTS.md` only up to `project_doc_max_bytes` (32 KiB by default). Open-source Codex does not count the user-level file toward it, but Codex desktop 26.1016 cut repository rules off where both files together reached 32 KiB (owner UAT, 22 October 2026), and raising the limit fixed it. So setup asks "Raise Codex's instruction limit" (recommended yes; stored as `codex_doc_limit_enabled`). On yes, setup raises that top-level key in `config.toml` to 65536, and the Codex session-start hook keeps it there; on no, a value Toolkit raised is put back; with no answer recorded, nothing changes. `toolkit-global-rules.cjs --write` is an explicit request and also raises it. `config.toml` is read only with a real TOML parser (Python 3.11 or later, `tomllib`, run isolated with `-I` from the Toolkit folder, so nothing in the opened folder is imported; without a yes the session start does not read it at all): Toolkit edits only when the key is absent everywhere (it inserts at the top of the file) or is one plain top-level decimal line (it replaces that line), checks that the result parses, reads 65536 and leaves every other value unchanged, and otherwise writes nothing and says to set it by hand. It never changes 0 (project docs off) or a value of 65536 or more. The change sits inside `# AI-AGENT-TOOLKIT:global-rules` comment markers that record the exact replaced line (and whether Toolkit created the file), so removal restores the exact bytes or deletes a file Toolkit created. Every raise or restore prints one session-start line and is an update-report entry; an unparseable or ineffective `config.toml` holds, and `--check` fails on it. Setup and `--check` report the combined size against the effective limit, warning when the repository rules may be cut off. `node repo/scripts/toolkit-global-rules.cjs --check|--write|--remove [--harness claude-code,codex,antigravity]` checks, refreshes or removes them; removal deletes a file only when Toolkit created it and nothing else remains, and records the removal in `~/.ai-agent-toolkit/global-rules.json`, so session starts leave that file alone (the install check says "removed by you") until `setup toolkit` or `--write` installs again.
- **Governed-repository rules** (`repo/contracts/agent-rules/toolkit-governed-rules.md`) are one block in a repository's `AGENTS.md`, installed by `repository-agent-rules` only in an ENABLED github.com repository when the owner asks. The block and the binding make GitHub governance run once the user has said yes; on their own they are not an answer. The session-start preflight compares it with the bundled template and prints one neutral note when it differs; it never writes.

Policy that affects agent judgement stays in these rule files, docs and validators, never only in hooks: source of truth, approval gates, generated-output ownership, the Antigravity explicit-copy rule, the native plugin cross-update ban, no package installs by default and no project repository writes by default.
