# Toolkit Local Bridge

This document defines the plugin/update architecture for `weijunswj/ai-agent-toolkit`.

## Current installation scope

Native Toolkit sources target Codex and Claude Code. OpenCode is not a Toolkit target in this release; it returns in its own later change. Antigravity receives portable workspace skills only. Candidate construction, metadata validation and copied files do not prove native invocation, selected model/effort, user UAT or installed acceptance. Qualify each selected host before advertising it as supported; retain route gaps visibly and preserve rollback.

The existing Codex/Claude managed-update paths remain host-local. Antigravity uses `--copy-antigravity-skills --antigravity-project-root <absolute-path>`, which previews by default and requires the explicit authorised `--write` effect. It chooses no provider, copies no credentials, changes no global settings and enables no auto-sync. Toolkit 3.3.0 removed the OpenCode and AG2 bridge targets; the next hub write drops their old records from `state.json`, and files they wrote earlier are left in place.

## Current Source-Of-Truth Chain

Current inspected chain:

1. Root `AGENTS.md` routes repo work and includes the managed source-of-truth contract.
2. `skills/**` stores complete copyable skill surfaces.
3. `repo/contracts/**` stores machine contracts, fixtures, templates, agent-rule inputs, and plugin source contracts.
4. `repo/source-watch/provenance/**` stores active third-party source locks and attribution records.
5. `repo/scripts/sync-repo-doc-contract.cjs` and `repo/scripts/sync-agent-instruction-shims.cjs` maintain only managed root blocks and shims.
6. `repo/scripts/validate-toolkit.cjs`, `repo/tests/*.test.cjs`, source-lock audit, and canonical-surface audit enforce drift and safety rules.
7. `.codex-plugin/**` and `.claude-plugin/**` are platform-specific native plugin metadata. They are not cross-platform source of truth.
8. The Toolkit Local Bridge Hub under the user profile stores bridge state, the manifest and update-report bookkeeping. It is not repo source of truth.

## Architecture

Codex and Claude Code update Toolkit through their own native plugin systems.

Codex agents verify and refresh only the Codex native Toolkit plugin cache; Claude Code remains responsible for its own native cache.

- Codex uses `.codex-plugin/plugin.json`.
- Claude Code uses `.claude-plugin/plugin.json`.
- Both native package manifests point at the same Toolkit `skills/` surface.
- Both native packages use hooks only for optional bridge autocheck, passive repo-local instruction managed-block preflight, and repo-backed auto-update.
- Codex never installs or updates Claude Code.
- Claude Code never installs or updates Codex.
- Toolkit does not publish to public marketplaces from this repo. Marketplace-ready metadata is present in the manifests, but publication remains a separate human action.

The shared bridge has one explicit portable route: Antigravity portable workspace skills under `.agents/skills/`. That copy is an explicit project write; it is never native/plugin auto-sync. The bridge writes into no other app.

## Local Bridge Hub

Default hub path: `%USERPROFILE%\.ai-agent-toolkit\current`.

The hub contains:

- `manifest.json`.
- `state.json`.
- Version data and a checksum over the current Toolkit skill files.
- Source commit or `unknown` when Git metadata is unavailable.
- Sync source: `repo`, `codex-plugin`, or `claude-plugin`.
- Per-source bridge versions in `bridge_versions_by_source`, allowlisted to `repo`, `codex-plugin`, and `claude-plugin`.
- A monotonic `hub_version` compatibility/reporting watermark. New bridges do not use it as downgrade authority.
- Sync timestamp.
- Repo auto-update state: `repo_auto_update_enabled`, `repo_path`, `repo_branch`, `repo_remote`, `last_repo_update`, `last_repo_update_status`, `last_repo_update_from_commit`, `last_repo_update_to_commit`, and `last_repo_update_error`.
- Update-report state: `last_update_report_path`, `update_report_enabled`, failure-only opening behavior, `update_report_retention_days`, max retained report count, and last cleanup status. Legacy `update_report_open_enabled=true` is retained only as migration evidence and is normalized to failure-only behavior.
- Codex instruction limit choice: `codex_doc_limit_enabled` (default false; set by the setup question "Raise Codex's instruction limit", or `--enable-codex-doc-limit` / `--disable-codex-doc-limit`). Only an explicit true lets the Codex session-start hook raise `project_doc_max_bytes` (see Instruction Layers).
- Rule-refresh pull requests always stop at the open PR for the owner to merge; Toolkit 3.7.0 removed the auto-merge choice, and the next state write drops its old `refresh_pr_auto_merge_enabled` key. The rate-limit ledger for SessionStart notes is `agent-rules-notices.json` beside the hub snapshot directory (next to `update.lock`), so snapshot writes by auto-sync or repo auto-update do not reset it.
- Codex plugin cache auto-refresh preference: `codex_plugin_auto_refresh_enabled`.
- Target paths.
- Target detected, enabled, disabled, stale, and synced state.

The lock file lives beside the hub at `%USERPROFILE%\.ai-agent-toolkit\update.lock`.

Writes are rename-first and atomic in the normal case. On Windows, when the final staging-to-`current` directory rename is blocked by a transient `EPERM`, `EBUSY`, or `ENOTEMPTY` after the previous target has already been moved to a backup path, the bridge may fall back to copying the validated staging directory into the empty target path and then cleaning up staging plus backup. If the fallback copy fails, it removes the partial target and restores the backup.

### Owned Staging Generations

Every bridge-created hub or target staging directory uses a generation-scoped ownership protocol. Before `mkdir`, the bridge exclusively creates an immutable sidecar that binds Toolkit owner/schema, generation ID, random ownership token, exact staging path and parent, exact final target, operation and source type, process lease identity, creation time, bridge version, and initial state. After `mkdir`, a second sidecar and an in-directory marker bind the token to the directory identity. Completion and handled failure use separate token-bound state markers.

The bridge cleans only its current proven generation in `finally` handling after success, payload-write failure, staged validation failure, replacement failure, and rollback. Initialization cleanup removes an unmarked partial directory only when the current invocation's own `mkdir` succeeded and the directory still has the identity captured immediately afterward; `EEXIST` and every other ambiguous creation result preserve both sidecar and directory for review. Immediately before deletion it revalidates the exact parent, target, generation ID, token, path containment, ordinary directory type, real path, directory identity, and unchanged ownership record. Ambiguous ownership is preserved and reported instead of deleted. A dead PID is only one liveness signal; it never establishes ownership or authorizes cleanup, and a reused live PID remains protected.

Ordinary `--audit` includes a bounded `staging_generations` inventory. It distinguishes live owned, dead safely attributable, completed awaiting cleanup, malformed, ownership-mismatched, unrelated matching, historical unmarked, special filesystem object, and indeterminate entries. Historical `.staging-*` directories without the new ownership format are reported but never modified.

Safe reconciliation stays inside the existing bridge command family and is dry-run first:

```powershell
node repo/scripts/toolkit-local-bridge.cjs --reconcile-staging <generation-id>
node repo/scripts/toolkit-local-bridge.cjs --reconcile-staging <generation-id> --write
```

The write form is the established explicit approval convention. It acquires the bridge lock, constructs the exact generation sidecar path under every approved managed parent, requires exactly one candidate across the complete parent set, and revalidates ownership immediately before mutation. This exact lookup is independent of the bounded general audit, which remains supplemental diagnostics only. It refuses live, indeterminate, malformed, mismatched, escaped, symlink, junction, reparse-point, or unrelated targets. Repeating an already successful exact reconciliation is a no-op only after absence was checked under every approved parent. Never use a generic recursive `.staging-*` cleaner or delete by name, timestamp, or dead PID.

Reconciliation uses an isolated command route before hook no-op handling, requested-state application, update-report retention cleanup, report writes/opening, repo auto-update, native plugin refresh, or ordinary state persistence. Its accepted controls are limited to `--reconcile-staging`, optional `--write`, `--hub`, `--sync-source`, and `--force-downgrade`; every other bridge flag is rejected before mutation. Dry-run creates no lock. Write mode may acquire and release the existing bridge lock, then remove only the exact generation and ownership sidecars.

Locks are owner-aware. Each lock records the PID of the process that created it, and acquisition classifies that owner with a signal-0 existence probe before deciding anything:

- A lock whose recorded owner is a live process is always respected and never deleted, regardless of age. Hook runs skip safely; manual runs fail with the owner PID in the message.
- A lock whose recorded owner is provably dead (no such process) is recovered immediately, even when the lock file is younger than the stale-age threshold, so a killed bridge run cannot wedge later setup or hook runs.
- A lock with a missing, malformed, or non-positive PID keeps the pre-existing age rule: fresh locks cause a safe skip, stale locks are removed before retry.
- An indeterminate liveness probe (for example permission denied) is not proof of death and also falls back to the age rule.
- A lock file with unreadable JSON or an unparsable `created_at` uses the file mtime for the age rule, so a mid-write lock from another process is not treated as instantly stale.
- The bridge never signals the recorded owner for real.

Recovery of a recoverable lock is race-safe through an atomic recovery claim and per-run ownership tokens:

1. Every acquisition, including the no-main-lock path, claims the existing recovery marker before its authoritative displaced-evidence inspection and keeps that marker through any evidence retirement, main-lock recheck or recovery, and exclusive main-lock creation (`wx`). An optional initial evidence inspection can only fail fast; it never authorizes creation. This serialization makes evidence validation and no-lock ownership commitment one race-safe protocol, so evidence created after an initial scan is seen before creation and no replacement writer can enter behind a recoverer.
2. A recoverable lock may only be displaced by the process that first exclusively creates the `update.lock.recovery` marker. The exclusive marker create is the atomic recovery claim: two contenders that inspected the same dead lock serialize on it, and the loser never deletes anything.
3. Reclaiming a marker left by a dead or stale recovery is itself atomic and identity-safe. The reclaimer must first exclusively create a tombstone named after a hash of the exact marker bytes it inspected; contenders that inspected the same marker generation compute the same tombstone path, so exactly one wins, and the tombstone is never deleted by the protocol (spent tombstones are only aged out after 24 hours, far beyond any contender's inspect-to-claim window). The winner re-reads the marker under its tombstone and proceeds only when the bytes are still the inspected generation; any change means another process cycled the marker and the reclaimer yields without touching it. A marker owned by a live process is never reclaimable.
4. While holding the marker, the recoverer re-inspects the lock. A replacement written in the interim has a live owner and is respected untouched.
5. The recoverable lock is displaced by rename (not deleted in place) and the displaced file's owner is verified not alive before it is discarded. A displaced generation that cannot be proved safe to discard is never renamed back over `update.lock`, because destination replacement semantics cannot guarantee no-clobber restoration across supported platforms. It remains preserved on disk as evidence, this contender does not write a replacement, and the skip/error message names the preserved path. This remains true even when the main path looked free before the preservation decision; a concurrently created main lock is never altered.
6. The replacement lock is exclusively created and carries a unique per-run ownership token in addition to the PID. The marker is then released by its own token.
7. Preserved displaced evidence is a persistent fail-closed acquisition barrier, not just a one-run refusal. Every acquisition -- including the no-main-lock path -- authoritatively inspects `update.lock.displaced.*` evidence while owning the recovery marker before creating anything, so a later or already-running contender does not acquire merely because the recovery marker was released, the intruding main lock went away, or the evidence is old. While the recorded owner is alive the evidence blocks and is never deleted, protecting a long-running displaced owner indefinitely; an owner whose liveness is indeterminate (for example a permission-denied probe) also fails closed; evidence with unusable owner data uses the age fallback. Evidence enumeration, read, or age-inspection failures also fail closed because unreadability is not proof of absence or death; only `ENOENT` proves that a particular enumerated or retirement-verified path vanished. Hook runs skip and manual runs fail with the preserved evidence path and precise reason; the messages never tell the user to delete evidence that may belong to a live owner.
8. Once the displaced owner is provably dead, the evidence is retired under recovery-marker ownership through the same atomic identity-safe tombstone protocol as marker reclaim (exclusive tombstone on the inspected bytes, verify-under-claim, yield untouched if the generation changed). `ENOENT` during verification means that generation genuinely vanished; every other read failure preserves the evidence and blocks. Exactly one contender retires each generation, and the barrier cannot become a permanent wedge after the owner dies. Artifact cleanup ages out only exact Toolkit-owned recovery-claim tombstones (`update.lock.recovery.claim-<16 hex>`) and displaced-evidence retirement tombstones (`update.lock.displaced.<UUID>.retired-<16 hex>`); it never deletes displaced evidence, unrelated similarly suffixed files, or directories.

Release removes the lock only when the current lock file still carries that run's ownership token: a lock replaced by another process is never deleted, even by the process that previously owned that path. Marker release is equally token-guarded. Locks are released in normal success and caught-failure paths; recovery from abrupt process termination relies on the dead-owner rule above, not on cleanup code running after a forced kill.

Every successful state write rereads the latest state while holding this authoritative lock. From that locked state generation, the bridge resolves the Toolkit source again and rebuilds adapter payloads, checksum, discoveries, target plans, skipped-target context, manifest inputs, and related report context before writing. Pre-lock derived values are audit-only and are never combined with a later locked state in a committed snapshot. The write preserves unrelated top-level and forward-compatible fields, updates only the running source in `bridge_versions_by_source`, and preserves every other recognized source entry. `hub_version` is then calculated as the maximum of its existing valid value and every valid per-source value, so an older source run or forced same-source downgrade cannot lower the compatibility watermark. Staged hub replacement remains atomic and crash-safe under the existing transaction.

An active `--write` run persists this prepared source state after it acquires the lock even when no target, repo, cache, or report action is needed. Report eligibility is evaluated only after that first snapshot; report metadata causes a second snapshot only when a report is actually created. A fully disabled hook remains a deliberate early no-write return when repo auto-update and auto-sync are disabled, or when no enabled target or maintenance action makes the hook active. Lock contention also remains a visible hook skip and does not claim that an unpersisted source version was recorded.

Downgrade enforcement is source-scoped. A running bridge compares itself only with `bridge_versions_by_source[sync_source]`; a newer repo, Codex, or Claude Code entry never blocks another source. `--force-downgrade` bypasses only that same-source comparison and updates only the running source entry. New bridges never use `hub_version` for downgrade enforcement.

Old state migrates lazily. When a valid legacy `hub_version` has one recognized `last_sync_source` and no usable per-source history, only that attributed source is seeded. Missing or unknown attribution seeds nothing, so an unattributed legacy watermark cannot cross-block a recognized source. Once any usable per-source history exists, `hub_version` is not used to infer a missing source entry. Arrays and other non-map values are treated as absent; unsupported and prototype-polluting keys are discarded; invalid values assigned to recognized source keys fail visibly instead of silently weakening same-source protection.

In hook mode a genuine same-source rollback skip is printed to stdout with source-specific remediation. For `claude-plugin`, Claude Code runs the installed copy in place from the managed checkout, so a newer record means another Toolkit copy, such as a test candidate, ran a session here before Toolkit 3.2.0; the message gives the one-time `--force-downgrade` command that clears it, or `setup toolkit` to install the newer version. For `codex-plugin`, run `setup toolkit` in Codex. For `repo`, update or restore the managed Toolkit source checkout.

### Mixed Cache Rollout

Codex hooks execute the bridge copy in Codex's installed plugin cache. Claude Code runs Toolkit in place from the managed checkout (measured on Claude Code 2.1.304 and 2.1.306; see Claude Code Install Check), so its hooks use whatever that checkout holds. A source patch or one refreshed Codex cache does not repair the other host's copy. During rollout, a new Codex cache may write per-source state while an older Claude Code bridge still uses the legacy global `hub_version` guard; that older bridge may continue to self-block until the managed checkout holds the fixed bridge. The issue is fully resolved on a machine only after the Codex cache and the managed checkout both have the fixed bridge.

Required post-merge refresh flows:

- Codex: run `setup toolkit` in Codex.
- Claude Code: run `setup toolkit --host claude-code` (or `setup toolkit` from Claude Code), then start a new Claude Code session. With automatic updates on, the next session start updates the managed checkout without this step.

The bridge remains pull-on-session-start: GitHub pushes to the configured branch are picked up by the next native hook run or explicit `--repo-update-now`; the Toolkit does not run a GitHub webhook listener or background push daemon.

When a native SessionStart hook runs and repo auto-update is enabled, the bridge:

1. Acquires the Toolkit bridge lock.
2. Validates `repo_path` exists and is a Git worktree.
3. Reads the current branch and validates `origin` matches `repo_remote`.
4. Refuses to continue when the working tree is dirty, leaving the current branch and local changes untouched.
5. If the clean configured checkout (setup configures only the managed clean checkout) is on a different branch, switches it to `repo_branch` with `git switch <repo_branch>` and records that auto-switch in the update report.
6. Fetches `origin <repo_branch>` into an invocation-owned ref and resolves its commit once.
7. Checks that resolved commit is a fast-forward, updates only with `git merge --ff-only <sha>`, and removes only the invocation-owned ref. A failed ref cleanup produces a warning and preserves the update result or original error.
8. Runs hook-light validation:

```powershell
node repo/scripts/validate-toolkit.cjs
node --test repo/tests/toolkit-local-bridge-hook-light.test.cjs
```

9. Checks the running host's native plugin cache state against the configured repo source. When Codex is the running host and `codex_plugin_auto_refresh_enabled` is true, the trusted `main` hook refreshes only the Codex Toolkit plugin cache through `repo/scripts/setup-codex-toolkit-plugin.cjs --write --json --repo-root <repo_path>` after repo validation and before the delegated hub sync completes, so a stale Codex cache can still be refreshed when that later step fails safely. Claude Code hooks run the Claude Code install check instead (see Claude Code Install Check) and do not mutate Codex or Claude plugin caches from the opposite host.
10. Delegates the hub sync to the freshly updated repo script with `--skip-repo-auto-update`, so the hub records the updated bridge version.

Before the repo-update work, the same startup hook also runs a passive repo-local instruction preflight against the current working directory. For Codex it checks `AGENTS.md`; for Claude Code it checks `AGENTS.md` and `CLAUDE.md`. The preflight reads only the expected files and bundled repo-local templates, verifies `AI-AGENT-TOOLKIT` managed marker structure, compares expected managed block content, and never writes repository files, creates backups, or performs repair. It is silent outside Toolkit-managed git roots: a root counts as managed only when one of the expected files carries an `AI-AGENT-TOOLKIT` managed block, or when hub state names it as the managed Toolkit checkout. Inside a managed root it prints at most one neutral line, chosen by direction: when the repository rules may come from a newer Toolkit than the running copy (a newer recorded Toolkit version, or a newer Toolkit source checkout), the line says the repository rules are authoritative and Toolkit can be refreshed when convenient; when no newer Toolkit is known on this machine, the line says the repository rules differ from the running Toolkit's templates and offers a refresh with `repository-agent-rules`. The line never asks the agent to halt or to question the user. Each line is shown once per (root, running version, finding digest); the record lives in `agent-rules-notices.json` beside the hub snapshot directory, so resume, compact and later sessions with the same finding stay quiet, including when auto-sync or repo auto-update rewrite the snapshot.

The delegated repo script builds the target payload from the updated local Toolkit repo `skills/` tree plus the small `ai-agent-toolkit` adapter skill. It must not use Codex or Claude private plugin caches as the skill payload source.

The delegated command shape is:

```powershell
node <repo_path>/repo/scripts/toolkit-local-bridge.cjs --sync-enabled --write --sync-source repo --hub <same-hub> --skip-repo-auto-update
```

The hook validation is intentionally lighter than `npm run validate:all` so SessionStart stays short. Run full validation manually before release, merge, or broad maintenance changes:

```powershell
npm run validate:all
node --test repo/tests/toolkit-local-bridge.test.cjs repo/tests/toolkit-local-bridge-codex.test.cjs repo/tests/toolkit-local-bridge-claude.test.cjs
```

Repo auto-update never runs `git pull`, merge commits, rebase, package installs, marketplace installs, credential writes, `n8n_live` actions, or arbitrary project-repo mutations. Codex native Toolkit cache refresh and exact supported n8n Skills hook reconciliation run only after the user enables Codex plugin cache auto-refresh. If validation, fetch, fast-forward, delegation, native cache refresh, or n8n hook reconciliation fails in hook mode, the hook prints or reports a concise warning, records the last status when possible, and exits successfully so agent startup is not blocked.

Meaningful work means at least one of:

- The configured Toolkit repo fast-forwarded.
- The configured Toolkit repo was already advanced before the hook run compared with the last recorded bridge update state. This is reported as an inference, likely from a manual pull or another local Git update, not as proof of a manual action.
- Delegated repo sync failed.
- Hook-light validation failed after a repo update.
- Repo auto-update auto-switched a clean non-configured branch back to the configured branch.
- Repo auto-update skipped safely because the tree was dirty, the remote did not match, branch switching failed, fetch failed, or the fetched commit was not a fast-forward. Dirty-checkout reports should name the configured Toolkit source path and suggest finishing or stashing those changes, or rerunning `setup toolkit` to use the dedicated clean managed `main` checkout for startup updates.
- The Codex native plugin cache is stale relative to the configured repo source, was auto-refreshed, or failed auto-refresh.

Normal no-op hook runs with the same observed repo commit and no stale plugin cache, skip, or validation issue do not write or open a report. Meaningful reports are also deduplicated by event signature: if a later hook sees the same repo status, target-sync result, native plugin cache status, and checksum, it does not create or open another timestamped report. In hook mode, the bridge prints only:

```text
Toolkit updated: <report path>
```

The report starts with a short `TL;DR` section for the triggering source (Codex plugin hook, Claude Code plugin hook, or manual/repo run), repo status, and any action needed. Details include the new and previous observed commits, sync source, Singapore time (`SGT`), a Repo Update section with configured branch and configured remote, changed files from the fast-forward or already-advanced observed range when available, the explicit live n8n skip note, repo update status, hook-light validation result, Codex native plugin cache status when checked, checksum, and any warning/error. If auto-update finds a clean local Toolkit repo on the wrong branch, the report says it auto-switched back to the configured branch. If the repo is dirty, the report explains that dirty local changes prevent auto-update and the hook leaves the current branch and changes untouched. For the default production configuration, this shows configured branch `main` and configured remote `https://github.com/weijunswj/ai-agent-toolkit` so users can see whether updates are coming from GitHub `main`. The latest report path is stored in hub state as `last_update_report_path` and appears in `--audit`.

For first-restart compatibility after a bridge update, an older installed native hook may fast-forward the configured local Toolkit repo and then delegate into the newly updated repo script without passing `--hook`. An unsuppressed delegated command with `--sync-enabled --write --sync-source repo --hub <same-hub> --skip-repo-auto-update` is report-eligible. When hub state contains `last_repo_update_from_commit`, `last_repo_update_to_commit`, and `last_repo_update_status`, the delegated repo script uses that stored metadata plus a local `git diff --name-only` over `repo_path` to populate the update report. New parent hooks pass `--suppress-update-report` to delegated sync so the parent hook remains the single report writer and duplicate reports are avoided.

Meaningful update reports are enabled by default and can be persisted with `--enable-update-reports` or disabled with `--disable-update-reports`. A central deterministic classifier marks each report as `action-required`, `successful-activity`, or `no-op`. Action-required reports open automatically; successful reports remain closed; true no-ops create no report. `--open-update-report` remains an explicit one-run request for the current report. Legacy `--enable-update-report-open` and `--disable-update-report-open` are compatibility aliases for failure-only behavior and cannot restore all-success opening. On Windows, opening uses only `notepad.exe <reportPath>` and only for files created under the Toolkit temp update-report folder.

During `setup toolkit`, report creation and retention remain in the upfront wizard. Existing `update_report_open_enabled=true` is explicitly migrated to action-required-only behavior, and the setup proposal states that failures open while successes stay closed.

Toolkit-managed update reports/logs older than the configured retention window are cleaned up best-effort on setup and hook/update runs. Default retention is 7 days and can be configured with `--update-report-retention-days <positive-integer>`. Cleanup also caps retained files to the newest 200 Toolkit reports inside the retention window. Cleanup only considers Toolkit report filenames under the Toolkit-managed update report/log directory, never arbitrary user files, and never treats cleanup failure as a setup or startup blocker. Setup and audit summaries include retention days, max retained reports, deleted count, skipped/error count, and the report/log directory path.

Codex plugin cache auto-refresh is included in the setup checklist. Codex may refresh only the Codex Toolkit native plugin cache from the managed `main` checkout. Claude Code runs its own install check (see Claude Code Install Check) and does not let Codex mutate Claude Code cache.

## Auto-Check, Auto-Setup, And Auto-Sync

Autocheck is allowed. Autosetup is forbidden.

- The bridge writes into no app; there is no target to detect or enable.
- Auto-sync enabled: native hooks record the running source version in the hub and may run repo-backed auto-update.
- Auto-sync disabled: hooks may print a concise reminder or do nothing.

## Cloud jobs

Some scheduled jobs run on GitHub instead of on a computer. `repo/contracts/cloud-jobs.json` lists each one: its workflow, schedule, the computer job it replaces, and the installation tokens it mints from the governance GitHub App (see Governance GitHub App above), one per repository. Each token names only which of the App's permissions it takes, at the App's level unless the row marks it read-only, so the App's permission list, their names and levels are kept in one place, the App's own setup. No personal token is used. `toolkit governance check` lists each job and its tokens beside the App's setup lines, and the permissions never to give: administration, secrets, workflows and account. Agents never create Apps, keys or secrets.

The programme sweep (`.github/workflows/toolkit-programme-sweep.yml`) runs after every push to main, when started by hand, and when its gate (`.github/workflows/toolkit-programme-sweep-gate.yml`) starts it. The gate runs every hour at minute 41 (GitHub delays and can drop scheduled runs at busy times, the start of every hour most of all) when a person opens, edits, closes or reopens an issue, adds a comment, or opens, updates, closes or reopens a pull request into main, and when a Validate run finishes. With only the built-in token it reads the binding merged on main, the sweep's recent runs, the board line on each parent issue, and whether any issue or pull request changed or a Validate run finished since the last successful sweep finished (a finished CI run changes no issue's update time), then either ends in seconds or starts the sweep on main. It starts it when no sweep has finished yet, when the board line shows the last pass left a saved place (once GitHub's hourly App limit has reset, if that stopped it), when anything changed since the last sweep finished (the sweep's own edits land before its run finishes, so they never count), or when six hours have passed. A start from activity waits until an hour after the last sweep. Activity during a running sweep queues one more run behind it, since the running pass may have read past the change, unless that run's follow-up job is already waiting to start the next one; nothing starts while a sweep is already queued. A pass that starts with GitHub's hourly count for the App already at the margin reads and draws nothing, keeps the saved place and changed-since bookmark, ends green with a paused note in the run summary and follows up once the limit has reset (at most once an hour), so changes made just before it are not left for the six-hour refresh. Activity from bots, the sweep's own App included, is ignored before a runner starts. The gate checks out only its own script from main, reads the binding merged on main and never sees the App's key or tokens. A pass that reads something and still leaves tasks starts one follow-up run itself: an hour and a minute after it began when GitHub's hourly App limit stopped it, at once when its own time limit did. On a private repository a pass stopped mid-way at the App limit gets no waiting runner, because that costs paid minutes; the hourly gate resumes it from its board note once the limit resets. A pass that found the limit already at the margin leaves no note, so it keeps its one follow-up. The follow-up still runs when the footer step fails, and after its wait it starts nothing when another sweep is queued, running or started after its own run. It holds only the built-in token, allowed to read contents and start workflow runs, and waits outside the sweep's one-at-a-time group, so the run after a merge is never held back. A GitHub blip in the gate or the follow-up (a 5xx, a 429 or a dropped connection) ends that run green with a notice, and the next start tries again; a missing token or repository, a 401, 403 or 404, and any other error still show red. The run after each merge keeps the board current when an hourly start is dropped. The push run starts only for main, never for pull requests or forks. It checks out the run's own commit without saved credentials, and its built-in token can only read contents. Its first step stops a run whose ref is not the default branch (a manual run can pick any branch or tag) with one warning naming the ref and the branch, so no App token is minted and nothing is edited. It then reads the evidence store from the checked-out binding. With no App variable it writes a notice and stops. It also stops with a notice when the store belongs to another owner or the state lives on a public branch, which this cloud sweep does not run yet. It then mints two tokens. The governed repository token gets issues and pull requests write, and contents, checks and commit statuses read. The evidence store token gets contents, issues and pull requests write. Only the refresh step receives the tokens. Each token reaches only its own repository: any other request is refused, and GitHub's signed-in user is never asked. Before reading anything else, the refresh checks that each token lists exactly its one repository. It also checks that the binding merged on the default branch was read at the run's own commit; if main moved meanwhile, it stops with a notice. A failed sign-in fails the job with a fixed message naming the variable and the secret, without GitHub's own text. The run summary shows the requests used and the cap, the tasks read, the tasks still queued and whether the pass completed. After the refresh the run cleans the "Generated by Claude Code" footer the cloud GitHub route adds, from posts the repository owner wrote in the governed repository and its evidence store, each under its own token. It reads posts changed in the last 26 hours, or since the time a manual run gives as `footer_since`, re-reads each post before editing it and reads the edit back. Only counts reach the run summary, never a post, its link or its text. Footer cleaning runs only after a refresh that ran on the run's own commit: when the refresh skips or fails, the footer step does not run and edits nothing; the refresh's own warning, notice or failure says why. A run that stopped at GitHub's hourly App limit skips footer cleaning, so it never spends the safety margin. GitHub may refuse an App's edit of a review body; those show as a warning and wait for a manual clean, while any other failed edit or read-back fails the step. A pass works for up to 50 minutes with no request cap of its own: it reads until GitHub's remaining hourly count for the App reaches the safety margin (a tenth of the hourly limit GitHub reports, never under 200, kept for the repository's other governance jobs), then saves where it got to, and the next run resumes, changed and new tasks first. It is killed at 55 minutes and the job stopped at 58, so it ends before the next hourly start.

Other governed repositories get the same two workflows from `node <toolkit>/repo/scripts/toolkit-cloud-workflows.cjs --repo <repo>`, which the repository rules install or refresh runs while governance is on. The pull request that turns governance on always carries them, rendered fresh next to the binding and pinned to the Toolkit checkout's own commit, which must be on its main branch (keep the checkout current so the pin is recent) (a version 1 binding moves to version 2 in the same pull request); when they cannot be rendered there, it keeps any existing copies and Toolkit prints the reason and the fix. The pull request that turns governance off removes both copies, only files carrying the Toolkit's rendered-copy marker (its read-back accepts no other removal), and `toolkit governance check` reports a copy still there once governance is off. Each copy is the Toolkit's own file pinned to the Toolkit commit it came from. It checks the public Toolkit repository out at that commit into `.toolkit/` and runs the scripts from there, while the binding and the working folder stay the governed repository's own. The gate follows the repository's own CI workflow when one is named with `--ci-workflow`, and otherwise leaves out the CI trigger. A later refresh keeps that CI workflow while it is still there, and otherwise drops the trigger. The installer pins only a commit already on the main branch of a checkout whose origin is the Toolkit repository. It refuses a Toolkit source checkout, a default branch other than `main`, and a same-named file that is not a Toolkit copy. `toolkit governance check` reports a missing or hand-edited copy as drift, and notes one that differs from what a refresh writes now (an older Toolkit commit, an action pin or the CI workflow it follows), which the next rules refresh updates. To tell such a copy from a hand edit whose hash was recomputed, it re-renders the copy at its own Toolkit commit, with the CI workflow the copy names, when the checkout has that commit and the render file (`repo/scripts/toolkit-cloud-workflows-render.cjs`) is unchanged since, and compares; otherwise the copy's hash is all it checks. Renaming or removing the CI workflow the gate follows makes its copy outdated, not edited. A Dependabot bump of an action's pinned version counts as an older copy, not a hand edit. The copies keep the Toolkit file's header comments, which are worded to hold in both places. Shard Timings is not copied, because it needs the Toolkit's own test-shard manifest and run summaries. The computer's PROGRAMME SWEEP task stays on until the owner retires it. Both use one lease in the evidence store, so only one sweep writes at a time; the other prints "another sweep is running", writes nothing and leaves no stop to report. A sweep renews its lease while it works, so a pass of up to 50 minutes keeps it; while it saves its state, the renewal rides that one commit. A run stopped by its timeout stops renewing, and its lease expires within twenty minutes and never after the run's own kill time, so the next hourly sweep reports where it stopped. A pass that ends with an error records its stop in the lease when no note on the computer holds it, so the next sweep on either host reports it.

## Windows Scheduled Tasks

Setup covers this computer only: it prints no task plan for any one repository. The separate scheduled-task approval row lets the owner permit updates; with that saved approval setup runs the computer-wide task update, and without it setup creates no tasks. Direct `node <Toolkit>/repo/scripts/toolkit-windows-tasks.cjs plan --repo-root <repo>` supplies one repository's detailed read-only plan and eligible apply command. `<Toolkit>` is this computer's recorded managed Toolkit checkout; `<repo>` is the target repository's main checkout, never a linked worktree. Fixed PROGRAMME SWEEP and SHARD TIMINGS qualify in ENABLED repositories with verified merged bindings; FOOTER SWEEP qualifies only for a verified github.com origin with fresh matching disabled or confirmed absent governance. Use the binding's task folder, else the repository default. A fresh confirmed governance change allows `apply` to switch a proven owned cleaner in the same folder and checkout, carrying its earlier valid scan boundary. Apply reads back selected registrations before the first cleaner run. Repository, checkout and Toolkit-copy changes, owner stops, disabled or unprovable participants and unpaired cleaners hold. A modified proven-owned PROGRAMME SWEEP or SHARD TIMINGS task needs the owner's keep-or-replace answer for that exact observation each time. Removal, same-job recovery with `apply --repair-owned`, folder overrides and custom definitions need explicit approval naming targets and changes; native denials remain stops. For the managed Toolkit checkout:

```powershell
node "C:\Users\<user>\.ai-agent-toolkit\source\ai-agent-toolkit\repo\scripts\toolkit-windows-tasks.cjs" apply --repo-root "C:\Users\<user>\.ai-agent-toolkit\source\ai-agent-toolkit"
```

It registers and independently reads back the selected jobs, recording their repository, canonical checkout and Toolkit paths and enrolled definitions in `~/.ai-agent-toolkit/user-state/tasks.json`, before starting a new or changed cleaner sweep once (once more if a closing console stopped it, 0xC000013A). It calls the cleaner healthy only when its own last-run record says it ended well. The local session checks the command result and reads back `toolkit-tasks.cjs`; the first sweep can take up to ten minutes. Registration alone is not a completed first run; failed, held, skipped, missing or unfinished results are not proof of success.

- **Tasks:** new enrolments with enabled verified merged governance create and read back PROGRAMME SWEEP, then create or verify SHARD TIMINGS. `<FOLDER> - PROGRAMME SWEEP` runs hourly for 24 hours from minute 01-09, assigned per repository on this computer: own-post footer cleaning first, then programme refresh and attention with fresh matching enabled governance. Fresh matching disabled governance or confirmed binding absence on a verified github.com origin selects FOOTER SWEEP for a new enrolment, with the same hours and own-post cleaning. A fresh confirmed governance change lets `apply` switch the proven owned cleaner shape in the same folder and checkout while carrying its earlier valid scan boundary. Preflight every participant before effects; when enabling, register and read back PROGRAMME SWEEP, retire FOOTER SWEEP, then create or verify SHARD TIMINGS last. When disabling, register and read back FOOTER SWEEP, retire PROGRAMME SWEEP, then remove owned SHARD TIMINGS last. Stale enabled matching bindings remain eligible for PROGRAMME SWEEP and SHARD TIMINGS, but stale or uncertain status never authorizes a shape switch or a new FOOTER SWEEP. Uncertain reads grant no new FOOTER SWEEP or shape switch, withhold store/programme effects, and leave origin cleaning at its current scan boundary. A modified proven-owned PROGRAMME SWEEP or SHARD TIMINGS task needs the owner's keep-or-replace answer for that exact observation each time. Missing history starts at 48 hours; damaged history reports a bounded fallback, and future history names a clock anomaly. Older posts may need separately authorised full-history cleaning. `<FOLDER> - SHARD TIMINGS` runs on Mondays at 08:01-08:09 in the computer's local time, using the same repository minute, and checks that repository each time. Only an existing repository with no shard manifest reports `no shards yet`; it changes no repository or external state and is a quiet expected skip. Missing or non-repository roots fail visibly. When the manifest becomes available in the registered checkout, timing starts automatically through Toolkit's fixed refresher with `--repo-root <checkout> --open-pr`, after fresh enabled governance and sign-in checks. It uses the Toolkit shard manifest and Validate summary contract (the `Validate` workflow on `main`, with `test-summary-*` artifacts); other CI formats need that contract before timing can work. A pull request opens only when shard times drift. All fixed jobs run `repo/scripts/toolkit-scheduled-job.cjs`, which starts only node and gh and records each run in `~/.ai-agent-toolkit/user-state/tasks/<id>/last-run.json`.
- **Folder and names:** the folder is the binding's `schedule_folder` (`TOOLKIT` here), else the repository name in capitals. Names are `<FOLDER> - <TASK>`; Windows keeps each task as a file, so a name never holds `\ / : * ? " < > |`.
- **Ownership:** a task is Toolkit's only when it sits in that folder, its Description carries `[toolkit-task v1 id=<id> def=<digest>]`, and its non-adopted registry entry agrees on id, folder, name and repository. Ordinary apply also requires the same canonical checkout and Toolkit runner, and an intact enrolled action, trigger, principal and settings baseline. Toolkit lists every other task and never changes it, including the root folder's n8n backups and a same-named task of your own.
- **How they run:** as you, only while you are logged on, with no stored password, through `conhost.exe --headless` so no console window opens. A second start while one runs is ignored, and each run stops at 30 minutes. A headless console host does not pass the job's exit code to Task Scheduler, so the job's result is in its last-run file.
- **Skipped and held runs:** a run that cannot start its work exits 0 and Task Scheduler shows success, so the last-run file says why and counts the skips in a row. A held run also exits 0, with its holds reported in that file. Only an explicit signed-out answer from `gh auth status` proves sign-out. Other authentication failures defer visibly; a confirmed offline cleaner retains its offline skip history, while weekly work stays deferred. While the sweep is held, skipping, has failed, or has not run for over 2 hours inside its hours, the session-start line of that repository on this computer adds `Programme sweep: ...; see toolkit tasks.`, and `toolkit tasks` shows the recorded status, reason and count. Expected `no shards yet` skips have no growing count or recovery streak. The first good run after other skips notes `Resumed after N skipped runs since <time> UTC.` Other computers see the last shared health file, including its timestamp; an offline computer cannot publish a new result.
- **A task you made yourself** can be recorded so the list shows it as known: `toolkit-windows-tasks.cjs adopt --folder <F> --task <name> --id <id> --purpose <text>`. Toolkit never changes or removes an adopted task.
- **List every task:** `node repo/scripts/toolkit-tasks.cjs [--json]`, read-only: Windows tasks live from Task Scheduler, Claude Code desktop tasks live by name and description, and Codex and cloud tasks from the registry, marked "from record, not checked live".
- **Remove:** `node repo/scripts/setup-toolkit.cjs --remove-toolkit-tasks` scopes removal by the verified primary checkout origin and matching non-adopted registry repository, including legacy enrolments without a recorded checkout and moved checkouts, writes and reads back a durable `stopped by owner` record before unregistering, and removes the folder only when nothing else is in it. It does not remove another repository's tasks. A worktree, subdirectory or projectless invocation does not widen or redirect removal; use the target's main checkout. Failed stop persistence prevents removal; failed unregister leaves the stop and reports that the live task may remain. Enrolment and baseline stay recorded across repeated removal and CLI restarts. `plan` and `toolkit tasks` show the stop even with no live task, and ordinary apply refuses recreation. Only an explicitly approved repair clears it after scheduler readback.

The daily TASK HEALTH job runs once per computer at its assigned minute between 07:51 and 07:59. Its minute comes from the stable computer id, independently of repository minutes. Its registry row has no repository or repository minute; approved updates repair older mixed rows. Repository removal leaves it alone. It uses the same task reader as `toolkit tasks` and reports missing or disabled tasks, edited definitions, missed slots, three or more unexpected skips, failed results and older task code. Owner-stopped jobs appear as stopped without alerts, and stopping TASK HEALTH suppresses stale-file and sharing reminders. Its path-free report is kept locally before sharing. Each enrolled repository with a freshly verified enabled binding to a private writable store has its results secret-scanned and written to that store only, with compare-and-swap plus readback at `task-health/<computer label>.json`; a store never receives another repository's results, and repositories without their own verified store stay local. A busy store waits within the health job's remaining deadline; a failed write retains the local report and a safe failure reason. Neutral labels are derived from the stable computer id. The existing session task line includes the cached flags, or `health file not shared: no verified evidence store`. Health reads other computers' files and lists duplicate ownership once per repository. The programme lock remains local to each computer; it does not serialise different computers' writes.

`toolkit-windows-tasks.cjs start --task <id>` starts one of Toolkit's own recorded tasks now. It refuses an adopted task, a task the owner stopped or turned off in Task Scheduler, an unrecorded id, a task that no longer carries Toolkit's marker, and a task whose live definition no longer matches the one Toolkit enrolled (edited by hand, or recorded before Toolkit kept that definition).

### Permission blocks and cleanup

`toolkit permissions` routes to `node <Toolkit>/repo/scripts/toolkit-permissions.cjs`. It prints the paste-once permission blocks and writes nothing; the owner pastes them, no agent does.

- **Owner shortcut:** `node <Toolkit>/repo/scripts/toolkit-permissions.cjs --apply`, typed by the owner in their own PowerShell or terminal (`--host claude` or `--host codex` for one app). It lists what would change, waits for the typed word `apply`, then for each app copies the file to a timestamped backup next to it, writes the merged file through a temporary file and reads it back. Claude Code's user settings keep every other key and line; missing block lines are added and stale Toolkit lines are reported, never removed. Codex's `toolkit.rules` is Toolkit's own file and is replaced whole; Codex is skipped when it has no settings folder. A file that is not a JSON object, or that changed after the preview, stops with nothing written. Only the computer blocks: the repo block is still pasted by hand. To undo, copy the backup back.
- **Agents never run `--apply`:** the rules forbid it, and the only hard block is the app's own: every computer block holds an ask line (Claude Code) or a prompt rule (Codex) for the exact command, and `--apply` must be the first argument so the Codex rule matches. A command written another way, such as a different interpreter form or a script that loads the file, matches neither. The command also refuses in a shell a coding agent started (the same exact markers `toolkit env show` refuses on) and without a terminal on both ends, but those are speed bumps, not locks: a process that clears the markers and fakes a terminal gets past both.
- **Older blocks:** blocks pasted before this command existed allow `--apply` with no ask. `--check` lists the missing ask line, and `--apply` adds it.
- **File layout:** the settings file keeps its permission bits, indent, line endings and byte order mark. A link to a missing file stops with nothing written.

- **Computer block:** for the app's user settings, once per computer. Toolkit's own reversible commands only, each pinned to the managed checkout's full path and one subcommand, plus the evidence store command (`toolkit-store.cjs`, below), which checks every store step itself. It names no repository.
- **Repo block:** for a governed repository's local settings, once per repository: pull request and issue comments. No block holds a raw `git push`.
- **Coverage:** every line maps to the guard that still checks it, and the print lists them. A line ends in a wildcard only where the script behind it checks its own arguments. The task list and the task update command are exact lines, so recording or forgetting a task and a run that carries an answers file still ask. Ask lines keep a same-job task repair, a folder override, a skipped first run, a keep-or-replace answer and a comment delete asking. Nothing checks a comment's target or words; the footer checks read only the footer.
- **Never printed:** merges, closes, deletes outside the cleanup and store commands, raw git pushes, history rewrites, settings edits, secrets and real keys, the controller takeover command and task removal.
- **Codex:** a Codex rule allows anything after its prefix and cannot ask for a flag. Comments, task apply, the task list and the task update command are therefore printed as prompt rules for Codex, and only the commands that check their own arguments are allow rules. The store command is one allow rule and no rule prompts for the store: when rules match, Codex takes the strictest, so a store prompt rule would ask on every step. An allow rule runs the command outside the sandbox, which is what a store checkout outside the workspace needs.
- **Limits:** a line matches the command text, so agents write each command as its line shows. On Windows, Claude Code reads a repository's local settings from the folder the session starts in, so a session started inside a worktree does not see the repo block; the computer block applies everywhere. Cloud sessions read neither block. The Codex rule files (`--host codex`) are printed for checking with `codex execpolicy check` and are not yet proven on a real Windows install.

`toolkit store` routes to `node <Toolkit>/repo/scripts/toolkit-store.cjs <subcommand> --store <store checkout>`, run from the governed repository or with `--repo-root`. Every evidence store step on a computer goes through it, so one line per host covers them all. A raw `git push` to a store that an enabled binding cached on this computer names (a delete included, a dry run excepted) is refused by the shell hook on Claude Code and Codex, pointing at `save`; other raw `git` in the store still works. It reads `cd`, `pushd`, `Set-Location`, `Push-Location`, `git -C`, `--git-dir`, a `GIT_DIR=` prefix on the same command, `--repo`, a URL and nested shells. Not read: a folder held in a shell variable, a `GIT_DIR` set by an earlier statement (`export`, `$env:`), git aliases and programs that run git themselves. A computer or cloud container with no cached binding is not judged, and a push the owner types in their own terminal is never seen.

- **Pre-flight, every subcommand:** the merged binding on this computer is enabled, fresh and names a GitHub store and branch; `--store` is the top of a checkout whose fetch and push addresses are all that store, on the bound branch; the checkout's own config holds only plain keys (no push rule, mirror, URL rewrite, proxy, credential helper, filter or hooks path), and the global or system config holds nothing that widens a push; the checkout is a full clone; GitHub shows the store private, writable and with the bound branch as its default. Git is run by its full path from `PATH`, without the caller's `GIT_*` variables (the ssh ones excepted), with hooks pointed at an empty folder the run owns, pathspec magic off, and no grafts, replace refs or commit-graph file. Any failure writes nothing.
- **Subcommands:** `status` reads; `sync` fast-forwards only; `save --path ... --message ...` stages only the named paths under the binding's store path, `archives/` or `evidence/` (never a deletion), secret-scans exactly the staged content (a file over 5 MB, binary or not UTF-8 is refused), commits, pushes the bound branch with a plain push and reads it back, merging the remote once with a merge commit if it moved; GitHub's compare must show the old remote tip inside the new one. `move --from --to --message` uses `git mv` only; `merge-branch --branch --message` merges a store branch with a merge commit, refuses any deletion or file outside the same folders, and scans every blob in every commit it brings in; `delete-merged-branch --branch` deletes a remote store branch only when GitHub shows its tip in the bound branch, and only while that tip is unchanged. Other branches are fetched into a private ref namespace, and a branch named like the bound one in another letter case is refused.

## Remove Toolkit From This Computer

Uninstalling the plugin leaves behind what Toolkit put elsewhere on the computer, so `remove toolkit` has its own command. It removes nothing until the owner has seen the list and said yes.

```powershell
node "<Toolkit>\repo\scripts\toolkit-remove.cjs" plan
node "<Toolkit>\repo\scripts\toolkit-remove.cjs" apply --confirm <plan code>
```

- **Plan:** read-only. It lists, under one plan code: every task that carries Toolkit's marker in any Task Scheduler folder (including folders this computer has no record of), the folders that would be left empty, Toolkit's own task files under `~/.ai-agent-toolkit/user-state/`, the Toolkit block in each app's global rules file, Toolkit's `project_doc_max_bytes` line and helper limit block in Codex's `config.toml`, Codex's approval records for the Toolkit hooks (`[hooks.state."ai-agent-toolkit@ai-agent-toolkit-local:..."]` tables, which `codex plugin remove` leaves behind) and the empty Toolkit plugin cache folder, Claude Code's `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` when Toolkit set it, the helper agent files Toolkit generated in `~/.claude/agents` and `~/.codex/agents`, the skill folders it copied (the official n8n skills and the Antigravity copies), and the Toolkit folder `~/.ai-agent-toolkit`. It lists, as a warning only, each MCP server (Claude Code user and project servers in `~/.claude.json`, Codex `[mcp_servers.*]`) whose key helper runs `toolkit-env.cjs` from inside the Toolkit folder: its settings stay, but it gets no key until Toolkit is reinstalled, and the key stays in the credential store. It also shows the reinstall note it will save (see below). It also prints the uninstall lines for each app that still has the plugin (`claude plugin uninstall` and `claude plugin marketplace remove`, `codex plugin remove` and `codex plugin marketplace remove`) and the app screen to use instead. The plugin state is not in the plan code.
- **Apply:** needs `--confirm` with the plan code the owner was shown. The agent shows the list, asks for the owner's OK in the host's question UI, runs the plugin uninstall lines whose command line is on PATH, and then runs apply. If anything on the list changed since the plan, the code no longer matches and nothing is removed; run the plan again.
- **Removed:** Toolkit's own unchanged tasks, tasks that carry the marker with a lost record, and tasks the launcher disabled after Toolkit went missing, when they still match their recorded definition exactly; each task is read again just before removal, and one that changed in between is left alone and reported. A folder goes only once it is empty. The Toolkit block leaves each global rules file through the rules owner, with a backup first. Codex's `config.toml` gets back the line Toolkit replaced, or loses the line Toolkit added (a file Toolkit created for that line alone is deleted), then loses Toolkit's helper limit block through its owner; backups first, and Codex may then use its own higher helper default. Claude Code's subagent limit goes only while it holds the value Toolkit recorded. Helper agent files go only while they carry Toolkit's generated marker, read again just before removal. Skill copies go only where Toolkit's ledger records them. Codex's Toolkit hook records go only once the Codex plugin is uninstalled: `config.toml` is backed up to `~/.ai-agent-toolkit/backups/remove-toolkit/`, the tables are taken out, and Python's `tomllib` must read the new file as the old one without exactly those tables; without Python, or on any other difference, the file is left alone and the result says to remove the tables by hand. The plugin cache folder goes only when it holds no files.
- **Reinstall note:** saved first, to `~/.ai-agent-toolkit/backups/remove-toolkit/reinstall.json` (kept with the backups). It records the helper stack each app's Toolkit helper files named and the checkout and Task Scheduler folder of each removed Toolkit task; no keys. A later `setup toolkit` installs a noted helper stack only where no Toolkit helper file is installed (Claude Code at its install check, Codex at its helper step), and on Windows lists each noted checkout that has no Toolkit task on record with its exact `toolkit-windows-tasks.cjs plan` and `apply` lines. Setup never creates the tasks itself, whatever the scheduled-task standing approval says; the agent asks the owner. Each entry leaves the note once restored, and the note goes when empty. Codex setup also no longer treats leftover Toolkit hook records alone as an earlier install, so a computer cleaned by an older `remove toolkit` reinstalls without naming the old marketplace folder.
- **Toolkit folder, last:** only once neither the Claude Code plugin (its plugin registry) nor the Codex plugin (its `config.toml` entry and plugin cache) is installed, because an installed plugin reads its records there. Its own entries go: `source` (the managed checkout), `current`, `user-state`, `agent-control` and the skill and global rules records. `env` (the list of the owner's keys; the keys themselves stay in the computer's credential store), `backups`, `agent-control/backups` and anything Toolkit does not know are kept, and the folder goes only when nothing is left in it. While a plugin is still installed, the folder stays and the result says to uninstall it and say `remove toolkit` again, and prints the exact `node ... toolkit-remove.cjs plan` line for when the skill has gone with the plugin.
- **Kept:** a task changed by hand stays unless it is named with `--include <task id>` in both the plan and the apply. A task of the owner's own that Toolkit only lists is always kept. A setting the owner set to a value of their own, a file without Toolkit's marker, a hand copy of a skill, and a global rules file or `config.toml` with broken Toolkit markers are left alone and reported.
- **Never touched:** any repository, the env store and every key, and every app setting, agent, skill and file the owner made.

A second run finds nothing and changes nothing. On a system with no Windows Task Scheduler the plan says so and leaves the task records alone.


## Hook Policy

Hooks are optional automation. They must not contain unique critical policy.

The startup hooks call the shared updater. Toolkit helper hooks call the shared deterministic routing guard through native adapters:

- Codex hook source: `.codex-plugin/hooks/hooks.json`.
- Claude Code hook source: `.claude-plugin/hooks/hooks.json`.
- Shared policy source: this doc, `AGENTS.md`, Toolkit docs, and validators.
- Deterministic enforcement: `repo/scripts/toolkit-local-bridge.cjs` and tests.

The shared updater may run a passive repo-local instruction preflight from the hook path. That preflight is a notice-only freshness check for expected `AI-AGENT-TOOLKIT` managed blocks; it does not install, repair, back up, create, refresh, or rewrite repo-local instruction files, and it never blocks the current task.

Antigravity does not need Codex or Claude hooks to receive core policy because the policy remains in portable docs and validators.

The bridge uses `SessionStart` for update and sync. Codex registers `PreToolUse` for helper launches and shell calls with the matcher `^(?:Agent|[A-Za-z0-9_-]*spawn_agent|Bash|exec_command|shell|local_shell|PowerShell)$`, and its after-tool programme refresh for the same shell names; Claude registers the parent `Agent|Task` path. Codex documents its shell and exec calls as `Bash`; the other shell names are listed so a call reported under one of them still reaches the checks. In a 29 October 2026 test, Codex Desktop ran every command through its code-mode tool `exec`: that program reached no hook, and each shell call it made reached `PreToolUse` as `Bash` with a string `command`, no `workdir`, and the session folder as `cwd`. A 30 October 2026 test showed that `cwd` stays the chat's folder even when the program ran the command in another folder, such as a lane worktree, so the push check does not take it as the run folder (below).

Codex code mode delivers nested shell calls as `Bash`; Toolkit hooks refused nested calls on Codex 0.166 in November 2026. In the 29 October 2026 test above the outer JavaScript `exec` cell reached no hook; the capture planned to re-measure that on Codex 0.166 did not run, so it stays an accepted delivery gap rather than a settled fact. Codex may run PowerShell under that name, so the closure reader checks an alternate PowerShell reading when backslash quotes could hide a guarded GitHub write. Calls to `write_stdin` in an already allowed shell and opaque Desktop REPL code remain accepted delivery gaps. A fixture pack cannot tell whether Codex trusts a real plugin: every Codex gate launch first passes the installed `toolkit-codex-install-state.cjs --check` as the [host contract](HOST-CONTRACT.md) defines. Any bundle file change, including `.git`, can stop all plugin hooks until the owner approves them again in `/hooks`.

Codex names a hook tool `spawn_agent` only in its default namespace and in V1 (`multi_agent`). A V2 (`multi_agent_v2`) spawn reaches hooks under the flattened name `<namespace>spawn_agent` (`collaborationspawn_agent` for the default namespace), with no `Agent` alias, and Codex treats a matcher made only of names and pipes as an exact list. The earlier `spawn_agent|Agent` matcher therefore never ran for the V2 spawn seen in the 19 October 2026 native UAT. Codex accepts a configured `features.multi_agent_v2.tool_namespace` only as `[A-Za-z0-9_-]+`, so the registered matcher and the hook's spawn recogniser are one constant (`CODEX_SPAWN_MATCHER`) over that alphabet, hyphen included; a hyphenated namespace such as `multi-agent` is matched and held unless bound. Changing the matcher changes the hook hash, so an installed Codex needs the owner to trust the changed hook again. Codex V2 (`multi_agent_v2`) forks the full parent history unless `fork_turns` is exactly `none`; the guard treats any other value, or its absence, as a session transition. An admitted Codex request exits 0 with no output, because Codex records a bare `permissionDecision: allow` as a failed hook run. A denial exits 2 with the reason on stderr.

Both helper hooks first ask one shared predicate (`repo/scripts/toolkit-governed-repo.cjs`) whether the work is Toolkit-governed. It answers yes when a launcher marker is set (`TOOLKIT_GATE_ROLE`, `TOOLKIT_NATIVE_HELPER_BINDING` or `TOOLKIT_CLAUDE_TASK_PROFILE_SHA256`), or when the repository's governance state (`toolkit-governance-state.cjs`) is ENABLED with the governed rules binding. UNDECIDED, DISABLED (plain folders included) and incomplete repositories are not governed. The named-helper policies apply only in a Toolkit gate run, a session with a launcher marker; in a governed repository without one, both hooks follow the normal-folder rule, because the rules let the main session start subagents outside gate work. Outside a gate run the Codex hook makes no helper decision. The Claude hook allows every main-session launch with no decision. In a governed repository, or unless the stored Claude profile is `broader-native` outside one, it refuses an `Agent` or `Task` launch whose caller is a subagent or teammate (`agent_id` present) with a plain reason: "a subagent can't start another agent (one layer only). Do the work in this subagent, or hand it back to the main session." A missing, unconfigured or unreadable profile reads as root-only, so the refusal stays. `agent_type` alone no longer marks a subagent in these hook decisions, in a gate run or elsewhere, because Claude Code also sends it from a main session started with `--agent`. The launcher-bound checks (the native helper adapter, the Claude task session and the dispatch observer) still refuse on `agent_type`, but a `--agent` main session cannot reach them, because the gate session launcher refuses `--agent`. After a decision failure the hook still refuses a subagent caller with that reason; otherwise it gates only a gate run (a set launcher marker).

Governance gate. Toolkit splits what it does in two. Wherever the plugin is installed, the global rules apply in every folder: the coding gates (G0, G1, G2), subagent limits, routes, safety rules and the portable skills. GitHub governance is the part that needs a github.com repository: parent and child issues for programme tracking, records and decision traces, a private evidence store, the governed rules block and the no-force-push ruleset. Only GitHub governance is switched per folder, and each folder is in one of three states:

- **No git** (a plain folder, for example a project folder on the desktop): DISABLED automatically, never held and never asked. Nothing is written into the folder.
- **Git, but not on github.com** (no origin remote, more than one origin URL, or another host such as GitLab): DISABLED automatically, with no question, held message or governance work refusal. Status keeps the identity reason. The global rules and coding gates still apply. If a GitHub origin is added later, the normal github.com question applies.
- **Git on github.com:** only the valid programme file merged on origin's default branch decides enabled or disabled, on every computer. Fresh confirmed absence, with no open proposal, holds and asks yes, no or later. Yes and no create a run-bound pending answer, then one decision pull request. No uses the minimal disabled file and needs no programme setup. Yes reuses the adoption proposal and asks only for missing parent, separate private store and required checks. After publication and readback, show the effects and checks and ask the owner to merge it immediately. Neither the answer nor proposal activates governance. Later makes no repository decision, releases this run and asks next chat.

How the question is shown depends on the host:

- **Claude Code:** a tap-to-answer card (Yes, No, Later) with the same three lines as text above it, so the question is seen even where the card is not drawn and the user can type the answer. A hook's own hold message is not shown in the mobile app or Remote Control, so Claude Code does not block the held message: the turn runs, but only to show the card. The message itself stays held and comes back after the answer, as with a typed one, and the instruction Claude gets says not to act on it. On that turn every other tool, read-only ones included, is refused, except loading tool definitions. The card must be exactly Toolkit's, with no answer filled in by whoever called it: Claude Code itself drops an answer the model fills in before the card is shown, and Toolkit's tool gate refuses such a call too. The tool gate notes each card it lets through, and the tapped answer counts only for a noted card, once, in the same run of the session that was asked, with the same checks as a typed answer. A dismissed card, or a typed "Other" answer on it, records nothing, and the next message asks again. Typing `yes`, `no` or `later` still works. A session with no session mark, one another session or a launcher started, a host that sends no session id get the text hold instead. Claude Code's hook input does not say whether a run is headless, so a `claude -p` run, and a resumed or forked run, get the card turn too: the held message reaches Claude with the instruction not to act on it, every tool but the card is refused, and nothing is recorded there (`claude -p` offers no card, and a resumed or forked run is a new run, so its answer counts only once it is asked again).
- **Codex:** the three lines as text; Codex has no card a hook can ask for.
- **Claude Projects thread (a Remote Control session):** the user answers by replying in the thread. Toolkit accepts only an eligible direct owner mention in a complete envelope, without attachments or decoded frame markup. The delivery needs a bounded id and a timestamp at or after the question, compared in whole seconds, no more than a day old and at most 2 minutes ahead of this computer's clock. Its hashed id stays spent across sessions for 24 hours and 2 minutes, covering the message lifetime and clock tolerance; capacity holds new deliveries instead of discarding live receipts. Merge and governance keep independent receipts using the same checks. The app's trailing notes are set aside. Coordinator quotations, relays, scheduled tasks, other people and launched sessions never answer governance questions.

The user can answer in their own words. In the held repository's own chat, after the question is shown, `yes`, `no` and `later` (and the full `toolkit governance` forms) answer in that run. A reply from another folder answers nothing for it. Any other message of the user's own after that question, typed or from an eligible thread delivery, goes to the agent with a one-use reply ticket: the agent reads what the user means and, when it clearly answers, records it with `toolkit-governance-answer.cjs` and that ticket, then tells the user what Toolkit recorded. A question or unrelated reply records nothing. When unsure, the agent records `confirm-yes`, `confirm-no` or `confirm-later` with the ticket instead: Toolkit records nothing and gives it a question naming exactly what would be recorded. The user's next own reply, a bare `yes` included, then receives a ticket that records only that named answer. Tickets work once, only for that session's run and repository, lapse after half an hour, and only the newest counts. Outside github.com governance is off automatically; no answer ticket is needed. Unreadable or unwritable reply state grants no wrapped answer or ticket; restore an intact local copy before sending a fresh wrapped reply and keep its spent receipts. The reply-ticket conversion preserves live tickets and confirmations, hashes spent ids and refuses pre-conversion wrapped deliveries that the old capped list may have forgotten. The held-message format stays unchanged. Bare typed exact answers work without delivery-receipt checks or ticket cleanup.

Software that runs as the user can fill in the card's answer the same way a tap arrives, and Toolkit cannot tell the two apart: another plugin's hook, an SDK host, or a process an agent starts that answers its own permission prompts (Claude Code's `--input-format stream-json` with `--permission-prompt-tool`). Each of these could equally send `yes` as a message today (the known limit below), so the card does not lower that bar.

The programme binding `.github/toolkit-programme.json` as merged on the repository's default branch is the repository's own governance setting, and it decides on every computer: a repository with a merged binding is never asked. Only that copy counts, read from the URL git really uses for `origin` and only when that is the same repository as the identity: a working tree, another branch, a fork's copy, a redirected remote or a copy of the state an earlier version left in the repository grants nothing, since an agent can write them. Default-branch protection. "CI green" means every check named in the programme binding's `required_checks` passed at the head, so `toolkit governance check` also checks, for an ENABLED github.com repository with a binding, that a passing check can never hide a failing or pending one: the default branch requires exactly the binding's checks (active rulesets and classic branch protection together), each pinned to an app so a job of the same name elsewhere cannot satisfy it; exactly one workflow job produces each (a job named by an expression that could produce it leaves this unverified); that job's workflow runs on every pull request to the default branch (no path filter, no branch filter that leaves it out); its job condition is absent or exactly `always()` or `!cancelled()`, because a skipped job reports success; a job that waits for others has a step whose result is the declared aggregate command's (no step condition, `continue-on-error`, custom shell or working directory; `TEST_LEGS: ${{ toJSON(needs) }}`; a script of plain node commands ending with this repository's `node repo/scripts/run-tests.cjs --verify-ci`, which fails unless every needed job succeeded), and without one it is unverified; and the default branch allows merge commits only. GitHub settings are read through the signed-in `gh` (classic branch protection needs admin); the workflows are read from the checkout, also with `--offline`, which takes the default branch from `origin/HEAD`. The workflow reader is default-deny: it follows only printable ASCII on every line, comments included, in plain `key: value` lines and `- ` items, each at its mapping's or list's indent, with block scalars only for `run`, `if`, `shell` and `continue-on-error` (no anchors, aliases, tags, explicit keys, flow mappings, values continued on the next line, duplicate keys, tabs, control characters, Unicode line breaks, non-ASCII spaces, lone carriage returns, second documents or a block scalar line shallower than its first), and a workflow with anything else is unverified. A leading byte order mark is removed first. `continue-on-error` counts as off only when written as the plain `false`, a job name written as any YAML null (`~`, `null`, `Null`, `NULL`) is no name, and only an `on` key (plain or quoted) is the trigger, never a `true` key. Anything that cannot be confirmed leaves default-branch protection unverified, never conformant, and the check's first line counts unverified items. `toolkit governance migrate` then lists repositories whose default branch misses a binding check or allows squash or rebase merges, with any workflow problem the ruleset does not fix, and, after its own typed yes, creates or updates one ruleset named "Toolkit: protected default branch" (the default branch, a pull request for every change, the binding's checks pinned to GitHub Actions, merge commits only, no bypass; an update replaces that ruleset's rules). A repository where no workflow job produces a binding check, or where that job's workflow does not run on every pull request to the default branch, is not offered it, because the required check would wait forever and block those merges. It never edits a ruleset or branch protection it did not create: an extra or unpinned check there, or a workflow that can mask its check, is listed to change by hand, and a refused write is reported once, not retried.

Dependency and security settings. For the same repositories `toolkit governance check` also reports Dependabot alerts, Dependabot security updates, a `.github/dependabot.yml` (or `.yaml`) entry for every package ecosystem it finds (npm, pip, GitHub Actions, Docker, Go, Cargo, Bundler, Composer, at the root and one folder down), secret scanning with push protection, CodeQL (default setup, or an advanced setup: a workflow on the default branch, run by a push, pull request, merge queue, schedule or as a reusable workflow, with CodeQL init and analyze steps in one job that is not switched off, or CodeQL results GitHub received on the default branch in the last 90 days from anything but default setup, such as a composite action; any other workflow whose text names CodeQL, other than its upload-sarif step, keeps default setup off and is reported for a hand check, and CodeQL run from outside the workflow files counts only once it has uploaded) and private vulnerability reporting. GitHub's free settings are on by default under governance: the owner's yes to governance covers them, so `toolkit governance security` (agents may run it) turn them on without another question, write a `dependabot.yml` only where none exists (weekly, a three-day cooldown, seven for GitHub Actions, patch and minor updates grouped), and read everything back. They write nothing when GitHub cannot be read, report a read-back that fails for any written setting as unverified with exit 2, leave alone a setting GitHub does not allow on the plan or under an organisation policy, and record each change with what GitHub showed before, in private operation history. On a public repository the free set includes secret scanning, push protection, CodeQL and private vulnerability reporting. Toolkit never asks about, turns on or reports as drift a GitHub feature that needs billing. On a private or internal repository GitHub bills for secret scanning, push protection and CodeQL, so the check reports them as not applicable (private repository) and nothing is asked or written; Dependabot alerts and security updates stay on there, because they are free everywhere. A binding's `paid_security` key is deprecated and ignored: off or on is accepted, and any other value makes the binding invalid. On a private repository the update pull requests also use the owner's Actions minutes. The auto-merge policy counts only from the binding merged on the default branch, read through GitHub: an edit in a working tree turns nothing on, and an unreadable binding counts as auto-merge off. Dependabot pull requests merge on their own only when the binding says so: `dependency_updates.auto_merge` is `off` by default, and `patch-minor` is the owner's standing permission for that repository. Then the check also wants the auto-merge workflow (copied from `skills/secure-ci-cd/templates/github-actions/dependency-auto-merge.yml`), the repository setting that allows auto-merge, and conformant default-branch protection with at least one required check. The workflow uses only the built-in token, never checks out the pull request's code, acts only on pull requests to the default branch whose every commit is Dependabot's, reads the policy from the default branch, refuses when no ruleset requires a check, and turns on GitHub auto-merge with a merge commit for patch and minor updates, pinned to the head commit it checked, so GitHub merges only after every required check passes. A re-run started by anyone else never turns it on. A major update, a minor update from a 0.x version, an update whose maintainers changed, or a GitHub Actions update (unless `dependency_updates.github_actions` is `auto-merge`; the default is `owner`) gets one comment for the owner and stays open. A push or re-run by anyone but Dependabot, or a base branch change, turns auto-merge off again and tells the owner; if that cannot be confirmed, the job fails instead. A merge made with the built-in token starts no push workflows on the base branch; they run on its next push. GitHub starts no pull request workflow for a push whose commit message asks to skip CI, so such a push does not turn auto-merge off, but the required checks then never report on it, which still blocks the merge. Files land in the working tree for a normal pull request; an existing file Toolkit did not write is listed to change by hand.

Governance GitHub App. The governance jobs on GitHub mint short-lived tokens from the repository's own GitHub App: one App per governed repository, because GitHub counts the hourly allowance per App installation, so a busy repository never slows another. The App is set by the repository variable `TOOLKIT_GOVERNANCE_APP_CLIENT_ID` and the repository secret `TOOLKIT_GOVERNANCE_APP_PRIVATE_KEY`. Its permissions are one list in `repo/scripts/toolkit-governance-app.cjs` (Contents, Issues and Pull requests read and write; Checks and Commit statuses read), and every workflow token stays within it. When a pull request that turns governance on is published, Toolkit shows the setup: a pre-filled "New GitHub App" link named for the repository, with the webhook off, installable only on the owner's account, and those permissions; installing it on the repository and its evidence store; and saving the Client ID and private key on the repository by hand on GitHub's website (Settings, Secrets and variables, Actions: a variable and a secret, each step stopping if the name is already there), with guarded `gh variable set` and `gh secret set` lines as the other way, then deleting the `.pem` file, and a last step that runs `toolkit governance check` to confirm the App and the cloud sweep copies are both in place. When one that turns governance off is published, it suggests the removal: deleting the variable and the secret on the same website page, or `gh variable delete` and `gh secret delete`, removing the repository from the installation, and, when no other repository uses the App, uninstalling and deleting it. It names the repositories this computer still knows as governed, and says other computers may know more. `toolkit governance check` reports a missing App while governance is on, and a left-over variable or secret once it is off; neither changes the exit code, and anything it cannot read is unverified, never missing. Toolkit only lists the repository's variable and secret names; it never creates, installs or deletes an App, key, variable or secret.

One governance App per repository, never overwritten by accident. A repository holds one value for each of the two fixed names, so a second person who saves their own App over an existing one silently replaces it: the first App stays installed, unused, with its access, and a half-replaced pair (one App's Client ID, another App's key) makes every governance job fail to get its token. So the setup reuses what is there. When both names exist, it says to reuse that App and prints no steps. When only one exists, it says to set just the missing one from the same App, prints a command that sets only that name, offers no new App, and shows how to replace it and remove the old App's installation. Every printed save command, in PowerShell and in macOS or Linux, first lists the repository's variable and secret names and stops, changing nothing, when either list cannot be read. When a name it would write is already there, it asks the person to type `replace`; any other answer, or no answer, keeps the existing App and changes nothing. The macOS or Linux command uses plain POSIX shell, so it runs in bash, zsh and dash. Detection uses the names only, never a value, and the names stay the same on every repository, so removal finds and cleans them the same way everywhere.

One shell-call reader (`repo/scripts/toolkit-shell-call.cjs`) feeds this check, the attribution and force-push checks, the merge hold and the governance gate, so every check reads the same command and judges the folder it runs in. It reads a string `command`, a string `cmd` (both when both are given) or an argument list (the script of a `bash -c`, `pwsh -Command` or `cmd /c` wrapper, else the words themselves), and takes the folder from Codex's `workdir`, else the tool's own `cwd`, else the session folder. Every folder or file a command names is read as the shell reads it: a leading `~` is the home folder, and on Windows a Git Bash drive path (`/c/...`, `/cygdrive/c/...`) is that drive and `/tmp` the user's temp folder. A push or new pull request whose folder cannot be found is refused, with a hint to run a step that creates the folder as its own command first; a folder written as a command (`$(...)`) or a variable the same command line does not assign is refused as unreadable; a leading home variable (`$HOME`, `$env:USERPROFILE`) reads as the home folder, and a variable an earlier command in the line assigned a literal to (`$d = 'C:\path'`, `d=/path`) reads as that value as the shell running it reads it (Claude Code's Bash tool: POSIX names, in their exact case; its PowerShell tool: PowerShell names, in any case). Codex names no shell, so there a name assigned in both forms or twice is left unread, and every push is also judged as if the assignments did not run (the folder the command is already in); a refusal under either reading stands, so a Codex push of an evidence store through a variable from a governed repository is refused, while a literal store path is not. A shell call whose command or folder has a shape it cannot read is refused when its raw input could commit, push, or create, edit or merge a pull request; any other such call runs. The check runs before the whole shell command, so when a `git commit` comes earlier in the same command and repository, it also reads what that commit could add, a superset of the real commit: the staged and unstaged tracked changes, and after a `git add` there, the untracked files git does not ignore (text files up to 1 MB). Those items say "not committed yet", with a reminder to run the commit and the push as separate commands when the file will not be in the commit. A `git merge`, `cherry-pick`, `revert`, `am` or `rebase` before the push in the same command is refused, because what it adds cannot be foreseen; `git pull` is not. A Codex call that names no folder (no `workdir`, and no `cd` or `git -C` to a full path first) gives only the chat's folder, and the command may run in another working tree of the same repository. Then a chat folder that is not a repository is refused. Only working trees the chat's folder can reach count: the one holding that folder and any nested below it, since Codex Desktop refuses a workdir outside the chat's folder. When more than one is reachable, a branch the chat's folder cannot find is refused, and a push of the current branch (`git push` or `git push origin HEAD`) is checked in every reachable working tree within the same budget only when the whole line is one plain git command, as defined above, and every tree passes. Any other line pushing HEAD from an unknown folder is refused, including a read before the push, a quoted location command after `&`, a pipeline or a substitution. A pull request of the current branch (`gh pr create` without `--head`) is also refused there because it is not a plain git line. After a commit earlier in the same command, each pushed branch must be checked out in exactly one working tree, which is the one read, so a one-command add, commit and push from a lane worktree is checked there; a branch no working tree has checked out, `--all` and `--tags` are refused, because a checkout or tag step in the same command could put the commit on them wherever it runs. With one reachable working tree the check runs as for a named folder. The refusal says to name the branch and run the commit and the push as separate commands, or to name the folder with `git -C <full path>` or `cd <full path>` first. All the pushes and pull requests of one shell command share one 30-second budget. Not checked: pushes through GitHub tools (not the shell), git aliases, scripts that run git themselves, binary files and files marked `-diff`, merge resolutions, and changes a `git apply`, `git stash pop` or checkout makes earlier in the same command, before a commit; a renamed file is read as new, so a credential the remote already has in it is refused again.

## Codex SessionStart Output Contract

The current official [Codex hooks documentation](https://developers.openai.com/codex/hooks) is the behavior source of truth:

- Plain text written to `stdout` by a `SessionStart` hook is added as extra developer context.
- JSON `stdout` may instead use `hookSpecificOutput.hookEventName: "SessionStart"` plus `hookSpecificOutput.additionalContext`. Do not mix JSON and plain text.
- `systemMessage` is surfaced as a UI or event-stream warning; it is not a substitute for model-visible `additionalContext` or plain-text `stdout`.
- Command hooks receive one JSON object on `stdin`, including `cwd`, and run with the session `cwd` as their working directory.
- Plugin hooks use the normal hook trust flow. Installing or enabling a plugin does not trust its hooks; new hooks and any changed plugin bundle contents are skipped until reviewed and trusted through `/hooks`. The file reader reports changed or unverified approval and never approves hooks itself.
- Only command handlers run today. Async command hooks and prompt/agent handlers are parsed but skipped, and `suppressOutput` is parsed but not implemented.

The Toolkit bridge already emits concise bridge status text on hook `stdout`, so its passive agent-rules preflight uses documented plain-text `stdout` rather than trying to combine status text with a JSON response. The preflight runs before bridge no-op handling, resolves the nearest Git root from the documented session working directory, and never creates, repairs, backs up, or writes repo-local instruction files. In a repository whose Toolkit GitHub governance is ENABLED it also compares the vendored Toolkit checks under `.github/scripts/` (plain-text check, personal-data guard) with the running Toolkit's sources, and notes a missing plain-text check; it only reports, once per finding.

## Portable Policy-First Layering

Layering:

1. `AGENTS.md` is compact cross-platform context and routing.
2. Portable skills and docs contain detailed cross-platform workflows; bridge setup specifics stay in docs and the shared updater.
3. Validators and schema checks enforce deterministic rules where practical.

## Instruction Layers

Toolkit instructions come in two layers, both inside versioned, hashed Toolkit markers (`repo/scripts/toolkit-managed-block.cjs`: `BEGIN <NAME> v2 toolkit=<version> sha256=<12 hex>`). Toolkit only writes between its markers; every byte outside them, line endings included, is kept.

- **Global rules** (`repo/contracts/agent-rules/global-rules.md` plus the n8n adapter) go into each harness's user-level file: `$CLAUDE_CONFIG_DIR/CLAUDE.md` or `~/.claude/CLAUDE.md`, `$CODEX_HOME/AGENTS.md` or `~/.codex/AGENTS.md`, and `~/.gemini/GEMINI.md` only with `--antigravity-global-rules` or when it already carries the block. `repo/scripts/toolkit-global-rules.cjs` owns them. Setup installs or refreshes them (Claude Code in its install check, Codex in a `## Global rules` section); the Claude Code install check and the Codex session-start hook (only once setup configured the bridge with auto-sync on) refresh their own file when stale. A file that is not UTF-8 (for example UTF-16 from Windows PowerShell) is held and never rewritten. Every change is backed up with its exact bytes under `~/.ai-agent-toolkit/backups/global-rules/` (pruned after the report retention days); a block edited by hand is restored and reported (in the setup output, the session-start update report, and one Codex session-start line); broken markers hold with `action-required` instead of guessing. Hand-written sections the block now covers (for example `Toolkit Controller Bootstrap`) are reported, never edited. Codex reads the repository's `AGENTS.md` only up to `project_doc_max_bytes` (32 KiB by default). Open-source Codex does not count the user-level file toward it, but Codex desktop 26.1016 cut repository rules off where both files together reached 32 KiB (owner UAT, 22 October 2026), and raising the limit fixed it. So setup asks "Raise Codex's instruction limit" (recommended yes; stored as `codex_doc_limit_enabled`). On yes, setup raises that top-level key in `config.toml` to 65536, and the Codex session-start hook keeps it there; on no, a value Toolkit raised is put back; with no answer recorded, nothing changes. `toolkit-global-rules.cjs --write` is an explicit request and also raises it. `config.toml` is read only with a real TOML parser (Python 3.11 or later, `tomllib`, run isolated with `-I` from the Toolkit folder, so nothing in the opened folder is imported; without a yes the session start does not read it at all): Toolkit edits only when the key is absent everywhere (it inserts at the top of the file) or is one plain top-level decimal line (it replaces that line), checks that the result parses, reads 65536 and leaves every other value unchanged, and otherwise writes nothing and says to set it by hand. It never changes 0 (project docs off) or a value of 65536 or more. The change sits inside `# AI-AGENT-TOOLKIT:global-rules` comment markers that record the exact replaced line (and whether Toolkit created the file), so removal restores the exact bytes or deletes a file Toolkit created. Every raise or restore prints one session-start line and is an update-report entry; an unparseable or ineffective `config.toml` holds, and `--check` fails on it. Setup and `--check` report the combined size against the effective limit, warning when the repository rules may be cut off. `node repo/scripts/toolkit-global-rules.cjs --check|--write|--remove [--harness claude-code,codex,antigravity]` checks, refreshes or removes them; removal deletes a file only when Toolkit created it and nothing else remains, and records the removal in `~/.ai-agent-toolkit/global-rules.json`, so session starts leave that file alone (the install check says "removed by you") until `setup toolkit` or `--write` installs again.
- **Governed-repository rules** (`repo/contracts/agent-rules/toolkit-governed-rules.md`) are one block in a repository's `AGENTS.md`, installed by `repository-agent-rules` in an ENABLED github.com repository when the owner asks, or prepared with the binding for an accepted pending yes adoption pull request. Only the valid binding merged on the default branch enables GitHub governance; a block, local answer or pending proposal grants no authority. The session-start preflight compares it with the bundled template and prints one neutral note when it differs; it never writes.

Policy that affects agent judgement stays in these rule files, docs and validators, never only in hooks: source of truth, approval gates, generated-output ownership, the Antigravity explicit-copy rule, the native plugin cross-update ban, no package installs by default and no project repository writes by default.
