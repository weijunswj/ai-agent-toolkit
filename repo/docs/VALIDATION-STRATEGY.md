# Validation Strategy

Use validation in two phases: fast targeted local checks before pushing, then the full read-only CI gate for PR and `main` readiness.

Last CI check-up: 6 November 2026, offline. No coverage gaps were found. Test timings need a CI refresh on both systems; live job times were not read.

Targeted validation is an iteration strategy, not a quality downgrade. Local `npm run validate:all` is not required before every push when CI already runs the full gate.

Release maintenance uses `repo/tests/toolkit-version.test.cjs` and `repo/tests/toolkit-rebump-prs.test.cjs`, `repo/tests/toolkit-rebump-prs-conflicts.test.cjs` and `repo/tests/toolkit-rebump-prs-push.test.cjs`: patch, minor and major intent, repeated main moves, fragment folding, frozen notes, conflict refusals, merge parentage, ordinary pushes and concurrent changes. Re-bump tests use disposable local repositories and a bare remote. They do not qualify computer authentication or the coordinator trigger; real agent UAT covers that route. Every re-bumped head needs fresh CI and full delta G2 review. The re-bump workflow adds `repo/tests/toolkit-rebump-prs-unattended.test.cjs` (listed authors only, no token in the branch scripts' environment), `repo/tests/toolkit-rebump-report.test.cjs` (one held comment, edited in place) and `repo/tests/toolkit-rebump-workflow.test.cjs` (trigger, permissions, pinned actions, nothing without the push key). They do not qualify the workflow on GitHub; the first merge after the push key is set does.

## Canonical Merge Gate

The programme job is `.github/workflows/toolkit-programme-sweep.yml`, started after each push to main, by hand, by its own follow-up after an early stop, and by `.github/workflows/toolkit-programme-sweep-gate.yml`, which runs hourly and on issue, comment and pull request activity with only the built-in token and starts the sweep only when there is work. The sweep runs under the governance GitHub App with two narrow installation tokens, keeps its sweep job's built-in token read-only, has no pull request trigger and never cancels an overlapping run. The same test file checks the gate's triggers, permissions and decisions (`repo/scripts/toolkit-programme-sweep-gate.cjs`) and the follow-up. `repo/tests/toolkit-programme-sweep-workflow.test.cjs` checks its triggers, pins, mint permissions against `repo/contracts/cloud-jobs.json`, notices, fixed failures, the merged binding read on a fresh runner and the token routing; `repo/tests/toolkit-cloud-jobs.test.cjs` checks the contract and the setup guide. The queued pass, its one state commit, the shared lease and their recovery are in `repo/tests/programme-incremental-sweep.test.cjs`, `repo/tests/programme-sweep-store.test.cjs`, `repo/tests/programme-sweep-lease.test.cjs` and `repo/tests/programme-sweep-parity.test.cjs`, which also measures a 103-task, 645-PR programme. These offline checks do not qualify a real runner or the App's installation; that needs real scheduled runs and a read-back of the parent page.

The hook pack runs in `hook-pack` on Linux and in the `hook-pack-windows` matrix on Windows, which runs the nine families (attribution, closure-matrix, closure-shell, fault, governance, issue-closure, merge, push and task-governance) in four groups of about the same measured time, so a run takes four Windows jobs instead of nine. Each family runs once. The Linux job keeps its 360-second pack budget; each Windows group has a 420-second budget; every job has a 15-minute timeout. The `gate` job waits for both jobs, including every family; missing, failed, cancelled or skipped results fail it, and with it the required `validate` check. Corpus coverage tests require the four groups to cover every row and host exactly once.

The read-only `issue-closure` job checks the current pull request title, body and every commit message against live native descendant state. It feeds the required `validate` result and reruns on title or body edits. It has only contents, issues and pull-request read permissions; stale heads and incomplete state fail the check. The existing fenced programme refresh owns parent repair and automatic completion under explicit merged binding permission.

For this repo, the canonical full validation command is:

```bash
npm run validate:all
```

The gate has one list: the `Run validation` step of the `gate` job in `.github/workflows/validate.yml`, which runs on every pull request and push to `main`. `npm run validate:all` runs the same commands in the same order from that step (`repo/scripts/run-validation-gate.cjs`), so the local and CI gates cannot drift. In CI the test files run first, in shards on Linux and Windows, and the last command of the step (`run-tests.cjs --verify-ci`) proves from the shard summaries that every shard passed and that each system ran every test file exactly once; a local run has no shards, so that command runs every test file instead (`run-tests.cjs --all`). The `validate` job of the Validate workflow is the CI gate for pull requests and `main`, and is the check to make required in the ruleset. It needs the `gate`, `personal-data` and `issue-closure` jobs and checks the shard summaries again (`run-tests.cjs --verify-ci`), so it never passes without proof that every test file ran.

### Light runs on title or body edits

A pull request title or body edit changes no code, so it does not run the test files again when an earlier run already tested exactly the same code. The `route` job decides first (`repo/scripts/ci-validate-route.cjs route`). The run is light only when the event is a pull request `edited` event with no base branch change, and an earlier completed pull request run of the same workflow, for the same head commit and head repository, passed every test and hook-pack job in its newest attempt and still keeps a summary artifact for every shard named with this run's tested commit. That tested commit is the pull request merge commit (`GITHUB_SHA`). Once GitHub has recomputed the merge commit for a moved base, the commit differs and the edit runs in full; until then the edit reuses results for the same merge commit a full run would test. Every other event, and any doubt or error, runs in full; the route job always exits 0, so it can only choose more testing.

A light run skips the test and hook-pack jobs and runs `personal-data`, `issue-closure` and the `gate` job as usual, so the text checks always see the new title and body. The gate job's `Find the test legs` step (`ci-validate-route.cjs legs`) checks the chosen run again and takes its job results; the gate then downloads that run's summaries with the workflow's read-only token and runs the whole gate list over them. Each shard summary records the commit it tested, and in CI `--verify-ci` refuses a summary of any other commit, in the gate job and again in the `validate` job. A run whose only failure was a text check, such as a footer in the body, still has reusable test results, so fixing the body runs light. If GitHub cannot be read in the gate job of a light run, the gate fails; re-run that workflow run, or push a commit for a full run. `repo/tests/ci-validate-route.test.cjs` covers each route decision offline; the first light runs on a real pull request qualify the GitHub side.

## Test Shards

`repo/contracts/ci/test-shards.json` splits `repo/tests/*.test.cjs` into named shards per system. Each named shard lists its files; one `rest` shard per system runs every file no other shard names, so a new test file always runs. A `.test.cjs` entry there that would not run fails every runner mode instead of being skipped: a name that does not start with a letter or digit or has characters other than letters, digits, dots, dashes and underscores, or a folder or link with a test name. `durations_seconds` holds the last measured time per file, which orders files longest first inside a shard and lets `node repo/scripts/run-tests.cjs --plan` estimate each shard. `node repo/scripts/refresh-shard-timings.cjs` reads the per-file times from the shard summaries of the latest green Validate run on `main` (each shard job uploads its summary as a `test-summary-<shard>-attempt-<n>-<commit>` artifact, one per run attempt, kept 7 days) and reports whether a refresh is due: more than 10% of test files without a recorded time, or a system whose slowest shard is estimated over 1.5 times its fastest on Linux or 1.3 times on Windows. It makes no model calls. With `--write` it updates the manifest in the checkout, moving files between the named shards when they are out of balance; with `--open-pr` it does the same on a new branch from `origin/main` and opens a pull request, and only when a trigger crossed. `--run <id>` reads another finished Validate run, such as a pull request's run that measured a new or split test file. A failed shard uploads its summary too, so the `gate` job names the tests that failed instead of reporting every file of that shard as not run; the refresh reads times only from the summaries of shards that passed. A re-run of a failed shard uploads a second summary, and the `gate` job keeps the newest attempt of each shard, so the re-run can clear it. Run it by hand or when planning a release. On GitHub the Toolkit Shard Timings workflow (`.github/workflows/toolkit-shard-timings.yml`) runs it once a day at 02:37 UTC and when started by hand. A push to `main` also starts it, as a catch-all in case the daily schedule stops firing: a first job checks, in seconds and with no checkout, whether a run's refresh job succeeded in the last 24 hours, and skips the refresh when one did. Only one run goes at a time. Its built-in token only reads contents, Actions runs and artifacts, and pull requests. With the governance GitHub App configured it runs `--open-pr`, pushing and opening the pull request with an App token minted for this repository with only contents and pull requests write, so the pull request's own checks start. While an earlier shard timing pull request is open it opens no second one, and one open over 7 days fails the run naming it, so it gets merged or closed. Without the App it only reports, and fails when a refresh is due (`--fail-if-due`), naming the owner's step: set up the App, or run `--write` and open the pull request by hand. Fallback-risk audit findings also show as file and line annotations on the pull request. It never runs for pull requests, forks or other branches.

A governed repository can keep its own shard list, in any language, at `.github/toolkit-test-shards.json` (schema `toolkit-test-shards/v2`, checked by `repo/scripts/governed-test-shards.cjs`). It is the v1 list plus, for each system it names (Linux, Windows or both), a `discover` glob that finds the test files from the repository root (`**` spans folders, `*` and `?` stay inside one name) and a `command` list with one `{files}` argument, such as `["python", "-m", "pytest", "{files}"]`. `node repo/scripts/run-tests.cjs --repo-root <dir> --shard <id> --os <system>` runs that command once per file with no shell, three at a time, times each file and writes the same shard summary as Toolkit's own shards; `--check` and `--plan` read the list without running anything. The command may not start with a shell or a program that runs one (`bash`, `cmd`, `pwsh`, `env`, `busybox`, `xargs` and the like, by any path or `.exe` name), so a file name never becomes shell syntax; on Windows it names a program such as `node.exe` or `python.exe`, not a `.cmd` script. A program that is not installed fails each file by name, and a file still running after `file_timeout_seconds` (default 900) is stopped, with every process it started, and fails by name. `--verify <folder>` is the gate check over a run's shard summaries: it fails, naming the file or shard, unless every shard reported on this commit (the newest run attempt counts) and passed, and together they ran each discovered file exactly once on each system the list names. Where a governed repository has a usable list, the cloud workflows installer (`repo/scripts/toolkit-cloud-workflows.cjs`) also copies two workflows into it, pinned to a Toolkit commit like the sweep copies. The test shards workflow (`.github/workflows/toolkit-test-shards.yml`, or the file the list's `workflow` names) is rendered from `repo/contracts/ci/governed-test-shards.yml`, which runs nowhere in the Toolkit: a matrix job per system with the list's shard ids, each running one shard through the Toolkit runner checked out into `.toolkit/` and uploading its summary as `test-summary-<shard>-attempt-<n>-<commit>`, also when it failed, and a gate job, `Toolkit test shards`, that runs `--verify`. It reads the repository only, uses no secret, keeps no checkout credentials and adds to the repository's own CI without replacing it. Shard Timings is the Toolkit's own workflow with a Toolkit checkout added; `refresh-shard-timings.cjs --repo-root <checkout>` sees the v2 list there, reads the newest green run of the workflow the list names, and writes per-file times and rebalanced named shards back to that list (v2 budgets sit under each system: `seconds_per_file` and `raised` by file). Because the copy's matrix carries the shard ids, a change to the list's shards makes it outdated, not edited, and the next rules refresh rewrites it. Without a list, or with one that does not validate, neither workflow is copied and the installer says why. The shard jobs set up Node only, so the installer copies neither workflow for a list whose command starts with any other program (such as `python`, `pytest` or `npx`) and names that program as the reason, instead of copying jobs that would fail on every file; that repository keeps those tests in its own CI until the jobs set up other runtimes. Toolkit's own list stays v1, and its own CI and Shard Timings are unchanged.

A test that pins a calendar date passes that same clock to every call that reads the time; otherwise it passes on the day it lands and fails once the real date moves past the pinned one. The `tests-clock-ahead` job proves it on every pull request: `node repo/scripts/run-tests.cjs --clock-ahead` runs every test file that pins a date (an ISO date literal or `Date.UTC(`, in the file or in a `repo/tests` helper it loads) with Node's clock 400 days ahead, through the `repo/scripts/test-clock-offset.cjs` preload in the test processes only. File times and git dates keep the real clock, so a test that compares a file it just wrote with Node's clock sets that file's time from `new Date()` first. The job uploads no summary and never counts toward shard coverage; the `gate` job waits for it, so a failure fails the required check. `--clock-offset-days <n>` moves the clock for a named, `--changed` or `--all` run too, to reproduce a failure locally.

`repo/scripts/check-test-durations.cjs <report.json>...` checks per-file times from a `--summary` or `--report-durations` file against the manifest's `budgets` field; with `--ci` it reads the shard summaries the `gate` job downloaded, and the gate runs it that way, so a test file over its budget fails CI. A raised budget needs a recorded reason. Without a budget, the check only reports the slowest files. This repository allows 120 seconds per file on Linux and Windows, measured in CI; split or speed up a file that goes over. Three files that sat close to that limit (`n8n-workflow-transport` on Linux, `toolkit-governance-gate` and `toolkit-setup-orchestrator-2` on Windows) have a raised 180-second budget until they are split. A budget failure is checked from the shard summaries of that run, so use "Re-run all jobs" to measure again. A local `npm run validate:all` leaves this one check out and says so, because local times are not CI times.

The test jobs in `validate.yml` are pinned word for word by the drift guard (`workflowErrors` in `repo/scripts/ci-test-shards.cjs`, run by `repo/tests/ci-test-shards.test.cjs` and again by `--verify-ci` in CI). Adding or renaming a shard changes the manifest and the matrix together. The guard refuses narrowed file lists, `node --test` filters, `if: false`, masked exit codes, `continue-on-error`, matrix `include`/`exclude` edits, a `gate` job that does not wait for every shard and the clock-ahead job, a `validate` job that does not wait for the gate and both text checks, and a test job that runs on a light run or skips when the route job failed. The guard compares the whole file, from the triggers to the last line, with its pinned text (`workflowText`), so a comment, a quoted or flow-style key, or a workflow-wide `defaults:` or `env:` cannot slip in beside the jobs, and any other edit to the file needs the same edit there. One kind of edit passes without it: a Dependabot update that changes only the commit SHA and `# vX.Y.Z` version comment of a pinned action, with the same action name, a full 40-character lower-case SHA and nothing else on the line. The guard's tests find the pins in the live file instead of naming today's SHAs, and they rerun every drift case with each pinned action updated, so such an update passes the whole test run too. A new major version of `actions/checkout` still needs a hand edit, because a test in `repo/tests/validate-toolkit.test.cjs` requires its major version. Only the commands of the `Run validation` step are read from `validate.yml`, which stays their one list: each must be a plain `node repo/scripts/<name>.cjs` line with simple arguments and no shell syntax, and the summary check stays last. As a second check, the guard also refuses the usual spellings of `set +e`, `|| echo` and a `shell:` key, because a custom shell can drop the `bash -e` that stops a step at its first failing command.

Every run, local or CI, gets its own scratch temp folder: `%USERPROFILE%\t\run-<time>-<random>` by default, or under the `--temp-root` CI passes (the runner temp folder). It is set as `TEMP`, `TMP` and `TMPDIR` for every child process, used in its long form (never an 8.3 short name), and removed when the run finishes, also on failure. The next run removes a folder left by an interrupted run once it is more than a day old. Anything a run must keep, such as a summary or durations report, is written with `--summary` or `--report-durations` to a path outside the run folder before the folder is removed. A temp root at or directly under a drive root is refused.

### Review temp permissions

`--temp-root` selects storage; it grants no filesystem permission. Follow the [Windows review launch recipe](HOST-CONTRACT.md#review-cli-permissions): a real repository worktree, the real Codex home, a preflight confirming an already elevated Windows backend, one pre-created absolute temp write grant, no source writes and restricted command networking. Stop on an unknown or different backend; never change it for the owner. The initial measurement used Codex CLI `0.166.0`, model `gpt-6.1-sol`, effort `high`, optional MCP servers disabled, and one probe command. A later `xhigh` launch read back the same permissions and completed one targeted run: 68 of 69 tests passed; only the default-root test failed. The hook pack returned no result in 30 minutes. None of this qualifies a complete suite. Launch model and effort come from the pinned stack registry revision, not these measurement records.

Set `TEMP`, `TMP` and `TMPDIR` inside every review command before starting Node. Set `NODE_PATH` to the main checkout's `node_modules` for worktree dependencies, as shown in the recipe. Launch-time variables are not inherited through the elevated boundary: children otherwise see an agent temp folder where fixture creation fails. After the in-command assignments, the runner gives its children and nested runners their own run folder and removes it when done. Keep the outer Codex process's own startup temp folder separate and outside the grant; do not add a second writable root for it.

Use a fresh per-run folder as the only write grant, pre-created with plain `mkdir` and inherited permissions, not Python `tempfile.mkdtemp`. Never grant a shared parent such as `%USERPROFILE%\t`. Keep the candidate worktree outside the grant and never make source writable. The measured default-root regression fails at `realpathSync.native(os.homedir())` with `EPERM` before any write, not at fixture creation under `t`. CI or the unsandboxed launch lane owns that test; do not broaden access for it. Codex leaves a lasting Modify ACL entry on the grant, so preserve evidence and delete the per-run folder at cleanup.

Write summaries and duration reports outside runner-owned run folders, within the grant, and preserve evidence before removing scratch. Check probe-owned fixtures separately from CLI temp files; inventory and retain any other entries rather than claiming the entire root was cleaned. A required test without a result remains missing evidence. A zero-usage empty turn runs no checks: inspect native events and any hook refusal, which JSON output can hide.

The review brief names local commands and the authorised network lane's commands, owner and evidence for the exact candidate commit. Fetching the candidate, reading GitHub check results and any other required network checks stay with that lane. The reviewer inspects those results and retains full review responsibility; missing required results still block acceptance. Boundary-probe success does not replace required execution evidence. The hook pack does not finish on this review route and can leave a process the sandbox cannot stop. The unsandboxed launch lane owns the unchanged pack at the exact candidate SHA: set the same temp variables, run `node repo/scripts/toolkit-hook-pack.cjs run --budget-seconds <agreed-budget>`, capture the full table and per-job CI evidence, and stop stragglers from outside the sandbox. Reviewers inspect that evidence and never run the pack on this route. Missing pack evidence remains a hold.

The whitespace check (`npm run validate:whitespace`, `repo/scripts/check-diff-whitespace.cjs`) compares the whole change with its base: in CI the pull request base or the previous `main` tip (`DIFF_BASE`), locally where the branch left `origin/main`, including uncommitted edits. A plain `git diff --check` sees only uncommitted edits, so on a clean CI checkout it checks nothing.

Do not run `--write` commands in the required validation workflow.

## Other Workflows

None of these is part of the merge gate.

- `.github/workflows/dependency-auto-merge.yml` (Dependency auto-merge): on Dependabot pull requests, turns on GitHub auto-merge, merge commit only, for patch and minor updates once every required check passes, when the programme binding allows it. Major, risky and GitHub Actions updates stay open for the owner. Governed repositories get a copy of this file.
- `.github/workflows/toolkit-rebump.yml` (Toolkit re-bump): after every push to `main`, re-bumps the owner's open release pull requests with the owner's push key and comments on the ones it holds. Without the key it does nothing and ends green. It is the one workflow here that pushes to pull request branches; it never pushes to `main`, merges or approves.
- `.github/workflows/source-watch-plan.yml` (Source Watch Advisory Plan): started by hand; writes the advisory third-party source update plan to the run summary and checks the source locks and Toolkit surfaces. Read-only.
- `.github/workflows/source-watch-pr.yml` (Source Watch PR Notifier): scheduled three times a day on trusted `main`; checks active third-party sources for updates and keeps one review notification pull request open while something is left to review.

## Fast Targeted Checks

Use narrow checks while actively editing so failures are easy to localise:

```bash
node repo/scripts/sync-repo-doc-contract.cjs --check
node repo/scripts/sync-agent-instruction-shims.cjs --check
node repo/scripts/audit-project-source-locks.cjs
npm run audit:surfaces
npm run audit:surfaces:check
node repo/scripts/run-tests.cjs repo/tests/<specific-test-file>.test.cjs
npm run test:changed
git diff --check
```

Pick the smallest command that checks the thing you changed. `npm run test:changed` runs the test files a change affects: changed test files, and test files that name a changed file.

Before pushing, run the smallest relevant targeted checks that cover the edited files and any generated outputs.

## Surface And Audit Checks

Run surface and audit checks after changing:

- `skills/**`
- `repo/contracts/**`
- `repo/source-watch/provenance/**`
- audit scripts
- audit baselines
- generated registries

For managed root contracts or instruction shims, run the retained synchronizer first, then check freshness and audit movement.

## Auto-Sync Is Convenience Only

There is no generic generated-surface auto-sync or writeback lane. The retained synchronizers are narrow: `sync-repo-doc-contract.cjs` maintains the managed source-of-truth block, and `sync-agent-instruction-shims.cjs` maintains root instruction shims plus exactly four portable n8n safety derivatives. Neither publishes Toolkit skills or project outputs, and neither is a substitute for `npm run validate:all`.

Canonical skill, contract, provenance, and audit-baseline changes are reviewed directly at their canonical paths in the PR. No generic Toolkit sync command exists.

CI should catch missed direct-canonical updates with read-only validation, not by silently mutating source or provenance.

## Local Full Validation

Run local `npm run validate:all` when the change is broad or risky, touches workflow, sync, generator, packaging, or security-sensitive behavior, or when CI fails and local reproduction is needed:

```bash
npm run validate:all
git diff --check
```

For narrow docs, template, or retained n8n-safety-derivative follow-ups, targeted local checks plus the read-only CI full gate are the expected workflow.

## Failure Loop Rule

Do not run `npm run validate:all` repeatedly while still iterating.

If full validation fails, inspect the failing section and run the narrow relevant command before retrying full validation. Fix the specific issue, then retry the full suite once.

## Reporting

Report targeted checks, any local full validation that was run, and the CI gate expectation. If a local full check is skipped, say why and identify the remaining risk.
