# Host Qualification Boundaries

This reference distinguishes a portable skill's instructions from platform evidence. It grants no authority and does not claim that any host is qualified.

## Evidence required per host and version

Record the exact host product and version, active repository identity, loaded skill folder digest, invocation route, and observed result. Independently establish each item:

1. **Invocation:** explicit invocation in a fresh context loads this skill. Folder presence, catalog visibility, and metadata are not invocation evidence.
2. **Route and effort:** the selected native route is the supported controller-capable route, with exact route/effort evidence. Unsupported or ambiguous routing remains unqualified.
3. **Permission:** the host's native permission controls permit only the bounded operation. Semantic approval, controller prose, receipts, and worker claims do not create or widen native permission. Pending or denied confirmation means zero effect.
4. **Delivery:** the controller receives and binds the actual child result, identity, and error state. A launch or returned link alone is insufficient.
5. **Resume and handoff:** after context loss, CURRENT and the original RUN/Lock, candidate/base/head/tree, unresolved outcomes, approval, and custody are independently recovered. No old worker or cached context is adopted as a new authority.
6. **Negative control:** ordinary executor invocation, wrong repository, missing role assignment, unavailable source, revoked approval, native denial, and unknown outcome fail closed with no effect.

## Successor installation and retirement evidence

This is an evidence contract, not permission to install or retire anything. The owner of any separately authorised host action records exact `SUCCESSOR_SOURCE`, `INSTALL_TARGET`, and `TEMPORARY_TARGET` identities and hashes; permission evidence method; an inert evidence destination; and a duplicate-install/fallback inventory. Evidence must not contain private device names or local paths.

Keep the temporary predecessor active while installing the successor. Verify installed bytes against the exact source, then prove fresh invocation and result delivery on the supported route. Only after those proofs may an owner separately authorise retirement of the exact temporary target. Retire only that target, independently prove it is inactive and that no duplicate or fallback copy remains, then prove bootstrap in a fresh context. A failed byte check, missing permission evidence, unproven invocation, denied action, or uncertain outcome means HOLD and no retirement. Installation, activation, and retirement remain separate owner-authorised host actions.

## Re-entry scenario/effect matrix

| Scenario | Required outcome |
| --- | --- |
| Same still-pending action; approval remains unexpired and unrevoked; only turn, worker, chat, or transport changed | Preserve the binding and continue only that admitted action; do not request duplicate approval. |
| Action/target/effects changed, approval expired or revoked, or recorded outcome leaves additional work uncovered | HOLD before that additional effect; obtain the required fresh approval or host confirmation. |
| Role, CURRENT, repository identity, exact source bytes, or handover is missing, stale, truncated, or contradictory | HOLD with zero new persistence, acceptance, projection, admission, or dispatch effects. |
| Dispatch outcome is unknown | Reconcile the original execution; do not retry or create a replacement effect. |
| Successor bytes, invocation, permission evidence, target identity, or duplicate inventory is uncertain | Keep the temporary target active; do not retire or activate another target. |
| Governed-record revision changed or write result is uncertain | Read the complete object and reconcile; do not write or retry from stale state. |

## Claims

Keep Codex CLI, Claude Code CLI, OpenCode CLI, and other host/version combinations separate. Reuse only registered evidence for the exact combination. A label, screenshot, installation receipt, unit test, another host's result, or worker self-report cannot fill a missing native proof item. Unproven capabilities must be marked `UNQUALIFIED` or `HOLD`, never silently inferred.

Native qualification, permission realization, installer behavior, and removal/retirement ordering belong to their separately authorised host owners. Do not install, activate, retire, or alter host configuration from this reference. Do not publish private device names or local paths.
