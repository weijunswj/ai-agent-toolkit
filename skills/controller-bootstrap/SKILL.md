# Controller Bootstrap

For adopted V3 work, apply the final execution clarification in the canonical Toolkit V3 contract at a safe renewal boundary. Planned G1 segment completion checkpoints and continues in the same session; a fresh executor is required only at the contract's mandated triggers, such as a newly activated instruction/profile version, and then only after verified checkpoint custody stops the old writer. Use the approved native host matrix, UAT impact disposition, fresh-context correction rechecks for the same selected reviewers and the separate local/remote retention rules. Missing exact routes and unqualified pre-inference guards remain explicit obligations.

This explicit-only skill guides an already-authorised repository controller through a bounded re-entry. It does not appoint the controller, create repository authority, grant a worker capability, or supply native host permission. The root agent must not infer that it owns the controller role merely because it is the root agent, and must not self-verify root admission.

## Entry checks

1. Confirm the explicit task, canonical repository binding, parent/child and release identity, owner, current recoverable packet, and the assigned controller route from trusted current evidence. A link, packet, prior chat, installation, skill invocation, or worker statement is not role or mutation authority.
2. Read the authoritative current packet first, using the existing CURRENT carrier where applicable. Independently bind source, scope, authority, evidence, pending effects and next action. If a required binding is absent, stale, contradictory or unavailable, hold the dependent action and continue independent authorised work. Do not reconstruct authority from chronology or model memory.
3. Verify the repository identity through the existing provider-backed identity boundary. Canonical spelling alone does not prove that a second binding or writer is distinct from an alias, rename, or existing assignment. An ambiguous same-repository writer or handover remains read-only pending owner reconciliation.
4. Obtain the independently accepted Toolkit governance tuple from the trusted authority observation. The task repository remains the task namespace. Do not derive accepted governance from a packet, candidate, local checkout, caller-supplied expected value, or this skill text.

## Exact dependency proof

Resolve the accepted Toolkit authority repository, commit, exact path, and Git blob object through the trusted source adapter. Verify exactly one binding for each source:

- `controller`: `repo/CONTROLLER.md`
- `architecture`: `repo/ARCHITECTURE.md`
- `stack-registry`: `repo/contracts/controller-kernel/stack-registry-v2.json` for historical v2 admissions, or `repo/contracts/controller-kernel/stack-registry-v3.json` for explicitly admitted continuous profiles. Bind the selected version and exact path; neither source aliases or replaces the other.

Verify the repository-to-commit-to-path-to-blob relationship and the complete returned bytes against both Git blob SHA-1 and content SHA-256. Controller and registry blobs must match the accepted tuple; Architecture must be independently bound at that same accepted snapshot. Reject missing, duplicate, unknown, truncated, unavailable, or conflicting sources. Never substitute an embedded copy, cached prose, a different provider, or a successful packet parse. Keep source bytes in the authorised retrieval/evidence channel and out of packet prose and logs.

If any source or trusted-reader result is unavailable or differs, preserve the current binding and history, make no new effect, and return the exact typed failure with a concise human-readable explanation. Do not call a changed policy a product defect without causal evidence.

## Re-entry and bounded work

- Confirm the approval still covers the exact owner, action, target, resources, effects, recipient, conditions, expiry, revocation state, and recorded outcome. An unchanged, unexpired, unrevoked approval remains valid for the same still-pending action when only the turn, worker, chat, or transport changes. Seek fresh approval or host confirmation only for a changed/new action, a revoked or expired approval, or additional work not covered by the recorded outcome. Assignment, custody, capability, and host-native permission remain separate.
- Initial V3 adoption reads the complete direction once. Unchanged continuation loads the current packet, small operating entry and relevant role/authority sections. Bind exact source identities; refresh only applicable changed or conflicting instructions. Do not reread the full Controller, Architecture or programme history before each ordinary effect. Missing required provenance holds only its dependent effect.
- Bind one repository, owner, RUN/Lock, candidate/base/head/tree, scoped path/effect ceiling, budget, unresolved outcome, and return boundary. Keep independent repositories as independent bindings. A result or returned link cannot switch a binding.
- Use the existing authority-packet and execution-loop public paths for admission and revalidation. Packet syntax, durable storage, Web acceptance, CURRENT projection, or a fresh-process readback alone is not an admission token.
- Dispatch only work that the accepted CURRENT and trusted admission permit. Revalidate immediately before each effect. An unknown dispatch outcome is not permission to retry. A late result belongs to its original execution; reconcile it before any replacement.
- On context loss, recover from CURRENT and the exact bound evidence, re-establish the same RUN/Lock and unresolved outcomes, then continue the same approved builder assignment and its ordinary in-scope corrections. No new issue or mini-gate is required merely because context changed. If CURRENT or handover is ambiguous, remain read-only and request the required owner/controller decision.
- For every controller decision, record the controller actor and stable provider/host actor identifier plus a distinguishable decision prefix. Record the human owner separately; never use the owner's identity as a substitute for the controller actor. If the controller actor or stable identifier cannot be established, return HOLD.
- Compare each feedback item with the implemented source and tests and with the planned child, seed, shared, and deferred contracts. Record whether it is implemented and tested, missing, explicitly deferred/shared/seed-owned, or contradictory. Keep missing required behavior unresolved; do not silently import deferred work into the candidate or close a contradiction without evidence.
- Optional timers may only refresh bounded observations under a separately enabled, qualified scheduler. They do not launch work, change active policy, grant authority, reset budgets, or replace transition checks.

## Controller record updates

Updating a shared Controller or other governed record is outside read-only bootstrap and requires its own applicable approval and supported native write permission. When that separate authority exists:

1. Independently fetch the complete current object, including its exact body, stable identity, revision/ETag, and permission evidence through the supported provider.
2. Derive the smallest intended edit from that fresh body. Compute the inverse/preserved content and verify that every unrelated section remains byte-for-byte unchanged.
3. Check that the recorded revision still matches. Use the provider's conditional-write mechanism; if conditional writes or required permission evidence are unavailable, stop without writing.
4. Write only the approved change, then independently fetch the complete object and verify the intended edit, revision transition, and preserved content.
5. If the write response is uncertain, read the object and reconcile the actual state before considering another write. Never retry an uncertain mutation from cached state.

## V3 roles and delegation

Use the current registry family: strong G0=G1 lead, preserved prior-G0 leaf binding, and fresh G2 peer roles without helpers. G0 MUST default-delegate suitable separable evidence gathering; G1 MUST default-delegate suitable independent implementation/validation. Record substantial direct-work exceptions briefly. No nested delegation, helper quota or extra permission for already-authorised direct work. Service tier is controller/launcher metadata; the latest owner choice is Standard for future launches, never a semantic worker/helper admission condition. Bind actual model/effort at the trusted launcher; preserve real topology and native permission limits.
