# GitHub Program Reconciler

This skill loads on its own (its OpenAI metadata sets `allow_implicit_invocation: true`). The reconciler, its state documents, managed blocks and sub-issue links act only where `.github/toolkit-programme.json` exists and the repository's GitHub governance is ENABLED; programme state commands refuse without it or while governance is off (DISABLED covers plain folders and repositories not on github.com). Ordinary GitHub reads, coding, reviews and the separate read-only decision-trace audit do not need that binding. Loading on its own grants no extra authority: every write still needs the fence and checks below.

**Who uses it.** The owner opts into the reconciler by adding `.github/toolkit-programme.json`, binding the parent issue and its private state store. The reconciler supports github.com only, and its state store supports `kind: github` only; with the binding's optional `state` block the documents' public views move to a protected branch of the repository itself, and the private store keeps the rest. The binding does not change the Toolkit-governed rules (the `TOOLKIT-GOVERNED-RULES` block in `AGENTS.md`) or their issue records. Company or third-party repositories without that block get no governed issue writes, only the coding-governance gates, subagents and portable skills; global rules still apply, including PRs after requested edits and task issues when the user asks to add one.

## When to run

Any session may run the dry-run `reconcile` (or `show`) at these significant events and report it to the controller. Only the appointed controller writes programme state; see "Who records what" below.

- The binding is added (the repository opts into the reconciler).
- A task (child issue) is added, deleted or modified.
- A merge completes.
- A PR is opened or its head moves.
- An issue is closed or reopened.
- Outcomes are reordered or reprioritised.
- A release ships.
- A controller is appointed or rebinds.

Check for the binding first at each event; without it, do not run programme state commands. Governed issue records are unchanged. The reconciler never deletes or merges. Only explicit `parent_lifecycle` permission in the merged binding allows the fenced refresh to reopen an incomplete parent or complete its non-empty native tree once every descendant is closed.

For closing, merging or asking the owner to merge, follow [Closing comments](../repository-agent-rules/repo-local/docs/agent-playbooks/closing-comments.md): any agent may use `closing-comment --pr N | --issue N --body-file F [--dry-run]` with authenticated `gh`, including while governance is off. It writes no programme state.

## Refresh after every write (required)

The programme pages stay current without any token: the session that changed GitHub brings them up to date with its own `gh` sign-in, and an hourly sweep catches everything else.

- **After any write in a governed repository** (an issue or comment created, edited, closed or reopened, a sub-issue link, a PR opened, edited, reviewed or merged, or a push that moves a PR head), run `node scripts/programme.cjs refresh` from its checkout before ending the turn. Any session may, executors included: `refresh` is the full `reconcile --apply` pass written under the controller that holds the parent now, and it takes no session, patch or verdict, so it records nothing that is a decision.
- **The plugin hook does this for you** in Claude Code and Codex: the after-tool hook marks the session after a GitHub write, and the turn-end hook starts `refresh` in the background once for each governed repository the session wrote for. Its output is appended to a `last-run-<checkout key>.log` file in `~/.ai-agent-toolkit/user-state/programme-refresh/`, one per checkout. Do not also run it by hand when the hook is installed.
- **Where it cannot run** (no plugin hooks, `gh` not signed in, as in cloud containers and Projects threads, which write through the GitHub connector, or no checkout of the repository on that computer, or governance not yet decided there), do nothing extra: the hourly sweep brings the pages up to date within the hour. If the owner is waiting on the page, say it updates at the next sweep.
- **The hourly sweep** runs `refresh` where `gh` is signed in: the Projects hourly nudge's programme step, or the programme sweep task on a computer that has the sign-in. On Windows that is the no-AI `<FOLDER> - PROGRAMME SWEEP` task. An eligible local agent registers it from the recorded managed Toolkit checkout against the repository's main checkout under the global Toolkit task standing approval. Setup and `plan` only report what is needed. Owner stops and native denials remain stops. The task cleans own origin posts first, includes the store only with fresh matching enabled governance, then runs `refresh` and `attention`. A footer-only task never counts as programme refresh coverage. It also catches the owner's own edits on the web, which reach no session.
- One pass per repository runs at a time on a computer. When another pass holds the lock, `refresh` leaves a flag and ends at once, and the running pass runs once more before it lets go; if that pass fails or a long burst reaches its limit of five passes, the next refresh or the hourly sweep picks the change up. `reconcile --apply` refuses instead (`PASS_RUNNING`). The lock is taken over only when its owner's process has ended, it was written before a restart the computer can tell (by its boot id on Linux, or elsewhere by an uptime lower than the lock recorded; on Windows a Fast Startup shutdown is not a restart), or it has been silent for 6 hours (a killed pass whose process id was reused); a lock from another computer sharing the profile is taken after 15 silent minutes. A pass that loses its lock stops before its next GitHub request. `refresh` refuses when no controller holds the parent (`PARENT_UNHELD`).

The full refresh, attention refresh and applying reconciliation share a ten-minute process budget, counted before the first pass opens its store. State writes stop with three minutes left for the parent page. The parent trace indexes and body redraw from the saved documents before links, order, PR links and task pages; each queue group and effect stops with two minutes left. That leaves one minute to settle intents and record the stop, then one for the stopped CURRENT redraw, with another two minutes before the scheduled twelve-minute kill for requests already in flight. Checks cannot cancel a running request. Another flagged pass starts only with at least six minutes left. Lifecycle changes, size-finding resolution and the PR watermark wait for a complete pass with no holds or stop. An unposted parent repair notice keeps its intent until a later pass runs it.

A pass that reaches its own limit records `PASS_STOPPED`, redraws CURRENT again if time allows and exits held. Its fixed diagnostics give the cause, phase, completed count, total and start time. Different diagnostics reopen an acknowledged, disposed or resolved stop as new; an identical report leaves an open or answered stop unchanged, while a resolved stop still reopens when reported again. A small atomic `<lock>.progress` note beside the lock records phase changes and every ten completed effects, without changing the lock format. A killed or crashed pass leaves the note; the next full applying pass records `PASS_STOPPED` with cause `interrupted` unless the verified stored parent already holds its exact diagnostics, including the millisecond start time, in any finding state. Even with no planned changes, an applying pass checks that stored evidence after the parent fence check. An issue-scoped apply clears a predecessor's note only when that exact evidence is already stored. A normal end removes the note once there is nothing unreported. A later complete pass resolves the finding. Run refresh again to pick up the remaining work; no intent is replayed without read-back.

## Facts copied by refresh

Under the existing pass lock and parent fence, `refresh` copies a complete issue observation into its child document. A completed close becomes `DONE`; a not-planned, duplicate or reasonless close becomes `RETIRED`. The close time is `completed_at`, the previous lifecycle is `before_close`, and `closed_by_sweep` identifies this factual write. A reopen restores that lifecycle, or `ACTIVE` if absent, and clears the close fields. A terminal lifecycle set by the controller without `closed_by_sweep` is kept even when GitHub's close reason disagrees; refresh raises `CHILD_STATE_CONFLICT` for that disagreement or a reopened issue. The ordinary `update --patch` checks remain: only the parent holder records terminal lifecycles, UAT or review decisions. Copying a close never supplies acceptance.

An uncatalogued native sub-issue of the bound parent or a catalogued task joins the end of Later as `COMMITTED`, with its title, native parent and `added_by_sweep`. Closed additions receive their close lifecycle in the same pass. Registered programme parents and issues belonging to another registered parent are never adopted or moved across programmes. Catalogue adoption and lifecycle copying are separate refresh effects, with source observations rechecked before compare-and-swap writes. Partial or failed reads cannot authorise them.

Child documents use `toolkit.programme-state.child.v2`; readers also accept v1 and upgrade it on its next changed write. The retained v1 schema describes historical documents only. Older Toolkit readers refuse v2 as invalid rather than interpreting it as v1. New finding codes also make an older reader refuse the parent with `attention[n].code is not a known finding code`. For that parent error, unknown sweep fields or a reader requiring the v1 child schema, **update Toolkit on that computer**, then retry. `migrate-state` moves the store and does not migrate schemas.

`prs` holds every discovered task PR as number, `OPEN`/`MERGED`/`CLOSED` and merge SHA or null; `pr` remains the current PR. Task blocks show the full history, open first, then merged by latest merge time, then closed. The parent graph shows one PR per row: the most recently opened one, whatever its state, or a dash. PR numbers rise in the order PRs are opened, so that is the highest number among the current PR and the history. Retired rows show a dash. Open the task page for the full list and merge links. Refresh shares open and closed scans, closing references, title/body references and task cross-reference batches within sixty additional PR discovery requests. Per-task native sub-issue observations are outside that sixty-request PR budget, like ordinary issue and comment reads. The parent's timeline is not needed: its PR links come from each PR's own title/body references. Incomplete task discovery retains that task's history and findings that depend on it, raises `PR_DISCOVERY_INCOMPLETE`, and retries next time; unrelated findings can still resolve. An incomplete PR graph keeps the private close watermark and existing unlinked-PR findings. Ordinary reconciliation retains its completed-task backfill path, and `PR_UNTRACKED` uses open PRs only.

The first complete scan seeds the private watermark without reporting historic closed PRs. Subsequent closed scans sort by update time and stop five minutes before the watermark, keeping a small overlap for boundary updates. The watermark uses the scan start time, so a close during the scan remains eligible next time. Existing task history is retained across these incremental scans. A failed watermark write holds that effect for retry. Ordinary `reconcile --apply` holds refresh-owned findings, including acknowledged ones, until refresh checks their facts again.

Refresh records these attention findings:

- `CLOSED_WITHOUT_ACCEPTANCE`: A copied completed close lacks accepted completion. Controller: record G2 and UAT, or confirm the close.
- `CHILD_REOPENED`: A sweep-closed task reopened and its previous lifecycle was restored. Reported once per reopening, retained until answered.
- `CHILD_ADDED`: A new native task joined the catalogue. Reported once per addition, retained until answered.
- `TASK_IDLE`: A task the graph shows `IN PROGRESS` that nothing is moving. It has no open or draft PR (current, in its history, or naming it), no live gate assignment and no holder on its state document, and neither that document nor a comment on the task has changed for six hours. A task waiting on the owner is left out. Every pass checks this, and the finding clears by itself once any of those is true again. Controller: hand the task to a lane, set it back to planned, put its decision on record or retire it.
- `PR_WITHOUT_TASK`: An open PR, or a PR closed or merged after the seeded watermark, references neither a catalogued task nor the parent. Its PR number occupies the finding's issue-number slot. Dependabot and GitHub Actions are excluded; source-watch also uses the Actions bot. Owner-authored generated PRs whose source branch starts with `toolkit/shard-timings-` are also excluded, matching the weekly test-timing refresh script. Other owner-authored PRs still count. The controller can dispose with a reason using the existing command. Unanswered closed-PR findings remain visible after the watermark advances.

A finding still `new` at least 24 hours after it last became new (`changed_at`) adds to the one-line `N waiting on you` count. Reopening starts that wait again; an unchanged report keeps its age. The parent's **Waiting on you** preview shows at most five short entries and a count of the rest; `programme.cjs attention` lists every finding with its next action. Acknowledged, disposed and resolved findings do not count. The injected pass clock determines age; crossing the threshold redraws only changed text and does not write an ageing record. An unchanged refresh writes no documents or pages.

## Binding

Pending governance proposals and run receipts never permit programme writes. Only a fresh validated default-branch enabled binding does. An off decision is the minimal disabled programme file merged through a pull request; local answers and project memory never decide.

The governed repository holds `.github/toolkit-programme.json` (no secrets). It is the repository's own governance setting: only the copy merged on the default branch counts, on every computer, and a working tree, another branch or a fork's copy never does.

```json
{
  "schema": "toolkit.programme-binding.v2",
  "repository": "owner/name",
  "governance": "enabled",
  "parents": [{ "issue": 12, "record_prefix": "INT-PROG-" }],
  "store": { "kind": "github", "repository": "owner/private-store", "branch": "main", "path": "state/owner/name/" },
  "required_checks": ["validate"]
}
```

- `governance` is `enabled` or `disabled`. A merged `disabled` keeps governance off, and only an owner-merged pull request turns it back on; the repository is DISABLED, so every programme command refuses (`GITHUB_GOVERNANCE_OFF`).
- `parents` lists the programme parent issues (`writer_prefix` defaults to `record_prefix`); the reconciler records against the first. **List one parent only for now:** with a second registered parent, a task under a sub-issue of that programme could still be moved across programmes, until a planning gate rules on descendants (see Attention, "Across programmes"). Children come from native sub-issues, never from the binding. A version 1 binding (`parent_issue`, `record_prefix`, `writer_prefix`) is still read, as enabled with one parent.
- The read holds when the repository's own or command-scope git config carries a transport, proxy or TLS override, or when `GIT_SSH` or `GIT_SSH_COMMAND` is set for an ssh origin; it ignores replace refs and the repository's hooks. Trust boundary: the user's own global and system git config and the rest of their environment (`GIT_CONFIG_GLOBAL`, `GIT_CONFIG_SYSTEM`, proxy and TLS variables such as `HTTPS_PROXY`) are trusted and not held.
- Offline queue: while governance is on but records do not bind (the merged binding is not freshly read) or GitHub cannot be reached, the turn-end checkpoint returns `QUEUED` and keeps the turn in `<user-state>/programme-sessions/<session>.queued.json` (at most 200 turns, 7 days). The next turn end that writes replays them in order, in one journal write (return IDs keep it idempotent), and deletes the queue only after that write is confirmed; a DISABLED state deletes it unreplayed. Each queued turn names its repository, issue and assignment. Limits: there is one queue per session, replayed only by that session's next turn end (or `programme.cjs checkpoint --session <id>`), so a session that never resumes leaves its queued turns unwritten; turns older than 7 days, or beyond the newest 200, are dropped with a note in the session's error log; a turn queued before a rebind is skipped with a note, never written into the new assignment's journal; each dropped or skipped turn, and each unreadable entry (`QUEUE_ENTRY_INVALID`, skipped while the rest replays), is noted once however often the write fails. Session start deletes the queues of a repository whose governance is confirmed off, and `toolkit-governance.cjs status` shows `Queue: <n> turns waiting (oldest <date>)`. A signed-out `gh` is an error (`GH_AUTH`), never queued. A `GIT_SSH` or `GIT_SSH_COMMAND` set for good (Plink, TortoiseGit) keeps every refresh of an ssh origin held, so its queued turns are dropped unwritten after 7 days; `status` says so.
- Programme commands and the turn-end checkpoint run only on a read of the merged binding no older than 24 hours (`toolkit-governance.cjs status` and session start refresh it), and they take the store, parent, prefixes and required checks from that merged binding, never from the working tree.

- The repository is the `origin` remote as GitHub names it; the file must agree and cannot override it (`REPO_IDENTITY_MISMATCH`).
- `store.kind` names the backend. The only kind is `github`: a separate repository that exists, is private and is writable, checked before every pass (`STATE_STORE_UNVERIFIED`). Another kind (a different store) is added in code with the same compare-and-swap contract; an unknown kind stops at setup. There is no fallback store.
- `required_checks` adds check names to the ones GitHub marks required. With neither, checks are never `GREEN`. (Toolkit's `main` requires `validate`; its binding names it too.)
- `projection` (optional) places the Programme Graph on the parent page: `replace_section` names a hand-kept section the graph replaces while it is still there (removed in the same body write), and `after_section` names the status section the graph follows. Toolkit uses `"after_section": "CURRENT", "replace_section": "Programme index"`.
- `state` (optional, version 2 only) moves the parent and child documents to the public state branch: exactly `{ "kind": "branch", "branch": "DO-NOT-DELETE-IF-TOOLKIT-GOVERNANCE-IS-ENABLED", "path": "state/" }`, on the bound repository itself. `store` stays required beside it. `migrate-state` prints this block; it takes effect only once a pull request merges it (see "The public state branch").

## Parent lifecycle

The optional version 2 `parent_lifecycle` block explicitly sets both `reopen_incomplete` and `complete_when_children_closed` to booleans. Absence grants no automatic lifecycle writes. Only the bound programme parent is affected. Every paginated native child and descendant counts, including optional and uncatalogued tasks. Unattended completion uses a full native-tree walk when planning and again immediately before the fenced close, each bounded to 120 seconds; a closed intermediary cannot hide an open descendant. An empty tree never completes automatically. Child acceptance and user testing requirements remain unchanged.

The existing fenced refresh is the only repair owner. It rechecks the native tree just before mutation, persists intent, verifies state independently, and recovers uncertain outcomes before retrying. Repair notices identify the closure event, actor and time, with closing source unavailable when the event has no commit. A deterministic marker prevents duplicate notices. Completion happens on the next successful refresh or sweep; schedules guarantee neither immediate nor overnight repair.

Use Refs for parent links in records and pull request bodies; avoid closing words before those links. The pre-write edit guard inspects only supplied new title/body text. Merge and read-only CI checks inspect the live title, body and every commit. The hooks also inspect merge-message overrides and explicit issue closes. Literal quoted text, quoted heredoc bodies and literal here-strings are inspected as text. Expanding text, unreadable files, editor content and unresolved stdin hold the affected write; provide literal text, a literal heredoc or a readable body file. URLs and the saved parenthesised record-link incident pattern are defensive matches, rather than claims about documented GitHub grammar. Reads remain unaffected except queries supplied through a variable: the call must start with one literal assignment for that variable. With an unreported shell, match variable-name case or name PowerShell explicitly. Known refusals also include guarded writes assigned to variables even with clean text, and a body assigned through a here-string then supplied as a variable; use a readable body file. gh pr create with --fill, --web or no title and body also refuses, because its text cannot be inspected; give a literal title and body.

Local writes needing GitHub state refuse unavailable or signed-out gh and name its recovery. Cloud checks refuse proven open descendants; unknown state is advisory, with required CI as backstop. Hooks share one invocation deadline across reads and merges, 7.5 seconds on Claude Code and fifty seconds on Codex. Every subprocess gets at most the remaining time.

Hooks and CI trust a child summary of zero to avoid a large tree walk; stale summaries can hide an open grandchild. Unattended completion never uses that shortcut. PR commit lists must be complete: more than 250 commits is unsupported and returns unknown rather than inspecting a truncated list. Shell inspection reads literal commands, recognised shell-script arguments, bounded loops, shell heredocs, PowerShell blocks and block comments, and skips PowerShell's stop-parsing word. An unquoted gh issue close, gh pr create, new or edit, or writing gh api call found elsewhere in a command, including with a brace or equals sign attached to gh, is refused by name, as is a gh command whose noun, or whose verb under pr or issue, comes from a variable; data commands and quoted text stay data. The reader works on words, so this covers the shapes it can see, not all shell syntax. Accepted gaps are aliases, functions defined outside the command and external scripts; a program name produced by a substitution, such as $(which gh) or & (Get-Command gh); encoded or opaque commands; a command name or whole script held in a variable, including Start-Process parameter splatting; gh api fields held in a variable after a literal endpoint; text piped into a shell from another command; a quoted command handed to a program Toolkit does not read, such as watch, trap, parallel, script, remote ssh or python; git subcommands that run commands, including bisect run, submodule foreach, rebase exec and configured aliases; cmd percent-variable text, a caret inside a word and an at sign before gh; brace expansion and dollar-prefixed quoted text; shell option spellings outside the reader's tables; gh.cmd and gh.bat; REST paths not starting repos/, and direct REST from other programs; a repeated -R before the verb; a lone carriage return as a separator; arithmetic shifts read as a heredoc; GitHub Enterprise hosts; body files generated by external scripts that do not name them; cloud shell merges and auto-merge text. Codex code-mode nested shell calls reach the hook as Bash. A PowerShell alternate reading holds ambiguous backslash quotes around a guarded GitHub write on Codex only; ordinary quoted data stays allowed. Accepted host delivery gaps are the outer JavaScript cell, write_stdin into an already allowed shell and opaque Desktop REPL code.

Shell interpretation follows a named shell, an argument-list shell runner or the reported Bash/PowerShell tool. When the shell is unreported, text with an escape that may still expand is held; use a named shell or literal file. Nested script arguments retain expansion information from their outer shell. Merge-message files use the same generated-file and literal-stdin checks as PR bodies.

## State documents

One private JSON document per outcome (`issue-<n>.json`) and one for the parent (`parent-<n>.json`) under the store path, plus executor journals under `journal/issue-<n>/`.

- **Parent:** fence, release-plan pointer and the **outcome catalogue** (issue, label, class `COMMITTED`/`OPTIONAL`/`COMPLETED`/`RETIRED`, expected native parent, `order`, the priority: lowest first within each group, ties by child number, so the top Later task starts next, lane, owner prefix, and an optional task `name` and one-line `description` for the Programme Graph). Now and Later are never stored: they come from each task's PR and gate. The catalogue is data: nothing is hard-coded to one programme.
- **Child:** lifecycle, completion time (`completed_at`), release, gate (role, state, assignment, session, route, returns), candidate (full 40-character SHAs), PR (number, state, head, required checks at that head), UAT, review verdicts, blockers, exactly one next action, pending effects and a `private` field that is never rendered.
- Writes use Contents API compare-and-swap on the blob sha with readback. Unchanged state is never written (GitHub would still make an empty commit). The revision moves only when content changes; timestamps and pending effects do not count.
- On a 409 the change is re-applied only when the other writer touched different top-level fields and the fence did not move; otherwise `STATE_CONFLICT` or `STALE_WRITER`.

**The public state branch.** With `state` in the merged binding, the parent and child documents live on `DO-NOT-DELETE-IF-TOOLKIT-GOVERNANCE-IS-ENABLED` under `state/` (`parent-<n>.json`, `issue-<n>.json`) in the bound repository, as public views; the private store keeps everything else. Without `state` everything works as described above.

- **What is public.** The document without `private` and without the gate's route; the holder's session and the gate's session appear only as 16-hex hashes (`holder_session_hash`, `session_hash`), the same hash journal names use. Every write and read checks the public view against closed key lists, and free text (next action, blockers, release, reviewer, catalogue labels, names, descriptions and lanes, the release-plan record) may not hold a path (`\`), an address (`://`), an `@`, something that reads as a host name (three dotted labels) or a session ID; a raw session ID is refused anywhere. A refused write is `STATE_INVALID` before anything is written; keep such text in `private`.
- **What stays private.** Journals (unchanged, in the private store), and per written revision a sidecar `<store path>private/<doc>/r<revision>-<digest>.json` holding the whole document and the digest of its exact public bytes, written before the public file. A read joins the public file to the sidecar of the same revision and digest (`STATE_SIDECAR_MISSING` holds a hand edit). Sidecars of the last 20 revisions are kept. The checkpoint `<store path>checkpoint.json` records the branch head and each document's revision and digest after every write, and a copy goes to this computer's `~/.ai-agent-toolkit/user-state/programme-state-checkpoint/`.
- **Writes** keep the same compare-and-swap, readback, fence and "unchanged state is never written" rules; each commit is `programme-state: <doc> r<revision> [skip ci]`. A private store that is no longer private stops every write (`STORE_NOT_PRIVATE`). `refresh` acts as the parent's holder by the stored hash of its session only: it can bring documents in line, and every decision (`claim`, `ack`, `dispose`, a verdict, UAT or review, a terminal lifecycle) refuses it (`ROLE_REFUSED`).
- **Recovery** runs inside the read path of any command or `refresh` (so the hourly sweep finds it), never from a hook. A missing branch with a checkpoint was deleted: it is restored at the checkpoint commit if GitHub still serves it and every file matches its digest, else rebuilt as a new commit from the sidecars if every digest matches, else held (`STATE_RESTORE_HELD`); unsettled intents also hold it, and it is never started empty. A missing branch with no checkpoint was never created, and only `migrate-state` creates it; with only this computer's checkpoint copy left it holds. A file below the checkpoint's revision (a force-push back, a deleted file) is `STATE_ROLLED_BACK`. Restores and recomputed checkpoints are reported under `State branch` in the command's output.
- **Protection.** The all-branch no-force-push ruleset covers force pushes; `toolkit governance migrate` offers a second ruleset, "Toolkit: keep programme state" (deletion, that branch only), after its own typed yes, for a repository whose merged binding has `state`. A private repository on GitHub Free reports `not-enforceable`.
- **Moving to it.** `migrate-state --dry-run` prints each public document, its sidecar path and digest, any problem (a field that is not public-safe, an intent not settled) and a plan digest; it writes nothing. The controller then runs `migrate-state --apply --plan-digest <digest> --controller --session <id>`, which asks for the owner's typed yes in a terminal (never from a pipe or an agent's shell), writes the sidecars, one orphan commit with the public documents and the checkpoint, reads every document back one to one, and prints the `state` block for the binding pull request. Any problem stops it before anything is written. The typed yes is never asked in a shell a coding agent started (the exact markers `toolkit env show` refuses on).
- **Until the binding pull request merges**, every write still goes to the private store: stop the programme sweep and make no programme writes (claims, verdicts, acks, `refresh`). The checkpoint records each private document's blob at the move, and any document that changed or appeared in the private store since holds every branch read (`STATE_MIGRATION_STALE`), so a write is never lost silently. Then run the dry run and `--apply` again: while nothing has been written to the branch since the move, it moves the newer documents onto it as a new commit on top (never forced); once the branch has been written, it refuses and the controller reports to the owner.

**Fence.** A document is held by one session and record prefix. Every write comes from the session that holds the parent document. `claim --takeover` increments the epoch in one compare-and-swap. A running pass re-reads the parent fence immediately before every state write and every GitHub change, so after a takeover the old pass stops at its next effect (`STALE_WRITER`); an intent it leaves `IN_FLIGHT` is settled by the successor's readback. The fence orders cooperating Toolkit writers under one account; it authenticates nobody and does not stop a person or another tool editing.

**Who records what.** Only the appointed controller writes programme state. Give the controller a stable writer name (for example `toolkit-421-controller`) and pass it as `--session`: coordinator sessions are replaced from time to time, and a fence held by one session would need a takeover after every replacement. Every coordinator, and every `refresh`, then writes under that one name; a different controller takes over on purpose with its own name. The controller creates the parent document (`init-parent --apply`) and holds it, and runs every writing command with `--controller`: `reconcile --apply`, `update-parent`, `claim`, `assign`, `reopen`, `interrupt`, `update` and `return`. It assigns each gate (`assign --issue <n> --role <gate> --assignment <id>`), records and consumes returns, records UAT and G2 review verdicts, and sets `DONE` or `RETIRED`. Without `--controller` a writing command is refused before it reads anything, and with it a session that does not hold the parent is refused by the fence. An executor the controller assigned (G0, G1 or G2) writes only its own checkpoint journal (see "Executor checkpoints"); helpers never write; every other session runs only the dry-run `reconcile` and `show` and reports to the controller. The one exception for all of them is `refresh` after their own GitHub writes, which decides nothing (see "Refresh after every write"). A lane controller the catalogue delegates a child to (`owner_prefix`) may hold that child with `claim --issue <n> --lane` and only `assign` and `interrupt` it. A controller stopped by a takeover stops and reports to the owner; only a controller appointed after that takeover verifies that the previous writer stopped, posts its takeover record on the parent issue, then runs `claim --parent --takeover --takeover-record <comment id> --controller`. The tool reads that comment back: on the parent issue, from the same account, with a decision ID carrying the writer prefix, naming the current epoch and posted after the last state write (`TAKEOVER_UNVERIFIED` otherwise). The replaced holder is refused from then on.

**Gates.** `NONE` → `ASSIGNED` (assigned, no journal yet) → `ACTIVE` (the assignment's journal seen) → `SUBMITTED` (a return captured) → `ACTIVE` again (`REOPEN`), `WAITING_OWNER`, or `RETIRED` (`ACCEPT`). `interrupt` marks a live gate `INTERRUPTED`. `assign` is refused while a gate is live (`ASSIGNMENT_LIVE`) unless `--supersede --reason`, and an assignment ID is never reused. `reopen --reason` puts `SUBMITTED` or `WAITING_OWNER` back to `ACTIVE`, and a `RETIRED` gate back to `ASSIGNED` under a new `--assignment`, which removes its acceptance.

**Returns.** A gate return is consumed by its return ID, never by session. The controller records a return reported in a thread or chat with `return --record <id> --assignment <id>`; reconcile captures one from a journal. `REOPEN` puts the gate back to `ACTIVE` with the same assignment, and the next return takes a new ID; `ACCEPT` retires the gate. A G1 `ACCEPT` needs a G2 review `PASSED` at the live PR head (`EVIDENCE_STALE` otherwise). Consuming the same ID again with the same verdict does nothing; a different verdict is `RETURN_CONFLICT`; a return from before a takeover is `STALE_RETURN`; one for another assignment is `STALE_ASSIGNMENT`.

**Executor checkpoints.** The controller tells the executor its issue and assignment. The executor reads its model and effort from session metadata, then runs `bind --issue <n> --assignment <id> --session <its own session ID> [--model <m> --effort <e> --route-read-back]` once (Claude Code: `CLAUDE_CODE_SESSION_ID`). That writes its journal, `journal/issue-<n>/<assignment>--<session hash>.json`, and a local binding under the user's `.ai-agent-toolkit/user-state/programme-sessions/`. After each turn the plugin's turn-end hook refreshes the journal with the branch, head, tree, dirty flag, ahead and behind, and the last fenced `toolkit-return` block in the final message (`return_id`, `verdict_requested` `ACCEPT` or `WAITING_OWNER`, `at_head`, `next_action`, `blockers` separated by `;`). `checkpoint --session <id>` does the same by hand, and `show --session <id>` lists the local binding and recorded errors. The hook never blocks a turn, prints nothing, returns at once for a session that has not bound, and writes nothing when nothing changed. A journal is evidence, not state: nothing changes until the controller's reconcile reads it. Where binding is not available (Codex today, cloud sessions and Projects threads), the executor reports in its thread and the controller uses `return --record`.

**Evidence at a head.** UAT `PASSED`, `UAT_RETAINED` and `UAT_PARTIAL_REQUIRED` must carry `at_head` (the full SHA), and a decided review must carry at least one verdict with its head; otherwise the write is refused. Evidence at an older head than the live PR head renders as `STALE_HEAD`.

## Attention

Completed tasks without a recorded PR discover their merged PR automatically, even with a retained candidate branch. Discovery combines explicit body references (`Refs`, `Completes`, `Closes`, `Fixes` or `Resolves`, including lists), closing PR links and timeline PR cross-references. Only merged PRs in the same repository qualify. Duplicate references count once; the greatest merge time wins, then the higher PR number on an exact timestamp tie. Planned effects list the candidates and selection reason. Existing PR numbers stay recorded. Retired tasks are excluded; their Programme Graph PR cell shows a dash and, when history exists, its count. Historical stored PRs remain intact.

Each observation pass shares a closed-PR scan of at most ten pages of one hundred, batches issue links in groups of twenty and caches PR details by number. A full tenth page or another page on either issue connection is incomplete. At most sixty additional discovery and uncached detail requests run per pass; unresolved tasks retry on later passes. Once no tasks qualify, this discovery adds no requests. A failed, truncated or budget-limited read reports `PR_DISCOVERY_INCOMPLETE` and selects nothing for the affected task. Complete discovery with no match reports `COMPLETED_PR_MISSING`. An earlier missing-PR finding stays open during incomplete discovery.

Backfill uses the existing guarded child-state mutation and exact commit readback. The mutation rechecks the fresh child and parent outcome, including on retries: a recorded PR or changed eligibility holds with `PR_BACKFILL_STALE` for replanning. Takeovers still stop the pass. Backfill records PR observations only; acceptance, UAT, review, lifecycle and issue closure stay under their existing rules. Both projections use the stored result in the same pass, and an interrupted projection is repaired on the next pass.

Findings the controller must answer stay on the primary parent document (the binding's first parent) as `attention`. Each entry is `{id, source, code, issue, head, state, first_seen, changed_at, diagnostics?}`: `id` is the first 12 hex characters of sha256 of `source|code|issue|head` (`head` only for `PR_HEAD_MOVED` and `CHECKS_RED`), `code` comes from a fixed table with its next action, and `state` is `new`, `acknowledged`, `resolved` or `disposed`. Size findings have bounded numeric `diagnostics`, never page text. No free text is stored; a dispose reason goes to `private.attention_notes`.

- **Sources.** `reconcile`: the reconciler's report-only codes (`ISSUE_MISSING`, `NATIVE_PARENT_UNEXPECTED`, `NATIVE_CHILD_UNKNOWN`, `DEPENDENCY_IMPLIES_PARENT`, `PR_HEAD_MOVED`, `CHECKS_RED`, `READY_TO_CLOSE`, `CHILD_STATE_CONFLICT`, `MANAGED_BLOCK_BROKEN`, `BODY_TOO_LARGE`, `TRACE_UNLINKED`, `TRACE_SUPERSEDED_UNMARKED`, `PR_UNTRACKED`, `COMPLETED_PR_MISSING`, `PR_DISCOVERY_INCOMPLETE`, `RETURN_CAPTURED`, `STALE_ASSIGNMENT`, `JOURNAL_ERROR`, `JOURNAL_INVALID`, `CLASS_LEGACY`, `ORDER_TIE`) and `DUPLICATE_HIERARCHY`. `inventory`: `NEEDS_PLACEMENT`, `CLOSED_PARENT_OPEN_CHILD`, `INVENTORY_INCOMPLETE` and `ATTENTION_FULL`.
- **Lifecycle.** A complete run of a source adds what it saw as `new`, leaves unchanged findings untouched (an unchanged run writes nothing) and resolves only that source's findings whose condition is gone, except size findings, which need a verified redraw in a complete pass without holds; a finding that comes back is `new` again with the same id. A full `reconcile --apply` or `refresh` is a complete reconcile run; `reconcile --issue` records only `BODY_TOO_LARGE`, from planning or apply refusals (preview writes nothing). An incomplete inventory records only `INVENTORY_INCOMPLETE` and resolves nothing. Only the parent's holder acknowledges or disposes (`ROLE_REFUSED` otherwise), and `refresh` never does. An acknowledged finding stays listed until it is resolved. **One-time codes** (`RETURN_CAPTURED`, `JOURNAL_ERROR`, `JOURNAL_INVALID`, `STALE_ASSIGNMENT`) are reported only on the pass that first reads a journal, so they stay open without being seen again: `RETURN_CAPTURED` while the live assignment has a return no verdict has consumed (a return left by an interrupted or superseded assignment does not hold it); `JOURNAL_ERROR` and `JOURNAL_INVALID` while they are new and the task has a live gate; `STALE_ASSIGNMENT` while it is new. An acknowledged one (apart from `RETURN_CAPTURED`) then resolves on the next complete pass. A fresh report of a one-time code reopens its entry as `new`, even when it was acknowledged or disposed, except a `JOURNAL_ERROR` whose error is no later than the entry's last change (a journal that still shows the old error), whether the entry was answered or has resolved since.
- **Bounds.** At most 200 entries are kept, dropping the oldest resolved or disposed ones first; new and acknowledged findings are never dropped. Past 500 of those, nothing more is added and `ATTENTION_FULL` is set until a complete run is back under the bound. Attention changes are written without a revision bump.
- **The inventory** (`inventory`, and inside every `refresh`) reads every open issue in one paged GraphQL query (pull requests are never listed) and gives each one class: `PARENT` (listed in the binding's `parents`), `CHILD` (a native descendant at any depth of a registered parent, or a catalogued outcome with no native parent yet, which the reconciler attaches), `OUTSIDE` (the label `programme:outside`, or a comment whose first line is `OUTSIDE-PROGRAMME` by an `OWNER`, `MEMBER` or `COLLABORATOR`; comments are read only for issues that would otherwise need placing) or `NEEDS_PLACEMENT`, with a finding. A closed registered parent with an open descendant raises `CLOSED_PARENT_OPEN_CHILD`. A run has a deadline (120 seconds by default); a missed deadline, a failed page or a parent chain that loops or runs deeper than 8 levels makes it incomplete. It never links, labels, comments, closes or catalogues anything.
- **Across programmes.** A catalogued outcome that sits natively under another registered parent is never reparented: the pass reports `DUPLICATE_HIERARCHY` and the controller decides. Under an unregistered parent it is still `NATIVE_PARENT_WRONG` with a reparent. The check reads only the outcome's direct native parent, so an outcome under a sub-issue of a second programme would still be reparented across programmes: **do not register a second parent in any binding** until a planning gate rules whether a registered parent owns its deeper descendants, and the pass holds against every registered parent in the ancestor chain.
- **Where it shows.** `attention` prints `Attention: <n> new, <m> acknowledged` or `Attention: clear`, then the open findings newest first, each with its id, next action and size diagnostics when present; a GitHub that cannot be read prints `Attention: unknown (<reason>)`, never clear. With `--refresh` it also prints the refresh pass's holds ("The refresh pass held") and exits 1. The parent's `CURRENT` block ends with the same line and up to 10 open findings, so a surface without `gh` reads it from the page. `claim`, `assign`, `return --consume` and an `update` to `DONE` or `RETIRED` print the stored line first (standard error, and `attention` in the JSON) from the parent they already read, with no extra GitHub request, and never refuse on it. At session start, Claude Code and Codex add the line from this computer's cache (`~/.ai-agent-toolkit/user-state/programme-attention/<owner>--<name>.json`, written by `refresh` and `attention`): every session while a finding is new or acknowledged, `Attention: clear` once after each change, `not checked on this computer yet` with no cache; a missing or hour-old cache starts `refresh` in the background, at most once per 15 minutes per repository, and the line says so only when one started. The hook itself reads only local files. It also adds a `Checkpoint:` line for each session on that computer whose last turn-end record failed, until a later one succeeds.
- **The controller answers attention.** Run `programme.cjs attention --refresh` (or read the parent's `Attention:` line) before launching a gate, before an acceptance or finality step, and before declaring a turn or the programme settled, and answer every `new` finding in that turn: fix it, `ack` it or `dispose` of it with a reason. Without the plugin hooks, run `refresh` and `attention` by hand at session start; `toolkit-governance.cjs status` shows which hosts here run the hooks (`Hooks:`).

## The reconcile pass

1. **Bind** repository identity, the store and the binding; read the parent and every catalogued child document.
2. **Observe** (read-only): issues (with open sub-issue counts), native parents, each expected parent's sub-issues in order, `blocked_by` edges, and for each child PR its head, base and the default branch, and required checks at that head.
3. **Recover first:** each pending effect from an earlier pass is settled by reading its target. Done or not done leaves the document; an unreadable target stays `UNKNOWN` and holds that target. Nothing is replayed without that read.
4. **Diff** into findings: `NATIVE_PARENT_MISSING`, `NATIVE_PARENT_WRONG`, `NATIVE_ORDER_DRIFT`, `PR_HEAD_MOVED` (review and UAT at the old head show `STALE_HEAD`), `CHECKS_PENDING`/`RED`/`UNKNOWN`/`GREEN_AT_HEAD`, `PROJECTION_STALE`, `CHILD_STATE_CONFLICT` (for example `DONE` on an open issue, or a merged PR where the current gate is not accepted, or only G0 is accepted), and report-only `READY_TO_CLOSE`, `NATIVE_PARENT_UNEXPECTED`, `NATIVE_CHILD_UNKNOWN`, `DEPENDENCY_IMPLIES_PARENT`, `TRACE_STALE` (the comment trace is missing or behind the comments), `TRACE_UNLINKED` and `TRACE_SUPERSEDED_UNMARKED` (the decision-trace audit), and `PR_UNTRACKED` (an open PR whose body says `Refs`, `Completes`, `Closes`, `Fixes` or `Resolves` `#n` for an open outcome whose state records no PR or branch; the controller confirms and records it with `update`). `CLASS_LEGACY` (report-only) names catalogue entries still using the older classes `CORE`, `HARDENING` or `LATER`. Until they are migrated they read as `COMMITTED` and sort like any other task, by group, `order` and child number; their old per-class numbers tie, so the first pass may reorder them and their native sub-issues. The finding carries a `patch` (see `reconcile --json`): apply it whole with `update-parent`; it sets `COMMITTED` and renumbers every open entry's `order` in the old CORE, HARDENING, LATER sequence, which becomes the priority. No write adds an older class (`PATCH_REFUSED`), and `init-parent` refuses them. `ORDER_TIE` (report-only) names queued rows in one group that share an `order`; child number decides until the controller sets distinct values with `update-parent`; while `CLASS_LEGACY` is also reported, migrate first, or set `COMMITTED` and the priority in one patch. Native siblings sort like the Programme Graph rows.
5. **Plan** these effects: create or update a child document, attach a sub-issue, reparent (`replace_parent`), reorder (fewest moves), replace the managed blocks, post an index comment for an overflowing trace. Refresh also has the dedicated fact-copy effects described above and records a complete PR-scan watermark in the parent sidecar. Only explicit parent-lifecycle permission permits a parent state change. Child closing, deleting, merging and detaching never appear. Dependencies never set a parent.
6. **Apply** (only with `--apply`): settle recovered intents once per document, write adoption, attention and child states, then redraw the parent page before the queue. Commit each group's `IN_FLIGHT` intents together on the parent document, check the fence before every GitHub change, and read each effect back independently (both sides for links; the whole body for blocks). Settle the group in one commit, keeping uncertain intents `UNKNOWN` and holding only their scope. Historical child-document intents still recover by the same read-back rules.
7. **Report** the repository, store and parent revision, findings, effects with outcomes, holds, write counts and one next action. The `READY_TO_CLOSE` close list names open issues whose PR is merged with required checks `GREEN` at its head, with the PR, head, current gate, UAT and review states. `gate_accepted` records whether the current gate is `RETIRED` with its latest return consumed as `ACCEPT`; `accepted` counts completion only for G1 or G2. `closable` marks entries with that acceptance, UAT recorded as `NOT_REQUIRED`, `PASSED` or `UAT_RETAINED` at the head, every review verdict at the head passed (or no review record), a merge into the default branch and no open sub-issue; the controller closes those as completed without asking (governed issue rule) unless a criterion is still open, and the reconciler itself never closes. A missing G1-or-later current-gate acceptance still reports `CHILD_STATE_CONFLICT`. A pass with nothing to do says `No changes` and writes nothing.

GitHub details the code relies on (checked against the REST docs and a private sandbox): `sub_issue_id` is the issue's database `id`, not its number; a second parent without `replace_parent` and a duplicate attach both return 422; a reorder needs exactly one of `before_id`/`after_id`; a stale Contents sha returns 409 and a create over an existing file 422.

## Managed blocks

Each catalogued issue body carries blocks in the Toolkit marker format (`<!-- AI-AGENT-TOOLKIT:programme-state:BEGIN <NAME> v2 toolkit=<version> sha256=<12 hex> -->` ... `END <NAME>`): `STATE` and `TRACE` on every page, `CURRENT` and `CONTEXT` on the parent, and `NAV` on task pages and their open or draft PRs.

Generated parts lead and hand-written text follows. The parent has four managed capital headings: `# CURRENT`, `# PROGRAMME GRAPH`, `# AGENT CONTEXT` and `# COMMENT TRACE`. Context follows the graph as a renderer-owned background stub; hand-written notes keep their bytes and order, and an existing trace stays in place. Toolkit never moves the parent's hand-written sections. If the page nears its size limit, shorten them by hand. Migration removes only one exact `## CURRENT` line adjacent to the old CURRENT block with blank lines between. On first insertion, only the first exact `## CURRENT` heading outside code fences and HTML comments migrates into the managed block (raw HTML blocks, a fence that starts on a list-marker line, a leading byte-order mark and a lone carriage return are not modelled yet). A task page and a task's PR page follow the fixed layout under "Task and PR page layout".

- **The Programme Graph** is the parent's `STATE` block, under `# PROGRAMME GRAPH`, directly under the `CURRENT` summary. The binding's existing `replace_section` migration still replaces a hand-kept index. One table has the columns `Task | Task Description | Child # | PR # | Class | Status | Last updated (SGT)`:
  - Task is the catalogue `name`, else the issue title without a leading short code and dash or a leading "Toolkit <version>:".
  - Class is worked out, never stored: `NOW` when the task is in progress (an open or draft PR, or active, waiting on the owner or held), else `LATER`, or `OPTIONAL` for an optional task. A planned release names where the work merges and does not change the group. A finished row shows `-`.
  - Status is `QUEUED` (planned, no open PR), `IN PROGRESS` (active, waiting on the owner, held, or planned with an open PR), `COMPLETED` (done) or `RETIRED`.
  - Task Description is the catalogue's one-line `description`. The gate a task is in (`G0`, `G1` or `G2`) shows in `CURRENT` and on the task page, not in the graph.
  - Last updated (SGT) shows the completion time for finished tasks, using the state document or the issue close time. For work in progress it shows the latest state write or task comment, excluding generated index comments. Queued tasks and missing times show `-`. Times use Singapore time (UTC+8), to the minute.
  - Rows sort `NOW`, `LATER`, then `OPTIONAL`, each by priority (`order`, lowest first) and then child issue number, so the top `LATER` row is what starts next; then every `COMPLETED` row and then every `RETIRED` row, each by completion time with the most recent last. Nested children sort like any other row. Native sub-issues follow the same order.
- **A child's `STATE` block** is headed `# STATUS` and shows status, class, lane, release, task description, the tracked PR with its head as a 7-character link plus the full SHA as text, CI at the head, UAT, review, next action and blockers, with its document revision. Under **Pull requests** it lists every PR found for the task, open first, each with its state and merge commit.
- **The `CURRENT` block** opens the parent's status section (the binding's `after_section`, else under the title) with a generated **In progress** list from the same state as the graph: each task in progress with its gate, PR, anything waiting on the owner (a decision, a UAT, or a blocker) and next action. Then one **Start next** line names the top `LATER` task whose PR has not merged and whose issue is open (or None), and the **Attention:** line shows the full count with up to ten recent or acknowledged findings. Waiting findings appear only in a separate preview of at most five short entries, with a count of the rest and the attention command for the full list. Other queued work shows only in the graph. The graph follows it, then the hand-written notes, which are never changed. Write those notes in plain English for the owner: where things stand, what is happening, what needs the owner, and the rules in force, each with a link; keep older notes in folded sections below.
- **The `NAV` block** is headed `# PATH` and opens every task page and every open or draft PR that names a task: `#<parent> > #<expected parents> > #<task> > PR #<pr>`, one line per task on a PR that names several. A merged or closed PR is not edited.
- **The `TRACE` block** is headed `# COMMENT TRACE`. On the parent it is added at the end the first time only and then updated where it stands, so keep hand-written text above it. On a task page it is the third generated block. It lists only that issue's own comments: the parent's list and a task's list never mix, and a controller working on a task reads both. A comment's topic is its first line when its second line is exactly `---`. The topic is the task's name as the graph shows it, or a short subject for a programme-wide comment (for example `Codex host support` or `Plain-text check`), never a category such as `RELEASE`. On a task page, untopiced comments fall under the task's own name; on the parent they fall under "Other comments". There is one line per topic, in first-seen order with the untopiced line last: `- **<topic>:** [<comment ID>](<issue URL>#issuecomment-<id>) · ...`, a replaced record followed by `(replaced by [<ID>](...))`, under a note that the body comes first and, within a topic, where comments disagree the latest one wins. Every link is the comment's full URL, so it opens the comment from anywhere: a bare `#issuecomment-` fragment only works when the comment is already on the page, and GitHub folds long timelines and the mobile app opens the issue itself. When the body would reach the threshold, the pass tries the largest topic lists first within its five-comment budget, each whole list in its own index comment (which carries the topic on its first line), and the line shrinks to `[list 1](...)`. When that cannot fit, full topic lines share directory pages instead. Newer comments line up in the body again until the next overflow. Topics stay on separate lines. Bot comments are left out.
- A `STATE` block in its place is updated in place; one anywhere else, higher or lower, moves to its place once, reported as "Move the state block". A section ends at the next heading of its level or higher or at the next managed block, and only blank lines are trimmed where text is joined. A page whose managed blocks were written by a newer Toolkit is held (`BLOCK_NEWER_TOOLKIT`) and left as it is, so computers on different Toolkit versions never flip it between layouts; update Toolkit there and run again. A hidden line in the parent block lists every child revision, so parent and child can be checked against each other.

### Task and PR page layout

Every open task page has one fixed order. Headings in capitals are generated or required; a heading in sentence case is optional.

1. `# PATH`, `# STATUS` and `# COMMENT TRACE`: the three generated blocks, as one run at the top.
2. The spec sections that the page has, in this order: `# PROBLEM`, `# FIX`, `# IF WE SKIP`, `# DONE WHEN`, `# NOT IN SCOPE`.
3. `# More`: every other piece of hand-written text, word for word and in its original order, the page's own title line included.

**When you file a task, write those five capital sections.** A pass also converts older pages: a bold label line such as `**The problem:** ...` or a heading such as `## Done when` becomes the matching capital heading, and the words under it do not change. A section runs to the next spec section or to someone's own heading of the same or a higher level. People's own headings keep their wording and case. Text inside code blocks, lists, quotes and details sections is never read as a heading.

- **Blocks shown as examples.** A managed block pasted inside a code block, a quote, a list item or indented code is hand-written text on every page, PR pages included: it is never updated, moved or cut, and the page's own blocks are added outside it. Below the start of a code block, HTML block or details section that is never closed, markers are read as before, so a real block there is not written twice.
- **The plan says when text moves.** The effect for a page about to be laid out reads `Lay out #<n>'s page in the fixed order ...`, with the finding `the page is not in the fixed section order`, and its result names the saved copy's path. A page that waits for the ten-page limit says so in its result.
- **Saved copy first.** Before a write that moves hand-written text, the page as it stands is saved to the private state store under `page-copies/issue-<n>-<digest>.json` and read back. If the copy cannot be saved the page is not written in that pass (`PAGE_COPY_FAILED`) and the next pass tries again. A page already in order needs no copy: only its blocks change.
- **Checked before writing.** The re-laid page must give the same bytes when laid out again and must hold every hand-written word; otherwise it is held.
- **Held pages.** A page that cannot be split safely keeps its text where it is, still gets fresh blocks in place, and raises `PAGE_LAYOUT_HELD` with the reason: an unclosed code block, HTML block or details section, a spec section or `# More` that appears twice, a block that belongs to another kind of page, or a secret-shaped value (no copy of it may be saved). Fix what the finding names and the next pass lays the page out.
- **Ten pages per pass.** A pass re-lays at most ten pages; the rest keep fresh blocks in place and follow in later passes.
- **Closed tasks** are history: their blocks are updated in place and their text is not moved. A closed page already in the fixed order stays in it.
- **A PR page** for an open or draft PR that says Refs, Closes, Fixes, Resolves or Completes for a catalogued task gets `# PATH` and `# STATUS` at the top. The status lists, for each task the PR names, its gate, the review at the PR head, UAT and release. The description below is left exactly as written, example blocks in it included. A merged or closed PR is never edited, including one that closes between planning and writing.

The parent starts moving graph rows only when the full projected body reaches 55,000 UTF-16 units. It moves the shortest prefix in this order: retired, completed, the trace's own paging, optional, Later, then Now. Finished rows move oldest completion first; open rows move oldest issue first. The remaining table and archive comments keep graph sort. An `Archived:` line links each group count and any continuation parts. Reopened tasks return to the body. Empty graph parts stay registered and are edited to an empty note, ready for reuse.

The public `page_archive` registry contains graph parts only and is outside the revision digest. A part starts pending before publication; only an exact read-back under the authenticated login records its comment id. The body hides verified rows only, then marks parts moved after its own guarded write reads back. An exact comment on the right issue, authored by its recorded login, remains verified read-only when the signed-in login changes: retain its link and never repost it unless the content must change. Only registered ids authored by the current login with matching issue and previous digest may be edited. Changed, foreign or missing comments are detached: their ids are never edited or adopted again, and fresh verified parts replace them within the five-post budget while redraw continues. Keep at most 32 excluded ids in `untrusted_ids`: the registered id if rejected, then the newest others. A part superseded by a fresh post from another login is excluded quietly, without a trust finding. When dropping older ids, advance `untrusted_before` to the highest dropped id and permanently exclude unregistered candidates at or below that floor, even otherwise exact ones. An independently verified registered id keeps its trust unless explicitly rejected; a rejected registered id stays pinned in the list. Existing larger lists remain readable and compact on the next exclusion. This conservative drop rule never restores adoption trust. `ARCHIVE_COMMENT_UNTRUSTED` stays visible until the owner disposes it (acknowledgement leaves it open); a successful redraw cannot resolve it. Lost-reply duplicates select the lowest exact verified comment id and detach the other candidates. Unreadable targets remain UNKNOWN until they can be checked. Nothing is deleted. Single-issue passes use recorded archives without posting or editing them. The registry, effect targets and finding diagnostics reject unknown fields and unsupported kinds. Older state readers refuse the new field, codes and effect kinds; update Toolkit before retrying.

Each issue gets at most five new comments per pass: graph archives first, trace pages last. The existing five-topic limit across the whole pass also remains. Trace paging tries the largest topic lists separately, then directory pages if they cannot fit. Directory pages retain separate topic lines, can link decisions and older topic indexes, and never link directories. All comment parts stay strictly below 60,000 units.

Issue `PATCH` has no compare-and-swap, so the pass builds from a fresh read and re-reads immediately before writing. A change refuses with `BODY_MOVED`; the next pass re-plans. The whole body must read back exactly. If no prefix fits below 55,000, the shortest prefix strictly below 60,000 is used with a lasting `BODY_NEAR_LIMIT` finding. If none fits, `BODY_TOO_LARGE` refuses the body and posts or edits no archive or trace comments. Both findings carry exact numeric section sizes, reduction needed and remainder, without page text. Planning-time and apply-time refusals persist; partial, incomplete, stopped or held passes cannot resolve them. A complete verified redraw with no remaining condition resolves them. Size and version are checked before publication as well as before the body write. Archive posts and edits have their own intents; recovery reads each target as done, not done or unknown, never replaying an uncertain edit. The renderer reads allowed public fields only, never `private`, sessions or routes.

## Decision traces

The programme issue body is the canonical record, and the reconcile pass keeps its `TRACE` block current from the issue's comments. Comments are linked directly, through a topic index, or through a directory and a topic index. Only decision comments (a tag on the first line, or a record ID) must be reachable: an owner decision that changes scope, authority or the plan is recorded as one, and other comments need no index entry. Records that replace others carry `SUPERSEDES=<record ID>` and belong to the same topic; the trace marks the replaced record "replaced by".

Both index kinds carry `<!-- decision-trace-index -->`; directories also carry `<!-- decision-trace-directory -->` and have no topic tag. Topic indexes keep their topic on the first line followed by `---`. Tool-generated pages carry `programme-trace intent=`. The audit holds them and directory pages to strict links: missing targets, cycles, unrelated links and directory nesting all fail it. Generated traversal allows at most two index hops and 1,024 generated index comments per issue. Full generated links must name the same repository (in any letter case) and issue; old fragment links remain supported. Hand-made indexes without an intent marker retain one-hop reading: foreign and missing references are ignored, and references to other indexes are not followed. A foreign link never covers a local comment. All legacy indexes remain root links unless a generated page links them. The reader uses only comments already read from that issue and never fetches foreign comments. Audit failures name the index and error code in `index_errors`, and the `TRACE_UNLINKED` finding says how to clear them. A missing or unrelated link in a generated page never stops the page redrawing: it covers nothing, so the comments it no longer reaches are listed in the body again; removing the dead link from the named index comment clears the finding. Only a cycle, too many hops or too many pages holds body projection, with `TRACE_INDEX_INVALID` and the same recovery text. G0 history reads all original comments separately, skipping both index kinds with the shared marker, so topic ordering and latest-comment decisions do not depend on pagination.

Audit with `node scripts/decision-trace-audit.cjs --repo <owner/name> --issue <n> --record-prefix <prefix>` (the `record_prefix` from the binding). It fails on any unlinked decision comment, unknown `SUPERSEDES=` target, a superseded record not marked "superseded by" or "replaced by" (in its own comment, or right after a link to it in the body or an index comment), or a body at the threshold, and lists other unlinked comments and comments without a record ID without failing. The reconcile pass runs it on every issue whose trace it does not rewrite in that pass and reports `TRACE_UNLINKED` and `TRACE_SUPERSEDED_UNMARKED`. `--repair --out <file>` writes a proposed body with the missing index lines in the same shape, and `--ledger <file>` (a `toolkit.decision-ledger.v1` file) adds each comment's topic tag after its link; publishing it is a separately authorised write followed by readback and a clean re-audit.

## Review truth

- Inventory the PR's submitted reviews and inline conversations completely (all pages) before classifying findings. An empty, stale, unavailable or incomplete inventory is not green.
- The controller records review verdicts with the reviewer and the exact full head SHA they reviewed (`update --patch` on `review.verdicts`). A verdict at an older head is stale once the PR head moves.
- Classify materiality against the agreed acceptance (ship blocker, follow-up, Later or optional, unsupported or duplicate; a follow-up joins an existing or new catalogued outcome in Later, placed by its priority). A finding is not final because an executor calls it blocking; a disposition needs closing evidence at the exact head and a controller reference.
- An initial nonblocking finding is recorded where the controller keeps deferred findings, with enough public-safe evidence to revalidate it before work on the same component, before that PR's finality and in the final programme sweep. Converge same-root findings instead of opening micro-issues.
- Executors inspect and recommend. They never reply to or resolve threads, dismiss reviews, mark Ready, merge or claim finality; the controller and owner do.

## Safety

- Dry runs and `show` write nothing. `--apply`, `refresh` and the other writing commands change only the bound repository's issue links and managed blocks, the bound store path and, with `state`, `state/` on the public state branch (a restore included).
- The reconciler may report a stale PR or issue but never closes, deletes, merges, detaches or removes branches; closing a completed child is a standing controller step, and the rest stay controller steps with the owner's approval. Removing a sub-issue link by hand is the rollback for a wrong attach.
- No labels, Projects boards, milestones or assignees are changed.
- Never put secrets or tokens anywhere in a state document, `private` included (it lives in the store's git history); secret-shaped values are refused. Keep local paths and session details in `private`, never in public fields.
- Return a compact report: binding, store revision, findings, effects and outcomes, holds and exactly one next action.

## Decision history

A decision comment starts with its tag on the first line and a `---` line after it. `scripts/decision-tags.cjs` is the only parser: the tag is the topic (the task's name, or a short subject for a programme-wide comment; `SCOPE-CONFIRMED` keeps its own meaning), 1-80 letters, digits, spaces and simple punctuation, compared in upper case with runs of spaces as one, with CRLF and leading blank lines accepted. A comment without one belongs to "Other comments". Each tag is its own list, and within a tag the latest comment wins.

Before planning a child, G0 runs `node scripts/decision-history.cjs --repo <owner/name> --child <n> [--edits]`. The parent and the record prefix come from the binding, or from `--parent` and `--record-prefix`. It is read-only and needs no fence: it reads the parent's and the child's comments separately and never mixes them. It takes the latest comment per tag as live. A record named by an explicit `SUPERSEDES=` anywhere in the two traces is replaced outright. Earlier comments in a tag are replaced by inference, or confirmed once a later comment tagged `SCOPE-CONFIRMED` exists on that issue. It also lists untagged comments, untagged records, and untagged comments that name a tag after its latest decision. It prints a live-scope summary: lists are capped with a count (`--max`, `--full` lists everything), `--json` gives the structure, and `--edits` adds the child body's revision count through GraphQL, or says it could not read it. The summary becomes the spec only after the owner confirms it; see the decision-trace playbook (`skills/repository-agent-rules/repo-local/docs/agent-playbooks/decision-trace.md`).

`--programme` reads the parent and every sub-issue once, for the report shown to the owner when governance is first enabled; G0 never uses it. `--ledger <file>` reads a `toolkit.decision-ledger.v1` crawl instead of GitHub. Its entries are untagged, its keyword topics are only hints, and issues it does not hold are reported as not read.
